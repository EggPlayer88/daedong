### 이전 작업자의 시간표 솔버 DB 화 시도 잔재

#### 1. DB 테이블 (정체 불명, ~12개)
- academic_events
- documents (?), period_config, rooms
- school_settings
- special_slots, swap_requests
- tasks, teacher_constraints
- teacher_subjects
- (그 외 2개 더, 미확인)

각 테이블의 정체, 컬럼 구조, 행 수, FK 관계 모두 미파악.

#### 2. teachers 테이블 비정상 컬럼
- id 가 UUID 타입 (D6 결정과 충돌)
- is_homeroom (boolean) — 잔재
- is_parttime (boolean) — 잔재
- allowed_days (jsonb) — 잔재
- + 정상 컬럼들 + Phase 5-A 가 추가한 컬럼들 (homeroom_class_id, 
  day_restriction, is_placeholder, is_external)

#### 3. RLS 정책 (~10개+)
- documents: 관리자 전체 관리(ALL), 본인 문서 관리(ALL), 승인된 사용자(SELECT)
- events: 관리자 전체 관리(ALL), 본인 일정 수정(ALL), 승인된 사용자(SELECT)
- teachers: 관리자 쓰기(ALL), 관리자 전체 읽기(SELECT), 본인 읽기(SELECT)
- storage.objects: 승인된 사용자 (SELECT, INSERT)
- school_settings: 관리자 쓰기(ALL)
- 모두 get_my_role() 함수 또는 teachers 테이블 조회 의존

#### 4. DB 함수 (정체 불명)
- get_my_role() — RLS 정책에서 호출
- 그 외 함수들 미파악

#### 5. FK 의존성 (teachers.id → )
- teacher_constraints.teacher_id ON DELETE CASCADE
- events.created_by ON DELETE SET NULL
- documents.uploaded_by ON DELETE SET NULL

#### 6. 이미 DROP 된 구 잔재 (이전 채팅에서 처리됨)
- subjects (UUID, allow_consecutive) — 17건 데이터 있었음
- classes (UUID, homeroom_teacher_id) — 0건
- teacher_assignments (UUID, hours_per_week, fixed_day) — 0건
- weekly_hours (UUID, subject_id, grade) — 0건

## 새 채팅 진행 방식

### Step 1: 전수 조사
~/projects/daedong/db-survey.sql 의 10개 섹션을 Supabase SQL Editor 에서 차례로 실행.
모든 결과를 캡처하거나 텍스트로 추출해서 클로드 코드에 전달.

### Step 2: 잔재 정체 식별 + 처리 분류
각 발견된 객체를 다음 카테고리로 분류:
- 유지 (코드가 쓰는 것)
- 삭제 (잔재)
- 검토 필요 (정체 불명)

### Step 3: 전면 정비 마이그레이션 작성
한 트랜잭션 (또는 단계별 트랜잭션) 으로 정리:
- 잔재 RLS 정책 DROP
- 잔재 트리거 DROP
- 잔재 함수 DROP
- 잔재 FK DROP
- 잔재 테이블 DROP CASCADE
- teachers.id UUID → TEXT
- 잔재 컬럼 DROP
- FK 재생성 (TEXT ↔ TEXT)

### Step 4: 009 시드 재실행
정비 후 placeholder 24명 + assignments 123건 시드.

### Step 5: 검증
앱 정상 동작 확인 + 데이터 정합성 검증.
