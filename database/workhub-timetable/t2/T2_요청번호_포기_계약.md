# 요청 번호 포기(취소 기록) — 앱 · SQL 계약 (timetable-operations.abandon.v1, Q1~Q3 확정)

2026-10-19 · Claude(SQL) → Codex(앱, PR #72) 제안. **SQL 은 이 PR(#73)에 구현 · 시험(I01~I10) 완료, 앱 parser · 화면은 아직 없음.**
PR #72 `operations-completion-sql-handoff.md` 1절 6항("미접수 명령을 안전하게 영구 포기하는 기능이 필요하면 원키 잠금 하의
취소 tombstone 및 접수증 계약을 먼저 제안한다")에 대한 답이다.

## 1. 풀려는 문제

응답 유실 → 복구 조회 NOT_FOUND → 같은 번호 재전송 → **재전송도 거절**(예: 미리보기 만료 CONFLICT)일 때, 앱은 지금 잠금에서 빠져나올 수 없다.
- 원장은 성공만 기록하므로, 거절 뒤에도 **늦게 도착한 최초 요청**이 그때 상태로 성공할 수 있다.
- 그래서 앱이 잠금을 풀고 새 번호로 다시 만들면, 늦은 최초 요청과 새 요청이 **둘 다 반영**될 수 있다(중복 반영).

## 2. 서버 계약

```
workhub_timetable_operations_abandon(p_member_id text, p_kind text, p_command jsonb, p_request_key text) → 봉투
contract = 'timetable-operations.abandon.v1'
```

| 인자 | 값 |
|---|---|
| `p_kind` | 그 번호를 보낸 RPC 의 종류. `operations`(operations_execute) · `publication`(publication_execute) · `school_day`(school_day_execute) · `execution`(execution_record) |
| `p_command` | 그 번호로 **원래 보낸 명령 그대로**(서버가 `canonical()` SHA-256 으로 대조) |
| `p_request_key` | 그 번호 |

같은 (학교, 소속, 종류, 번호) 잠금 안에서 원장을 읽는다 — 실행 · 재전송 · 복구 조회와 같은 잠금이라 경합해도 둘 중 하나로만 끝난다.

| 원장 상태 | 응답 `data` | 뜻 |
|---|---|---|
| 이미 반영됨 | `{kind, requestKey, commandHash, outcome:'applied', receipt:<원래 접수증 그대로>, decidedAt}` | 포기하지 않았다. **성공한 것**으로 화면에 보여야 함 |
| 없음 | `{…, outcome:'abandoned', receipt:null, decidedAt}` + 취소 기록 남김 | 이 번호는 앞으로 **절대 반영되지 않음** |
| 이미 포기함 | 처음 포기했을 때와 같은 응답(같은 `decidedAt`) | 다시 불러도 안전 |

- 키는 정확히 6개: `kind · requestKey · commandHash · outcome · receipt · decidedAt`(밀리초 ISO, 앱 timestamp 형식).
- 오류: 다른 명령(지문 다름) → `IDEMPOTENCY_CONFLICT`, 모르는 종류 · 객체 아닌 명령 · 번호 형식 → `INVALID_INPUT`, T2 미설치 → `NOT_READY`.
- **준비 상태 · 모듈 켜짐 · 권한을 보지 않는다**(복구 조회와 같음 — 모듈을 꺼도 빠져나올 수 있어야 함). 자기 소속 번호만 닫을 수 있다.
- 취소 기록 뒤 그 번호로 오는 **실행 · 재전송 · 복구 조회는 모두 `CONFLICT`**(반영 안 함). 다른 명령이면 여전히 `IDEMPOTENCY_CONFLICT`.
- 원장 행은 고칠 수도 지울 수도 없다. 감사 기록은 남기지 않는다(바뀐 학교 자료가 없음).

## 3. 앱 흐름 제안 (Codex 확인 필요)

1. 재전송이 업무 오류로 끝나면(IDEMPOTENCY_CONFLICT 제외) 지금처럼 원키 · 입력을 보존하고 잠금 유지.
   화면에 "이 요청 닫기(다시 반영되지 않게 하기)" 버튼을 보인다.
2. 누르면 `_abandon(종류, 원래 명령, 원래 번호)`:
   - `outcome: applied` → 원래 요청이 **사실은 반영됨**. 접수증을 기존 접수증 parser 로 읽어 성공 화면 + 재조회. 잠금 해제.
   - `outcome: abandoned` → 잠금 해제. 입력은 보존해 "새 요청으로 다시 만들기"(새 번호 · 새 미리보기).
   - 오류 · 통신 실패 → 잠금 유지, 같은 인자로 다시 `_abandon`(멱등).
3. 사용자가 확인 없이 원키를 지우는 길은 계속 없다.
