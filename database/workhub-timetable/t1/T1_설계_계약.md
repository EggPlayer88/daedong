## 2. 확정 정책(2026-10-18 계란님)과 SQL 에서의 모양

| 정책 | SQL 에서 |
|---|---|
| 1. 주당 시수는 담당자가 준비 초안에 입력하고 기준판에 고정한다. 추정하지 않는다 | 준비 원본의 `requiredPeriods` 는 항상 `null`. 시수는 초안 `plans[].weeklyPeriods` 로만 들어오고, 확정할 때 `courseLoads` 에 그대로 고정된다. 0 이면 확정 거부(앱 `COURSE_LOAD_MISMATCH`) |
| 2. 공간 capacity = 동시에 열 수 있는 수업 수. 담당자 입력. 없으면 1 로 채우지 않는다 | `timetable_spaces.capacity` 는 NULL 허용(1~1000). NULL 인 공간은 **자원에 넣지 않고** 그 공간을 쓰는 수업이 있으면 `SPACE_CAPACITY_MISSING`(확정 차단)으로 알린다. T1-04-07 이 "기준판의 공간 정원 = 담당자 입력 이력"을 확인한다 |
| 3. 수업 ↔ 학급 · 수강집단은 담당자가 ID 로 직접 고른다. 이름 추정 없음 | `timetable_course_links*` 에 담당자가 고른 학급 ID · 공간 ID 만 저장. 학생 반 문자열(`student_enrollments.class_label`)이나 수업 이름은 읽지 않는다. 연결이 없으면 학생 쪽 자원이 없어 확정 불가 |
| 4. 권한 = 기존 `year.manage` | `p5_manager` 그대로. 그 밖의 사람: readiness `not_allowed`, get 은 빈 화면 값, 나머지 `FORBIDDEN`. 새 권한 · 공개 범위 변경 없음 |
| 5. 확정본 SQL 은 고치지 않는다 | R0 의 `terms_timetable_basis_pending` 교체는 별도 파일 T1-02. 알림 출처 제약(P3 가 만들고 P8-02 가 넓힘)은 T2 의 별도 파일. 기존 함수 · 표 · 행은 바꾸지 않는다(T1-00 지문으로 확인) |

## 3. 새 계약 `timetable.setup.v1` (앱 parser 가 아직 없음 — 이 절이 기준)

봉투는 다른 계약과 같다: `{contract:'timetable.setup.v1', schoolId, memberId, data}` 또는 `{…, error:{code}}`.
기준 parser 는 `test/app_contract_t1.ts` 의 `setupSnapshot` · `setupReceipt` 이다. 앱이 입력 화면을 만들 때 이 두 함수와 같은 규칙으로 읽으면 된다.

### 3-1. `workhub_timetable_setup_get(p_member_id)` → data

```
{ termId, termLabel, firstDay, lastDay, referenceDay, sourceRevision, sourceFingerprint, canEdit: true,
  spaces:  [{ id, kind: 'room'|'equipment', label, capacity: 1..1000 | null, version }],      // 지우지 않은 공간, kind · 이름 · id 순
  classes: [{ id, label, grade }],                                                            // 대상 학기 학년도의 P1 학급(빠진 것 제외), sort_order 순
  courses: [{ id, label, inTimetable, teacherLabels: string[], studentCount,
              link: null | { version, studentGroup, classIds: string[], spaceIds: string[] } }],
  findings:[{ code, targetId, message, blocksConfirm }] }
```

- 대상 학기 = 닫히지 않았고 아직 끝나지 않은 학기 중 오늘이 든 학기, 없으면 가장 먼저 시작하는 다음 학기. 없으면 `NOT_FOUND`.
  T1-07 을 적용하면 담당자가 고른 학기가 먼저다(`timetable.target.v1` — `T1-07_대상학기_설계와_앱연결.md`). 고르지 않으면 위 규칙 그대로.
- 기준일(`referenceDay`) = max(학기 시작일, 오늘). 담당 · 수강은 그날 유효한 것(P8 종료 사건 반영)만 센다.
- `courses` 는 그 학기의 수업 전부(학기 중 시작 수업 포함). `inTimetable=false` 는 준비 원본에 들어가지 않는 수업.
- `sourceRevision` · `sourceFingerprint` 는 준비 원본(`preparation_get`)과 같은 값이다. 입력 화면은 이것이 바뀌면 준비 화면을 다시 읽게 하면 된다.

`findings` 코드(문구는 사람이 읽는 용도, 판단은 코드로):

| code | blocksConfirm | 뜻 | 담당자가 할 일 |
|---|---|---|---|
| `SPACE_CAPACITY_MISSING` | 예 | 수업에 연결한 공간의 정원이 비어 있음 | 정원 입력(공간 저장) |
| `STUDENT_OVERLAP` (targetId `수업A/수업B`) | 예 | 남은 학기([기준일, 학기 끝)) 안에서 같은 학생의 두 수강 기간이 실제로 겹치는데 같은 학급 · 수강집단 자원으로 묶이지 않음(엔진이 충돌을 모름). 앞 수업이 끝난 날 다음 수업이 시작하는 이동은 겹침이 아님 | 두 수업을 같은 학급에 연결(예: 선택 과목을 그 학생들의 학급들에 연결) |
| `LINK_CLASS_REMOVED` · `LINK_SPACE_REMOVED` | 예 | 연결한 학급이 학교 구성에서 빠짐 · 공간이 지워짐 | 연결 다시 고르기 |
| `COURSE_STARTS_LATER` · `COURSE_ENDS_EARLY` | 예 | 학기 중에 시작 · 끝나는 수업(주간 기준판 하나로 표현 불가) | 학기 단위로 수업 정리(P5) |
| `TEACHER_CHANGES_IN_TERM` | 예 | 학기 중 담당 교사가 바뀜(P8 교체 · 종료 포함) | 같은 이유 — T2 에서 기간별 기준판을 다룰 때까지 확정 불가 |
| `TEACHER_LEAVES_IN_TERM` | 예 | 남은 학기의 담당 구간을 그 교사의 재직 기간(소속 active · 소속 기간)이 다 덮지 못함 — 소속 마지막 날이 학기 끝 전 · 소속이 늦게 시작 · 재직 중 아님 | 담당 교체(P8) 또는 소속 기간 확인(P1). T2 기간별 기준판 전까지 확정 불가 |
| `COURSE_ID_UNSUPPORTED` | 예 | 수업 ID 가 시간표 식별자 형식(영문 · 숫자 · `_` · `-` 1~100자)이 아님 | 상의(자동 변환하지 않음) |
| `COURSE_TEACHER_MISSING` | 아니오* | 담당 교사 없음 | 담당 지정(P5) |
| `COURSE_LINK_MISSING` | 아니오* | 학급 · 수강집단 연결 없음 | 연결 |

\* 확정은 앱 `compilePreparation` 이 `MISSING_TEACHER` · `MISSING_STUDENTS` 로 막는다. 서버도 같은 판정으로 `INVALID_INPUT`.
`blocksConfirm=true` 문구는 준비 원본의 `unsupportedFeatures` 에도 그대로 들어간다(같은 문구 하나로, 최대 100개 — 넘으면 99개 + "그 밖에 N건").

### 3-2. `workhub_timetable_setup_execute(p_member_id, p_command, p_request_key, p_recover_only)` → data

명령(정확히 이 키만):

```
{ kind:'space_save',   spaceId: null|id, expectedVersion: null|n, input:{ kind:'room'|'equipment', label, capacity: null|1..1000 } }
{ kind:'space_remove', spaceId: id, expectedVersion: n }
{ kind:'course_link',  courseId: id, expectedVersion: null|n, input:{ classIds: id[] ≤20, studentGroup: boolean, spaceIds: id[] ≤10 } }
```

- 새로 만들 때 `spaceId` · `expectedVersion` 은 둘 다 null, 고칠 때 둘 다 값. 수업 연결은 처음이면 `expectedVersion: null`, 다음부터 현재 판.
- 이름: 1~100자(코드 포인트), 앞뒤 공백은 저장할 때 다듬음, 제어 문자 없음. 살아 있는 공간 이름은 학교 · 종류마다 하나(겹치면 `CONFLICT`).
- `classIds` 와 `studentGroup:true` 는 함께 쓰지 않는다(같은 학생을 두 자원으로 세지 않게). 수강집단 자원 ID 는 `sg_<수업 ID>`.
- 학급은 그 수업 학년도의 빠지지 않은 P1 학급, 공간은 지우지 않은 공간이어야 한다(아니면 `INVALID_INPUT`). 닫힌 학기 수업은 `CONFLICT`.
- 수업에 연결된 공간(닫히지 않은 학기)은 지울 수 없다(`CONFLICT`) — 연결을 먼저 바꾼다.

접수증: `{ requestKey, kind, targetId, version, sourceFingerprint: hex64 | null }` — `version` = 바뀐 뒤 판(새로 만들면 1, 고치면 +1), `sourceFingerprint` = 바뀐 뒤 대상 학기 준비 원본 지문(대상 학기가 없으면 null).
요청 번호 규칙은 다른 쓰기와 같다: 같은 번호 · 같은 명령 → 원래 접수증, 다른 명령 → `IDEMPOTENCY_CONFLICT`, `p_recover_only=true` 이고 원장에 없으면 `NOT_FOUND`. 원장 확인이 준비 · 권한 검사보다 먼저다(모듈을 중지해도 복구는 된다).

## 4. 기존 계약(앱 parser 그대로)

- `timetable.v1` readiness: `{available:true}` 또는 `{available:false, reason}` — 켜지지 않음 · 중지 `not_installed`, `year.manage` 없음 `not_allowed`, 대상 학기에 기준판 없음 `basis_missing`.
- `timetable.v1` get(`p_week_start` 월요일, 아니면 `INVALID_INPUT`): 담당자 + 기준판 있음 → `{basis, canDesign:true, canSave:true, drafts(최근 40, version 1), weekStart, lessons:[]}`. 그 밖 → `{basis:null, canDesign:false, canSave:false, drafts:[], weekStart, lessons:[]}`.
- `timetable.v1` save_draft: 앱 `timetableSaveInput` 과 같은 검사(현재 기준판 ID · 판 · 지문, 학교 조건 fixed · unavailable 을 빼지 않음, 배치가 모든 필수조건 통과). 덮어쓰지 않고 새 초안. 접수증 `{requestKey, draftId, version:1, basisRevision}`.
- `timetable.preparation.v1` get: 앱 `PreparationSource` 그대로. `canEdit` · `canConfirm` 은 담당자에게 항상 true(그 밖은 `FORBIDDEN`). `savedDraft` = 학기마다 1개의 준비 초안(현재 판).
- `timetable.preparation.v1` execute: 원본 판 · 지문 · 학기(다르면 `CONFLICT`) → 초안 구조(`preparationDraft`, 다르면 `INVALID_INPUT`) → 준비 초안 판(다르면 `CONFLICT`) → 확정이면 `compilePreparation` 과 같은 기준판(못 만들면 `INVALID_INPUT`). 접수증 `{requestKey, kind, draftId, draftRevision, sourceFingerprint, basis}` — 확정이면 고칠 수 없는 기준판 본문(재전송 · 복구도 같은 본문).

### 4-1. 기준판 배열 순서(K-3)

앱 `preparationReceipt` 는 원본 + 초안으로 `compilePreparation` 을 다시 돌려 **정준형(키 정렬)으로 같아야** 받는다. 배열 순서는 정렬되지 않으므로 서버가 그대로 맞춘다.

| 배열 | 순서 |
|---|---|
| `resources` · `unsupportedFeatures` | 준비 원본 순서 그대로. 원본의 자원 순서 = 교사 → 학급 → 수강집단 → 공간(정원 있는 것), 같은 종류 안에서는 이름(C 정렬) · ID |
| `slots` | 초안 순서 그대로 |
| `courseLoads` · `lessons` | 초안 `plans` 순서, 활동은 `blocks` 순서. 활동 이름 = 수업 이름 + `' '` + plan 안 순번 + `'회'` |
| 수업 `resourceIds` | 원본 자원 순서로 걸러낸 것 |
| `fixed` · `unavailable` · `preferences` | 빈 배열(확정 시점). 편성 초안에서 담당자가 넣는다 |

### 4-2. 서버가 앱 검사를 다시 하는 곳

앱이 보내기 전에 검사해도 서버는 같은 규칙을 다시 본다(다른 경로 · 오래된 화면 · 동시 변경). 이식한 함수는 `T1-01` 6절이며, 판정이 앱과 같은지 무작위 변형 1.9만 건으로 대조했다(`T1_시험결과.md`).

| 앱 | SQL |
|---|---|
| `validateBasis` | `t1_basis_issues` (빈 배열 = 통과, 첫 구조 오류에서 멈춤 — 통과/거절만 같고 코드 목록은 진단용) |
| `validatePlacements` | `t1_placement_issues` |
| `reviewTimetableFoundation(...).ready` | `t1_foundation_ready` (자원별 날마다 겹치지 않는 시간대 최대 차시 합 ≥ 배정 차시, 지원 불가 0) |
| `preparationDraft(d, source)` | `t1_draft_ok` |
| `compilePreparation` | `t1_compile` |

## 5. 원본 판(sourceRevision)

학기마다 `timetable_source_marks` 에 (판, 지문)을 쌓는다. 조회 · 입력 · 준비 쓰기가 학교 잠금 안에서 지문을 다시 계산하고, 마지막 판과 다르면 새 판을 만든다(되돌아가도 새 판). 그래서 앱이 본 판이 지금과 다르면 정확히 `CONFLICT` 가 된다.
지문 = 원본 중 `sourceRevision` · `sourceFingerprint` · `canEdit` · `canConfirm` · `savedDraft` 를 뺀 부분의 SHA-256(`p2_sha`, 정준형).

## 6. 표(11개, RLS 켜고 정책 없음 — API 역할 · PUBLIC 권한 0: 표 · 열 단위 모든 종류, T1-04-02 가 확인)

| 표 | 무엇 | 고칠 수 있나 |
|---|---|---|
| `timetable_spaces` | 공간 · 장비(정원 NULL 허용), 지우기 = `removed_at` | 판 비교로만 |
| `timetable_course_links` · `_classes` · `_spaces` | 수업 연결(현재 판) | 판 비교로만 |
| `timetable_setup_history` | 입력 판마다의 값 | 불변 |
| `timetable_source_marks` | 원본 판 | 불변 |
| `timetable_prep_drafts` · `_revisions` | 준비 초안(학기마다 1개) · 판 이력 | 이력 불변 |
| `timetable_basis_revisions` | 기준판(앱 `TimetableBasis` 그대로, 본문의 학교 · 학기 · 판 · 지문 = 행) | 불변 |
| `timetable_drafts` | 편성 초안 | 불변 |
| `timetable_requests` | 요청 원장(반영된 쓰기만, 접수증) | 불변 |

`terms.current_timetable_basis_id` 는 T1-02 뒤 `(school_id, current_timetable_basis_id, id) → timetable_basis_revisions(school_id, id, term_id)` — 같은 학교 · 같은 학기의 기준판만 걸린다. 확정할 때 학기 행을 잠그고 판을 올린다(R0 제약 처분표의 예약 그대로).

## 7. 판단해서 정한 것 (되돌리려면)

| 정한 것 | 왜 | 되돌리려면 |
|---|---|---|
| 학기 중 시작 · 끝 수업, 학기 중 담당 교체는 확정 차단 | 주간 기준판 하나에 담으면 그 기간 밖에도 수업이 잡힌다(틀린 시간표). 정책 0원칙 "담은 척하지 않는다" | T2 에서 기간별 기준판을 만들 때 `t1_build` 의 rk 2~4 를 바꾼다 |
| 수강 학생이 겹치는데 같은 자원으로 묶이지 않은 수업 쌍은 확정 차단 | 엔진은 자원만 보므로 학생 충돌을 모른다. 이름으로 묶지 않는다(정책 3) | `t1_build` 의 `STUDENT_OVERLAP`(rk 8) |
| 교사 자원 ID = 소속(membership) ID, 수강집단 = `sg_<수업 ID>` | K-4 와 같은 규칙. 사람 · 수업마다 유일 | `t1_build` 자원 CTE |
