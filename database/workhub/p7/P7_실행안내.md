# 수합 운영 · 홈 요약 · 업무 인계 · 새 학년도(P7) 실행 안내

2026-10-16 · 작성: Claude Code · 검토: Codex · 실행: 계란님

P7 은 통합 SQL 요청서(`docs/workhub/pilot-completion/sql-handoff.md`)의 **7단계 — 수합 운영 · 홈 요약 · 업무 인계 · 학년도 전환** 증분 SQL 입니다.
앱 계약은 PR #48 의 `apps/workhub/src/collections/operations.ts`(`collection-operations.v1`) ·
`home/overview.ts`(`home.v1`) · `administration/transitions.ts`(`school-transitions.v1`)입니다.

- **SQL 을 적용해도 아무 학교에서도 켜지지 않습니다(비활성 설치).** 6개 공개 함수가 모두 `NOT_READY` 를 돌려주고 아무것도 쓰지 않습니다.
- 켜는 것은 `P7-04` 하나입니다(앱 배포 뒤, 별도 승인). 모듈은 넷이고 **기본값이 없습니다**: 수합 운영(`collection_ops`) · 홈 요약(`home`) · 업무 전환(`transitions`) · 공식 담당 인계(`duty_handover`).
- **`P7-05`(R1 · P2 보강)는 정상 실행 순서에 넣지 않았습니다.** "기존 R1 은 고치지 않는다"의 예외라 따로 승인받아야 합니다(7절).
  P7-05 전에는 마감 · 보관 · 재개 · 기한 연장과 수합 · 협업 인계가 모두 `NOT_READY` 입니다. **화면만 막는 마감은 만들지 않았습니다.**
  P7-05 없이도 되는 것: 제출 현황 · 미제출 알림, 홈 요약, 공식 담당 인계, 새 학년도 만들기.
- 알림은 사이트 안 알림(P3)만 만듭니다. 문자 · 메일은 보내지 않습니다.
- 인계는 받는 교사가 **수락해야** 넘어갑니다. 신청만으로는 아무 권한도 바뀌지 않습니다. 상담 · 메시지 · 개인 할 일 · 개인 문서 · 학생 기록은 인계 대상이 아닙니다.
- 새 학년도는 학년도 · 학기 · (고르면) 부서 · 학급 · 교과 틀만 새로 만듭니다. 학생 진급 · 반 배정 · 담당 · 일정은 옮기지 않고, 지금 학년도는 그대로 둡니다.
- 기존 로그인 · 가입 승인 · 회원 · 평가계획서 · 수합 · 업무실 · 학교 관리 · 협업 · 메시지는 건드리지 않습니다(`P7-00` 지문으로 확인).
- **R0 · R1 · R1S · P1~P6 를 다시 실행하거나 고치지 않습니다. R0-90 도 쓰지 않습니다.** (P7-05 만 예외이며 별도 승인)

## 4. 멈춤 기준

아래 중 하나라도 보이면 **다음 파일로 넘어가지 말고** 그 행·메시지를 알려 주세요.

- P7-00 실행 전 결과에 `FAIL`
- P7-01/02 가 `ERROR` 로 끝남, 또는 마지막 결과에 `ok` 가 아닌 행
- P7-03 에 `FAIL`
- P7-00 실행 후 구조 지문(S1~S6)이 실행 전과 다름
- 6번 사이트 확인에서 기존 기능 하나라도 이상

P7-01·02 가 이미 적용된 뒤 멈춰야 한다면 **되돌리는 SQL 을 즉석에서 만들지 않습니다.** 활성화 행이 없으면 P7 함수는 모두
`NOT_READY` 이고, 새 표에는 API 역할 권한이 없으며, 기존 표·함수는 그대로입니다
(시험 II: P1~P3 + P7 비활성 설치 위에서 R1 시험 244건 그대로 통과). 그대로 두고 원인을 먼저 봅니다.

## 6. 계란님이 정할 값

이 SQL 은 어떤 정책값도 정해 두지 않았습니다. 칸이 남아 있으면 아무것도 쓰지 않고 멈춥니다.

**P7-04 (모듈 켜기)**

| 칸 | 무엇 | 규칙 |
|---|---|---|
| `approver_user_id` | 승인한 학교 관리자(school_admin)의 회원 id(Auth UID). 대상 학교 = 그 사람이 지금 관리자인 학교 1곳 | — |
| `approval_ref` | 승인 근거(결재 번호 등) | 1~200자 |
| `modules` | 켤 모듈 목록 | `collection_ops` · `home` · `transitions` · `duty_handover` 중 1~4개, 중복 없이 |

- `duty_handover` 는 **교사끼리 공식 담당(일반 업무)을 넘기는 것**입니다. 받는 사람이 수락하면 학교 관리의 담당이 바로 바뀝니다(학교 관리 판 +2, 변경 원장 2행).
  관리자 결재 없이 교사끼리 넘기는 것을 허용할지는 학교가 정할 일이라 따로 켜게 했습니다(`P7_설계결정.md` 7절 Q2).
- 이미 행이 있는 모듈은 멈춥니다(다시 켜려면 `P2-81`).

**P7-05 (R1 · P2 보강) — 따로 승인할 때만**

| 칸 | 무엇 | 규칙 |

## 8. 실제 환경에서 시험하지 못한 것

시험은 로컬 PostgreSQL 17 에 Supabase 의 역할 · `auth.uid()` 를 흉내 낸 DB 에서 했습니다(`P7_시험결과.md`).
다음은 실제 Supabase · Vercel 에서 처음 확인하게 됩니다.

- 실제 PostgREST 를 거친 호출과 오류 변환. 시험은 PostgREST 와 같은 역할 전환 경로(authenticator → set role → JWT claims)로 불렀습니다
- 실제 앱 화면(PR #48)의 왕복. 앱 서비스 · parser 는 실제 코드에 시험 응답을 넣어 대조했지만(V) 브라우저는 거치지 않았습니다
- 사이트 알림이 실제 알림 화면에 뜨는지. 시험은 P3 알림 표에 1행이 생기는 것까지 확인했습니다
- 운영 DB 의 잠금 대기와 응답 시간. 시험은 동시 요청 2~3건까지
- 학교 시간대 경계(자정 무렵) 의 기한 · 오늘 판정. 시험은 `Asia/Seoul` 오늘 기준으로만 했습니다
- 마감 뒤 이미 낸 파일(PDF · HWPX) 내려받기. 게이트는 새 행 쓰기만 막고 읽기 · 서명 URL 경로는 건드리지 않지만, 실제 Storage 내려받기는 시험하지 않았습니다
