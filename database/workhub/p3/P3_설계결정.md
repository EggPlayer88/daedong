## 2. 요청 번호(멱등)

| 정한 것 | 이유 | 되돌리려면 |
|---|---|---|
| **반영된 요청만 원장(`message_requests`)에 남김.** 업무 거절은 남기지 않음 | 앱 메신저 계약은 거절(`INVALID_INPUT`·`CONFLICT` 등)에 `commandHash` 를 요구하지 않고, 거절 뒤 화면이 고쳐서 다시 보낸다. P2 와 다른 점이다 | P3-02 `p3_apply` 서브트랜잭션 |
| 같은 번호·같은 내용 → 처음 접수증 그대로 · 같은 번호·다른 내용 → `IDEMPOTENCY_CONFLICT` | 응답 유실 뒤 재전송이 두 번 보내지지 않게(시험 E02·E03·K01) | `p3_apply` |
| `replay_only` + 없는 번호 → `NOT_FOUND`(새로 쓰지 않음) | 앱이 "결과 모름" 복구 때 쓰는 조회. 조회가 전송이 되면 안 된다 | 〃 |
| 재조회는 **모듈이 꺼져 있어도** 됨(원장 대조가 먼저) | 끄는 순간 보낸 사람이 "보냈는지"를 확인할 길이 없어지면 다시 보내다 중복이 난다(시험 N03·N04) | `workhub_message_mutate` 앞부분 |
| 같은 학교·소속·종류·번호로 advisory lock | 같은 번호 동시 2건이 둘 다 쓰지 않게 | `p3_lock` |

## 3. 대화·메시지

| 정한 것 | 이유 | 되돌리려면 |
|---|---|---|
| 1:1 은 두 사람 조합(`direct_key`)으로 하나. 누가 먼저 시작해도 같은 대화 | 같은 두 사람의 대화가 여러 개로 갈리지 않게(시험 E07·K02) | `message_threads_direct_key` + `p3_direct` |
| 개별 전송(`individual`)은 받는 사람마다 1:1 대화에 따로 보냄. 원장 1행 · 메시지 N개 | 받는 사람끼리 서로의 명단을 보지 않게(시험 G02) | `p3_apply` start 분기 |
| 한 사람이라도 받을 수 없으면(판 다름·자격 없음) **전체 거절**, 아무에게도 안 보냄 | "일부만 갔음"은 보낸 사람이 알아차리기 어렵다(시험 G05) | 〃 |
| 받는 사람 판(`expectedVersion`)은 `memberships.version` | 화면이 본 뒤 그 사람의 소속·기간이 바뀌었으면 `CONFLICT` 로 다시 보게 | `p3_recipient` |
| 단체 대화 참여자는 만들 때 고정. 대화 판은 바뀌지 않음 | 계약에 참여자 추가·나가기가 없다. 메시지가 늘 때 판을 올리면 동시 답장이 서로 `CONFLICT` 가 난다(시험 F10·K03) | `message_threads` 판 규칙 |
| 답장은 확인한 참여자 명단(`recipientMemberIds`)이 지금 명단과 같아야 함. 참여자 한 명이라도 자격을 잃으면 `canSend=false`·답장 `CONFLICT` | 그 사람이 못 받는 것을 보낸 사람이 모른 채 보내지 않게(시험 H14~H16) | `p3_post` |
| 순번은 대화별 1부터 빈칸 없이(대화 행을 잠그고 +1) | 앱이 순번 오름차순·`throughSequence` 로 읽음을 계산한다 | `p3_post` |
| 읽음은 올라가기만(`P3_READ_MONOTONIC`). 낮은 순번 읽음은 성공 접수증(요청 그대로) · 서버 값은 유지 | 늦게 도착한 읽음이 읽은 위치를 되돌리지 않게. 접수증은 앱 parser 가 요청 순번과 대조한다 | `p3_apply` read_thread |
| 자기 메시지는 읽지 않은 수에 넣지 않음 · 보내도 읽은 순번을 올리지 않음 | 읽음은 받는 쪽의 행동만 기록한다 | `p3_thread_dto` |
| 본문·제목 길이는 UTF-16 길이(앱 `string.length` 와 같음) | 이모지 한 글자에서 화면과 서버 판정이 갈리지 않게(시험 H07) | `p3_len` |
| 메시지 삭제·수정·회수 없음 | 계약에 없다. 정리 정책도 정해지지 않았다(8절) | — |

## 4. 알림함

| 정한 것 | 이유 | 되돌리려면 |
|---|---|---|
| 알림은 `p3_notify(학교, 받는 소속, 제목, 본문, 출처 모듈, 출처 id, dedupe 키)` 내부 함수로만 생김. **이번 배치에는 부르는 쪽이 없음** | 일정·업무·수합 사건을 알림으로 바꾸는 작업자는 7단계 범위다. 지금 만들면 아무 검토 없이 알림이 쏟아진다 | 뒤 배치 |

## 5. 첨부(HWPX)

| 정한 것 | 이유 | 되돌리려면 |
|---|---|---|
| 수합과 **다른 원장 · 다른 버킷**(`workhub-message-files`) | 수합 파일의 공개 범위(제출자·관리자)와 메시지 파일의 공개 범위(대화 참여자)는 다르다. 같은 버킷이면 한쪽 정책이 다른 쪽을 연다 | P3-02 버킷·정책 |
| 경로 `학교/소속/파일id/original.hwpx`. 서버가 발급한 경로에만 본인이 한 번 올림(덮어쓰기·서명 URL·목록 없음) | 남의 경로·임의 경로 업로드와 바꿔치기를 Storage 정책 단계에서 막는다(시험 O16~O21) | `message_insertable` |
| 예약 30분. 지나면 그 경로 업로드 거부, 상태는 `rejected(upload_expired)` | 버려진 예약이 영원히 열려 있지 않게 | `p3_prepare`·`p3_complete` |
| complete 는 실물 id·크기·주인을 고정. 실물이 바뀌면(삭제 후 다시 올림) `rejected(object_changed)` | 확인한 실물과 보낸 실물이 같아야 한다(시험 O42·O43) | `p3_complete`·`p3_claim` |
| **기본 확인은 서버 확인 API 만**(service_role 전용 claim/finish). 브라우저는 결과를 쓸 수 없음 | 브라우저가 "확인됨"을 쓰면 확인이 없는 것과 같다 | P3-02 권한 |
| claim 은 90초 임대 · 파일당 10분에 6번 · 계정당 10분에 60번. 넘으면 `pending_basic` 만 돌려줌 | 같은 파일을 여러 창이 동시에 내려받아 확인하지 않게. 확인 API 가 실패해도 영구 거절이 아니라 다시 할 수 있게(시험 O39~O41) | `p3_claim` |
| claim·finish 의 요청 번호는 그 파일 complete 번호와 같아야 함 | 확인 API 를 다른 파일·다른 요청에 끼워 쓰지 못하게(시험 O27) | `p3_bound_file` |
| finish 결과는 `{profile:'hwpx_basic_v1', accepted, actualBytes, actualSha256, reasonCode}` 만. 다른 항목(악성코드 등)이 있으면 거부 | **검사하지 않은 것을 검사했다고 기록하지 않는다.** 감사 기록에도 `malware_scan=false` | `p3_finish` |
| 첨부는 ready · 본인 소유 · 아직 안 붙은 파일만, 한 파일은 한 전송에만 | 같은 파일을 여러 대화에 퍼 나르면 공개 범위 판단이 꼬인다. 개별 전송은 받는 사람별 메시지에 같은 파일을 각각 연결 | `p3_take_files` |
| 내려받기: `file_access` 가 위치만 주고(URL 없음), Storage SELECT 정책이 참여자·자격·모듈을 다시 확인 | 서명 URL 을 주면 대화 밖으로 새도 막을 수 없다. 받는 사람이 자격을 잃거나 첨부를 끄면 바로 막힌다(시험 O53·O56·O57) | `message_readable` |
| 메시지 버킷을 여는 다른 정책이 생기면 첨부 준비를 `storage_missing` 으로 내림 | 누가 대시보드에서 정책을 넓히면 조용히 열리지 않게(시험 O61) | `p3_storage_ok` |

## 6. 앱(PR #48)과 다르게 정하거나 앱이 정하지 않은 것

| 항목 | SQL 이 한 것 | 비고 |
|---|---|---|
| 첨부 예약 재조회의 상태 | 처음 예약 응답이 아니라 **지금 상태**(`awaiting_upload`·`pending_basic`·`ready`)를 돌려줌 | 앱 `MessageFileIntent.state` 가 셋 다 허용한다 |
| 거절된 파일의 예약 재조회 | `CONFLICT` | 앱 intent 상태에 `rejected` 가 없다 → 계약 공백 1 |
| 앱이 대화를 모르는 읽음 표시 | 서버는 `NOT_FOUND` | 앱은 보내지 않고 `INVALID_INPUT` 으로 먼저 막는다(쓰기 없음, 코드만 다름) |
| 제목·본문 앞뒤 공백 | 서버도 걷어 냄(같은 결과) | 앱이 먼저 걷어 보낸다 |

## 7. 계약 공백 (앱 쪽 결정이 필요)

1. **거절된 첨부의 예약 재조회** — 앱 `MessageFileIntent.state` 에 `rejected` 가 없어 서버는 `CONFLICT` 를 돌려줍니다.
   앱이 이 경우 `status()` 로 확인하게 하거나, intent 에 `rejected` 를 더하는 것 중 하나를 PR #48 에서 정해야 합니다.
2. **알림 출처** — 앱 `NotificationSource.module` 은 `calendar·tasks·collections·messages·students·knowledge` 입니다. 협업(cooperation)은 목록에 없습니다.
   7단계에서 협업 알림을 만들 때 앱 목록을 늘리거나 `tasks` 로 보낼지 정해야 합니다.
3. **단체 대화 참여자 변경·나가기** — 계약에 없습니다. 지금은 만들 때 고정이고, 한 명이 자격을 잃으면 그 대화는 답장 불가(`canSend=false`)가 됩니다.
