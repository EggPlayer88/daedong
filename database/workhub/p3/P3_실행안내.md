# 업무실 메신저 · 업무 알림 · 메시지 HWPX 첨부(P3) 실행 안내

2026-10-16 · 작성: Claude Code · 검토: Codex · 실행: 계란님

P3 는 통합 SQL 요청서(`docs/workhub/pilot-completion/sql-handoff.md`)의 **3단계 — 메시지 · 알림 · HWPX 첨부** 증분 SQL 입니다.
앱 계약은 PR #48 의 `apps/workhub/src/messaging/*.ts`(메신저·알림함·첨부)와 `apps/main/api/messages/check-hwpx.py`(서버 확인 API)입니다.

- **SQL 을 적용해도 아무 학교에서도 켜지지 않습니다(비활성 설치).** 메시지는 `NOT_READY`, 첨부는 `verification_missing` 입니다.
  메시지를 켜는 것은 `P3-04`, 첨부를 켜는 것은 `P3-05` 이고, 둘 다 앱 병합·배포 뒤 별도 승인입니다.
- **SQL 만 적용했다고 첨부가 준비 완료로 보이지 않습니다.** 첨부는 서버 확인 API 가 운영에 배포된 것을 확인한 기록(`verification_ref`)을
  받는 `P3-05` 를 실행해야만 `ready` 가 됩니다. 확인은 HWPX 구조·크기·SHA 기본 확인이며, **악성코드 검사가 아니고 그렇게 기록하지도 않습니다.**
- 기존 로그인·가입 승인·회원·평가계획서·수합·업무실 일정/업무·학교 관리·협업 자료는 건드리지 않습니다(`P3-00` 지문으로 확인).
- **R0·R1·R1S·P1·P2 를 다시 실행하거나 고치지 않습니다. R0-90 도 쓰지 않습니다.**

## 7. 실제 환경에서 시험하지 못한 것

시험은 로컬 PostgreSQL 17 에 Supabase 의 역할·`auth.uid()`·`storage.objects` 를 흉내 낸 DB 에서 했습니다(`P3_시험결과.md`).
다음은 실제 Supabase·Vercel 에서 처음 확인하게 됩니다.

- 실제 PostgREST · **실제 Storage API** 를 거친 업로드·내려받기. 시험은 `storage.objects` 행 INSERT/SELECT 와
  `storage.operation` 설정으로 RLS 판정만 흉내 냈습니다(Storage 서버가 실제로 그 값을 넣는지는 R1S 와 같은 전제)
- 운영 SQL Editor 의 `postgres` 역할이 `storage.objects` 에 정책을 만들 수 있는지 — P3-02 가 먼저 시험해 보고 안 되면 멈춥니다
- 실제 Vercel 에서 서버 확인 API(`check-hwpx.py`)의 실행·시간 제한·서비스 키. 시험은 PR #48 의 실제 `check_file` 코드를 가져와
  Supabase 호출만 시험 DB(service_role)와 메모리 저장소로 바꿔 끼워 돌렸습니다
- 실제 앱 화면(PR #48)의 왕복. 앱 어댑터·parser·확인 API 연결 코드는 실제 코드로 대조했지만 브라우저·Supabase 클라이언트는 거치지 않았습니다
- 알림을 만드는 쪽 — 이번 배치에는 없습니다(알림함은 비어 있음). 뒤 단계가 `p3_notify` 로 넣습니다
- 운영 DB 의 잠금 대기와 응답 시간. 시험은 동시 요청 4건까지
