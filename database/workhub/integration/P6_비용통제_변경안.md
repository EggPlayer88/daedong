# P6 Claude 비서 — 비용 통제 변경안 (통합 검토 6번)

2026-10-16 · Claude Code. **제안서입니다. 아직 SQL · 앱 어느 쪽도 바꾸지 않았습니다.**
비용 구조 변경은 CLAUDE.md 2절의 승인 사항이라, 계란님 결정 뒤 SQL 은 Claude(P6 브랜치), 앱은 Codex 가 고칩니다.
기준: SQL = PR #55(P6) 현재판, 앱 = PR #48 `5f3d40f`.

**결론: 이 변경이 들어가기 전에는 비서(AI) 활성화를 "완료"로 보지 않습니다.**
지금 구조로는 한 번의 실제 비용이 예약액을 넘을 수 있어, 예산 한도가 상한 역할을 하지 못합니다.

## 1. 지금 무엇이 문제인가

| | 지금 | 근거 |
|---|---|---|
| 예약액 | `ceil((max_input_tokens × 입력 단가 + max_output_tokens × 출력 단가) / 10⁶)` | P6-01 `assistant_policies_reserve_check`, 설계결정 D-P6-2 |
| 출력 | 모델에 `max_tokens = max_output_tokens` 를 보냄 → **출력은 상한이 실제로 지켜짐** | P6-02 claim 응답 `maxTokens`, 앱 `_assistant.py` `provider_body` |
| 입력 | `max_input_tokens` 는 **예약 계산에만 쓰이고, 보내기 전에 아무도 세지 않음** | 설계결정 7절 4항 "실제 사용량이 상한을 넘으면 그대로 정산(예약보다 클 수 있음)" |
| 실제로 보내는 입력 | 지시문(`assistant-policy.txt`) + 도구 정의(`TOOL`) + 이전 대화 최대 32개 × 8,000자 + 근거 최대 30개 × 16,000자 + 질문 4,000자 | 앱 `assistant-limits.json`, `provider_body` |

글자 수 한도만으로 계산하면 한 요청의 입력이 **약 74만 자**까지 갈 수 있습니다. 한국어는 대략 글자당 1토큰 안팎이라,
예를 들어 `max_input_tokens` 를 5만으로 정하면 실제 입력은 그 10배를 넘을 수 있습니다(모델이 받아 주는 한).
그러면 예약액 · 사람 하루 한도 · 학교 한 달 한도가 모두 "예상"일 뿐 상한이 되지 못합니다.

## 2. 바꾸는 방향 — "보내기 전에 세고, 넘으면 보내지 않는다"

원칙(요청서 그대로):
- 한도 초과는 **외부 호출 전에** 처리합니다.
- 이미 발생한 비용은 **실제 사용량으로** 정산합니다. 비용을 작게 기록하지 않습니다.
- 근거를 **조용히 잘라** 한도에 맞추지 않습니다. 넘으면 교사에게 "근거를 줄여 다시 물어 달라"고 알립니다.

### 2-1. 앱(Codex) — `apps/main/api/workhub-ai/_assistant.py`

| # | 바꿀 곳 | 내용 |
|---|---|---|
| A1 | `claimed()` | claim 응답의 `policy` 에 새 칸 `maxInputTokens` 를 받아 검사(정수 ≥ 1) |
| A2 | `execute()` — `workhub_ai_start` **전** | `provider_body(claim)` 로 **실제로 보낼 본문 전체**(system · tools · tool_choice · messages)를 만든 뒤, 같은 본문으로 입력 토큰을 셈. 셈 방법은 결정 D4 |
| A3 | 셈 결과 > `maxInputTokens` | `workhub_ai_start` 를 **부르지 않음**. 새 RPC `workhub_ai_release`(아래 S2)로 "입력 초과"를 기록하고 교사에게 `INPUT_TOO_LARGE`(근거 · 대화를 줄여 다시) 응답. 근거를 빼거나 자르지 않음 |
| A4 | 셈이 실패(네트워크 · 4xx/5xx) | 역시 `start` 를 부르지 않고 `release`(사유 `count_failed`). 외부 모델 호출 0, 비용 0 |
| A5 | 셈과 보내기 사이 | 셈한 본문과 **같은 바이트**를 보냄(다시 만들지 않음). `prompt caching` · 확장 사고(thinking) · 서버 도구는 쓰지 않음(쓰면 단가 구조가 달라져 예약식이 틀려짐 — 결정 D6) |
| A6 | 화면 · 계약 | `assistant.v1` 질문 결과에 `rejected` 사유 `INPUT_TOO_LARGE` 추가(문구: "보낼 자료가 너무 많습니다. 근거나 이전 대화를 줄여 다시 물어봐 주세요.") |

### 2-2. SQL(Claude, P6 브랜치) — 결정 뒤 작성

| # | 바꿀 곳 | 내용 |
|---|---|---|
| S1 | P6-02 claim 응답 | `policy.maxInputTokens = max_input_tokens` 추가 |
| S2 | 새 함수 `workhub_ai_release(…, p_reason)` (service_role 전용) | **시작 전(`started_at IS NULL`) 임대만** 끝냄: 상태 `rejected` · 코드 `INPUT_TOO_LARGE` 또는 `COUNT_FAILED` · `cost_state='settled'` · 실제 0원. 같은 요청 번호 재전송은 같은 응답. 시작한 요청에는 `CONFLICT`(이미 호출했을 수 있으므로 0원 처리 금지) |
| S3 | `workhub_ai_finish` | 실제 입력 > `max_input_tokens` 또는 출력 > `max_output_tokens` 이면 **실제 사용량 그대로 정산**하고, 요청에 `over_reservation = true` 표시 + 감사 1행. 값을 깎지 않음 |
| S4 | 준비 상태 | `over_reservation` 이 한 건이라도 확인 전이면 그 학교 준비 상태 `not_configured`(사유 `over_reservation`) — 모델 호출 0. P6-05 로 관리자가 확인(정산 금액 · 원인)해야 다시 열림 |
| S5 | P6-03 사후 점검 | "예약 초과 정산" 행 추가(0건이면 ok, 있으면 FAIL + 요청 번호) |
| S6 | P6-04 양식 | `max_input_tokens` 설명을 "보내기 전 상한(넘으면 보내지 않음)"으로 바꿈. 예약식은 그대로(입력 상한이 실제로 지켜지므로 예약 = 최대 비용) |

이렇게 하면 한 요청의 실제 비용 ≤ 예약액이 **구조로** 보장되고(A2 · A3 + 모델의 `max_tokens`),
보장이 깨진 경우(셈과 실제가 다를 때)는 S3 · S4 가 실제대로 기록하고 그 학교를 멈춥니다.

### 2-3. 시험(변경 시 함께)

- 입력이 상한 + 1 → `start` 호출 0 · 모델 호출 0 · 원장 `rejected INPUT_TOO_LARGE` 0원 · 같은 번호 재전송 같은 응답
- 셈 실패 → 모델 호출 0 · `COUNT_FAILED`
- 시작한 요청에 `release` → `CONFLICT`, 원장 그대로
- 실제 사용량이 상한 초과로 끝 기록 → 실제 금액 그대로 정산 · `over_reservation` · 준비 상태 닫힘 · P6-03 FAIL → P6-05 확인 뒤 열림
- 동시 4명이 마지막 한도 근처 → 기존 H06 그대로(예약 단위가 최대 비용이므로 합계가 한도를 넘지 않음)
- 앱 대조: `INPUT_TOO_LARGE` 응답을 앱 parser 가 받아들이고 화면 문구 확인
