## 1. 지금 무엇이 문제인가

| | 지금 | 근거 |
|---|---|---|
| 예약액 | `ceil((max_input_tokens × 입력 단가 + max_output_tokens × 출력 단가) / 10⁶)` | P6-01 `assistant_policies_reserve_check`, 설계결정 D-P6-2 |
| 출력 | 모델에 `max_tokens = max_output_tokens` 를 보냄 → 출력 토큰은 그 값을 넘지 않음 | P6-02 claim 응답 `maxTokens`, 앱 `_assistant.py` `provider_body` |
| 입력 | `max_input_tokens` 는 **예약 계산에만 쓰이고, 보내기 전에 아무도 세지 않음** | 설계결정 7절 4항 "실제 사용량이 상한을 넘으면 그대로 정산(예약보다 클 수 있음)" |
| 실제로 보내는 입력 | 지시문 + 도구 정의 + 이전 대화 최대 32개 × 8,000자 + 근거 최대 30개 × 16,000자 + 질문 4,000자 | 앱 `assistant-limits.json`, `provider_body` |

글자 수 한도로만 계산하면 한 요청의 입력이 약 74만 자까지 갈 수 있습니다. `max_input_tokens` 를 예컨대 5만으로 정해도
실제 입력은 그 몇 배가 될 수 있고(모델이 받아 주는 한), 그러면 예약액 · 사람 하루 한도 · 학교 한 달 한도가 "예상"일 뿐입니다.

## 2. 바꾸는 방향

### 2-0. 이 변경이 보장하는 것과 보장하지 않는 것

이 변경은 **절대 상한이 아닙니다.** 네 겹으로 비용을 묶습니다.

1. **사전 확인** — 보내기 전에 실제로 보낼 입력 전체의 토큰을 셈. 상한을 넘으면 유료 답변 생성을 부르지 않음.
2. **보수적 예약** — 예약액은 `max_input_tokens`(셈에 여유분을 뺀 허용치보다 큼) · `max_output_tokens` 기준. 예산 확인은 예약액으로.
3. **실제 정산** — 끝나면 공급자가 돌려준 실제 사용량으로 정산. 작게 기록하거나 깎지 않음.
4. **초과 뒤 차단** — 실제가 예약을 넘은 요청이 한 건이라도 생기면 그 학교의 추가 호출을 막고, 관리자 확인(P6-05) 뒤에만 다시 엶.

보장하지 않는 것: 토큰 셈은 공급자가 "추정"이라고 안내하는 값이라, 셈과 실제가 여유분 이상 다르면 **그 한 건은 예약을 넘을 수 있습니다.**
그 한 건은 실제대로 기록되고(3), 그 뒤 호출은 막힙니다(4). 이미 시작해 진행 중인 다른 요청은 끝까지 가고 실제대로 정산됩니다.

원칙(요청서 그대로):
- 한도 초과는 **유료 답변 생성 전에** 처리합니다.
- 이미 발생한 비용은 **실제 사용량으로** 정산합니다. 비용을 작게 기록하지 않습니다.
- 근거를 **조용히 잘라** 한도에 맞추지 않습니다. 넘으면 교사에게 "근거를 줄여 다시 물어 달라"고 알립니다.

### 2-3. 해제 RPC — `workhub_ai_release`

```
workhub_ai_release(p_actor_user_id uuid, p_member_id text, p_request_key text, p_lease_token text,
                   p_reason text,            -- 'input_too_large' | 'count_failed'
                   p_counted_tokens integer) -- input_too_large 면 셈 결과(≥ 1), count_failed 면 NULL
```

**한 트랜잭션 안에서, `start` 와 같은 잠금으로:**

1. `p6_lock('req' ‖ 학교 ‖ 계정 ‖ 요청 번호)` — `prepare` · `start` · `finish` 와 **같은 열쇠**. 그 뒤 요청 행을 `FOR UPDATE`.
2. 행이 없거나 소유(인증 UID · 소속)가 다르면 `NOT_FOUND`.
3. 이미 이 임대로 해제된 행(`state='rejected'` · `released_lease = p_lease_token` · 같은 사유)이면 **처음과 같은 응답**(재전송).
4. `started_at IS NOT NULL`(시작함) → `CONFLICT`. 원장 · 예약 그대로. **시작한 요청은 해제로 0원 처리하지 않음.**
5. `state <> 'claimed'` 또는 `lease_token <> p_lease_token`(다른 임대가 다시 인수함 — 낡은 임대) → `CONFLICT`. 새 임대는 건드리지 않음.
6. 위를 통과하면(같은 임대 · 시작 안 함. 임대 기한이 지났어도 됨 — 그 임대로는 `start` 가 불가능하므로 안전):
   `state='rejected'`, `result={code}`, `cost_state='settled'`, `actual_micro_usd=0`, `released_lease`, `released_at`, `release_tokens` 기록 + 감사 1행.
7. 응답 `data` = `{"state":"rejected","requestKey":…,"code":"INPUT_TOO_LARGE"|"COUNT_FAILED"}`(3-2절, `prepare` 재조회와 같은 모양).

`start` 쪽은 바꾸지 않습니다(이미 같은 잠금 · `state='claimed'` · 같은 임대 · 기한 안일 때만 `started:true`). 그래서 같은 임대로
`start` 와 `release` 가 동시에 와도 **둘 중 하나만** 이깁니다: `start` 가 먼저면 `release` 는 4번으로 `CONFLICT`, `release` 가 먼저면 `start` 는 `started:false`.

### 2-4. "외부 호출"과 "유료 답변 생성"을 나눠 셉니다

토큰 셈(Token Counting)은 공급자 안내상 과금되지 않지만 **외부 호출**이고, 보낼 본문 전체(질문 · 이전 대화 · 근거, 학생 근거 포함)가 공급자에게 전달됩니다.
그래서 "비용 0"과 "외부로 나간 것 0"은 다릅니다.

| 경우 | 외부 호출(셈 + 생성) | 유료 답변 생성 | 원장 금액 | 학생 근거가 공급자에게 감 |
|---|---|---|---|---|
| 준비 안 됨 · 예산 초과 · 권한 없음(prepare 단계) | 0 | 0 | 기록 없음 | 아니오 |
| 정책에 `maxInputTokens` 없음(A1) | 0 | 0 | 임대만, 기한 뒤 0 | 아니오 |
| 셈 → 상한 초과(`INPUT_TOO_LARGE`) | 1(셈) | 0 | 0(해제) | **예(셈 요청으로)** |
| 셈 실패(`COUNT_FAILED`) | 1회 시도 | 0 | 0(해제) | 시도함(도달 여부 모름) |
| 셈 통과 → 생성 | 2 | 1 | 실제 사용량 | 예 |
| `start` 결과 모름(A7) | 1(셈) | 0 또는 모름 | 예약액(`provider_unknown`, P6-05 확인) | 예(셈) |

화면 · 보고서 · 시험 이름에서 "외부 호출 0"은 첫 두 줄에만 씁니다. 나머지는 "유료 답변 생성 0"으로 씁니다.
셈 API 의 과금 여부 · 사용량 한도 · 데이터 보관은 **공급자 문서로 다시 확인할 항목**이고(결정 D4 · D8), 이 문서가 확정하지 않습니다.

### 2-5. 셈과 생성은 같은 입력으로

- 셈 요청 본문 = 생성 본문 객체에서 `model` · `system` · `tools` · `tool_choice` · `messages` 다섯 칸을 **그대로**(같은 객체 참조) 꺼낸 것. 생성 본문의 나머지 칸은 `max_tokens` 뿐.
- 둘 사이에 근거 · 이전 대화를 다시 읽거나 다시 만들지 않음. 시간(오늘 날짜 문구 등)이 들어가는 칸도 한 번 만든 값을 씀.
- 앱 시험: 가짜 공급자가 받은 두 요청에서 다섯 칸을 정규 JSON 으로 바꿔 **바이트가 같은지** 확인(5-2절 B1).

## 3. 정확한 JSON (제안 — 칸 이름 · 값은 결정 뒤 확정)

### 3-1. claim 응답의 `policy` (service_role `workhub_ai_prepare` → `data`)

```json
{
  "state": "claimed",
  "requestKey": "…",
  "leaseToken": "…",
  "input": { "…": "…" },
  "history": [],
  "sources": [],
  "policy": {
    "approved": true,
    "configVersion": 3,
    "model": "<결정 D1>",
    "maxTokens": 2048,
    "maxInputTokens": 38000,
    "budget": {
      "reservationId": "…",
      "policyVersion": 3,
      "currency": "USD",
      "reservedMicroUsd": 210000,
      "dailyLimitMicroUsd": 2000000,
      "monthlyLimitMicroUsd": 20000000
    }
  }
}
```

숫자는 모양을 보이기 위한 예(`max_input_tokens` 40000 · 여유분 5% → 38000)이고, **어떤 값도 정한 것이 아닙니다**(D1~D5).
`maxInputTokens` 는 `policy` 바로 아래, `maxTokens` 옆. `budget` 안에 넣지 않음(돈이 아니라 토큰).

### 3-2. 해제 응답 · 재조회 응답 (`workhub_ai_release` · `workhub_ai_prepare` 재조회 → `data`)

```json
{ "state": "rejected", "requestKey": "…", "code": "INPUT_TOO_LARGE" }
{ "state": "rejected", "requestKey": "…", "code": "COUNT_FAILED" }
```

앱이 교사에게 돌려주는 질문 결과도 같은 모양(지금 `OUTPUT_INVALID` · `PROVIDER_REJECTED` · `TRUNCATED` 와 같은 자리).

### 3-3. 준비 상태 (service_role `workhub_ai_server_readiness` → `data`)

```json
{ "available": false, "reason": "over_reservation" }
```

지금 허용값 `not_configured` · `not_allowed` · `budget_exhausted` 에 하나를 더합니다. 다른 칸은 없음(요청 번호 · 금액은 교사 화면에 내지 않고 P6-05 · P6-03 에서 관리자가 봄).
판정 순서: `not_configured` → **`over_reservation`** → `not_allowed` → `budget_exhausted`(학교 전체가 멈춘 상태를 개인 사유보다 먼저 알림).

### 3-4. 화면 문구 (A11, 제안)

| 값 | 문구 |
|---|---|
| `INPUT_TOO_LARGE` | 보낼 자료가 너무 많습니다. 근거나 이전 대화를 줄여 다시 물어봐 주세요. (요청하지 않았고 비용은 없습니다) |
| `COUNT_FAILED` | 보내기 전 확인을 하지 못해 요청하지 않았습니다. 비용은 없습니다. 잠시 뒤 다시 시도해 주세요. |
| `over_reservation` | 비용 확인이 필요해 비서를 잠시 멈췄습니다. 관리자에게 알려 주세요. |

## 4. 옛 앱 호환과 배포 순서

지금 앱(#59)은 claim `policy` 를 `exact()` 로 검사하고, 거절 코드 · 준비 사유를 고정 목록으로 검사합니다. 그래서:

| 조합 | 결과 | 안전한가 |
|---|---|---|
| 새 SQL + **옛 앱** | claim 에 `maxInputTokens` 가 있어 `INVALID_RESPONSE`(외부 호출 0). 준비 사유 `over_reservation` · 새 거절 코드도 `INVALID_RESPONSE` | 비용 · 외부 호출은 안전, 기능은 멈춤 |
| 옛 SQL + **새 앱** | claim 에 `maxInputTokens` 가 없어 `NOT_READY`(외부 호출 0, A1) | 안전, 기능은 멈춤 |
| 새 SQL + 새 앱 | 정상 | — |

어느 쪽이 먼저여도 비용 사고는 없지만, **비서가 켜진 학교가 있다면** 둘 사이 시간 동안 비서가 멈춥니다. 지금은 P6 이 켜진 곳이 없으므로(설치도 아직):

1. 계란님 결정 D1~D10(아래 6절).
2. **앱(Codex) 먼저** 배포 — A1~A11. P6 이 꺼져 있어 교사 화면 변화 없음. 배포 기록(커밋 · 시각)을 남김.
3. **SQL(Claude)** — P6 이 운영 DB 에 아직 설치 전이면 PR #55 의 P6-01~04 를 직접 고치고 INT-03 목록을 다시 만듦.
   이미 설치된 뒤라면 P6-01/02 를 고치지 않고 **별도 보강 파일(P6-06)** 로 만들고 따로 승인받음.
4. 계란님 설치(비활성) → P6-03 · INT-03 FAIL 없음 확인.
5. 활성화(P6-04)는 결정한 값으로 **별도 승인**. 이 문서 · 이 PR 은 활성화 승인이 아님.
