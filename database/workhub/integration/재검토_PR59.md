### 4-1. INT-03 보완 (재검토 3번) — 통합 브랜치 `131e05d`

| 틈 | 고친 것 | 회귀 |
|---|---|---|
| ① 상속 실행 권한을 놓침(직접 ACL 만 비교) | 목록에 함수마다 `eff` = anon · authenticated · service_role 각각의 `has_function_privilege(…, 'EXECUTE')` 를 더하고, `INT-03-04` 가 직접 부여(`exec`)와 실효 권한(`eff`) 둘 다 대조 | III "그룹 역할에 EXECUTE, anon 이 상속 구성원(`WITH INHERIT TRUE`)" → `INT-03-04` 만 FAIL → 되돌리면 ok |
| ② 소유자를 `mode()` 와 비교 → 전부 바뀌면 놓침 | **허용표 `own(role) = ('postgres')`** 와 비교(승인된 설치 역할 — SQL Editor 실행 역할). 다른 역할 · API 역할 소유는 모두 FAIL | III "점검 범위 함수 소유자를 전부 다른 역할로" → `INT-03-08` 만 FAIL → 되돌리면 ok |

- 목록(manifest)은 다시 기계로 만들었고(`gen_manifest.py write`, 2,167줄), 시험 I 가 지금 SQL 과 같음을 확인합니다. 망가뜨리기 III 는 **15/15**.
- 알아 둘 점: Supabase 의 `anon` · `authenticated` · `service_role` 은 NOINHERIT 라, 그냥 `GRANT 그룹 TO anon` 은 실제로 권한을 주지 않습니다(`has_function_privilege` 도 false — 맞는 판정). 상속이 실제로 열리는 경우(`WITH INHERIT TRUE`)를 시험했습니다.
- **운영 DB 의 실제 역할 구성 · 소유자로 기준선을 확인해야 합니다**(실행안내 0-1). 그때 다른 값이 나오면 그것을 정답으로 삼아 허용표나 목록을 고치지 않고 멈춥니다.
