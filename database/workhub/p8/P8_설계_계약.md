## 1. Q4 — 새 학년도 시작 연도 (P8-01)

- 규칙: **시작일의 연도 = 학년도 숫자.** 월 · 일은 보지 않고, 끝이 다음 해여도 됩니다(예: 2027학년도 2027-03-02 ~ 2028-02-28 통과, 2027학년도 2026-12-01 시작 거부).
- 검사하는 곳은 **새로 만드는 두 경로뿐**: P1 `workhub_school_admin_mutate`(`save_configuration`, `mode=create_year`) · P7 `workhub_school_transition_preview` / `_mutate`(`apply`, `plan.kind=new_year`).
  거부는 각 계약의 봉투 그대로(P1 `{error:{code:'INVALID_INPUT'}}`, P7 `{error:{code:'INVALID_INPUT'}}`).
- 소급 거부 없음: 기존 학년도 수정(`mode=update`) · 조회 · 이미 접수된 요청 번호의 재전송(원장 먼저)은 검사하지 않습니다. 시험 D 가 2031-12 에 시작한 2032학년도(옛 자료)를 수정해 봅니다.
- 함수 2개(`p1_save_configuration` · `p7_plan_eval`)는 원본에 **한 자리씩만** 더했습니다(`-- [P8-01]` 표시). 시험 A04a 가 원본과 줄 단위로 비교해 표시 없는 차이가 없음을 확인합니다.
- 앱 대조: PR #60 `academicYearStartMatches` 의 판정 = 서버 판정(실제 입력 2건).

## 2. C6 — 협업 사이트 알림 (P8-02)

- 협업 이력(`workhub.cooperation_history`)에 행이 생기는 **같은 트랜잭션**에서 알림 1건(트리거). 원본 변경이 되돌려지면 알림도 없습니다(시험 E: 강제 실패 뒤 알림 0).
- 출처는 정확히 `{module:'cooperation', id:<협업 요청 ID>}`. 메일 · 푸시 · 예약 작업 없음.
- 내용: 제목 = 행동별 고정 문구, 본문 = 협업 제목(최대 120자). **협업 설명 · 의견 · 학생 · 상담 · DM 본문은 복사하지 않습니다.**
- 알림을 읽는 것(`read_notice`)은 수락 · 완료가 아닙니다(시험 E: 읽은 뒤에도 협업 상태 그대로). 원본을 열 때는 앱이 `workhub_cooperation_get` 으로 지금 상태 · 권한을 다시 받습니다 —
  당사자가 아니게 되었으면 `NOT_FOUND`(시험 E: 인계로 빠진 사람).
- 켜는 조건: `cooperation_notices` 활성 **그리고** 메신저(P3) 준비. 켜기 전에는 알림을 만들지 않으므로 옛 앱(#59 이전, cooperation 출처를 모름)의 알림함이 깨지지 않습니다.

### 행동 × 받는 사람 × 중복 방지

| 행동(이력 action) | 하는 사람 | 알림 받는 사람 | 제목(고정) |
|---|---|---|---|
| `create` | 보낸 사람 | 받는 사람 | 협업 요청이 왔습니다 |
| `accept` | 받는 사람 | 보낸 사람 | 협업 요청이 수락되었습니다 |
| `decline` | 받는 사람 | 보낸 사람 | 협업 요청이 거절되었습니다 |
| `request_completion` | 받는 사람 | 보낸 사람 | 협업 완료 확인 요청이 왔습니다 |
| `retract_completion` | 받는 사람 | 보낸 사람 | 협업 완료 확인 요청이 철회되었습니다 |
| `confirm_completion` | 보낸 사람 | 받는 사람 | 협업 완료가 확인되었습니다 |
| `return_completion` | 보낸 사람 | 받는 사람 | 협업 완료 확인이 반려되었습니다 |
| `cancel` | 보낸 사람 | 받는 사람 | 협업 요청이 취소되었습니다 |
| `handover`(P7 업무 인계로 받는 사람이 바뀜, P7-05 필요) | 새 받는 사람(인계 수락) | 보낸 사람 | 협업 받는 사람이 바뀌었습니다 |

- 받는 사람 = 그 행동을 한 사람의 **상대 당사자 1명**. 하는 사람 본인에게는 보내지 않습니다.
- 중복 방지 키 = `'p8:coop:' || 요청 ID || ':' || 이력 판`. 이력 (요청, 판)은 유일하고, 같은 요청 번호 재전송은 원장 재생이라 이력이 새로 생기지 않습니다 → 같은 행동으로 두 번 생기지 않습니다(알림 표 유일 키가 한 번 더 막음).
- 다른 학교 · 모듈 중지 · 메신저 미준비이면 0건(시험 E).

## 3. Q2 — 공식 담당 인계의 관리자 확인 (P8-03)

| 단계 | 명령 | 상태 · 판 | 누가 | 알림 |
|---|---|---|---|---|
| 신청 | `apply` | `awaiting_admin` 1 | 요청자 | 없음 |
| 관리자 확인 | `admin_confirm` | `pending` 2 | 관리자(year.manage), **요청자 · 받는 사람 본인 아님** | 받는 사람 · 요청자 |
| 관리자 반려 | `admin_reject` | `rejected` 2 | 〃 | 요청자 |
| 대기 중 철회 | `cancel` | `cancelled` 2 | 요청자 | 없음 |
| 수락 | `accept` | `accepted` 3 — **담당 이전과 같은 트랜잭션** | 받는 사람 | (P7 그대로) |
| 거절 · 철회(확인 뒤) | `reject` · `cancel` | `rejected` · `cancelled` 3 | 받는 사람 · 요청자 | (P7 그대로) |

- 명령 모양: `{kind:'admin_confirm'|'admin_reject', recordId, expectedVersion, reason}` — P7 의 기록 명령과 같은 칸.
- 거절 코드: 관리자 아님(당사자면 `FORBIDDEN`, 아니면 `NOT_FOUND`) · 켜지지 않음 `NOT_READY` · 본인 확인 `FORBIDDEN` · 판 · 상태 다름 `CONFLICT`.
- **두 번 다시 검사**: 관리자 확인 때와 수락 때 모두 원본 판 · 담당 기간 · 받는 사람 자격을 다시 봅니다(`p8_handover_recheck`). 그사이 담당이 바뀌었으면 `CONFLICT`.
- 동시성: 같은 기록을 두 관리자가 동시에 확인 → 하나만 `pending`, 다른 하나 `CONFLICT`(시험 F).
- 목록(`workhub_school_transition_list`): 학교에 `duty_admin_review` 활성화 행이 **생긴 뒤**(켬 · 중지)에는 새 모양
  `{…, dutyApproval:'admin_review_v1'|null}` + 기록마다 `requesterMemberId · requiresAdminReview · canAdminReview · adminReview` 를 **모든 기록에** 줍니다.
  행이 없으면(설치만) 지금 모양 그대로 — 옛 앱이 읽습니다. PR #60 parser 는 `dutyApproval` 키가 있으면 새 모양으로 읽습니다.
- 옛 접수증을 고치지 않음: 같은 요청 번호 + 같은 내용이면 언제나 원래 접수증을 먼저 돌려줍니다(원장 먼저). 중지 중에도 재생은 됩니다.
- 켜기 전(설치만): 공식 담당 인계의 미리보기 · 신청 · 확인 · 수락은 `NOT_READY`, 자원 목록에도 공식 담당이 나오지 않습니다. 협업 · 수합 인계 · 새 학년도 · 대기 중 기록의 거절 · 취소는 지금과 같습니다.
- 설치 거부: 공식 담당이 든 인계 기록이 이미 있으면(P7 옛 흐름) 멈춥니다. 확인 이력을 지어내거나 "확인 불필요"로 거짓 응답하지 않으려는 것입니다. 운영 DB 에는 P7 이 없으므로 이 경우가 없습니다.

## 4. 수업 담당 · 수강 변경 (P8-04)

앱 계약 `teaching-relations.v1`(PR #60 `teaching-relations-contract.md` · `relations-*.ts`)의 세 함수입니다.

| 함수 | 하는 일 |
|---|---|
| `workhub_teaching_relations(p_member_id, p_course_id)` | 지금 관계 조회(담당 · 수강 · 학적, 관계 판, 영향 기록 수). 학생 300 · 수강 1000 · 담당 300 상한 |
| `workhub_teaching_relation_preview(p_member_id, p_intent)` | 의도 4종(`assignment_replace` · `assignment_end` · `membership_end` · `student_transfer_out`)의 **전체 영향 미리보기**(10분, 한 번만 사용) |
| `workhub_teaching_relation_commit(p_member_id, p_command, p_request_key)` | 미리보기의 정확한 판으로 확정. 영향 전체를 다시 계산해 미리보기와 같을 때만 |

- **증분만**: P5 의 담당 · 학적 · 수강 행은 UPDATE/DELETE 하지 않습니다. 종료는 `teaching_relation_ends` 에 사건으로 쌓고, 유효 끝 = 원래 끝 · 마지막 사건의 `lastDay + 1` · 시작 전 취소면 시작일(빈 기간). 관계 판 = 1 + 그 관계의 사건 수.
  시험 G 가 확정 전후 P5 행 해시가 같음을 봅니다.
- **교체**: 옛 담당 종료 + 새 담당 생성을 한 트랜잭션에서. 새 담당 시작 = 옛 담당 `lastDay + 1`.
- **종료가 반영되는 곳**: 지금 담당 판단(`p5_current_assignment` — 종료 뒤 쓰기 · 상담 · 명부 권한 없음), 수업 보임(`p5_course_visible` · `p5_catalog`), 명부 재업로드(종료된 수강 · 학적은 `CONFLICT`),
  새 기록 트리거 5개(관찰 · 상담 판, 평가 판, 활동 채택, 활동 원문 판, 학적 종료 뒤 새 수강). P4 근거 확인(`p5_document_student_check`)은 그대로 — 종료일 뒤 기록이 있으면 확정을 거절하고 종료 뒤 새 기록은 트리거가 막으므로 남은 근거는 모두 유효 기간 안입니다.
- `lastDay ≥ basisDate`(학교 오늘). 대상 관계는 `lastDay ≥ 시작일`. 전출의 다른 수강 중 아직 시작 전인 것은 `cancel_before_start`.
- 확정 거절: 공통 봉투 + `ok:false, code, requestKey, commandHash`. `commandHash` = SHA-256(`relationCanonical(명령)`) — PR #60 `csvHash(relationCanonical())` 와 같음(실제 거절 봉투 13건, 한글 사유 포함).
- 미리보기 만료 뒤 새 확정은 `CONFLICT`, **이미 완료된 같은 요청 번호는 재생**(만료 · 중지 뒤에도). 같은 번호 다른 내용은 `IDEMPOTENCY_CONFLICT`.
- 켜기 전 · 수업(P5) 미준비: 세 함수 모두 `UNAVAILABLE`(봉투 그대로). **수업 기록 열람(P5 `workhub_teaching_*`)은 막지 않습니다** — 관계 함수가 없거나 꺼져도 P5 화면은 따로 동작합니다.

## 5. 옛 앱 보존 · 설치와 켜기

- 설치(P8-01~04)만으로 옛 앱(PR #48 · #59)의 응답 모양이 바뀌는 곳은 없습니다. 바뀌는 동작은 Q4(새 학년도 시작 연도 — 확정 정책, 바로 효력)와 P8-03 설치 뒤 **공식 담당 인계가 `NOT_READY`** 가 되는 것뿐입니다(관리자 확인 없는 인계를 더 만들지 않음 — 안전 쪽).
- 켜기(P8-06)는 PR #60 이 운영에 배포된 **뒤에만**. 양식은 `app_deploy_ref` 칸이 비면 아무것도 쓰지 않고 멈추고, 그 근거를 감사 기록에 남깁니다.
- 끄기 · 다시 켜기는 `P2-80` · `P2-81`(모듈 이름만 셋 중 하나). 자료는 지우지 않습니다.
