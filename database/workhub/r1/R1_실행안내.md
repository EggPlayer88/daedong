# 업무실 수합(R1) 실행 안내

2026-10-15 · 작성: Claude Code · 검토: Codex · 실행: 계란님

R1 은 업무실에 **파일형 문서 수합**의 서버 쪽(DB·호환 함수·비공개 파일 권한)을 더합니다.
요청서는 PR #34 의 `docs/workhub/32-collection-server-sql-request.md`, 앱 연결 설명은 `33-collection-server-connection.md` 입니다.

**SQL 을 적용해도 수합은 바로 열리지 않습니다.** 준비 상태(`R1-04` 마지막 행)가 `ready` 가 되려면
① 학교 정책 게시(R1-06), ② 서버 검증 작업자 구현·배포, ③ 작업자 연결(R1-05) 과 heartbeat 가 모두 필요합니다.
②는 아직 구현 전이므로, 이번에는 R1-00~04 까지만 적용하고 화면은 "준비 중"으로 보이는 것이 정상입니다.

## 대상

| 대상 | 값 |
|---|---|
| Supabase 프로젝트 | `dhaoszbqtbofqftgjfyb` (SQL Editor: https://supabase.com/dashboard/project/dhaoszbqtbofqftgjfyb/sql/new) |
| 전제 | R0-01·R0-02·R0-03 적용됨 (2026-10-15). **R0 를 다시 실행하지 않고, R0-90 도 쓰지 않습니다.** |
| 실행 역할 | SQL Editor 기본 역할 `postgres`. 역할 바꾸기(impersonate)는 켜지 않습니다 |

R1-01~03 은 각각 파일 전체가 한 트랜잭션입니다. 중간에 `ERROR` 가 나면 그 파일은 아무것도 남기지 않습니다.
각 파일은 시작할 때 앞 단계 판(`2026-10-15.1`)을 확인하고, 이미 적용됐거나 다른 판이면 멈춥니다(덮어쓰지 않음).

## 실행 전에

1. SQL Editor 위쪽의 프로젝트가 **`dhaoszbqtbofqftgjfyb`** 인지 확인합니다.
2. **SQL Editor 는 마지막 결과만 보여 줍니다.** 각 파일은 마지막 결과가 확인표가 되도록 만들었습니다.
3. 기존 사이트가 정상인지 한 번 봐 둡니다: 로그인, 평가계획서 목록, 제출 파일 하나 내려받기, 업무실 일정 하나 열기.

## 실행 순서 (이번)

| 순서 | 할 일 | 정상 결과 | 아니면 |
|---|---|---|---|
| 1 | `R1-00` 실행 → 결과 전체를 '실행 전' 으로 저장 | `점검` 8행이 `ok`/`info`, 이어서 `지문` 행들(수는 public 표 개수에 따라 다름, 시험 DB 는 40행) | `FAIL` 이 있으면 멈추고 그 행을 알려 주세요. `WARN` 은 아래 표 참고 |
| 2 | `R1-01` 실행 | `R1-01-1`~`5` 모두 `ok` | 멈춤. 메시지 그대로 알려 주세요 |
| 3 | `R1-02` 실행 | `R1-02-1`~`4` 모두 `ok` | 〃 |
| 4 | `R1-03` 실행 | `R1-03-1`~`6` 모두 `ok`, `R1-03-6` 값 `verification_missing` 또는 `policy_missing` | 〃 |
| 5 | `R1-04` 실행 | `FAIL` 없음. `R1-04-14` 가 `info` + `verification_missing` | 〃 |
| 6 | `R1-00` 다시 실행 → 1번과 비교 | **`지문` 행의 fingerprint 가 모두 같음** (점검 행 P6·P7 은 달라지는 것이 정상) | 다른 행 이름을 알려 주세요 |
| 7 | 사이트 확인 | 로그인·평가계획서·기존 제출 내려받기·업무실 일정/업무 정상. 수합 화면은 "준비 중" | |

- 지문이 같다는 것은 **그 지문이 보는 범위**에서만의 증거입니다. `auth.users` 는 id 목록만, 다른 버킷의 Storage 파일은
  버킷·경로·객체 ID·owner 네 열만 봅니다. 비밀번호·세션·파일 본문은 지문에 없습니다 → 파일 본문은 7번에서 기존 제출 파일을
  실제로 내려받아 열어 보는 것으로 확인합니다.
- 1번 `P8` 이 `FAIL` 이면(Storage 가 요청 종류 `storage.operation` 을 알려 주지 않는 판) R1-03 이 시작 전에 멈춥니다. 그 행을 알려 주세요.
- 6번에서 `F8 R0자료`·`F9 기존자료` 행만 다르고 그사이 누가 가입·제출·업무실 사용을 했다면 그 때문일 수 있습니다.
  `F1`~`F7`(구조) 은 반드시 같아야 합니다.
- 1번 `WARN` 의 뜻: `P3`(오늘이 든 학년도 없음) → 설치는 되지만 수합 만들기가 거부됩니다. `P5`(버킷을 한정하지 않은 Storage 정책)
  → 설치는 되지만 준비 상태가 `storage_missing` 으로 닫힙니다. 둘 다 알려 주시면 원인을 같이 봅니다.
- 중간에 멈췄다면: 멈춘 파일만 원인을 고친 뒤 **그 파일부터** 다시 실행합니다. 앞 파일은 다시 실행하지 않습니다(이미 적용됐다고 멈춥니다).
  어디까지 적용됐는지는 `R1-04` 의 `R1-04-01` 또는 `select * from workhub_private.batch_installs` 로 봅니다.

## 중지·재개 (자료 보존)

문제가 보이면 지우지 말고 멈춥니다. 자료·접수·감사·Storage 실물은 그대로 남습니다.

| 상황 | 실행 | 결과 |
|---|---|---|
| 새 제출·업로드만 막기 | `R1-80` 에 `writes_stopped` + 사유 | 수합 쓰기·업로드·작업자의 새 인수 중지. 목록·상세·이미 받은 파일 내려받기는 됨. **이미 인수한 검증·정리 작업의 마무리(봉인·실패·정리 확정)는 받음** |
| 수합 전체 막기 | `R1-80` 에 `all_stopped` + 사유 | 위 + 조회·내려받기 허가·Storage 읽기 중지. 작업자의 새 봉인·정리 확정도 `NOT_READY`(실패 보고만 받음). 화면은 "준비 중" |
| 다시 열기 | `R1-81` 에 사유 | 스위치만 열림. 정책·작업자 조건은 다시 확인되므로 `R1-04-14` 로 실제 상태 확인 |

- 어느 경우에도 **R0 일정·업무, 로그인, 기존 평가계획서·제출 파일은 영향이 없습니다**(시험 S08).
- 바꾼 사람·시각·사유는 `workhub_private.r1_switch_log` 에 남고 고칠 수 없습니다.
- 같은 요청 번호로 다시 보낸 명령은 중지 중에도 최초 접수증을 돌려줍니다(이중 접수 없음, 시험 S04).

### 작업자 연결 끊기 (R1-05 이후에만 해당)

작업자가 잘못 동작하면 먼저 `R1-80`(writes_stopped)으로 새 인수를 멈춘 뒤, 곧바로 아래 두 줄로 연결을 끊습니다. 행은 지우지 않습니다.
writes_stopped 만으로는 이미 인수한 작업(lease 최대 5분·정리 10분)의 봉인이 들어올 수 있습니다 — 연결을 끊으면 그것까지 `FORBIDDEN` 입니다.

```sql
update workhub_private.api_role_principals set revoked_at = now() where service_principal_id = 'svc_file_worker' and revoked_at is null;
update workhub.service_principal_scopes set revoked_at = now() where service_principal_id = 'svc_file_worker' and revoked_at is null;
```

끊으면 준비 상태가 `verification_missing` 으로 닫히고, 작업자 함수는 `FORBIDDEN` 을 돌려줍니다.

### 제거가 필요할 때

R1 에는 DROP 파일이 없습니다. 교사가 올린 제출·파일을 지우는 일은 되돌릴 수 없기 때문입니다.
정말 걷어내야 하면 `R1-82` 결과(남은 자료 수, R1 밖의 의존)를 알려 주세요. 그 결과를 근거로 자료 내보내기 → 확인 → 제거
순서의 별도 SQL 을 따로 작성해 승인받습니다. `DROP SCHEMA ... CASCADE` 와 R0-90 은 쓰지 않습니다.

## 실제 환경에서 시험하지 못한 것 (적용 뒤 같이 확인)

`R1_시험결과.md` 의 "미실행" 절에 자세히 있습니다. 요약하면:

1. **Storage 정책 생성 권한** — Supabase 의 `postgres` 가 `storage.objects` 에 정책을 만들 수 있는지(R1-03 이 시작 전에 확인하고, 안 되면 아무것도 만들지 않고 멈춤).
2. **실제 PostgREST 응답** — 앱(`supabase-js`)으로 부른 호환 함수의 HTTP 응답 모양.
3. **실제 Storage 업로드·내려받기** — SDK 업로드 시 Storage 서버가 `owner`·`owner_id` 를 어떻게 채우는지, 정책 판정이 시험과 같은지.
4. **service_role 경로** — 작업자가 PostgREST 로 부를 때 `role` 설정값이 `service_role` 로 보이는지.

2~4 는 정책·작업자 전에는 수합이 닫혀 있어 실사용에 영향이 없습니다. 실사용 확인 때 모아서 봅니다.
