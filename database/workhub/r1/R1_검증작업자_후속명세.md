# 수합 파일 검증·정리 작업자 — 후속 구현 명세

2026-10-15 · 작성: Claude Code · 상태: **연결 전** — 검사·정리 핵심 코드는 있고, R1 에 붙이는 어댑터와 배포가 남음 (이 문서는 R1 SQL 이 기대하는 계약입니다)
Codex 재검토 반영판: 함수 8개, Codex 처리 코어(`workers/collection_files/`, `docs/workhub/36-collection-file-workers.md`) 대응표는 7절.

파일 검사·정리 핵심 코드는 이미 있습니다 — Codex 의 처리 코어(`workers/collection_files/`: 문서 구조 검사·검증 처리·정리 처리).
R1 SQL 은 그 작업자가 쓸 함수 8개와 표를 만들었습니다. 남은 것은 코어의 원장·Storage 포트(지금은 시험 대역)를 이 함수들과 실제 Storage 에 붙이는 어댑터, 그리고 배포입니다. 처음부터 다시 만들 필요는 없습니다.
이 작업자가 배포되고 heartbeat 를 보내기 전까지 수합의 준비 상태는 `verification_missing` 이고, 화면은 "준비 중" 입니다.
SQL 적용 완료와 작업자 완료는 별개입니다.

## 1. 실행 환경

| 항목 | 요구 |
|---|---|
| 위치 | 서버 전용(예: Vercel 서버리스 cron 또는 별도 워커). 브라우저·앱 번들에 넣지 않음 |
| DB 호출 | Supabase PostgREST + **service_role 키**(서버 환경 변수). `rpc('workhub_file_worker_*')` |
| Storage | 같은 service_role 로 Storage API(`download`, `remove`). `DELETE FROM storage.objects` 는 쓰지 않음 |
| 주체 | R1-05 로 `svc_file_worker` ↔ `service_role` 연결 + 학교 범위 승인. 함수가 주체를 스스로 해석하므로 인자로 넘기지 않음 |
| JWT | service_role 호출에 사람 `sub` 가 실리면 거부됨(`FORBIDDEN`). 사용자 세션을 재사용하지 않음 |

교사 쪽 Storage 요청은 직접 업로드·직접 내려받기만 정책을 통과합니다(서명 URL 발급 불가). 작업자는 service_role 이라 이 정책을 거치지 않습니다.

## 2. 주기 작업

```
매 1분:  heartbeat(학교, workerId, {checks:[...], release}, ttl=120)
         claim(학교, workerId, 최대 20) → 각 작업: 내려받기 → 검사 → (job_inspect) → seal 또는 fail
매 1시간: cleanup_claim(학교, workerId, 최대 50) → 각 항목: cleanup_inspect → Storage remove → cleanup_done(deleted) 또는 cleanup_done(retained, 사유)
```

- `heartbeat` TTL 60~1800초. 만료되면 준비 상태가 닫힙니다(새 업로드·제출 중지, 기존 내려받기는 유지).
- `checks` 는 실제로 하는 검사만 신고합니다. `size, sha256, signature, container, encryption` 5종이 모두 있어야 준비 상태가 열리고,
  학교 정책이 미검사 파일을 허용하지 않으면 `malware` 도 있어야 합니다.
- `release` 는 배포 판 표식(`^[A-Za-z0-9_.:+-]{1,50}$`). heartbeat 행은 누적됩니다(이력).

## 3. 검증 작업 (claim → job_inspect → seal/fail)

`claim` 이 돌려주는 항목: `jobId, leaseToken, leaseExpiresAt(5분), fileId, bucket, path, storageObjectId, extension, claimedBytes, claimedSha256, maxFileBytes, policy`.

- `policy` = 검사 기준. **예약 때 고정한 학교·공통 정책판 ∩ 오늘 유효한 정책**(형식·크기·미검사 허용). 검사 도중 정책이 줄었으면 더 엄격한 쪽입니다.
  `maxFileBytes` 는 `policy.maxFileBytes` 와 같습니다.
- 압축 해제 한도(항목 수·확장 크기·압축률·XML 크기)는 **아직 승인 정책 항목이 아닙니다.** 작업자가 자기 기술 상한을 쓰고,
  정책으로 올릴지는 계란님 결정 사항입니다(인계표 3절 2번).
- claim 은 다음 작업을 스스로 닫고 돌려주지 않습니다: 시도 횟수 초과(`verification_exhausted`), 실물 없음(`object_missing`),
  실물 바뀜(`object_changed`), 파일 상태가 검사 대상이 아님(`file_state`). 파일은 `rejected`, 작업은 `failed` 가 되고
  **감사(`file.verify_fail`, final) + outbox(`file.verified`)가 같은 트랜잭션에** 남습니다. 기록이 실패하면 claim 전체가 되돌아갑니다(시험 H10~H13).

작업자가 할 일:

1. `bucket/path` 를 service_role 로 내려받는다. 크기가 `maxFileBytes` 를 넘으면 중단하고 `rejected`.
2. 검사한다.
   - `size` 실제 바이트 수, `sha256` 실제 해시(신고값과 같아야 ready)
   - `signature` 확장자와 파일 표식(PDF `%PDF-`, ZIP 계열 `PK\x03\x04`, HWP OLE 등) 일치
   - `container` hwpx·docx·xlsx·pptx 의 ZIP 항목 수·압축 해제 크기 한도(압축 폭탄), 경로 이상
   - `encryption` 암호화·DRM 문서 거부
   - `malware` (가능할 때) 악성 검사. 하지 않았으면 `scanState: "not_scanned"`, `checks.malware` 를 넣지 않음
3. (선택) 오래 걸린 검사 뒤 `job_inspect(jobId, leaseToken)` 로 `leaseValid`·`objectMatches`·`policy` 를 다시 본다. 읽기만 합니다.
4. 결과를 `seal(jobId, leaseToken, fileId, path, storageObjectId, result)` 로 봉인한다. 봉인이 lease·실물을 **원자적으로 다시 확인**하므로 3번은 빠른 포기용입니다.

```json
{"outcome": "ready", "sizeBytes": 3000, "sha256": "<64 hex>", "detectedMime": "application/pdf", "expandedBytes": null,
 "scanState": "clean", "rejectReason": null,
 "checks": {"size": true, "sha256": true, "signature": true, "container": true, "encryption": true, "malware": true}}
```

| outcome | 조건(SQL 이 다시 확인) |
|---|---|
| `ready` | 크기·해시가 신고값과 같음, 필수 검사 5종 true, `scanState` 가 `clean`(이때 `malware: true` 필요) 또는 `not_scanned`, `rejectReason` null |
| `rejected` | `rejectReason` 필수(`^[a-z_]{2,40}$`, 예: `hash_mismatch`, `signature_mismatch`, `encrypted`, `zip_bomb`, `unsupported`) |
| `quarantined` | 악성 판정. `scanState: "rejected"` + `rejectReason` |

- **lease 대조(seal·fail 공통)**: 인자 중 NULL 이 있으면 `INVALID_INPUT`. 작업 상태 leased, 같은 token, 만료 전, 같은 주체여야 하고
  비교는 NULL 안전입니다. 만료된 lease·재인수 뒤의 옛 token·다른 주체는 `CONFLICT`(시험 H01~H09).
  seal 은 여기에 fileId·정확한 path·Storage 객체 ID·파일 상태까지 대조합니다.
- 같은 인자·같은 결과를 다시 보내면 `{replayed: true}` 로 같은 응답(네트워크 재시도 안전). 다른 결과면 `CONFLICT`.
- **봉인 응답을 잃었을 때**: 같은 인자로 seal 을 다시 보내거나 `job_inspect` 로 `state=done`·`outcome` 을 읽습니다.
  작업자가 재시작돼 보낸 내용 자체를 잃었다면 lease 가 끝나기를 기다렸다가 다시 인수해 처음부터 검사합니다(새 token).
- 검사 자체를 못 했으면(일시 오류) `fail(jobId, leaseToken, errorCode, retryAfterSeconds 10~3600)` → 다시 대기.
  마지막 시도의 fail 은 `final: true`, 파일 `rejected`(`verification_exhausted`) + 감사·outbox(시험 H14).
- 봉인 뒤 크기·해시·형식·검사 결과는 DB 에서도 바꿀 수 없습니다. 수정본은 새 fileId 입니다.

## 4. 정리 작업 (cleanup_claim → cleanup_inspect → Storage 삭제 → cleanup_done)

대상(SQL 이 고름): 어디에도 연결된 적 없는 파일 중
- 업로드 예약이 만료되고 1일 지난 것(`upload_expired`)
- 검증 실패·격리 후 학교 정책의 보존 일수가 지난 것(`rejected_file`)
- 검증됐지만 보존 일수 동안 첨부되지 않은 것(`unattached_retention`)

승인된 정책이 없으면 아무것도 고르지 않습니다. 인수된 파일은 정리 원장에 `blocked` 로 올라가고, **그 뒤 첨부·업로드 확인·Storage 업로드는 영구히 거부**됩니다.
lease 가 끝나도 blocked 는 풀리지 않습니다(다음 실행이 같은 원장 행을 새 token 으로 다시 인수).

1. `cleanup_inspect(ledgerId, leaseToken)` 로 삭제 직전 확인: `leaseValid`, `linked=false`, `verifying=false`, `objectMatches`(원장에 적힌 그 객체인지).
   하나라도 아니면 지우지 않고 다음 실행으로 넘깁니다.
2. Storage API `remove([path])` (service_role).
3. 성공하면 `cleanup_done(ledgerId, leaseToken, 'deleted', null)`. **실물 행이 남아 있으면 `CONFLICT`** — 메타데이터만 지운 척할 수 없습니다.
4. 지우지 말아야 할 사정이 있으면 `cleanup_done(ledgerId, leaseToken, 'retained', '<사유>')`. 파일은 그대로 남습니다.
5. 응답을 잃었으면 같은 인자로 다시 보냅니다 → `{replayed: true}`. 다른 결과·옛 token 은 `CONFLICT`(시험 H19~H24).
   또는 `cleanup_inspect` 로 `outcome` 을 읽습니다. lease 가 끝났는데 아직 blocked 면 다시 인수해, 실물이 이미 없으면 삭제 없이 `deleted` 로 확정합니다.

lease 대조는 검증 작업과 같습니다(NULL → `INVALID_INPUT`, 만료·다른 주체·옛 token → `CONFLICT`). 원장에 lease 주체(`leased_by_service_id`)를 기록합니다.

## 5. 중지 중 진행 작업의 범위

| 스위치 | 새 인수(claim·cleanup_claim) | 이미 인수한 작업의 seal·cleanup_done | fail | inspect |
|---|---|---|---|---|
| `open` | 됨 | 됨 | 됨 | 됨 |
| `writes_stopped` | 0건 | **됨** — 진행 중 작업의 마무리(쓰기 중지 중에는 어차피 첨부·제출이 막힘) | 됨 | 됨 |
| `all_stopped` | 0건 | **`NOT_READY`** — 작업은 leased, 원장은 blocked 그대로(파일은 계속 막힘) | 됨(대기열로 되돌림) | 됨, `leaseValid=false` |

재개 뒤에는 같은 lease 가 살아 있으면 그대로 확정되고(시험 S16), 끝났으면 다시 인수합니다.
작업자 자체를 즉시 멈추려면 스위치가 아니라 **연결을 끊습니다**(실행안내 "작업자 연결 끊기") — 모든 작업자 함수가 `FORBIDDEN`.

## 6. 배포 전 확인 (실제 Storage 실물로)

| 시험 | 기대 |
|---|---|
| 정상 PDF·HWPX 업로드 → 검증 | `ready`, 앱에서 첨부·제출·내려받기 |
| 신고 해시와 다른 실물(업로드 직전 파일 바꿔치기) | `rejected`(`hash_mismatch`) |
| 확장자만 바꾼 파일 | `rejected`(`signature_mismatch`) |
| 암호 걸린 docx | `rejected`(`encrypted`) |
| ZIP 폭탄형 hwpx | `rejected`(`zip_bomb`) |
| 작업자 중지(heartbeat 만료) | 준비 상태 `verification_missing`, 기존 제출 내려받기는 됨 |
| lease 만료 뒤 늦은 seal | `CONFLICT` |
| 교사 세션으로 `createSignedUrl`·`createSignedUploadUrl` | 거부(Storage RLS) — 실제 Storage 에서 처음 확인 |
| 정리: 보존 일수 지난 미첨부 파일 | Storage 에서 사라지고 원장 `completed`, 첨부된 파일은 그대로 |

## 7. Codex 처리 코어(`workers/collection_files`, 문서 36) 대응표

문서 36 의 포트는 "내부 인터페이스 제안"입니다. 어댑터는 아래 R1 함수에 붙입니다.

| 문서 36 포트·요구 | R1 SQL | 차이·남은 일 |
|---|---|---|
| 검증 job 선점/임대/재인수 | `claim` (5분 lease, 만료 작업 재인수 = token +1) | — |
| `ledger.inspect(job)` → `{job, policy}` | `job_inspect(jobId, leaseToken)` → `leaseValid`·`policy`·`objectMatches`·끝난 결과 | 정책 객체 모양이 다름: R1 은 `{extensions, maxFileBytes, allowUnscanned, *PolicyId}`. `approval_ref`·`purpose` 는 없음 |
| 정책 `limits`(압축 항목 수·확장 크기·압축률·XML 크기) | **없음** | 정책 항목 신설은 계란님 결정. 그 전까지 코어의 기술 상한 사용 |
| `storage.stat/read` | Storage API(service_role) + claim 의 `storageObjectId` | 실물 identity = `storage.objects.id`. 같은 경로 덮어쓰기는 UPDATE 정책이 없어 교사 쪽에서 불가 |
| `scanner.scan` | `seal` 결과의 `scanState`·`checks.malware` | 스캐너 신원·엔진 판·서명 판은 R1 에 저장하지 않음(봉인 결과 4KB 안의 `checks` 만). 필요하면 후속 열 |
| `ledger.commit_result(lease, evidence, key, hash)` | `seal(jobId, leaseToken, fileId, path, storageObjectId, result)` | 접수 키 `verify_<run_id>` 대신 **인자 전체의 지문**(`result_sha256`)으로 멱등. 같은 인자 재전송 = `replayed`, 다른 결과 = `CONFLICT` |
| 접수 응답 유실 → 미확정 보관, 같은 임대로 재전송 | 같은 인자로 seal 재전송, 또는 `job_inspect` 로 `done`·`outcome` 확인 | 문서 36 이 "아직 없음"이라 한 **재시작·만료 뒤 복구** = lease 만료 후 재인수(새 token)로 다시 검사 |
| 늦은 결과 봉인 거부 | seal·fail 이 만료 lease·옛 token 을 `CONFLICT` | — |
| 사전 오류(`SIZE_LIMIT`·`OBJECT_CHANGED` 등) | 작업자가 `seal(rejected, 사유)` 로 확정하거나 `fail` 로 재시도 | 미지원 형식(PDF·HWP 파서 없음)은 `rejected`(`unsupported`) 로 닫을지 `fail` 로 둘지 작업자 구현 때 결정 — 무한 재시도는 시도 상한(5회)이 막음 |
| 정리 `ledger.reserve` → ticket | `cleanup_claim` → `{ledgerId, leaseToken, …}` (원장 blocked = 영구 차단) | ticket 의 `inspection_hash`·`approval_hash` 대신 원장의 `manifest_sha256`·정책판 ID |
| `ledger.recheck(ticket)` (삭제 직전 확인) | `cleanup_inspect(ledgerId, leaseToken)` | hold·복구 가능한 요청 개념은 R1 에 없음 → 참조(`linked`)·검증 중(`verifying`)만 |
| `storage.head`·`storage.remove` | Storage API. 부재 확인은 `cleanup_inspect.objectPresent` 로도 가능 | 권한 오류를 부재로 바꾸지 않는 것은 어댑터 책임 |
| `ledger.finalize(ticket, evidence_hash)` → purged | `cleanup_done(…, 'deleted')` (실물 남아 있으면 `CONFLICT`) | 같은 인자 재전송 = `replayed` |
| 만료 후 재인수(같은 삭제 ID) | `cleanup_claim` 이 blocked 행을 같은 `ledgerId`·새 token 으로 다시 줌 | 옛 ticket 의 token 은 `CONFLICT` |
| 준비 상태 활성화 증거(문서 36 §6-7) | heartbeat `checks` 5종(+malware) + R1-05 연결 + 승인 정책 | PDF·HWP 미지원이 남아 있으면 정책의 허용 형식에서 빼야 함(형식별 지원 신고는 R1 에 없음) |
| `dry_run` 기본 | SQL 쪽 개념 없음 | 어댑터가 `cleanup_claim` 을 부르는 순간 차단이 생기므로, dry run 은 claim 전 단계에서만 가능 |
