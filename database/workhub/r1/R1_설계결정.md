# R1 설계 결정 (판단해서 정한 것)

2026-10-15 · 작성: Claude Code · 기준: PR #34 `docs/workhub/32` (검토 기준 커밋 fbb8369), 앱 대조 PR #35 (4e07eb3)

요청서가 정하지 않았거나 두 가지로 읽힐 수 있는 곳에서 고른 것입니다. 각 항목에 **왜**와 **되돌리려면 어디를** 적었습니다.
`DECISIONS.md` 의 D 번호는 새로 만들지 않았습니다(확정은 계란님). 아래 K 번호는 이 문서 안에서만 쓰는 이름입니다.

## 범위·적용

**K1. R0 를 고치는 곳은 한 군데 — 서비스 주체 작업 목록 CHECK.**
R1-01 이 `service_principals_action_registry` 를 `school.bootstrap` → `school.bootstrap, file.verify, file.cleanup` 으로 교체합니다.
R0 가 "새 작업 종류는 그 작업을 여는 배치가 교체한다" 고 남긴 확장 지점이고, R0 원문과 다르면 R1-01 이 멈춥니다.
R1-00 지문은 이 CHECK 하나만 빼고 R0 구조 전부를 봅니다. → 되돌리기: R1-01 §2 와 R1-00 F6 의 제외 조건.

**K2. 판 표식 `batch_installs` 와 앞 단계 확인.**
각 파일이 시작할 때 앞 파일의 판(`2026-10-15.1`)을 확인하고, 자기 판이 이미 있으면 멈춥니다. 다시 실행해서 덮어쓰는 경로는 없습니다.
부분 적용 뒤에는 멈춘 파일부터 이어 갑니다. → 판을 올릴 때: 각 파일 첫 DO 블록의 판 문자열과 `c_db_ok()`.

**K3. 제거(DROP) 파일을 두지 않고 비파괴 중지 스위치를 둔다.**
요청서 9-5 대로입니다. 스위치는 `open | writes_stopped | all_stopped` 한 행이고, 준비 상태·명령·Storage 정책·작업자 함수가 모두 이 값을 봅니다.
작업자의 진행 중 작업을 어디까지 받는지는 K25.
제거가 필요하면 R1-82 로 남은 자료를 본 뒤 별도 SQL 을 승인받습니다. → R1-03 `c_switch()` 를 부르는 곳.

**K4. 정책값과 작업자 연결은 SQL 본체에 넣지 않고 양식(R1-06·R1-05)으로 분리.**
허용 형식·크기·보존 기간 같은 운영값은 학교 승인 사항이고(요청서 6절), 작업자 연결은 인증·보안 경계라 CLAUDE.md 2절의 승인 대상입니다.
두 양식 모두 `<...>` 칸이 남아 있으면 아무것도 쓰지 않습니다. 대상 학교는 "승인자가 현재 school_admin 인 활성 학교 1곳" 으로 정합니다
(학교가 여러 곳이어도 모호하지 않게).

## 준비 상태

**K5. 준비 상태는 매 호출마다 계산하고, 판정 순서는 DB(중지 포함) → Storage → 검증기 → 정책.**
`ready` 조건: R1-01~03 판 3개 + 스위치 open, 비공개 버킷 + 설치한 정책 2개의 식이 설치 때 기록한 md5 와 같음 + 다른 permissive 정책이
새 버킷을 열지 않음, 만료 전 heartbeat(활성 주체·이 학교 범위·실행 경로 연결·필수 검사 5종), 오늘 유효한 정책 3종의 교집합이 비지 않음.
미검사 불허 정책이면 악성 검사(`malware`)를 하는 작업자가 있어야 합니다. → `c_readiness`.

**K6. "다른 버킷으로 한정된 정책" 판정은 식 문자열의 맨 앞을 본다.**
`(bucket_id = 'x'::text)` 또는 `((bucket_id = 'x'::text) AND ...` 로 시작하고 x 가 수합 버킷이 아니면 한정된 것으로 봅니다.
기존 `submissions` 버킷 정책이 이 형태라 통과합니다. 모양이 다른 정책(함수 호출 등)은 보수적으로 "열 수 있음" 으로 보고 `storage_missing` 으로 닫습니다.
R1-00 의 P5 가 같은 규칙으로 적용 전에 미리 알려 줍니다. → `c_other_bucket`.

## 권한·주체

**K7. 작업자 실행 경로는 두 가지만: PostgREST service_role → `api_role_principals` 1행, 직접 DB 연결 → R0 `session_user` 매핑.**
PostgREST 에서는 `session_user` 가 `authenticator` 라 R0 매핑을 쓸 수 없습니다. 호출자가 주체 ID 를 인자로 고르지 못하게,
운영자가 승인 근거와 함께 등록한 연결 1행으로만 해석합니다. JWT 에 사람(`sub`)이 실려 있으면 service_role 이어도 거부합니다(시험 A10).
→ `worker_actor`, R1-05.

**K8. 작업자 함수는 봉투 없이 오류 코드만 올린다.**
앱이 부르는 함수가 아니고, 서버 코드가 예외 코드로 분기하기 쉽게 했습니다(`NOT_FOUND`·`FORBIDDEN`·`INVALID_INPUT`·`CONFLICT`).

**K9. 잠금 순서: 소속 gate(R0) → 수합/단위 행 → 대상 소속(ID 순 FOR SHARE) → 파일 행.**
요청서의 "공통 잠금" 순서에 대상 소속 잠금을 하나 더 끼웠습니다. 생성·수정 중에 대상 교사의 소속이 끝나는 경합을 막기 위함입니다.
동시 저장 시험(D10)에서 교착 없이 하나만 성공했습니다.

**K10. 자기검토 판정은 소속이 아니라 계정 기준.**
검토자 계정이 어느 단위 책임자 계정과 같으면 `FORBIDDEN`. 같은 사람이 소속을 둘 가진 경우도 막습니다. → `c_validate_targets`.

## 명령·멱등

**K11. 명령 접수 연산 이름은 하나(`collection.mutate`), 감사·outbox 주제는 명령별(`collection.<kind>`).**
같은 요청 번호를 다른 종류의 명령에 재사용하면 본문 지문이 달라 `IDEMPOTENCY_CONFLICT` 가 됩니다. 파일은 `file.prepare`·`file.complete`.

**K12. 재전송은 최초 접수증을 그대로 돌려주되, 지금도 그 원본을 읽을 수 있을 때만.**
권한이 회수된 뒤의 재전송은 `NOT_FOUND`. 접수증에는 ID·판·시각·요청 번호만 있고 본문은 없습니다(metadata-only).

**K13. 업무 오류는 안쪽 블록의 예외 처리(하위 트랜잭션)로 되돌린 뒤 봉투로 돌려준다.**
그래서 오류 봉투가 나간 명령은 원본·접수증·감사·outbox 가 모두 0건입니다(시험 C22·G05·X02). 소속 gate 실패는 R0 와 같이 봉투 없는 예외입니다.

**K14. 마감 지난 날짜로도 요청을 만들 수 있다.**
요청서가 금지하지 않았고, 지난 일을 뒤늦게 모으는 경우가 있어 막지 않았습니다. 제출의 지연 여부는 서버 접수 시각으로 정합니다.
→ 막으려면 `c_cmd_create` 의 dueDate 검사.

**K15. 생성 때는 배부 파일을 받지 않는다(`INVALID_INPUT`). 배부 파일은 update 로 붙인다.**
파일 업로드 준비에는 부모 수합 ID 와 판이 필요한데, 생성 전에는 수합이 없기 때문입니다.

## 파일

**K16. 업로드 예약의 기대판 검사는 "같은 부모, 예약 때 판 ≤ 지금 판" 이면 통과.**
엄격하게 "같은 판" 을 요구하면, 파일을 올리는 사이 다른 공동 작성자가 초안을 저장할 때마다 다시 올려야 하는 끝없는 CONFLICT 가 생깁니다.
부모·목적·업로더가 다르면 `FORBIDDEN`, 예약 판이 지금보다 크면 `CONFLICT` 입니다. → `c_link_files`.

**K17. 경로는 `학교ID/fileId/32자리 무작위`. URL 을 발급하지 않는다.**
내려받기 허가(`file_access`)는 5분짜리 접근 기록만 남기고 `{file,bucket,path}` 를 돌려줍니다. 실제 Storage 읽기 때 SELECT 정책이
그 기록과 원본 해석을 **다시** 통과해야 합니다. 그래서 허가 뒤 소속이 끝나면 같은 기록으로도 못 읽습니다(시험 G41).

**K18. 업로드 만료는 상태를 바꾸지 않고 응답에서 파생한다.**
만료됐고 실물이 없으면 `complete`/`status` 가 `rejected` 로 보여 주지만, 행은 `uploading` 으로 둡니다(읽기 함수에서 쓰지 않기 위해).
정리 작업이 "만료 + 1일" 뒤에 원장에 올립니다. → `c_file_state`, `cleanup_claim`.

**K19. 검증 작업 인수(claim)는 감사에 남기지 않고, 봉인·실패·정리는 남긴다.**
인수는 재시도마다 생기는 운영 이벤트라 감사 기록을 부풀립니다. 결과가 바뀌는 순간만 남깁니다.

**K20. heartbeat 는 행을 계속 쌓는다(덮어쓰지 않음).**
어떤 작업자가 언제 어떤 검사 능력을 신고했는지 이력이 남습니다. 오래된 행 정리는 R1 범위 밖(후속).

**K21. 첨부 파일 문항의 화면 이름은 `첨부 파일`.**
문항판에 파일 문항을 만들 때 쓰는 고정 라벨입니다. 앱에 이 문구를 보여 주는 곳이 생기면 맞춰야 합니다. → `c_write_body`.

## Codex 재검토(2026-10-15)로 더한 결정

**K22. Storage 정책은 요청 종류(`storage.operation`)를 허용 목록으로 본다.**
업로드는 `object.upload`, 읽기는 `object.get_authenticated`(업로드 요청 안의 되읽기는 `object.upload`)만 통과합니다.
서명 내려받기 URL 은 발급 뒤 쓸 때 접근 기록 회수·소속 종료를 다시 보지 않고, 서명 업로드 URL(upsert)은 검증 뒤 같은 경로를 덮어쓸 길을 엽니다.
금지 목록이 아니라 허용 목록인 이유: Storage 에 새 요청 종류가 생겨도 닫힌 쪽으로 실패하게. 값이 없으면 거부합니다.
요청 종류 이름은 Supabase Storage 원본 `src/http/routes/operations.ts`(커밋 23f25e7)에서 확인했고, `storage.` 접두어는 있든 없든 같게 봅니다.
판정은 정책 식이 아니라 두 판정 함수 안에서 하므로 정책 식 지문(`r1_storage_policies`)은 그대로입니다.
`storage.operation()` 이 없는 Storage 판이면 R1-03 이 시작 전에 멈춥니다(R1-00 P8). → `c_storage_op()`, `object_insertable/readable`.

**K23. 제출판 1,000 상한은 수합 단위 advisory 잠금 뒤에 센다.**
단위 행 잠금은 같은 단위만 줄 세우므로, 다른 단위 둘이 999 에서 동시에 제출하면 둘 다 통과했습니다(1,001 → 상세 NOT_READY).
수합 행을 `FOR UPDATE` 하는 대신 advisory 잠금을 쓴 이유: 수합 행은 상세·목록이 읽고 다른 명령도 잠그므로, 제출끼리만 줄 세우는 편이 영향이 작습니다.
잠금 순서는 항상 "단위 행 → 이 잠금"이고 그 뒤 다른 단위를 잠그지 않아 교착이 없습니다(시험 Q02, 잠금을 빼면 실패함을 확인). → `c_cmd_submit`.

**K24. 첨부 개수 상한은 요청 정책과 오늘 유효한 정책 중 작은 값.**
요청 정책은 게시 때 학교 정책 안이었어도, 그 뒤 학교·공통 정책이 줄 수 있습니다. 새 초안 저장·배부 파일 연결(`c_link_files`)과
저장 없이 바로 제출(`c_cmd_submit`) 모두 오늘 값으로 다시 보고, 넘으면 `FILE_FAILED`(파일 형식·크기가 정책 밖일 때와 같은 코드).
이미 받은 제출판은 그대로입니다(시험 M01~M05).

**K25. 중지 중 작업자의 진행 작업: writes_stopped 는 마무리를 받고, all_stopped 는 새 확정을 받지 않는다.**
writes_stopped 는 교사 쓰기를 막는 단계라 이미 인수한 검증·정리의 결과를 기록해도 새로 노출되는 것이 없습니다(첨부·제출이 막혀 있음).
all_stopped 는 비상 정지라 seal·cleanup_done 을 `NOT_READY` 로 거부하고 작업은 leased, 원장은 blocked 그대로 둡니다 — 파일은 계속 막히므로 안전한 쪽.
fail 은 작업을 대기열로 되돌릴 뿐이라 어느 단계에서도 받습니다. 작업자를 즉시 멈추는 수단은 스위치가 아니라 연결 회수입니다.

**K26. 작업자 lease 대조를 하나로: NULL 인자 거부, NULL 안전 비교, 만료·주체·token.**
seal·fail·cleanup_done 이 같은 규칙을 씁니다. 정리 원장에 lease 주체 열(`leased_by_service_id`)을 더해 검증 작업과 같은 수준으로 대조합니다.
claim 의 최종 거부와 fail 의 마지막 시도는 `c_job_close` 하나로 모아 작업·파일·감사·outbox 를 한 트랜잭션에 남깁니다.

**K27. 재전송은 멱등, 복구는 읽기 전용 확인 함수로.**
cleanup_done 도 seal 처럼 같은 token·같은 결과 재전송에 `replayed: true`. 다른 결과·옛 token 은 `CONFLICT`.
문서 36 의 `ledger.inspect`·`recheck` 에 대응하는 `job_inspect`·`cleanup_inspect` 를 더했습니다. 상태를 바꾸지 않으며 끝난 결과도 돌려줍니다.
claim 응답의 `maxFileBytes` 는 고정 100MiB 대신 예약 정책판 ∩ 오늘 정책으로 계산하고 `policy` 객체를 같이 싣습니다.
