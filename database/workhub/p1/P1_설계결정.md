# P1 학교 관리 — 설계 결정

2026-10-16 · Claude Code. 사후 검토용으로 "왜"와 "되돌리려면 어디를"을 함께 적습니다.
되돌림은 모두 **새 증분 SQL 로 함수를 다시 정의**하는 방식입니다(P1 파일을 고쳐 다시 실행하지 않음, DROP 없음).

## 1. R0 와의 대응

| 앱(계약) | R0/P1 저장 | 변환 |
|---|---|---|
| 소속 `ended` | `memberships.status = 'left'`, `left_reason = 'other'` | R0 의 상태 이름을 바꾸지 않고 응답에서만 바꿈 |
| 기간 `startsOn`·`lastDay`(마지막 날 포함) | `valid_from`·`valid_to`(끝 미포함 `[)`) | 서버가 `valid_to = lastDay + 1`. 무기한은 앱 `9999-12-31` ↔ DB `NULL` |
| 대기·반려 소속의 기간 | 시작일 없음 | 응답의 `startsOn` = 신청일, `lastDay` = `9999-12-31` (앱 parser 가 날짜를 요구) |
| 학년도 구성 `configuration` | `schools` + `academic_years` + `terms` + P1 표 3개(`year_departments`·`year_classes`·`year_subjects`) | 부서·학급·교과는 **학년도별 행**. 새 학년도에 같은 이름이 있어도 다른 ID(자동 병합 없음) |
| 공식 담당 | `staff_assignments` (종류 4: homeroom·department·subject·duty) | 대상은 종류별 열 + 복합 FK 로 같은 학교·학년도만 |
| 스냅샷 `version` | `school_admin_activations.revision` | 학교 하나에 판 하나. 무엇을 바꿔도 +1 |

## 2. 정한 것

1. **권한은 R0 권한 3개를 재사용** — 구성 저장 `year.manage`, 담당 배정·종료 `role.grant`, 소속 처리 `membership.approve`.
   새 권한 코드를 만들지 않았습니다(권한 신설은 승인 사항). 담당 배정에 `role.grant` 를 쓴 것은 "누가 무엇을 맡는지 정하는 일"이 역할 부여와 같은 관리자 범위라고 봤기 때문입니다.
   → 되돌리기: `workhub_school_admin_mutate` 의 `v_perm` CASE 와 `p1_capabilities`.
2. **오류 모양** — 업무 오류는 봉투(`error.code`), 그리고 그 경우 **DB 변경 0** (본문 전체를 BEGIN…EXCEPTION 하위 블록에서 실행).
   로그인·소속 확인 실패(`FORBIDDEN`·`INACTIVE_MEMBERSHIP`)는 R0 처럼 봉투 없는 예외로 둡니다. 앱 연결 모듈이 이 둘을 받으면 연결 문맥을 무효화하므로, 봉투로 바꾸면 계정이 바뀐 상황을 놓칩니다.
   예상하지 못한 오류는 다시 던져 앱이 `RESULT_UNKNOWN`(쓰기)·`QUERY_FAILED`(읽기)로 다룹니다. → `p1_envelope`, mutate 의 EXCEPTION 절.
3. **변경 순서** — 학교별 advisory lock → `member_actor` → 설치·활성 확인 → 명령 모양 → 권한 → 요청 번호 → `claim_receipt`(이미 있으면 처음 접수증) → 활성화 행 잠금 → 명령 검사 → 기대 판(CAS) → 종류별 처리 → 판 +1·변경 원장·접수증·감사·outbox.
   advisory lock 을 `member_actor` 보다 먼저 잡은 것은 학교 행 갱신과 공유 잠금이 엇갈려 교착이 나는 경우를 막기 위해서입니다.
   권한을 요청 번호 재조회보다 먼저 보므로 **역할을 회수당한 사람은 같은 키로 재전송해도 접수증을 받지 못합니다**(시험 K05).
4. **중지 중에도 이미 반영된 요청의 재조회는 처음 접수증** — 응답이 끊긴 앱이 결과를 확정할 수 있게. 새 변경만 `NOT_READY`(시험 L03).
5. **R0 제약 3개를 넓힘** — 학년 수 1..6 → 1..20 (앱의 특수·기타 학교급 한도), 학기 이름 30 → 50자(앱 한도), 학기 겹침 금지를 `DEFERRABLE INITIALLY IMMEDIATE` 로.
   마지막 것은 1학기 끝과 2학기 시작을 한 요청에서 함께 옮길 때 중간 상태가 겹치기 때문입니다. 저장 함수 안에서만 DEFERRED 로 바꾸고 끝에 IMMEDIATE 로 되돌려 검사합니다. 다른 경로의 동작은 그대로입니다.
   → 되돌리기: 새 SQL 로 제약을 원래 정의로(그 전에 넓힌 범위의 자료가 없는지 확인).
6. **구성에서 빠진 부서·학급·교과는 지우지 않고 닫음**(`removed_at`). 공식 담당이 참조하면 `CONFLICT`. 이름·번호 맞바꾸기는 두 단계로 처리합니다.
   모르는 ID(다른 학교·학년도)는 `INVALID_INPUT`. 신규 행은 앱의 `draft-<uuid>` 대신 서버가 ID 를 발급하고, 재전송은 접수증으로 끝나므로 행을 두 번 만들지 않습니다.
7. **학기는 번호를 바꿀 수 없음** — R0 가 학기 번호 변경을 막습니다. 빠진 학기는 참조가 없을 때만 지웁니다(FK 가 지킴).
8. **학기·학년도의 상태(planning 등)는 건드리지 않음** — 새 학년도·학기는 `planning` 으로 만듭니다. 상태 전환은 7단계(학년도 전환) 몫입니다.
9. **소속 상태 전이** — 대기 → 재직/반려, 재직·중지 → 재직/중지/종료, 종료·반려 → 재직(복구). 자기 자신은 `FORBIDDEN`.
   재직이 되려면 계정이 활성·가입 승인 상태여야 합니다. 남은 담당이 새 기간 밖에 있거나(중지면 현재·앞으로의 담당 전부), 게시된 수합의 책임자·검토자이면 `CONFLICT`(인계 먼저).
   역할은 새 기간 안에서 시작해야 하고(아니면 `CONFLICT`), 역할 마지막 날은 소속 마지막 날로 줄입니다. 마지막 학교 관리자는 내보낼 수 없습니다.
10. **업무실 관계(`member_relations`)는 오늘 유효한 공식 담당에서** — 부서 담당 → 부서, 담임 → 그 학급의 학년, 교과 담당 → 교과.
    활성화와 무관합니다(중지해도 관계는 유지). R0 원래 함수는 빈 관계를 돌려줬으므로 담당이 없는 동안은 R0 와 같습니다.
    `workhub_context` 의 이름표는 현재 학년도의 부서·교과 이름을 더합니다.
11. **기본 학년도** — 오늘이 든 학년도, 없으면 가장 가까운 앞으로의 학년도, 없으면 가장 최근 학년도.
12. **조회 한도** — 소속 5000, 담당 10000, 학년도 100. 넘으면 봉투 없는 예외(`SCHOOL_ADMIN_LIMIT`)로 앱이 "조회 실패"를 보입니다. 앱 계약의 배열 한도와 같습니다.

## 3. 남긴 차이(계약 대비)

- 학기 번호 변경: 앱 편집기는 막지 않지만 서버는 `INVALID_INPUT`. 실제로 번호를 바꿀 일이 드물어 시범 전 필수는 아니라고 봤습니다.
- 담임의 "학년" 관계만 계산합니다. 교과 담당 교사의 학년은 공식 자료에 없어서 계산하지 않습니다.
- R1 의무 확인은 게시된 수합의 책임자·검토자만 봅니다. 다른 모듈(2~7단계)의 책임은 그 단계 SQL 이 같은 확인을 더해야 합니다.
- 마지막 관리자 보호는 "자기 변경 금지" 때문에 실제로는 다른 관리자가 있어야만 도달합니다. 안전 장치로 남겼습니다.
- 부서장(대표) 표시는 없습니다. 앱 계약에도 없습니다.

## 4. 중지했을 때 (P1-80)

- 준비 상태 `not_configured`, 조회 `NOT_READY`, 새 변경 `NOT_READY`.
- 이미 반영된 요청의 재조회는 처음 접수증. 학년도·소속·담당 자료와 업무실 관계는 그대로.
- 재개(P1-81)하면 판이 이어집니다.
