# 업무실 DB 첫 구축(R0) 실행 안내

2026-10-15 · 작성: Claude Code · 실행: 계란님

R0 는 업무실(workhub)의 **최소 왕복**만 엽니다. 승인된 superadmin 한 명이 학교에 연결되어 일정·업무를 저장하고, 다시 불러와도 남아 있는 데까지입니다. 교사 17명은 아직 업무실을 쓰지 못합니다(지금과 같음). `/workhub` 메뉴는 지금처럼 superadmin 에게만 보입니다.

## 대상 (계란님 결정, 2026-10-15)

지금 쓰는 프로젝트를 개발·검증 환경으로 씁니다. 새 Supabase 프로젝트·Google 로그인 설정·Vercel 환경값은 만들지 않습니다.

| 대상 | 값 |
|---|---|
| Supabase 프로젝트 | `dhaoszbqtbofqftgjfyb` (SQL Editor: https://supabase.com/dashboard/project/dhaoszbqtbofqftgjfyb/sql/new) |
| 사이트 | https://daedong-school.vercel.app · 업무실 https://daedong-school.vercel.app/workhub |
| 로그인 | 지금 쓰는 승인된 superadmin 계정 |

**하지 않는 것:** `migrations/001~007` 다시 실행, 회원 새로 만들기·승격, 새 프로젝트 연결. (별도 검증 환경이 필요해지면 선택 부록 `R0_검증환경_연결안내.md` 참고.)

## 파일

| 파일 | 하는 일 | 쓰기 |
|---|---|---|
| `R0-00_전후지문.sql` | 기존 구조 지문 (실행 전·후) | 읽기만 |
| `R0-01_B01_기반.sql` | 학교·계정·소속·역할·학년도·학기·접수·감사·outbox 표, 공통 함수 | 새 schema 만 |
| `R0-02_B02_일정업무.sql` | 일정·업무 표, 앱 호환 함수 7개 | 새 schema + `public.workhub_*` 7개 |
| `R0-03_학교초기설정.sql` | 학교·첫 관리자·학년도·학기 입력 (3단계로 나뉨) | 새 schema 만 |
| `R0-90_되돌림.sql` | **정상 순서에 넣지 않습니다.** 아래 "되돌림" 참고 | 업무실 전체 삭제 |

기존 `public` 표·함수·(사용자 작성)트리거·정책·권한은 바꾸지 않습니다. 실행 후 지문이 실행 전과 같으면 이것이 확인된 것입니다.

**의도한 변화 한 가지:** 첫 관리자의 업무실 계정이 그 Auth 계정을 `ON DELETE RESTRICT` 로 참조합니다. 그래서 그 Auth 계정은 R0 이후 삭제할 수 없고, PostgreSQL 이 `auth.users` 에 내부 참조 무결성 트리거를 더합니다. R0-00 지문은 내부 트리거를 보지 않으므로, 지문이 같다는 것이 "Auth 관련 동작이 전부 같다" 는 뜻은 아닙니다(설계결정 J8).

## 실행 전에

1. **학년도·1학기·2학기의 시작일과 마지막 날 6개**를 학교 공식 학사일정에서 확인합니다. 추정하지 않습니다(방학·개학일로 학기 경계를 짐작하지 않음).
2. 기존 사이트가 정상인지 한 번 봐 둡니다: 로그인, 평가계획서 목록, 제출 파일 하나 내려받기.
3. SQL Editor 위쪽의 **프로젝트가 `dhaoszbqtbofqftgjfyb`** 인지, 실행 역할이 **`postgres`**(기본값)인지 확인합니다. 역할 바꾸기(impersonate)는 켜지 않습니다.
4. **SQL Editor 는 마지막 결과만 보여 줍니다.** R0-03 처럼 단계가 나뉜 파일은 그 단계 부분만 드래그해 선택한 뒤 실행합니다.

## 실행 순서

각 줄의 정상 결과를 확인한 뒤 다음 줄로 갑니다.

| 순서 | 할 일 | 정상 결과 |
|---|---|---|
| 1 | `R0-00` 전체 실행 → 결과를 '실행 전 지문' 으로 저장(메모장 등) | 9행 (구조 지문 7 + 회원 수 2) |
| 2 | `R0-01` 전체 실행 | 마지막 결과 `B01-1`~`B01-7` 모두 `ok` |
| 3 | `R0-02` 전체 실행 | 마지막 결과 `B02-1`~`B02-5` 모두 `ok` |
| 4 | `R0-03` 의 **[1단계]** 만 선택해 실행 | 본인 superadmin 행의 `is_active`·`auth_linked`·`name_ok` 가 모두 `true` → 그 행의 `id` 복사 |
| 5 | `R0-03` **[2단계]** 의 `<...>` 칸을 아래 표대로 모두 채움 | 빈칸·`<...>` 없음 |
| 6 | 채운 **[2단계]** 만 선택해 실행 | 결과 한 줄에 `school_status: active` |

| 9 | 사이트 확인 (아래) | 모두 정상 |

- R0-01·R0-02 는 파일 전체가 한 트랜잭션입니다. 중간에 `ERROR` 가 나면 그 파일은 아무것도 남기지 않습니다. 메시지를 그대로 알려 주세요.
- `R0 중단: ... 이미 있습니다` 가 나오면 다시 실행하거나 되돌리지 말고, 결과를 알려 주세요. 이전 실행 기록과 현재 구조를 먼저 확인합니다.
- R0-03 파일 전체를 한 번에 실행하지 않습니다(관리자 조회 결과를 보기 전에 입력 단계가 실행됨). 칸이 하나라도 `<...>` 로 남아 있으면 거부되고 아무것도 쓰이지 않습니다.

날짜는 **끝나는 날까지 포함해서** 적습니다(다음 날로 바꾸지 않음). 오늘이 학년도 안에 있어야 하고, 두 학기는 학년도 안에서 서로 겹치지 않아야 합니다.

## 멈춤 기준

아래 중 하나라도 해당하면 **다음 단계로 가지 말고** 결과를 알려 주세요. 오류가 났다고 R0-01 부터 다시 실행하거나 R0-90 을 실행하지 않습니다.

- 결과에 `ERROR`·`FAIL`·`false` 가 있다
- 실행 후 지문의 `fingerprint` 가 하나라도 다르다
- 기존 사이트(로그인·평가계획서·제출 파일)가 평소와 다르게 동작한다

## 되돌림 (정상 순서가 아님)

R0-90 은 **업무실을 통째로 지우는 되돌림**입니다. 업무실에 저장한 일정·업무·감사 기록도 함께 사라지며 되살릴 수 없습니다. 백업을 복원하는 기능이 아닙니다. 문제가 생기면 먼저 원인을 확인하고, 되돌림은 마지막 수단으로 씁니다.

**R0 전용입니다.** 후속 배치(교사 연결·수합 등)를 실행한 뒤에는 쓰지 않습니다. `DROP SCHEMA ... CASCADE` 가 다른 스키마의 종속 객체까지 지울 수 있기 때문입니다. R0-90 은 다음 중 하나라도 있으면 **아무것도 지우기 전에 멈춥니다**: R0 이후에 생긴 업무실 표, 업무실을 참조하는 바깥 객체(FK·뷰·DEFAULT·저장 생성열·RLS 정책·트리거·함수 등, 종류를 알 수 없는 참조 포함).

쓸 때는 [1단계] 지워질 표와 행 수 확인 → [2단계] 제거(실패하면 아무것도 지워지지 않음) → [3단계] 세 칸 모두 `true` → R0-00 으로 지문 확인 순서입니다. `btree_gist` 확장은 남습니다.

## 참고

- 첫 관리자 Auth 계정은 R0 이후 Supabase 대시보드에서 **삭제할 수 없습니다**(의도한 보호).
- Supabase 보안 점검(Advisors)에 `public.workhub_*` 함수가 "SECURITY DEFINER" 경고로 뜰 수 있습니다. 의도한 구조입니다(함수 안에서 승인·소속을 직접 확인).
- 시험 도구의 자료 비교 범위: 구조, 회원·Auth·제출·Storage 목록(`storage.buckets`·`storage.objects`)의 행 수·행 해시. Storage 파일 본문 바이트는 비교하지 않았으므로, 실행 전후 제출 파일 하나를 실제로 내려받아 봅니다.
