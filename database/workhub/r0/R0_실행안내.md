# 업무실 DB 첫 구축(R0) 실행 안내

2026-10-14 · 작성: Claude Code · 실행: 계란님 (검증 환경 → 운영 순서)

R0 는 업무실(workhub)의 **최소 왕복**만 엽니다. 승인된 superadmin 한 명이 학교에 연결되어 일정·업무를 저장하고, 다시 불러와도 남아 있는 데까지입니다. 교사 17명은 아직 업무실을 쓰지 못합니다(지금과 같음).

## 파일과 순서

| 순서 | 파일 | 하는 일 | 쓰기 |
|---|---|---|---|
| 0 | `R0-00_전후지문.sql` | 기존 구조 지문 (실행 전) | 읽기만 |
| 1 | `R0-01_B01_기반.sql` | 학교·계정·소속·역할·학년도·학기·접수·감사·outbox 표, 공통 함수 | 새 schema 만 |
| 2 | `R0-02_B02_일정업무.sql` | 일정·업무 표, 앱 호환 함수 7개 | 새 schema + `public.workhub_*` 7개 |
| 3 | `R0-03_학교초기설정.sql` | 학교·첫 관리자·학년도·학기 입력 | 새 schema 만 |
| 4 | `R0-00_전후지문.sql` | 기존 구조 지문 (실행 후) → 0번과 비교 | 읽기만 |
| 되돌림 | `R0-90_되돌림.sql` | 1~3 이 만든 것 전부 제거 | 새 schema + 7개 함수 삭제 |

기존 `public` 표·함수·(사용자 작성)트리거·정책·권한은 바꾸지 않습니다. 4번에서 지문이 0번과 같으면 이것이 확인된 것입니다.

**의도한 변화 한 가지:** 첫 관리자의 업무실 계정이 그 Auth 계정을 `ON DELETE RESTRICT` 로 참조합니다. 그래서 그 Auth 계정은 R0 이후 삭제할 수 없고, PostgreSQL 이 `auth.users` 에 내부 참조 무결성 트리거를 더합니다. R0-00 지문은 내부 트리거를 보지 않으므로, 지문이 같다는 것이 "Auth 관련 동작이 전부 같다" 는 뜻은 아닙니다(설계결정 J8).

## 실행 전에

1. **검증 환경부터.** 새 Supabase 를 만들어도 사이트는 저절로 그 DB 를 쓰지 않습니다. **`R0_검증환경_연결안내.md`** 의 1~7단계로 "검증 사이트 → 검증 DB" 를 따로 연결하고, 지금 붙은 DB 가 검증 DB 인지 확인한 뒤 아래를 진행합니다. (운영 사이트·운영 환경값은 건드리지 않습니다.)
2. **SQL Editor 의 실행 역할은 `postgres`** (기본값) 그대로 둡니다. 역할 바꾸기(impersonate) 기능을 켜지 않습니다.
3. **SQL Editor 는 마지막 결과만 보여 줍니다.** 단계가 나뉜 파일(R0-03, R0-90)은 해당 단계 부분만 드래그해 선택한 뒤 실행합니다.

## 1단계 — 실행 전 지문

`R0-00_전후지문.sql` 을 실행하고 결과 9행을 **그대로 복사해 저장**합니다 (메모장 등).

## 2단계 — R0-01

전체를 실행합니다. 마지막 결과 7행(`B01-1` ~ `B01-7`)의 `status` 가 **모두 `ok`** 여야 합니다.

- 중간에 `ERROR` 가 나면 이 파일 전체가 취소되어 아무것도 남지 않습니다. 메시지를 그대로 알려 주세요.
- `R0 중단: workhub ... 이미 있습니다` → 이미 실행한 것입니다. 다시 실행하지 않습니다.

## 3단계 — R0-02

전체를 실행합니다. 마지막 결과 5행(`B02-1` ~ `B02-5`)이 **모두 `ok`** 여야 합니다.

## 4단계 — R0-03 학교 초기 설정

1. **[1단계] 부분만** 선택해 실행 → superadmin 목록이 나옵니다. `is_active`, `auth_linked`, `name_ok` 가 모두 `true` 인 행의 `id` 를 복사합니다.
2. **[2단계]** 의 `<...>` 칸을 모두 채웁니다. 날짜는 **마지막 날을 포함해서** 적습니다(예: 학년도 마지막 날 `2027-02-28`).

   | 칸 | 예시 | 비고 |
   |---|---|---|
   | admin_user_id | 1단계에서 복사한 id | |
   | approval_ref | `2026-10-14 계란 승인 R0 초기설정` | 감사 기록에 남는 승인 근거 |
   | school_code | `daedong-ms` | 영문·숫자·`-`·`_` 2~40자 |
   | school_name | `대동여자중학교` | |
   | school_level | `middle` | |
   | grade_count | `3` | |
   | school_year | `2026` | |
   | year_first_day / year_last_day | 학교 학사일정의 학년도 첫날·마지막 날 | 오늘이 이 기간 안이어야 합니다. **예시값을 그대로 복사하지 않습니다** |
   | terms | 1학기·2학기 첫날·마지막 날 (학사일정 기준) | 학년도 안, 서로 겹치지 않게 |

3. **[2단계] 부분만** 선택해 실행 → `school_status: active` 가 들어간 결과 한 줄이 나옵니다.
   - 칸이 하나라도 `<...>` 로 남으면 거부되고 아무것도 쓰이지 않습니다.
   - 첫 관리자가 승인된 superadmin 이 아니면 거부됩니다.
4. **[3단계] 부분만** 선택해 실행 → `S-1` ~ `S-8` 이 **모두 `true`** 여야 합니다.

## 5단계 — 실행 후 지문

`R0-00_전후지문.sql` 을 다시 실행해 1단계 결과와 비교합니다. `fingerprint` 7개가 **모두 같아야** 합니다. (`rows:` 두 줄은 그사이 가입한 사람이 있으면 달라질 수 있습니다.)

## 6단계 — 화면 확인

**검증 사이트**(운영 주소가 아님)에서 그 superadmin 계정으로 로그인해 `R0_검증환경_연결안내.md` 8단계 표(a~h)를 확인합니다.
요약: 연결 상태 확인 → 학교 이름 → 일정 저장·새로고침 → 포함·제외 함께 선택 저장 → 업무 저장·새로고침 → 재로그인 → SQL 로 저장 확인 → 기존 메뉴 정상.

## 멈춤 기준

아래 중 하나라도 해당하면 **다음 단계로 가지 말고** 결과를 알려 주세요.

- 검증 행에 `FAIL` 이나 `false` 가 있다
- 5단계 지문이 하나라도 다르다
- 6단계에서 기존 사이트(평가계획서 등)가 평소와 다르게 동작한다

## 되돌림

R0-90 은 **업무실을 통째로 지우는 되돌림**입니다. 업무실에 저장한 일정·업무·감사 기록도 함께 사라지며 되살릴 수 없습니다. 업무실 자료를 남기는 "복원" 이 아닙니다.
R0 는 새 schema(`workhub`, `workhub_private`)와 `public.workhub_*` 함수 7개만 만들었으므로, 그것을 지우면 기존 `public` 은 R0 이전 구조로 돌아갑니다.

**R0 전용입니다.** 후속 배치(교사 연결·수합 등)를 실행한 뒤에는 이 파일을 쓰지 않습니다. `DROP SCHEMA ... CASCADE` 가 다른 스키마의 종속 객체까지 지울 수 있기 때문입니다. R0-90 은 R0 이후에 생긴 표나 업무실을 참조하는 바깥 객체가 있으면 지우기 전에 멈춥니다.

1. `R0-90_되돌림.sql` 의 **[1단계]** 만 실행 → 지워질 표와 대략의 행 수 확인. 남겨야 할 자료가 있으면 여기서 멈춥니다
2. **[2단계]** 만 실행 → 실패하면 아무것도 지워지지 않습니다
3. **[3단계]** 만 실행 → 세 칸 모두 `true`
4. `R0-00_전후지문.sql` 로 지문이 설치 전과 같은지 확인

`btree_gist` 확장은 다른 곳에서 쓸 수 있어 남겨 둡니다(되돌린 뒤에도 남음). 되돌린 뒤 다시 설치해도 됩니다(시험에서 확인).

## 운영 적용 시 주의

- 검증 환경에서 1~6단계를 모두 통과한 뒤에 운영에 같은 순서로 실행합니다.
- 지문(R0-00)은 구조만 봅니다. 운영 적용 **전후**에 화면으로 한 번씩 확인합니다: 교사 계정 로그인, 신규 가입 → 승인 대기 → 승인, 평가계획서 열기, 제출 파일 하나 내려받기. (시험 도구의 자료 비교도 회원·Auth 해시와 제출 **행 수**까지이고, Storage 파일 본문은 비교하지 않았습니다.)
- 운영에서 R0-90 을 실행하면 그때까지 업무실에 저장한 자료가 모두 사라집니다. 운영 적용 뒤 문제가 생기면 먼저 원인을 확인하고, 되돌림은 마지막 수단으로 씁니다.
- 운영의 첫 관리자 Auth 계정은 R0 이후 **Supabase 대시보드에서 삭제할 수 없습니다**(업무실 계정이 참조, 의도된 보호). 삭제가 필요하면 먼저 R0-90 으로 되돌립니다.
- Supabase 보안 점검(Advisors)에 `public.workhub_*` 함수가 "SECURITY DEFINER" 경고로 뜰 수 있습니다. 의도한 구조입니다(함수 안에서 승인·소속을 직접 확인).
