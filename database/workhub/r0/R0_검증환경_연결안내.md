# R0 검증 환경 연결 안내 (검증 사이트 · 검증 DB · 로그인)

2026-10-14 · 작성: Claude Code · 설정 변경: 계란님 (외부 서비스 설정은 CLAUDE.md 2절 승인 사항)

새 Supabase 프로젝트를 만들고 SQL 을 실행해도, **사이트는 저절로 그 DB 를 쓰지 않습니다.**
사이트는 배포할 때 넣어 둔 주소(`VITE_SUPABASE_URL`)와 공개 키(`VITE_SUPABASE_ANON_KEY`)로 DB 를 고릅니다.
그래서 지금 운영 사이트에서 R0 를 확인하면 **운영 DB** 를 보게 됩니다. 이 문서는 운영을 건드리지 않고
"검증 사이트 → 검증 DB" 한 쌍을 따로 만드는 순서입니다.

## 한눈에

```
운영:  daedong-school.vercel.app        → 운영 Supabase    (그대로 둠, 값 변경 없음)
검증:  verify/workhub-r0 브랜치 미리보기 → 검증 Supabase    (새로 만듦)
```

| 무엇 | 어디서 | 바꾸는 것 | 운영에 영향 |
|---|---|---|---|
| 검증 Supabase 프로젝트 | Supabase | 새 프로젝트 | 없음 |
| Google 로그인 연결 | Google Cloud · 검증 Supabase | 검증용 OAuth 클라이언트 새로 만들기 | 없음 |
| 검증 사이트 환경값 | Vercel | **한 브랜치 전용** Preview 환경값 2개 추가 | 없음 (Production 값은 손대지 않음) |
| 검증 브랜치 | GitHub | `verify/workhub-r0` 브랜치 (코드 변경 없음) | 없음 |

## 1. 검증 Supabase 프로젝트 만들기

1. Supabase 대시보드 → **New project**. 이름은 `daedong-verify` 처럼 운영과 헷갈리지 않게, 지역은 운영과 같게.
2. 만든 뒤 **Project Settings → General** 의 **Reference ID**(예: `abcd…`)를 메모합니다. 이후 "검증 ref" 라고 부릅니다.
   운영 프로젝트의 Reference ID 도 같이 메모해 두면, 뒤에서 어느 쪽에 붙었는지 비교할 수 있습니다.
3. **SQL Editor** 에서 저장소 `migrations/` 의 **001 ~ 007** 을 번호 순서대로 하나씩 실행합니다.
   `000_reset_v1_project.sql` 은 실행하지 않습니다(옛 v1 정리용).

## 2. Google 로그인 연결 (검증 프로젝트용)

운영 OAuth 설정을 고치지 않도록 **검증용 OAuth 클라이언트를 따로** 만듭니다.

1. Google Cloud 콘솔 → **API 및 서비스 → 사용자 인증 정보 → 사용자 인증 정보 만들기 → OAuth 클라이언트 ID**
   - 유형: 웹 애플리케이션, 이름: `daedong-verify`
   - **승인된 리디렉션 URI**: `https://<검증 ref>.supabase.co/auth/v1/callback`
2. 만들어진 **클라이언트 ID·클라이언트 보안 비밀**을 복사합니다.
3. 검증 Supabase → **Authentication → Sign In / Providers → Google** 을 켜고 위 두 값을 붙여 넣습니다.

> OAuth 동의 화면이 "테스트" 상태라면 로그인할 계정(계란님 계정)을 테스트 사용자에 넣어야 합니다.

## 3. 검증 사이트 주소 정하기

Vercel 은 브랜치마다 고정 미리보기 주소를 줍니다. 검증 전용 브랜치 `verify/workhub-r0` 를 쓰면 주소는 보통
`https://daedong-git-verify-workhub-r0-eggplayer88s-projects.vercel.app` 가 됩니다 (이 PR 의 미리보기 주소 `daedong-git-claude-project-thread-x5pbx1-eggplayer88s-projects.vercel.app` 와 같은 규칙).
정확한 주소는 브랜치를 만든 뒤 Vercel 의 그 배포 화면 **Domains** 에서 확인합니다.

- 브랜치는 `main` 과 내용이 같아도 됩니다(코드 변경 없음). 계란님이 말씀하시면 Claude 가 만들어 push 합니다.
- **4단계(환경값)를 먼저 넣고 브랜치를 만듭니다.** 순서가 바뀌면 첫 배포가 운영 DB 를 가리킵니다.
  Vercel 이 브랜치를 목록에서만 고르게 해서 브랜치가 먼저 있어야 하면, 브랜치를 먼저 만들고 환경값을 넣은 뒤 그 배포를 **Redeploy** 합니다.
  (첫 배포가 운영 DB 를 가리켜도 운영에는 업무실이 없어 연결 진단이 준비 안 됨으로 나올 뿐 바뀌는 것은 없습니다. 다만 그 상태에서 로그인하지는 않습니다.)

## 4. 검증 사이트 환경값 (Vercel)

Vercel → 이 사이트 프로젝트 → **Settings → Environment Variables → Add**

| Key | Value | Environments |
|---|---|---|
| `VITE_SUPABASE_URL` | `https://<검증 ref>.supabase.co` | **Preview** 만 체크, 브랜치 칸에 `verify/workhub-r0` |
| `VITE_SUPABASE_ANON_KEY` | 검증 Supabase → Project Settings → API 의 anon(public) 키 | 위와 같음 |

- **Production 행은 건드리지 않습니다.** 이미 있는 `VITE_SUPABASE_*` 행을 "편집" 하지 말고 **새로 추가**합니다.
  브랜치를 지정한 값은 그 브랜치에서만 기존 값보다 우선합니다.
- 같은 두 값을 서버 함수(문서작성 AI)도 읽으므로, 검증 사이트의 서버 함수도 검증 DB 를 봅니다.
  다만 `ANTHROPIC_API_KEY` 는 운영과 같은 키라서 검증 사이트에서 문서작성 AI 를 쓰면 실제 비용이 납니다. 이번 검증에서는 쓰지 않습니다.
- `service_role` 키는 넣지 않습니다(이 사이트는 쓰지 않음).

## 5. 검증 Supabase 의 로그인 주소 허용

검증 Supabase → **Authentication → URL Configuration**

- **Site URL**: 3단계의 검증 사이트 주소
- **Redirect URLs**: `https://<검증 사이트 주소>/**` 추가
  (내 PC 에서 `npm run dev` 로도 볼 경우 `http://localhost:5175/**` 도 추가)

사이트는 로그인 후 "지금 열려 있는 주소" 로 돌아오게 되어 있어(`packages/shared/src/auth.js`), 이 목록에 없으면 로그인 뒤 운영 주소나 오류 화면으로 튕깁니다.

## 6. 첫 로그인과 관리자 지정

1. 검증 사이트에서 Google 로그인 → 승인 대기 화면이 나오면 정상입니다(가입 행이 검증 DB 에 생김).
2. 검증 Supabase SQL Editor:
   ```sql
   UPDATE public.users SET role = 'superadmin', is_active = true WHERE email = '<내 이메일>';
   ```
3. 검증 사이트를 새로고침해 기존 메뉴가 보이는지 확인합니다.

## 7. 지금 붙은 DB 가 검증 DB 인지 확인 (세 가지 모두)

| 확인 | 방법 | 기대 |
|---|---|---|
| ① 로그인 화면 | Google 계정 선택 화면 아래 "…(으)로 이동" 에 나오는 주소 | `<검증 ref>.supabase.co` |
| ② 브라우저 저장소 | 검증 사이트에서 F12 → Application(애플리케이션) → Local Storage → 사이트 주소 | `sb-<검증 ref>-auth-token` 항목이 있음 (운영 ref 가 아님) |
| ③ 가입 기록 | 검증 Supabase → Authentication → Users | 방금 로그인한 계정, 마지막 로그인 시각이 지금 |

셋 중 하나라도 운영 ref 가 보이면 **멈추고** 4단계를 다시 확인합니다. R0 SQL 을 실행하기 전입니다.

## 8. R0 실행과 화면 확인

1. `R0_실행안내.md` 의 1~5단계를 **검증 Supabase SQL Editor** 에서 진행합니다. (SQL Editor 상단 프로젝트 이름이 검증 프로젝트인지 매번 확인)
   학년도·학기 날짜는 예시값을 복사하지 말고 학교 학사일정 기준으로 넣습니다.
2. 검증 사이트에서 **신축 업무실 · 시험** 메뉴(`/workhub`)를 엽니다.
3. 아래를 차례로 확인합니다.

| 순서 | 확인 | 기대 |
|---|---|---|
| a | 화면 아래 **연결 상태 확인** | "학교 소속 조회까지 확인했습니다", 확인된 학교 소속 1곳. **운영 DB 에는 업무실이 없으므로 이 결과 자체가 검증 DB 에 붙었다는 네 번째 근거**입니다 |
| b | 학교 이름 | R0-03 에 넣은 이름 |
| c | 일정 1건 저장 → 새로고침 | 그대로 있음 |
| d | 같은 교사(본인)를 직접 포함과 제외에 함께 두고 저장 | 저장됨(제외 우선) |
| e | 업무 1건 저장 → 완료 표시 → 새로고침 | 그대로 있음 |
| f | 로그아웃 → 다시 로그인 | c·e 가 그대로 있음 |
| g | 검증 SQL Editor: `select title, version from workhub.events order by updated_at desc limit 5;` | 화면에서 저장한 제목이 보임 |
| h | 기존 메뉴(평가계획서 등) 한두 개 열기 | 평소처럼 동작 |

## 9. 끝난 뒤

- 검증 환경은 운영 적용이 끝날 때까지 둡니다. 다시 시험할 때는 `R0-90` 으로 되돌리고 R0-01 부터 다시 실행할 수 있습니다(검증 DB 에서만).
- 운영 적용은 이 문서가 아니라 `R0_실행안내.md` 의 "운영 적용 시 주의" 를 따릅니다. 운영 Vercel 환경값은 바꿀 필요가 없습니다(운영 사이트는 이미 운영 DB 를 봄).
- 검증 Supabase 프로젝트를 지울 때는 Vercel 의 브랜치 전용 환경값 2개와 Google 검증용 OAuth 클라이언트도 함께 정리합니다.

## 참고: 진단 화면에 프로젝트 표시

지금 연결 진단은 상태·학교 수만 보여 주고 어느 Supabase 인지는 보여 주지 않습니다. 그래서 7단계처럼 화면 밖에서 확인합니다.
진단 화면이나 지원용 JSON 에 "연결된 프로젝트 ref" 를 표시하면 이 확인이 한 번에 끝납니다. 앱(`apps/workhub`) 쪽 변경이라 별도 PR 로 제안합니다.
