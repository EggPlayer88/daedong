# P2 설계 결정

2026-10-16 · Claude Code. "판단해서 정한 것"과 그 이유, 되돌리려면 고칠 곳을 적습니다. 확정은 계란님입니다.

## 1. 공통 틀 (3~7단계가 이어 씀)

| 정한 것 | 이유 | 되돌리려면 |
|---|---|---|
| `workhub.module_activations(school_id, module)` 한 표로 학교·모듈별 켜기/중지 | 단계마다 활성화 표를 따로 만들면 중지·재개 파일도 단계마다 생긴다. 모듈 이름은 `^[a-z][a-z_]{2,39}$` 로 열어 두어 3단계부터 행만 추가 | P2-01 표 정의, P2-04 의 모듈 목록 |
| `workhub.request_receipts` 한 표로 쓰기 요청 번호 관리(학교·계정·소속·모듈·요청 번호 유일) | R0 `idempotency_receipts` 는 R0 연산 이름에 묶여 있어 고치지 않고 새로 둔다(R0 수정 금지). 같은 번호 재전송·다른 내용·응답 유실을 한곳에서 가른다 | P2-01 `p2_receipt`·`p2_store`·`p2_replay` |
| **업무 거절도 접수증에 남김**(`outcome='rejected'`, `UNAVAILABLE` 포함) | 앱은 `INVALID_INPUT·FORBIDDEN·NOT_FOUND·CONFLICT·UNAVAILABLE` 거절을 "확정"으로 보고 새 번호로 다시 만든다. 같은 번호로 다시 오면 처음 결과를 그대로 돌려주는 것이 계약과 맞다. 대신 모듈을 켠 뒤에도 그 번호는 계속 `UNAVAILABLE` 이다(시험 C09) | P2-02 `p2_write` 의 예외 처리 |
| 같은 번호·다른 내용(`IDEMPOTENCY_CONFLICT`)과 형식이 틀린 요청 번호는 **남기지 않음** | 남기면 첫 요청의 기록을 덮거나, 저장할 수 없는 키를 저장하게 된다 | 〃 |
| 로그인·소속 확인 실패와 예상 밖 오류는 봉투 없는 예외 | R0 `member_actor` 를 그대로 쓴다. 앱은 이것을 `CANCELLED`·`SAVE_UNCERTAIN`·`QUERY_FAILED` 로 바꿔 "결과 모름"으로 보관한다. 예상 밖 오류는 접수증이 없으므로 같은 번호 재전송이 다시 실행된다(시험 G05·M05) | — |
| canonical JSON 을 SQL 로 다시 구현(`p2_canonical`) | 앱이 `commandHash`·`previewHash` 를 `sha256(canonical(...))` 로 직접 다시 계산해 비교한다. 키는 `COLLATE "C"` 정렬, 문자열·숫자는 PostgreSQL jsonb 출력 그대로 | P2-01 `p2_canonical` |

**canonical 의 전제**: 숫자는 정수만, 객체 키는 ASCII 만 씁니다(이번 계약이 그렇습니다). 키에 한글·이모지를 쓰면 JS 정렬(UTF-16)과 C 정렬(코드 포인트)이
드물게 갈릴 수 있습니다. 값(문자열)에는 한글·이모지·제어문자 모두 같음을 시험했습니다(A05, 앱 대조 거절 36건).

## 2. 일정 일괄 가져오기

| 정한 것 | 이유 | 되돌리려면 |
|---|---|---|
| prepare 는 일정을 쓰지 않고 **불변 미리보기** 1행만 남김(30분 유효) | 교사가 화면에서 보고 고른 것과 적용 대상이 정확히 같아야 한다. commit 은 미리보기의 행(key·sourceId·지문·eventId·판·상태)과 하나라도 다르면 `INVALID_INPUT` | P2-02 `p2_batch_apply` 선택 대조 |
| 비교는 잠그지 않고, commit 이 계보 revision · 일정 version 으로 다시 확인 | 비교는 50행까지 읽기만 하므로 잠금을 오래 쥐지 않는다. 그사이 바뀌면 commit 이 `CONFLICT` 로 전체 거절 | 〃 |
| commit 은 고른 행 전체를 한 트랜잭션으로. 하나라도 어긋나면 전부 미적용 | "일부만 들어감"은 교사가 화면에서 알아차리기 어렵다(시험 G06) | 〃 |
| 기준선(baseline)은 **서버 정규화본**(직접 포함 교사 정렬 등)으로 저장 | 사이트 일정(`event_dto`)과 같은 모양이어야 "사이트에서 바뀌었나"를 정확히 가린다 | P2-02 계보 저장 |
| "중복/변경" 판정은 **앱이 보낸 원문**과 기준선을 비교 | 앱 parser 가 `canonical(baseline) === canonical(incoming)` 로 다시 검사한다. 서버만 정규화본으로 비교하면 앱이 미리보기 전체를 거부한다 | P2-02 prepare 의 `d = led.baseline` |
| 원본 묶음(sourceKey)은 만든 교사(+편집자 표)만 갱신. 다른 교사가 같은 key 로 비교하면 전 행 `held` | 학사일정을 담당자 둘이 번갈아 덮어쓰지 않게. 편집자 추가 화면은 이번 계약에 없어 표만 두었다 | `p2_source_editor`, `calendar_import_source_editors` |
| 비교 뒤 그사이 남이 같은 새 key 를 먼저 만들면 `CONFLICT` | 소유자가 바뀐 묶음에 쓰지 않게(시험 H02) | `p2_batch_apply` 원본 묶음 부분 |
| 사이트에서 지운·취소된 일정은 다시 만들지 않고 `held` | 지운 사람의 판단을 가져오기가 되살리지 않게 | prepare 의 held 분기 |
| 남의 일정을 "나만 보기"로 바꾸는 행은 `held`(관리자여도) | R0 사이트 저장과 같은 규칙. 개인 일정이 되면 작성자 외에는 아무도 못 본다 | prepare·commit 의 private 검사 |
| 작성자는 바꾸지 않음(관리자가 갱신해도 원래 작성자) | R0 `workhub_calendar_save` 와 같음 | — |
| 만료·적용 끝난 미리보기는 지우지 않음 | 자동 정리는 이번 범위가 아니다(보류 항목). 행이 작아 시범 운영 동안 문제되지 않는다 | — |

## 3. 협업 요청

| 정한 것 | 이유 | 되돌리려면 |
|---|---|---|
| 상태 전이표를 SQL 함수 하나(`p2_coop_next`)로 — 앱 `allowedActions`·`nextCooperationStatus` 와 같은 표 | 앱 상세 parser 가 이력을 처음부터 다시 따라가 현재 상태와 맞는지 본다. 어긋나면 화면이 열리지 않는다 | P2-01 `p2_coop_next`·`p2_coop_role_action` |
| 역할에 없는 동작은 `FORBIDDEN`, 역할엔 있지만 지금 상태에서 안 되는 동작·옛 판은 `CONFLICT` | 앱 문구: FORBIDDEN "접근할 수 없음", CONFLICT "다른 곳에서 변경됨 → 최신 확인" | `p2_coop_apply` |
| 당사자가 아니면 `NOT_FOUND`(있는지도 알리지 않음) | 다른 교사 사이의 요청 존재를 드러내지 않게 | 〃 |
| 받는 사람: 같은 학교 · 오늘 유효한 소속 · 소속 active · 계정 active · 가입 승인 · **지금 업무실에 들어올 수 있는 사람**(기존 회원표 활성 · superadmin, R0 `legacy_gate` 와 같은 기준). 대기·거절·정지·끝난 소속·다른 학교·업무실 자격 없는 교사 제외 | 계약의 "받을 수 있는 교사". 만들 때 받는 사람 소속을 `FOR SHARE` 로 잡아 동시 상태 변경과 줄 세움 | `p2_member_reachable` |
| 받는 사람 후보가 500명을 넘으면 오류(앱 `QUERY_FAILED`) | 앱 parser 한도가 500. 잘라서 보내면 "그 사람이 없다"로 잘못 보인다. 한 학교 500명 초과는 검색 API 가 필요할 때 | catalog 의 `COOPERATION_LIMIT` |
| 원본 업무는 내 업무 중 todo·doing·waiting, 40개씩, 마감일(빈 값 마지막)·제목·id 순 | 앱 parser 페이지 한도 40. 위치 값은 소속에 묶어 다른 교사가 못 씀 | catalog |
| 원본 업무 연결은 보낸 사람에게만 보임(`taskLink`) | 앱이 다른 교사의 개인 업무 연결을 거부한다(`ownerUserId` 검사) | `p2_coop_dto` |
| 목록 위치 값은 소속·함·상태·검색어에 묶음 | 다른 필터의 위치로 건너뛰면 빠짐·겹침이 생긴다 | list 의 `v_fhash` |
| 받는 사람 설명 = 오늘 유효한 공식 담당(P1 `staff_assignments`) 이름 | P1 이 켜지기 전에는 빈 값 | catalog |
| 알림은 outbox 사건(`notify_membership_id`)만 남김 | 보내는 작업자는 이번 범위가 아니다. 기록만으로 나중에 보낼 수 있다 | `p2_coop_apply` 의 `emit_outbox` |

## 4. 잠금 순서

일정 commit: 요청 번호(advisory) → 원본 묶음 행 → 계보 행(sourceId 순) → 일정(id 순).
협업 변경: 요청 번호(advisory) → 받는 사람 소속(FOR SHARE) 또는 요청 행(FOR UPDATE) → 원본 업무(FOR UPDATE).
둘 다 R0 `member_actor(lock)` · `lock_member_roles` 를 먼저 잡아 역할 회수와 줄 세웁니다.

## 5. 보안

- 공개 함수 6개는 `authenticated` 만 실행, `SECURITY DEFINER` + `search_path=''`. 학교·계정은 `p_member_id` 와 `auth.uid()` 로 서버가 정합니다.
- 새 표 11개는 RLS 켜짐 + API 역할 권한 0. 내부 함수도 API 역할 실행 불가.
- 감사: 일정 적용은 일정의 공개 범위대로(개인 일정은 `owner_only`), 협업은 모두 `owner_only`.

## 6. 하지 않은 것

자동 정리(만료 미리보기·오래된 접수증), 알림 발송 작업자, 원본 묶음 편집자 추가 화면·API, 받는 사람 검색 API(500명 초과),
메뉴 공개 범위 변경. 모두 보류 항목이거나 이번 계약에 없습니다.
