# 업무실 일정 일괄 가져오기 · 협업 요청(P2) 실행 안내

2026-10-16 · 작성: Claude Code · 검토: Codex · 실행: 계란님

P2 는 통합 SQL 요청서(`docs/workhub/pilot-completion/sql-handoff.md`)의 **2단계 — 일정 일괄 가져오기 · 협업 요청** 증분 SQL 입니다.
앱 계약은 PR #48 의 `calendar-batch.v1`(`apps/workhub/src/calendar/batch-*.ts`)과 `cooperation.v1`(`apps/workhub/src/cooperation/*.ts`)입니다.

- **SQL 을 적용해도 아무 학교에서도 켜지지 않습니다(비활성 설치).** 모듈 활성화 행이 0이라 모든 함수가 `UNAVAILABLE` 을 돌려줍니다.
  켜는 것은 `P2-04` 이고, 그것은 앱 병합·배포 뒤 별도 승인입니다.
- 기존 로그인·가입 승인·회원·평가계획서·수합·업무실 일정/업무 자료는 건드리지 않습니다(`P2-00` 지문으로 확인).
- **R0·R1·R1S·P1 을 다시 실행하거나 고치지 않습니다. R0-90 도 쓰지 않습니다.**

## 3. 이번에 실행할 순서 (비활성 설치)

| 순서 | 할 일 | 정상 결과 | 아니면 |
|---|---|---|---|
| 1 | `P2-00` 실행 → 결과 전체를 '실행 전'으로 저장 | `점검` C1·C2 `ok`, C3 `미적용(P2-01 전)`, `변경` V1 `0` | `FAIL` 이 있으면 멈추고 그 행을 알려 주세요 |
| 2 | `P2-01` 실행 | `P2-01-1`~`5` 모두 `ok` | 멈춤. 메시지 그대로 알려 주세요 |
| 3 | `P2-02` 실행 | `P2-02-1`~`5` 모두 `ok` | 〃 |
| 4 | `P2-03` 실행 | `FAIL` 없음. 마지막 행(`P2-03-11`)이 `info` + `(활성화 없음)` | 〃 |
| 5 | `P2-00` 다시 실행 → 1번과 비교 | **`지문` 행 S1~S6·D1 이 모두 같음.** C3 이 `P2-01@2026-10-16.1, P2-02@2026-10-16.1`, V1 이 `11` | 다른 행 이름을 알려 주세요 |
| 6 | 사이트 확인 | 로그인·평가계획서·수합·업무실 일정/업무·학교 관리 정상. 일정 일괄·협업 화면은 지금과 같이 "서버 연결 준비" | |

- D1 은 자료 지문입니다. 그사이 누가 가입·제출·업무실 사용을 했다면 달라질 수 있습니다. S1~S6(구조)은 반드시 같아야 합니다.
- **P2 적용 뒤 `P1-00`(그리고 `R1-00`·`R1S-00`)을 다시 돌리면** 구조 지문이 바뀝니다. 그 파일들은 P2 표·함수를 빼지 않고 세기 때문입니다(의도).
  `P1-03`·`R1-04`·`R1S-03` 은 그대로 `FAIL` 없음입니다.

## 4. 멈춤 기준

아래 중 하나라도 보이면 **다음 파일로 넘어가지 말고** 그 행·메시지를 알려 주세요.

- P2-00 실행 전 결과에 `FAIL`
- P2-01/02 가 `ERROR` 로 끝남, 또는 마지막 결과에 `ok` 가 아닌 행
- P2-03 에 `FAIL`
- P2-00 실행 후 구조 지문(S1~S6)이 실행 전과 다름
- 6번 사이트 확인에서 기존 기능 하나라도 이상

P2-01·02 가 이미 적용된 뒤 멈춰야 한다면 **되돌리는 SQL 을 즉석에서 만들지 않습니다.** 활성화 행이 없으면 P2 함수는 모두
`UNAVAILABLE` 이고 기존 표·함수는 그대로입니다(시험 II: 비활성 설치 위에서 R1 시험 244건 그대로 통과). 그대로 두고 원인을 먼저 봅니다.

## 5. 그다음 (이번에 하지 않음)

1. PR #48(앱) 검토 반영 · 병합 → Vercel 운영 배포. 메뉴 공개 범위는 지금처럼 superadmin 전용
2. 배포된 화면이 "서버 연결 준비"(`UNAVAILABLE`)를 보이는지 확인 — 이 응답이 오면 앱이 P2 함수와 연결된 것입니다
3. 학교 승인 → `P2-04` 칸을 채워 실행(모듈 하나씩 켜도 됩니다) → `P2-03` 마지막 행이 `daedong-ms:calendar_batch=active` 등
4. 일정 일괄: 작은 파일(2~3행)로 비교 → 적용 → 같은 파일 다시 비교가 모두 "중복"인지 확인
5. 협업: 두 교사가 요청 → 수락 → 완료 요청 → 완료 확인을 한 번 해 보고 상세 이력을 확인

이상하면 바로 `P2-80`(그 모듈만 중지). 중지해도 자료·접수증은 그대로이고, 이미 받은 요청의 재조회는 됩니다.

## 6. 계란님이 정할 값

이 SQL 은 어떤 값도 정해 두지 않았습니다. 칸이 남아 있으면 아무것도 쓰지 않고 멈춥니다.

**P2-04 (활성화)**

| 칸 | 무엇 | 예 |
|---|---|---|
| `approver_user_id` | 승인한 학교 관리자(school_admin)의 회원 id(Auth UID). 대상 학교 = 그 사람이 지금 관리자인 학교 1곳 | — |
| `approval_ref` | 승인 근거 1~200자 | "2026-10-20 교무회의, 협업 요청 시범 운영 승인" |
| `modules` | 켤 모듈 `"calendar_batch"`·`"cooperation"` 중 하나 또는 둘 | `["cooperation"]` |

**P2-80 / P2-81 (중지·재개)**

| 칸 | 무엇 | 예 |
|---|---|---|
| 학교 코드 | R0-03 에서 정한 code | `daedong-ms` |
| 모듈 | `calendar_batch` · `cooperation` (3단계부터는 그 단계 모듈 이름) | `cooperation` |
| 사유 | 1~200자 | "2026-10-21 알림 문구 확인 중" |

**정책으로 정해 주실 것(SQL 에 값으로 넣지 않음)** — `P2_설계결정.md` 7절

- 협업 받는 사람 범위: 2026-10-16 결정("좁히기")대로 지금 업무실에 들어올 수 있는 사람(기존 회원표 활성 · superadmin)만 받는 사람입니다.
  메뉴를 일반 교사에게 넓힐 때 함께 바꿉니다.

## 7. 실제 환경에서 시험하지 못한 것

시험은 로컬 PostgreSQL 17 에 Supabase 의 역할·`auth.uid()` 를 흉내 낸 DB 에서 했습니다(`P2_시험결과.md`).
다음은 실제 Supabase·Vercel 에서 처음 확인하게 됩니다.

- 실제 PostgREST 를 거친 호출(시험은 같은 경로 authenticator → set role → `request.jwt.claims` 를 직접 흉내)
- 실제 회원 자료에서의 받는 사람 목록(이름·담당 표시)과 실제 학사일정 파일의 비교 결과
- 실제 앱 화면(PR #48)의 왕복. 앱 어댑터·parser 는 실제 코드로 대조했지만 브라우저·Supabase 클라이언트는 거치지 않았습니다
- 알림 사건(outbox `cooperation.*`·`event.saved`)을 실제로 보내는 작업자 — 아직 없습니다. 기록만 남습니다
- 운영 DB 의 잠금 대기와 응답 시간. 시험은 동시 요청 2건까지
