# 업무실 수합 HWPX 기본 확인(R1S) 실행 안내

2026-10-16 · 작성: Claude Code · 검토: Codex · 실행: 계란님

R1S 는 R1(수합 서버) 위에 **HWPX 기본 확인 경로**를 더하는 증분 SQL 입니다.
전용 파일 검사기(검증 작업자, R1-05)가 아직 없으므로, 학교가 승인하면 **HWPX 한 가지 형식만**
서버 확인 API(PR #45 `api/collections/check-hwpx.py`)가 크기·해시·HWPX 구조를 확인한 뒤 받을 수 있게 합니다.

- **악성코드 검사가 아닙니다.** 확인을 통과한 파일도 `scan_state = not_scanned` 로 남고,
  검사 결과에 `malwareScan:false, contentValidation:false` 가 함께 기록됩니다. "검사 완료(clean)"로 적는 경로는 없습니다.
- 미검사 허용(`allowUnscanned=true`)을 켜는 방식이 **아닙니다.** 정책의 `allowUnscanned` 는 계속 `false` 이고,
  기본 확인 근거(확인 기록 + 확인 서버 주체)가 있는 HWPX 만 받습니다.
- **SQL 을 적용해도 아무 학교도 켜지지 않습니다(비활성 설치).** 켜는 것은 R1S-04 이고, 그것은 앱·API 병합·배포 뒤입니다.

- R1S 적용 뒤 **R1-04 를 돌리면 03·04·09 행이 FAIL** 로 보입니다. 공개 함수가 17→20개가 되고 작업 목록 CHECK 에
  `file.basic_check` 가 더해졌기 때문입니다(의도한 변경). R1-04 의 나머지 행은 R1S-03 에 같은 식으로 들어 있습니다.
- 5번 `F8`·`F9`·`G3` 은 자료 지문입니다. 그사이 누가 가입·제출·업무실 사용을 했다면 달라질 수 있습니다.
  `F1`~`F7`·`G1`·`G2`·`G4`(구조) 는 반드시 같아야 합니다.

## 4. 멈춤 기준

아래 중 하나라도 보이면 **다음 파일로 넘어가지 말고** 그 행·메시지를 알려 주세요.

- R1S-00 실행 전 결과에 `FAIL`
- R1S-01/02 가 `ERROR` 로 끝남, 또는 마지막 결과에 `ok` 가 아닌 행
- R1S-03 에 `FAIL`
- R1S-00 실행 후 구조 지문(F1~F7·G1·G2·G4)이 실행 전과 다름
- 6번 사이트 확인에서 기존 기능 하나라도 이상

R1S-01·02 가 이미 적용된 뒤 멈춰야 한다면 **되돌리는 SQL 을 즉석에서 만들지 않습니다.** 비활성 설치 상태에서는
R1 원래 판정 그대로 동작하므로(시험 II: R1 시험 244건 그대로 통과) 그대로 두고 원인을 먼저 봅니다.

## 6. 배포 확인 (R1S-04 전에)

R1S-04 의 `deployment_ref` 칸은 이 확인을 한 배포를 가리킵니다.

1. 운영 주소의 배포 커밋(7자리)을 Vercel 에서 확인 → `deployment_ref` 에 적습니다.
2. Production 환경 변수에 `SUPABASE_SERVICE_ROLE_KEY` 가 있고, Preview·Development 에는 없음을 확인합니다.
3. R1S-04 전에는 확인 API 가 `NOT_READY` 로 응답하는 것이 정상입니다(활성화 행이 없음). 이 응답이 오면 API 가
   배포되어 DB 와 연결된 것입니다. 이 날짜를 `deployment_checked_on` 에 적습니다.
4. R1S-04 직후 실제 HWPX 파일 1개를 올려 `ready` 가 되고, `.pdf` 등 다른 파일은 고르는 단계에서 막히는지 봅니다.
   이상하면 바로 `R1S-80`.

## 7. 계란님이 정할 값 (R1S-04 입력 칸)

이 SQL 은 어떤 값도 정해 두지 않았습니다. 칸이 남아 있으면 아무것도 쓰지 않고 멈춥니다.

| 칸 | 무엇 | 예 |
|---|---|---|
| `approver_user_id` | 승인한 학교 관리자(school_admin)의 회원 id(Auth UID). 대상 학교는 그 사람이 관리자인 학교 1곳 | — |
| `approval_ref` | 승인 근거 1~200자 | "2026-10-20 교무회의, 악성코드 검사 없는 HWPX 기본 확인 운영 승인" |
| `deployment_ref` | 확인 API 배포 확인값 1~200자 | "Vercel 운영 배포 abc1234, Production 키 등록 확인" |
| `deployment_checked_on` | 6절 확인을 한 날 (오늘 또는 그 이전) | 2026-10-21 |
| `policies` | `"existing"` = 이미 게시된 정책을 씀(HWPX 포함 · 미검사 불허여야 함) 또는 R1-06 과 같은 모양의 정책 3종 객체 | 지금은 게시된 정책이 없으므로 객체가 필요 |

정책 객체의 수치(파일 크기 상한, 파일 수, 확장자 목록 등)도 계란님이 정합니다. 기본 확인 경로는 그중 **HWPX 만**,
**30MiB 이하만**(프로필 기술 한도) 받습니다. 정책이 더 작으면 정책 값이 이깁니다.

## 8. 실제 환경에서 시험하지 못한 것

시험은 로컬 PostgreSQL 에 Supabase 의 역할·`auth.uid()`·Storage 표를 흉내 낸 DB 에서 했습니다(`R1S_시험결과.md`).
다음은 실제 Supabase·Vercel 에서 처음 확인하게 됩니다.

- PostgREST 로 service_role 이 부를 때 `request.jwt.claims` 를 함수 안에서 바꿔 `auth.uid()` 를 사람 UID 로 보는 방식
  (`R1S_설계결정.md` 2절). 시험 DB 의 `auth.uid()` 는 Supabase 와 같은 식이지만 실제 PostgREST 를 거치지 않았습니다.
- 실제 `is_approved`·`get_my_role` 의 기존 데이터에서의 결과
- Storage HTTP 로 실물을 내려받는 경로(PR #45 `_hwpx_basic.py`), `sb_secret_` 키로 Storage 접근
- Vercel 서버 함수의 시간 제한·환경 변수 범위
