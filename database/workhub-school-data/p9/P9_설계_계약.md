## 2. A — 기존 회원을 업무실 소속으로 연결

### 2-1. 원칙

1. **기존 회원 보존**: `public.users`·`auth.users` 는 읽기만 합니다(FOR SHARE). 회원 행을 고치거나 새 로그인 계정을 만들지 않습니다(R0 원칙 그대로). 결과 확인에서 회원표 지문이 전후 같아야 통과입니다.
2. **같은 사람만 잇기**: R0 가 정해 둔 `legacy_link_method = 'same_auth_user'` 하나만 씁니다(회원 id = Auth UID, 이번 실측에서 18명 모두 성립). 이메일·이름으로 추측해 잇지 않습니다.
3. **접근은 그대로**: 연결된 교사는 소속이 생겨도 `legacy_gate`(superadmin)에 막혀 업무실에 들어오지 못합니다. 공개 확대는 별도 승인입니다.
4. **역할은 주지 않음**: `membership_roles` 를 만들지 않습니다(관리자·일정 관리자 권한 없음).

### 2-2. 실행 경로 — 권장: SQL Editor 양식 1회 (앱 명령은 엑셀 세팅 때)

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A1 (권장)** | R0-03 처럼 계란님이 SQL Editor 에서 양식 2개 실행: P9-04 미리보기(읽기 전용) → P9-05 반영(미리보기 지문 붙여넣기) | 새 공개 API 없음(공격면 0), 앱 작업 없이 바로 가능, 17명 1회 작업에 맞음 | 화면에서 하지 못함 |
| A2 | 학교 관리 화면 "회원 연결" 명령(미리보기·확정 RPC) | 화면에서 대상 고르기 | 계정 행을 만드는 공개 함수가 생김(인증 인접), 앱 작업 필요 |

A1 과 A2 는 같은 내부 함수(`p9_link_plan` · `p9_link_apply`)를 씁니다. 나중에 엑셀 세팅(5-2)을 만들 때 A2 를 그 위에 얹습니다.

### 2-3. 미리보기 (P9-04, 읽기 전용)

입력:

| 칸 | 뜻 | 제약 |
|---|---|---|
| `approver_user_id` | 승인한 학교 관리자의 Auth UID | 지금 school_admin 인 학교가 정확히 1곳 (P1-04 와 같은 규칙) |
| `targets` | `'all_unlinked'` 또는 회원 id 배열(최대 300) | 기본값 없음 — 반드시 고름 |
| `starts_on` | 소속 시작일 | 학교 학년도 안, **오늘 이전** 이어야 바로 유효. 권장 = 2026-08-13(현재 학기 시작, 시범 수업 기간과 맞음) |
| `last_day` | 소속 마지막 날(포함) 또는 빈칸(무기한) | 빈칸 권장(소속은 학년도를 넘어 이어짐, 전출·퇴직은 P1 소속 화면에서 종료) |
| `employment_type` | `teacher` 기본, 사람별로 덮어쓰기 가능 | R0 값 `teacher`·`contract_teacher`·`lecturer`·`staff`·`other` |

출력: 사람마다 한 줄(이름·이메일은 앞 2글자만 가린 형태, 회원 id 는 그대로) + `결과 예정` + 미리보기 지문(sha256) + 만료 시각(30분).

| 결과 예정 | 조건 |
|---|---|
| `link` | 활성 회원 · Auth 계정 있음 · 업무실 계정 없음 · 이 학교 소속 없음 → 계정 + 재직 소속 생성 |
| `skip_linked` | 이미 같은 Auth UID 의 업무실 계정이 있고 이 학교 소속이 기간과 겹침(계란님 포함) — **중복 방지** |
| `membership_only` | 계정은 있는데 이 학교 소속이 없거나 지난 기간뿐 → 소속만 새로 생성 |
| `skip_inactive` | 회원 비활성 · Auth 계정 없음 · 이름 형식 벗어남 |
| `skip_role` | `teacher`·`superadmin` 밖의 역할(지금 0명) |
| `conflict` | 대기(pending) 소속 있음 · 소속 기간 겹침 등 — 반영하면 실패할 줄 |

### 2-4. 반영 (P9-05)

- 입력 = 미리보기와 같은 칸 + `preview_fingerprint` + `approval_ref`(1~200자) + `request_key`.
- 반영 시점에 같은 입력으로 다시 계산해 **지문이 같고 30분 안**일 때만 반영합니다. 그 사이 회원이 비활성화되거나 누가 먼저 연결했으면 지문이 달라져 전체 거절(일부만 반영하지 않음).
- `conflict` 가 한 줄이라도 있으면 전체 거절.
- 같은 `request_key` 재실행은 처음 결과를 그대로 돌려주고 아무것도 더 만들지 않습니다(중복 방지 2중).
- 실행 주체: 서비스 주체 `svc_member_link`. 양식이 범위 승인을 넣고 끝에 회수합니다(R0 초기 설정과 같은 방식, T61). 소속의 `decided_by_membership_id` = 승인 관리자 소속.
- 만드는 행: `accounts`(display_name = 회원 이름, email, `legacy_link_method='same_auth_user'`, `legacy_approval_state='approved'`, `legacy_link_run_id`) · `memberships`(status `active`, 기간, `employment_type`) · 이관 원장 2표(아래) · 감사 1건/사람 + 실행 요약 1건.

새 표(R0 가 F5 로 미뤄 둔 이관 원장):

```
workhub.migration_runs        id · school_id · kind('legacy_member_link') · request_key(unique) · preview_fingerprint
                              · approver_membership_id · approval_ref · input(jsonb) · counts(jsonb) · applied_at   — 고칠 수 없음
workhub.migration_run_items   run_id · legacy_user_id · outcome(link|membership_only|skip_*) · account_id · membership_id — 고칠 수 없음
```

R0 변경 2개: `accounts_legacy_run_pending` CHECK 제거 → `accounts_legacy_run_fk`(→ migration_runs) 추가. R0 J1 이 "교사 일괄 연결 배치에서 풀고 연결"이라고 예고한 그 변경입니다.

## 3. B — 관리자가 일반 교사를 수업 담당자로 배정

### 3-1. 문제

수업 담당 후보는 `p2_member_reachable` = "지금 업무실을 쓸 수 있는 사람(superadmin)"입니다(D-P5-1a). 이 함수는 협업·메시지·인계 받는 사람에도 쓰이므로 **그 함수를 넓히면 안 됩니다**(받는 사람이 넓어짐 = 사실상 공개 확대).

### 3-2. 설계 — 담당 자격 함수를 따로 둔다

```
workhub_private.p9_teacher_assignable(p_school_id text, p_membership_id text) RETURNS boolean
  = 같은 학교 · 소속 status 'active' · 오늘이 소속 기간 안 · 학교 active
    · 계정 active · legacy_approval_state 'approved'
    · public.users 활성 · role IN ('teacher','superadmin')      ← p2_member_reachable 과 다른 줄은 이것 하나
```

바꾸는 함수 4개 — 본문에서 `p2_member_reachable` 호출 한 곳씩만 `p9_teacher_assignable` 로 바꿉니다(설치 전 본문 md5 를 확인하고 다르면 멈춤, P8-04 방식):

| 함수 | 쓰임 | 현재 판 |
|---|---|---|
| `p5_catalog` | 관리자 화면 `approvedTeachers` | P8-04 가 바꾼 판 |
| `p5_course_create` | 수업 만들 때 담당 확인 | P5-02 원본 |
| `p8_rel_snapshot` | 담당 교체 후보 목록 | P8-04 |
| `p8_rel_eval` | 담당 교체 확정 확인 | P8-04 |

**바꾸지 않는 것**: `p2_member_reachable`, `legacy_gate`, `member_actor`, 메뉴, T1 교사 판정(이미 역할을 보지 않음).

### 3-3. 알아 둘 점

- 담당으로 배정된 일반 교사는 **업무실에 들어오지 못하므로** 자기 수업의 관찰·평가 기록, 명부 업로드(담당 교사로서)를 할 수 없습니다. 지금은 관리자가 수업·명부·시간표를 세팅하는 용도입니다.
- 이 점이 **T2 결정과 겹칩니다**: D-T2 "실시 기록 작성 = 담당 교사 본인만"을 택하면, 공개 범위를 넓히기 전까지 일반 교사 담당 수업의 실시 기록은 아무도 못 씁니다. 교환 승인 "최소 두 명의 승인 담당자"도 superadmin 이 1명뿐이면 준비 조건을 못 채웁니다. (T2 스레드에 전달할 내용)
- 공개 범위를 나중에 넓히면 이미 배정된 교사는 그날부터 자기 수업을 봅니다 — 의도한 동작입니다.
- 설치하는 순간 효력이 있지만(모듈 없음), A 를 하기 전에는 후보가 그대로 1명이라 화면 변화가 없습니다. 순서: A → B 를 권장.

## 4. C — 수업·학생 정정, 수업 취소·보관

### 4-1. 원칙

- 지금 P5 행은 모두 고칠 수 없게 잠겨 있습니다(`courses_identity` · `students_immutable` · `student_enrollments_immutable` 등). **행을 지우지 않습니다.**
- 정정은 "**제자리 정정 + 이전 값 이력**": 같은 ID 를 유지하므로 관찰·평가·활동·시간표 연결·P4 근거가 그대로 따라옵니다. 이전 값은 정정 이력 표에 판마다 남습니다.
- 수업 학기·교과는 고치지 않습니다(학년도 FK·시간표 학기와 묶임) → 잘못 만들었으면 **취소하고 새로 만들기**.
- 관계 종료는 이미 있는 P8 종료 사건(`teaching_relation_ends`, "시작 전 취소" = `last_day` NULL)을 그대로 씁니다 → T1 · P5 가 이미 이 규칙으로 실효 기간을 계산하므로 고칠 곳이 적습니다.
- 모든 명령은 학교 관리자(`p5_manager`)만, **미리보기(영향 건수) → 확정**(10분, 지문 대조, 한 번만 사용) — P8-04 와 같은 틀.

### 4-2. 명령 목록

| 명령 | 입력 | 허용 조건 | 결과 |
|---|---|---|---|
| `course_correct` | courseId · expectedVersion · label? · validFrom? · validThrough? · reason | 이름 1~120자. 새 기간은 학기 안이고 **담당·수강·기록 날짜를 모두 덮어야 함**(줄여서 기존 관계를 잘라내지 않음 — 그건 P8 종료로). 공개된 시간표 수업(T2)이 있으면 기간 변경 거절 | `courses` 제자리 갱신, version+1, `course_revisions` 에 이전 값 |
| `course_cancel` | courseId · expectedVersion · reason | **내용 0건**: 관찰·상담·평가·평가기준·활동 원문 없음, T2 공개 수업 없음 | 상태 `cancelled`(되돌릴 수 없음). 모든 담당·수강에 P8 "시작 전 취소" 사건. 목록 기본 보기에서 숨김("취소된 수업" 필터), 시간표 준비에서 빠짐 |
| `course_archive` | courseId · expectedVersion · reason | 내용이 있어도 됨. **오늘 이후 예정된 T2 공개 수업이 없을 것**(있으면 먼저 학사 변경으로 정리) | 상태 `archived`. 새 쓰기(기록·명부·평가기준·활동) 거절, 기존 기록 열람은 지금 규칙 그대로(쓴 교사 본인). 목록 기본 보기에서 숨김 |
| `course_restore` | courseId · expectedVersion · reason | `archived` 만 | 상태 `active` 로 |
| `student_correct` | studentId · expectedVersion · name? · schoolStudentKey? · reason | 학생번호는 학교 안 중복 불가(→ CONFLICT) | `students` 제자리, `student_revisions` 에 이전 값 |
| `enrollment_correct` | enrollmentId · expectedVersion · grade? · classLabel? · seatNumber? · reason | 학년 ≤ 학교 학년 수, 같은 학년·반·번호 중복 불가 | `student_enrollments` 제자리, `enrollment_revisions` |
| `student_void` | studentId · expectedVersion · reason | **그 학생 기록 0건**(관찰·상담·평가·활동 채택) | 상태 `voided`(되돌릴 수 없음). 학적·모든 수강에 P8 "시작 전 취소". 명부·시간표 학생 수에서 빠짐. 같은 학생번호로 다시 올리면 CONFLICT(새 번호를 쓰거나 정정) |

판(version): 수업·학생은 기존 `version` 칸을 올립니다. 학적은 판 칸이 없어 `1 + 정정 이력 수`로 계산합니다.

### 4-3. 기존 연결·이력이 어떻게 남는가

| 연결 | 정정 | 취소 | 보관 |
|---|---|---|---|
| 관찰·상담·평가 | 같은 ID 라 그대로 | 내용이 있으면 취소 불가 | 그대로, 열람 가능, 새로 쓰기 불가 |
| P4 문서 근거 | 그대로(이름은 현재 값으로 보임) | 해당 없음 | 기존 근거 확인은 그대로 통과 |
| 시간표 연결(T1) | 다음 준비 자료에 새 이름. 이미 만든 기준판·편성 초안·공개 수업은 **만들 때 이름 그대로**(이력) | 준비 자료에서 빠짐 → 원본 지문이 바뀌어 기준판을 다시 확정해야 함 | 준비 자료에서 빠짐 |
| 공개된 시간표(T2) | 공개 수업 이름은 다시 공개할 때 바뀜 | 공개 수업 있으면 거절 | 앞으로 예정 수업 있으면 거절 |
| 감사 | 명령마다 1건(이전·이후 판, 사유). 학생 이름 원문은 감사에 넣지 않음 | 같음 | 같음 |

### 4-4. 새 표 · 바꾸는 것

새 표(모두 고칠 수 없음, RLS 켜고 API 직접 접근 0): `course_revisions` · `student_revisions` · `enrollment_revisions`(이전 값 + 판 + 사유 + 요청 번호) · `teaching_lifecycle_events`(kind course|student, state, 사유) · `teaching_fix_previews`(10분) · `teaching_fix_commits`(확정 원장).

공개 함수 2개(authenticated, 모듈 `teaching_corrections` 이 켜져 있을 때만): `workhub_teaching_fix_preview(p_member_id, p_intent)` · `workhub_teaching_fix_commit(p_member_id, p_command, p_request_key)`.

바꾸는 기존 객체(설치 전 본문·정의 해시 확인, 다르면 멈춤):

## 5. 시범 자료 정리와 엑셀 세팅으로 가는 길

### 5-1. 시범 자료(10-20) 정리 — 권장: 지우지 않고 취소

| 대상 | 방법 | 결과 |
|---|---|---|
| 시범 수업 9개 | `course_cancel` ×9 (기록 0건이라 가능) | 목록·시간표 준비에서 사라짐, 행과 감사는 남음 |
| 가명 학생 15명(`SIM-`) | `student_void` ×15 | 명부·학생 수에서 사라짐, 학생번호 `SIM-…` 는 다시 못 씀(실제 번호와 겹치지 않음) |
| 학급 3 · 교과 3 | 실제 학급·교과로 그대로 쓰거나, 학교 구성에서 빼기(`removed_at`) | |

### 5-2. 최종 목표(엑셀로 학교 세팅)와의 관계

엑셀 세팅은 이 문서 범위가 아니지만, 위 명령을 그 재료로 쓰도록 맞췄습니다.

- 엑셀 한 파일(교사 · 교과 · 학급 · 수업 · 명부 시트) → 서버 미리보기가 줄마다 `생성 / 같음 / 정정 / 충돌`을 계산 → 한 번에 확정(전부 아니면 전부).
- 교사 시트는 A 의 `p9_link_plan`(이메일 → 회원 id 는 서버가 대조, 추측 없음), 정정은 C 의 정정 명령, 빠진 수업은 취소·보관 제안으로 이어집니다.
- 그래서 C 의 명령은 한 건씩이지만 내부 함수는 "의도 목록"을 받게 만들고, 미리보기 지문 규칙을 엑셀 세팅에서도 그대로 씁니다.

## 7. 앱 계약 (Codex 용)

계약 이름 `teaching-corrections.v1`. 오류 코드는 P5 와 같은 집합(`FORBIDDEN` · `NOT_FOUND` · `INVALID_INPUT` · `CONFLICT` · `UNAVAILABLE` · `NOT_READY`)을 쓰고, `CONFLICT` 에 이유 코드를 붙입니다.

```ts
type FixIntent =
  | { kind:'course_correct'; courseId:string; expectedVersion:number; label?:string; validFrom?:string; validThrough?:string; reason:string }
  | { kind:'course_cancel' | 'course_archive' | 'course_restore'; courseId:string; expectedVersion:number; reason:string }
  | { kind:'student_correct'; studentId:string; expectedVersion:number; name?:string; schoolStudentKey?:string; reason:string }
  | { kind:'enrollment_correct'; enrollmentId:string; expectedVersion:number; grade?:number; classLabel?:string; seatNumber?:number; reason:string }
  | { kind:'student_void'; studentId:string; expectedVersion:number; reason:string }
// 바꿀 칸이 하나도 없으면 INVALID_INPUT. reason 1~2000자. 날짜 YYYY-MM-DD, validThrough 는 포함 마지막 날.

type FixPreview = { previewId:string; fingerprint:string /* sha256 hex */; expiresAt:string;
  intent:FixIntent; allowed:boolean; blockers:ConflictReason[];
  impact:{ assignments:number; courseMemberships:number; enrollments:number; records:number; timetableLinks:number; publishedLessons:number } }
type ConflictReason = 'HAS_CONTENT'|'IN_PUBLISHED_TIMETABLE'|'FUTURE_LESSONS'|'PERIOD_CUTS_RELATIONS'|'KEY_TAKEN'|'SEAT_TAKEN'|'ALREADY_CLOSED'|'VERSION_CHANGED'
type FixCommand = { previewId:string; fingerprint:string; intent:FixIntent }
type FixReceipt = { requestKey:string; kind:FixIntent['kind']; entityId:string; version:number; appliedAt:string }
// 같은 requestKey 재전송 = 처음 접수증. 미리보기 만료·이미 사용·지문 다름 = CONFLICT('VERSION_CHANGED').
```

DTO 추가 칸: 수업 `state:'active'|'archived'|'cancelled'`, 학생 `state:'active'|'voided'`. 이전 앱은 모르는 칸을 무시하는지 Codex 확인 필요(엄격 파서면 판 올림).

화면(관리자만, 메뉴는 그대로 superadmin): 수업 상세의 "정정 · 보관 · 취소", 명부 줄의 "정정 · 등록 취소", 목록의 "보관 · 취소된 수업 보기" 필터. 모두 미리보기의 영향 건수를 보여 준 뒤 확정.
