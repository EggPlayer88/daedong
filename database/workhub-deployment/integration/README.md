# 전체 구축 SQL 통합 검증 — INT-05

이 폴더는 실제 Supabase에 연결하지 않고, 새 임시 PostgreSQL 17 하나에 기존 R0~T2 기반과 미적용 구축 증분을 순서대로 올려 검증한다. 운영 DB 적용, 기존 회원 연결, 실제 공급자 호출, 기능 공개는 수행하지 않는다.

## 범위와 순서

기존 설치 기반은 기존 시험의 원본 파일과 합성 Supabase 구조를 사용한다. R0 뒤 39개 단계(기존 기반 + 아래 증분)를 같은 `int05_stages` DB에 순차 설치한다. 각 단계 직후 새 `INT-05_전체구축_통합점검.sql` 18행이 현재 설치 기록과 구조에 맞는지 확인한다.

미적용 설치는 아래 15파일이다. 활성화·정책 승인·회원 연결 양식은 자동 설치 목록에 넣지 않는다.

1. 학교 자료 P9-01·02
2. 학교 자료 P10-01·02
3. 시간표 운영 T3-01·02·03
4. 시간표 일괄 가져오기 T4-01
5. 학교 AI P10-01·02·03·09·10
6. 과거 학교 원문 K1-01
7. 개인 AI 기억 M1-01

학교 자료 `P10-xx`와 학교 AI의 설치 기록 `P10-AI-xx`는 별도 단계다. 승인 양식 없이 설치해도 달라지는 기존 동작이 있다. 학교 AI 설치는 옛 AI 직접 준비·시작 권한을 차단하고 새 게이트로 옮긴다. T4는 기존 시간표 동작을 보강한다. 따라서 “비활성 설치이므로 모든 기존 동작이 동일하다”고 판단하지 않는다. 실제 설치 전에는 배포 문서의 단계별 설치 영향을 함께 확인한다.

## INT-05가 확인하는 것

- 기존 단계별 함수 본문·인자·반환형·소유자·실효 실행 권한·`search_path`
- 제약, 보호 트리거의 정의와 켜짐, Storage·표 정책
- 업무실 3개 스키마의 표/RLS/소유자/실효 API 권한
- 열 형식·필수값·기본값·생성/identity 여부·실효 열 권한, 인덱스와 열거형
- 모든 알려진 설치 단계의 의존과 부분 설치 상태
- K1은 설치 기록 표가 없으므로 정확한 두 공개 함수의 존재로 단계 판정

이 파일은 SELECT 기반 읽기 전용 점검이다. 정상 결과는 18행이며 `FAIL`이 없어야 한다. 실제 읽기 전용 트랜잭션에서도 실행한다. 운영 설치 기록과 구조가 시험 모델과 다르면 실패를 무시하지 않고 차이를 확인한다. 이전 INT-04, T2-07 등 이미 적용된 원문과 생성기는 변경하지 않는다.

## 재현

PostgreSQL 17, Python(`psycopg2`), Node 및 저장소 의존성을 준비한다. 공통 실행기가 단계별 추가 회귀까지 묶는다.

```sh
npm run test:workhub:deployment
```

통합 적재만 직접 실행할 때:

```sh
export WORKHUB_DEPLOYMENT_PG_BIN=/path/to/postgresql17/bin
export WORKHUB_DEPLOYMENT_REPORT=/tmp/workhub-deployment-integration
python3 database/workhub-deployment/integration/test/run_integrated.py
```

Windows PowerShell에서는 같은 환경값을 `$env:변수명`으로 설정하고 `python`을 쓴다. 기본 시험 포트는 55609이며 `WORKHUB_DEPLOYMENT_TEST_PORT`로 49152~65535 사이 미사용 포트를 지정한다. 주소는 항상 `127.0.0.1`이고 새 임시 폴더만 사용한다. 운영 DSN과 외부 연결/키 환경변수, 비어 있지 않은 모든 `PG*` 환경변수(대소문자 무시), 임의 실행 인자를 받지 않는다. 종료 시 시험 서버를 멈추고 임시 파일 위치를 출력한다.

일반 실행은 원본 SQL로 다시 만든 예상 목록과 저장된 INT-05 원문을 대조한다. 차이가 있으면 자동으로 덮어쓰지 않고 실패한다. SQL 변경 후 검토용 재생성이 필요할 때만 직접 실행에 `WORKHUB_WRITE_INT05=1`을 명시한다. 이 생성 모드는 CI 일반 실행에서 사용하지 않는다.

```sh
python3 database/workhub-deployment/integration/test/test_runner_safety.py
```

안전 회귀는 통합 실행기를 시작할 때에도 먼저 수행한다. 위 명령은 DB를 만들지 않고 외부 DSN·libpq 옵션·키 환경변수와 임의 인자를 사전 거부하는지 검사한다.

## 결과물과 판정 한계

- `summary.json`: SQL 통합 회귀 수, 단계 수, 실제 앱 응답 대조 수, 운영 적용 없음
- `stage-results.json`: 각 설치 단계의 INT-05 18행
- `integrated-app-captures.json`, `integrated-app.log`: 같은 DB에서 받은 K1·M1·학교 AI 상태 응답의 현재 앱 parser 대조
- 공통 실행기의 단계별 로그: 각 모듈의 별도 세부 회귀

회원·소속·제출·Storage 목록의 전후 해시를 비교한다. 기존 P1·P5·T1·P6 활성화와 이전에 시작된 P6 요청을 합성 자료로 만들고, 설치가 그 값을 보존하는지 및 원번호로 끝낼 수 있는지 검증한다. 설치 확인 후 별도 합성 승인을 거쳐 K1 원문과 M1 기억 CRUD·복구·닫기를 실행하며, 이 시험 승인을 실제 활성화로 세지 않는다.

Storage 파일 본문, 실제 Supabase 확장/소유권 설정, PostgREST 네트워크 왕복, Vercel 서버 변수, 실제 API 키와 비용은 이 시험으로 확인되지 않는다. 운영 적용 가능 판정과 실제 활성화 승인은 별개이며 이번 작업에서는 모두 보류한다.
