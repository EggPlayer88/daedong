# 전체 구축 통합 SQL 시험 결과

2026-10-21 · 격리 PostgreSQL 17.6 · 실제 운영 접속/SQL 적용/회원 연결/AI 공급자 호출 없음

| 확인 범위 | 결과 |
| --- | ---: |
| 한 임시 DB에서 전체 단계 설치·보존·훼손·RPC 검증 | **116 통과 / 0 실패** |
| 사전 접속 차단 회귀 | **7 통과 / 0 실패** |
| INT-05 단계 대조 | R0 기준선 + 뒤의 **39단계**, 매번 **18행 FAIL 0** |
| 현재 앱 parser에 실제 RPC 응답 대조 | **25건**: 정상 18, 예상 업무 거절 7 |
| 최종 동시 설치 상태의 각 모듈 국소 사후점검 | **8개 점검 파일 FAIL 0** |
| 보안·구조 훼손 후 탐지 및 원복 | **13종** 모두 탐지, 복구 후 FAIL 0 |
| INT-05 원본 SQL 재생성 결과 | 저장 파일과 일치 — 자동 덮어쓰기 없음 |
| INT-05 실제 읽기 전용 트랜잭션 실행 | 통과 |

위 116건은 통합 실행기의 명시적인 판정 수다. 설치 단계의 18행이나 앱 대조 25건을 116건에 다시 더하지 않는다. 공통 실행기가 별도로 돌리는 모듈별 상세 회귀 숫자는 해당 로그와 전체 배포 검증 보고서에 따로 기록한다.

## 확인한 내용

- 학교 자료 P9/P10, 시간표 T3/T4, 학교 AI P10 전체(01·02·03·09·10), K1, M1을 기존 기반 위에 실제 의존 순서대로 설치했다. 학교 자료와 AI의 P10 설치 기록이 서로 섞이지 않았다.
- 기존 auth/public 회원, 업무실 계정/소속/역할, 평가계획 제출, Storage 객체 목록의 내용 해시와 행 수가 설치 전후 같았다.
- 합성으로 미리 활성화한 P1·P5·T1·P6 상태는 그대로였고, 새 학교 정책·API 자격증명·기존 회원 연결·기억 승인 자료는 자동으로 생성되지 않았다.
- 설치 전에 시작한 P6 요청은 원문/예약을 보존한 채 새 AI 원장에 한 번만 이관됐다. 모든 증분 설치 뒤에도 원래 요청 번호로 종료하고 두 원장을 정산할 수 있었다. 옛 직접 준비/시작 권한 차단은 예정된 설치 영향으로 검증했다.
- K1 과거 규정 원문·이력과 M1 생성/수정/선택/삭제/복구/닫기가 같은 DB에서 동작했다. 기억·학교 자료 작업이 학교 AI 정책이나 API 키를 자동으로 켜지 않았다.
- RLS, 직접 표·열 권한, 익명 실행, 스키마 권한, 보호 트리거, 함수 소유자·본문·오버로드·누락, 추가 열·기본값·인덱스를 훼손하면 새 INT-05가 실패했다.
- 외부 DSN, 임의 인자, 비어있지 않은 모든 `PG*` 환경변수(대소문자 무시), API 자격증명이 있으면 DB 생성 전에 멈춘다. `PGHOSTADDR`가 명시한 `host`보다 우선하는 libpq 동작도 사전 거부 범위에 넣었다. 거부 문구에는 비밀 값을 출력하지 않는다.

## 재현과 산출물

공통 실행: `npm run test:workhub:deployment`. 통합만은 `--integration-only`를 붙인다. 자세한 환경값과 직접 실행 명령은 상위 README에 있다. 사전 안전 회귀는 통합 실행기 시작 시 자동 실행한다.

결과 디렉터리의 `summary.json`, `stage-results.json`, `integrated-app-captures.json`, `integrated-app.log`가 기계 판정 근거다. 최초 생성 후 일반 재실행으로 고정 원문 일치를 확인했다.

## 남은 경계

실제 Supabase/PostgREST/Storage 파일 본문/Vercel/Claude API는 시험하지 않았다. 합성 Supabase와 원본 설치 파일을 사용하는 구축 회귀이며, 운영 자료나 권한 상태를 읽었다는 뜻이 아니다. 새 SQL의 비활성 설치도 옛 AI 실행 경로 등 일부 기존 동작을 바꾸므로 앱 배포 순서와 단계별 영향 확인이 필요하다. 실제 SQL 적용·회원 연결·기능 활성화와 최종 검토는 사용자 요청대로 계속 보류한다.
