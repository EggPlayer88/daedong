## 즉시 진행 가능 — Phase 4C (셀 단위 편집)

### Phase 4C-1: 드래프트 편집 페이지 + 단일 셀 편집

**목표**: 드래프트 시간표를 셀별로 수정 가능한 UI

**작업 범위**:
- `TimetableEditPage.jsx` (또는 TimetablesListPage 의 미리보기 모드 확장)
- 드래프트 시간표만 편집 가능 (활성/이전은 읽기 전용)
- 셀 클릭 → 편집 폼 (교사/과목 변경)
- 변경사항 미리보기 → "저장" 버튼
- 저장 시 `timetables.data` 업데이트 + `edit_log` 에 기록

**결정 사항** (DECISIONS.md 의 Phase 4C 결정 4, 5, 6, 7 따름):
- 드래프트만 편집 (활성은 임시 변경 시스템으로)
- 단일 셀 편집 + swap 둘 다 (4C-2 에서 swap)
- 확실한 충돌만 강제 차단 (4C-2 에서)
- edit_log 누적 (4C-3 에서)

**검증 시나리오**:
1. 시간표 목록 → 드래프트 클릭 → 미리보기 (4B-2)
2. "편집 시작" 버튼 추가 → 편집 모드 진입
3. 셀 클릭 → 교사/과목 변경 폼
4. 저장 → 시간표 업데이트 확인

### Phase 4C-2: Swap 편집 + 충돌 강제 차단

**목표**: 두 셀 swap + 동시간 교사 중복 차단

**작업 범위**:
- 편집 모드에서 "swap" 액션 추가
- 첫 셀 선택 → "다른 셀 선택" 모드
- 두 번째 셀 선택 시 swap 실행
- 충돌 검증: 한 교사 동시간 두 학급 → 강제 차단 (에러 표시)
- 시수 불일치는 경고만 표시 (저장 가능)

### Phase 4C-3: edit_log 누적 + 변경 이력 표시

**목표**: 모든 편집을 추적 가능하게

**작업 범위**:
- `edit_log` JSONB 에 각 편집을 누적 기록
- 편집 이력 보기 화면 추가 (목록 페이지에서 진입)
- 형식 예:
  ```json
  {
    "events": [
      {
        "ts": "2026-05-12T10:30:00Z",
        "user": "admin",
        "type": "cell_edit",
        "before": { "tid": "t1" },
        "after": { "tid": "t2" },
        "location": { "class": "c1", "day": "월", "period": 3 }
      },
      ...
    ]
  }
  ```

## Phase 5 — 임시교사 시스템

**목표**: 학기 시작 시 회원가입 안 한 신규 교사를 위한 자리 만들기

**왜 필요한가**:
- 학교 운영 흐름: 학기 시작 직전 신규 교사 발령
- 시간표는 발령 받기 전에 미리 짜야 함
- 그래서 "진짜 교사" 없이 시간표 짜고, 나중에 매핑

**작업 범위**:
- `teachers.is_placeholder` 컬럼 추가 (SQL)
- 임시교사 등록 페이지 (관리자) — 이름, 담당 과목만 입력
- 임시교사도 시간표에 배치 가능 (TCH 상수 → DB 로 옮기는 작업과 함께)
- 신규 회원가입자 → 임시교사 매핑 화면
- 매핑 시 시간표 데이터 자동 인계 (같은 ID 만 변경하면 됨)

**결정 필요**:
- `TCH` 상수를 DB 로 옮길지, 임시교사만 DB 에 넣을지
- 매핑 UI 의 형태 (드래그앤드롭, 또는 셀렉트 박스)

## Phase 6 — 인증 통합

**목표**: 페르소나 셀렉터를 진짜 인증으로 교체

**왜 필요한가**:
- 시뮬레이션 셀렉터로는 진짜 운영 불가
- 보안: 본인만 본인 시간표 / 변동 요청 수정 가능해야

**작업 범위**:
- 003 마이그레이션 역방향: UUID 컬럼 복원
- 페르소나 셀렉터 제거
- `currentUser` 가 실제 로그인 사용자 (`teachers` 테이블 row)
- RLS 정책 작성:
  - 일반 교사: 본인 데이터만 read/write
  - 시간표관리자: 모든 시간표 read, 본인 외 변동 승인 가능
  - 슈퍼관리자: 전체 권한
- 'admin' fallback 제거 (`changesAPI.notifyAdmins` 등)

**난이도**: 상. 기존 인증 시스템 (이전 채팅 작업) 과 통합 필요.

## Phase 7 — 영구 변경 시스템

**목표**: 학기 중간 영구 변경 (단순 임시 변경이 아닌 시간표 자체 변경)

**왜 필요한가**:
- 학기 중 교사 휴직, 신규 발령 → 영구 변경 필요
- 임시 변경 (`timetable_changes`) 은 일회성
- 영구 변경 = 새 timetables row 생성 + 활성화

**작업 범위**:
- 영구 변경 등록 UI (관리자 모드)
- 임시 변경과의 충돌 검토:
  - "이미 다음 주 화요일에 임시 변경이 잡혀있는데, 새 활성 시간표는 어떻게?"
  - 사용자에게 검토 화면 보여주고 결정
- 롤백 기능: active → rolled_back, 이전 active 복원
- 시간 여행: 날짜 입력 → 그 시점에 active 였던 시간표 표시

**Phase 4C 의 edit_log 가 기반**.

## Phase 8 — AI 재설계

**목표**: 시범운영 피드백 반영한 AI 정교화

**왜 보류**:
- 어떤 AI 가 진짜 도움 되는지 모름 (시범운영 전)
- 만들기 쉬워서 함정에 빠지기 쉬움

**시범운영 후 정리할 것**:
- 지금까지 만든 AI 기능 중 안 쓰이는 것 → 제거
- 자주 쓰이는 것 → 정교화
- 새로 필요한 기능 추가

**보류된 후보들**:
- (a) 보강 부담 자동 모니터링 — 매주 자동 알림
- (b) 변동 다건 영향 분석 — 일괄 승인 전 미리보기
- (c) 안내문 일괄 생성 — 주간 종합 안내문
- 자연어 변동 요청 — "수요일 3교시 자습으로 바꿔줘"
- 시간표 솔버 + AI 통합 — 제약 조건 자연어 입력
