## Phase 4C (셀 단위 편집)

### Phase 4C-1: 드래프트 편집 페이지 + 카드 바구니 방식 — ✅ 완료

**목표**: 드래프트 시간표를 카드 바구니 메탈 모델로 편집

**구현된 범위**:
- `TimetableEditPage.jsx` 신규 페이지 (드래프트 카드의 "✏️ 편집" 버튼으로 진입)
- 드래프트 시간표만 편집 가능 (활성/이전은 읽기 전용 유지)
- 메탈 모델: 시간표 = 서랍, 학급-과목-교사 묶음 = 카드
- 셀 클릭 라우터 (5가지):
  * 점유된 셀 + 카드 미선택 → 카드를 바구니로 빼냄
  * 빈 셀 + 카드 선택 → 그 자리에 배치
  * 점유된 셀 + 카드 선택 → 자동 교환 (기존 카드가 바구니로 이동)
  * 빈 셀 + 카드 미선택 → "+ 새 카드 추가" 메뉴 → NewCardModal
  * 특별활동(창체) → 클릭 차단
- 바구니 카드 우상단 ✕ 로 카드 삭제 (confirm 필요)
- 카드 선택 시 그 교사가 동시간 다른 학급에 배정된 셀은 빨간색 + 클릭 차단 (사전 차단)
- 시수 편차는 경고만 (강제 차단 X)
- 저장 시 바구니가 비어있어야 가능 + `data` + `edit_log.events` 동시 업데이트
- 이탈 보호 (변경 사항 또는 바구니에 카드 남았으면 confirm)

**결정 근거** (DECISIONS.md):
- 결정 4 (드래프트만 편집)
- 결정 5 (단일 셀 편집 + swap) — 결정 8 로 갱신
- 결정 6 (확실한 충돌만 강제 차단) — 사전 차단으로 격상
- 결정 7 (edit_log 누적) — 이벤트 기록 시작
- 결정 8 (카드 바구니 방식)

### Phase 4C-3: edit_log 이력 표시 UI — ✅ 완료

**구현된 범위**:
- `TimetableHistoryPage.jsx` 신규 페이지 (목록 페이지의 "📜 이력" 버튼으로 진입)
- 활성/드래프트/이전 시간표 모두 이력 조회 가능 (읽기 전용)
- `edit_log.events` 를 시간 역순으로 나열 — 누가, 언제, 어디서, 무엇을 어떻게 바꿨는지
- 이벤트 타입별 표시:
  * `cell_edit` (before=null) — "➕ 추가 | 1-1반 월3교시 | (비어있음) → 국어 / 김국어T2"
  * `cell_edit` (before=있음) — "✏️ 변경 | 1-1반 월3교시 | 국어/김국어T2 → 수학/박수학T1"
  * `cell_clear` — "➖ 비우기 | 1-1반 월3교시 | 국어/김국어T2 → (비어있음)"
  * `swap` (통합) — "🔄 교환 | 1-1반 월3교시 | 국어/김국어T2 ⇄ 수학/박수학T1"
- 같은 ts + 같은 location 의 cell_clear → cell_edit 페어는 자동 swap 으로 통합
- 날짜가 바뀌면 날짜 헤더 구분선 표시 (사용자 로컬 타임존)
- events 가 비어있으면 "이력 없음" 안내 카드 (4C-1 이전 시간표 또는 미편집 드래프트)
- 이력은 읽기 전용. 롤백/되돌리기는 Phase 7 (영구 변경 시스템) 에서

**후속 보강 메모**:
- events 100건 넘으면 페이지네이션/가상화 필요 (시범운영 후 보강)
- ev.user 는 페르소나 ID 문자열 (예: 'admin', 't2') — Phase 6 인증 통합 후 실제 사용자명으로 갱신 (코드에 TODO 표기됨)

## Phase 5 — 임시교사 시스템

**목표**: 학기 시작 시 회원가입 안 한 신규 교사를 위한 자리 만들기

**왜 필요한가**:
- 학교 운영 흐름: 학기 시작 직전 신규 교사 발령
- 시간표는 발령 받기 전에 미리 짜야 함
- 그래서 "진짜 교사" 없이 시간표 짜고, 나중에 매핑

**작업 범위**:
- `teachers.is_placeholder` 컬럼 추가 (SQL)
- 임시교사 등록 페이지 (관리자) — 이름, 담당 과목만 입력
- 임시교사도 시간표에 배치 가능 (TCH 상수 → DB 로 옮기는 작업과 함께)
- 신규 회원가입자 → 임시교사 매핑 화면
- 매핑 시 시간표 데이터 자동 인계 (같은 ID 만 변경하면 됨)

**결정 필요**:
- `TCH` 상수를 DB 로 옮길지, 임시교사만 DB 에 넣을지
- 매핑 UI 의 형태 (드래그앤드롭, 또는 셀렉트 박스)

## Phase 6 — 인증 통합

**목표**: 페르소나 셀렉터를 진짜 인증으로 교체

**왜 필요한가**:
- 시뮬레이션 셀렉터로는 진짜 운영 불가
- 보안: 본인만 본인 시간표 / 변동 요청 수정 가능해야

**작업 범위**:
- 003 마이그레이션 역방향: UUID 컬럼 복원
- 페르소나 셀렉터 제거
- `currentUser` 가 실제 로그인 사용자 (`teachers` 테이블 row)
- RLS 정책 작성:
  - 일반 교사: 본인 데이터만 read/write
  - 시간표관리자: 모든 시간표 read, 본인 외 변동 승인 가능
  - 슈퍼관리자: 전체 권한
- 'admin' fallback 제거 (`changesAPI.notifyAdmins` 등)

**난이도**: 상. 기존 인증 시스템 (이전 채팅 작업) 과 통합 필요.

## Phase 7 — 영구 변경 시스템

**목표**: 학기 중간 영구 변경 (단순 임시 변경이 아닌 시간표 자체 변경)

**왜 필요한가**:
- 학기 중 교사 휴직, 신규 발령 → 영구 변경 필요
- 임시 변경 (`timetable_changes`) 은 일회성
- 영구 변경 = 새 timetables row 생성 + 활성화

**작업 범위**:
- 영구 변경 등록 UI (관리자 모드)
- 임시 변경과의 충돌 검토:
  - "이미 다음 주 화요일에 임시 변경이 잡혀있는데, 새 활성 시간표는 어떻게?"
  - 사용자에게 검토 화면 보여주고 결정
- 롤백 기능: active → rolled_back, 이전 active 복원
- 시간 여행: 날짜 입력 → 그 시점에 active 였던 시간표 표시

**Phase 4C 의 edit_log 가 기반**.
