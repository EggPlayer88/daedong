# 8차 개발 — 수합과 학생 기록의 작성·확인

작성일: 2026-10-13 · 기준: 7차 수합 진행표·학생 기록 찾기(PR #14)

## 작업의 목적과 범위

7차까지 구현한 조회·검색에서 실제 입력과 저장 확인으로 흐름을 잇는다. 이번 작업은 교사가 누구에게 무엇을 요청하는지, 어떤 학생의 어느 활동을 기록하는지 확인하고 빠진 내용을 수정할 수 있도록 하는 화면 개선이다.

DB 구축과 시간표는 계속 보류한다. 기존 로그인·회원·학교 권한·store 계약·SQL·문서 엔진·AI 공급자와 비용 설정은 변경하지 않는다. 수합·학생 화면은 합성 자료 미리보기에만 적용하며 운영 메뉴 공개 범위를 넓히지 않는다. 사이트 AI는 Claude 전제를 유지한다.

## 수합 요청 작성과 응답

수합을 만들 때 안내·기한·검토 방식, 응답 문항, 제출 단위와 역할을 구분해서 확인한다. 작성 중 요청 미리보기와 저장된 비공개 초안의 점검을 통해 문항·필수 여부·책임자·검토자를 살핀다. 초안 저장과 게시, 응답 초안 저장과 최종 제출은 각각 별개의 행동이다.

화면의 점검은 입력을 돕는 안내다. 게시 시점의 소속·기한·상태와 책임자·검토 권한, 최종 제출의 버전 충돌·필수 응답 검사는 기존 store가 판단한다. 안내가 완료됐다는 이유로 그 검사를 생략하지 않는다.

교사는 다음을 확인할 수 있어야 한다.

1. 요청의 제목·안내·마감·응답 문항이 받는 사람에게 어떻게 보이는가.
2. 몇 부를 받을 예정이며 각 단위의 최종 제출 책임자와 공동 작성자는 누구인가.
3. 검토가 필요한 경우 누가 검토하고 어떤 단계에서 완료가 되는가.
4. 아직 저장하지 않은 입력, 저장된 비공개 초안, 게시된 요청 중 현재 어느 상태인가.
5. 응답의 필수 글·숫자·재제출 사유 중 무엇을 더 입력해야 하는가.

숫자 0은 유효한 응답이고 빈 숫자는 미입력이다. 공동 작성자가 여러 명이어도 부수는 제출 단위 기준이다. 입력 안내를 위해 새 응답 규정이나 학교 정책을 도입하지 않는다.

기존 저장소의 요청당 제출 단위 100개 한도를 안내하고 100개에 도달하면 추가 버튼을 잠근다. 이는 학교 규정이 아닌 현행 구현 한도다. 숫자 칸에 `-`처럼 아직 완성되지 않은 값을 입력하면 빈 선택 응답으로 잘못 제출하지 않게 한다. 기존에 허용하는 0·음수·소수는 계속 허용한다.

동시에 원본이 수정되면 최신 원본의 제목·문항·대상을 비교해 보여 준다. 교사가 그 원본을 확인해 저장 기준판으로 선택한 뒤에도 저장 시점의 버전 충돌은 기존 저장소가 다시 확인한다. 작성한 입력을 비교 원본으로 자동 덮어쓰지 않는다.

## 학생 관찰과 수업 활동 채택

학생·승인된 수업·관찰일을 작성 맥락으로 표시한다. 이름이나 명부의 배열 순서는 저장 대상 ID를 대신하지 않는다. 작성 중 명부가 바뀌거나 대상이 사라졌을 때 다른 첫 학생으로 바꾸어 저장하지 않는다.

직접 관찰과 정정에서는 활동·직접 확인한 사실·확인 여부와 정정 사유를 점검한다. 빠진 입력을 안내하고 수정할 위치로 연결한다. 저장 성공은 저장소가 반환한 기록을 바탕으로 학생·날짜·개정판을 알려 주고 실제 저장한 기록 확인으로 연결한다. 다음 학생을 자동 선택하거나 여러 학생에게 같은 문장을 일괄 기록하지 않는다.

수업 활동의 학생 선택과 학생 연결 확정은 별개다. 확정된 학생 A와 화면에서 바꾼 미확정 학생 B가 다르면 관찰 채택을 진행하지 않는다. 교사가 실제 연결을 먼저 확인해야 한다. 원문·질문판·연결판에 대한 기존 재검토 계약도 유지한다.

읽기·저장 실패를 성공이나 0건으로 바꾸지 않는다. 입력을 보존하면서 원본을 다시 확인하고, 취소·저장 이전에 입력을 없애는 화면 이동은 기존 편집 보호를 통과한다. 단, 실제 권한 상실 때 이전 자료를 보존해 열람하는 기능으로 확대하지 않는다.

활동 작성 중 임시 조회 오류가 나면 원문·명부 화면을 제거하고 직접 입력한 내용만 현재 소속의 메모리에 보관한다. 복구 후 같은 활동에 복원하거나 보관한 입력을 명시적으로 취소한다. 브라우저 저장소에 별도로 기록하지 않으며 학교·소속 전환 시 기존 화면의 수명과 함께 폐기한다. 작성 중 원문이나 학생 연결판이 바뀌면 입력을 보관하되 이전 확인으로 채택하지 않는다.

## 교사 화면 검토 순서

합성 미리보기에서 다음 흐름을 확인한다. 실제 학교·학생 자료는 입력하지 않는다.

| 흐름 | 확인할 결과 |
|---|---|
| 수합 만들기 → 안내·문항·단위 입력 | 요청 미리보기, 책임자·검토자, 필수 입력을 알 수 있음 |
| 초안 저장 → 게시 전 확인 → 게시 | 비공개 저장과 대상 고정·게시를 구분함 |
| 공동 작성자의 초안 저장 | 입력이 보존되고 최종 제출 담당자를 알 수 있음 |
| 책임자의 필수 응답·재제출 사유 확인 → 제출 | 숫자 0, 필수 누락, 버전 충돌을 기존 계약대로 처리함 |
| 학생 선택 → 직접 관찰 저장 → 기록 확인 | 화면에서 확인한 학생·수업·날짜의 기록으로 이동함 |
| 관찰 정정 중 명부·읽기 상태 변화 | 다른 학생으로 바뀌지 않고 입력과 오류를 확인함 |
| 활동 학생 선택 변경 → 연결 확정 → 채택 | 미확정 선택으로 이전 학생에게 잘못 채택되지 않음 |
| 입력 중 메뉴·필터·학교 이동 | 저장 또는 명시적 취소 전 입력이 사라지지 않음 |

## 검증과 후속 작업

전체 자동 회귀 1,077건(신규 수합 17·학생 14 포함), TypeScript 검사와 두 앱 빌드가 통과했다. 실제 Chrome 91개(새 수합 입력 11·학생 입력 17, 기존 업무·조회·구조·검색 55, 독립 HTML 8)를 검증했다. 별도 읽기 전용 교차검토 Chrome 6개도 통과했다. 상세 실행 결과는 [누적 진행 현황](PROGRESS.md)을 따른다. 합성 화면 검증과 실제 계정·DB 연결은 구분한다.

실제 수합 파일·문서 생성, 명부 연결·원자료 수신, 서버 권한·보존 정책, Claude 지식 검색·개인 비서 연동은 후속 단계다. DB 재개 시 확정 설계와 계정 보존 절차를 거쳐 검증 환경에서 연결하고, 운영 공개 전 실제 교사 파일럿을 진행한다.
