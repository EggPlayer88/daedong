# 파일형 문서 수합 서버 연결 — 구현·검토 인계

2026-10-15 · `feat/workhub-collection-server` · PR #33 후속

## 이번 변화

실제 연결 업무실의 슈퍼관리자 메뉴에 자료 수합을 추가했다. 기존 로그인과 학교 연결을 사용하며, 수합 서버 준비 상태를 먼저 읽는다. DB 함수가 없거나 조회에 실패한 상태를 빈 목록으로 바꾸지 않는다. DB·비공개 파일 저장소·파일 검사 서비스·승인된 정책이 모두 준비돼야 등록 화면을 연다.

연결 화면은 수합 초안 생성, 양식 파일 연결, 대상 공개, 공동 초안 저장, 최종 제출, 지정 교사의 검토·보완 흐름을 서버 명령으로 실행한다. 기존 미리보기의 동기 메모리 저장소를 실제 저장소인 것처럼 재사용하지 않는다. 실제 접수증을 받은 뒤 원본을 다시 조회한다. 이번 서버 화면의 생성 양식은 교사마다 한 부를 받는 기본 파일 수합이다. 공동 단위 생성·철회/정정창 관리·전체 ZIP 등의 기존 미리보기 기능을 전부 서버 화면으로 이관한 것은 아니다.

## 연결 구조

```text
기존 로그인 / 학교 소속
   ↓ 기존 SupabaseConnection
CollectionServerPanel → 수합 서버 어댑터 → public.workhub_* RPC (Claude R1 SQL 필요)
                            ↓
                   기존 공용 Supabase Storage 인스턴스
                   준비된 비공개 경로에 신규 업로드만
                            ↓
                   별도 서버 파일 검사 작업자 (후속 구현 필요)
                            ↓
                   검증된 파일 참조 → 초안 저장 → 최종 접수
```

- SQL과 Storage 권한의 작성 요청은 [R1 SQL 요청서](32-collection-server-sql-request.md)를 따른다. 실제 Supabase에는 이번 코드 작업으로 쓴 자료가 없다.
- 공개 RPC 9개의 인자·응답·오류·판·파일 부모 계약은 `collections/contracts.ts`, `validation.ts`, `supabase-collections.ts`와 요청서에 있다.
- Storage는 기존 `@daedong/shared` 인스턴스를 사용한다. `createClient`나 로그인 경로를 추가하지 않는다. 덮어쓰기·공개 URL·브라우저 삭제를 제공하지 않는다. SDK 동작은 [Supabase 업로드 문서](https://supabase.com/docs/reference/javascript/storage-from-upload), [다운로드 문서](https://supabase.com/docs/reference/javascript/storage-from-download)를 확인했다.
- 파일은 학교·파일 ID·서버가 발급한 불투명 키에만 전송한다. 클라이언트 파일 크기/표식/SHA-256은 신고값과 전송 무결성 확인이다. 서버 검사나 악성 파일 검사 완료 증거로 쓰지 않는다.
- 내려받기는 정확한 양식/초안 판 또는 제출판의 권한을 검사하고, 실물 bytes/hash를 확인한 뒤 접근 권한을 다시 확인한다. 만료 또는 회수된 권한을 캐시로 대체하지 않는다.

## 실패와 입력 보호

서버 접수 여부가 불명확한 저장은 같은 명령·키를 현재 탭 메모리에 보관한다. 새 명령으로 바꾸거나 성공 표시 후 닫지 않는다. 기존 연결 복구 저장소에 수합 명령을 추가하여 일시적인 연결 실패 때도 재검증한 동일 소속에서만 복구한다. 새로고침 이후 복구를 제공하는 영속 저장소는 아니다.

파일 전송 응답이 끊기면 같은 예약의 현재 상태를 먼저 확인한다. `pending_verification`은 제출 가능한 파일이 아니다. 서버가 파일을 준비 완료로 확정한 뒤에만 양식/응답에 연결한다. 연결하지 않은 파일의 회수·만료는 후속 서버 계약이며 화면이 Storage 실물을 지우지 않는다.

실제 다른 계정·학교·권한으로 바뀌면 이전 자료와 늦은 응답을 버린다. 포커스·날짜 재확인 신호는 수합 목록·상세에도 전달하되 작성 중인 입력을 최신 조회 내용으로 덮어쓰지 않는다.

## 판단해서 정한 것

| 결정 | 이유 | 되돌리거나 바꿀 위치 |
|---|---|---|
| 실제 연결 전용 비동기 화면 | 기존 미리보기의 즉시 성공·메모리 권한을 서버 저장에 쓰지 않기 위해 | `CollectionServerPanel.tsx`, `ConnectedWorkspace.tsx` |
| 기존 승인·로그인 경계 재사용 | 세션을 분리하지 않고 기존 회원을 유지하기 위해 | `legacy-storage.ts`, 기존 `SupabaseConnection` 사용부 |
| 준비 상태가 불확실하면 작성 차단 | SQL만 적용하고 파일 검사가 끝난 것처럼 사용되는 것을 막기 위해 | `CollectionReadiness`, SQL 요청서 §6 |
| 서버가 발급한 경로와 신규 업로드만 | 저장된 원문 교체와 다른 자료에의 잘못된 연결을 막기 위해 | 서버 어댑터·R1 Storage 정책 |
| 같은 키로 결과 재확인 | 응답 유실 후 이중 수합/제출을 막기 위해 | `pending-requests.tsx`, 어댑터·서버 receipt |
| 일반 교사 공개 범위 유지 | 사용자 승인 없이 신규 기능을 전체 공개하지 않기 위해 | `modules.ts`는 기존 `visibility: superadmin` 유지 |

## 검토 순서와 남은 작업

1. 이번 앱 코드와 R1 요청서의 계약을 함께 검토한다. SQL 확정본은 Claude가 별도 작성한다.
2. SQL 초안의 PostgreSQL 17 시험·기존 자료 보존·실제 역할과 Storage 정책을 Codex가 대조한다.
3. 사용자 승인 뒤 현재 Supabase에 R1을 단계적으로 적용한다. R0 재실행·R0-90 되돌림은 사용하지 않는다.
4. 서버 파일 검사기·작업 실행·만료/회수 기능을 구현하고 정책을 확인한다. 이 단계가 없으면 수합은 계속 미준비로 표시해야 한다.
5. 실제 PostgREST/Storage 연결을 자동 검증하고, 기존 시범용 PR을 단계적으로 통합한다.
6. 사용자 요청대로 실사용 확인은 이후에 모은다. 일정/업무 실제 저장, 여러 교사의 파일 제출·검토·보완, 기존 평가계획서 보존·다운로드, 모바일을 포함한다.

**SQL 적용, Storage 구성, 서버 검사기 배포, 실제 교사 간 문서 수합은 아직 완료하지 않았다.** 이번 자동 검증은 합성 응답·파일과 로컬 Chromium을 이용한 앱 계약 검증이며 실제 Supabase 성공 증거가 아니다. 정확한 최종 시험 수와 PR 상태는 [누적 진행 기록](PROGRESS.md)을 따른다.
