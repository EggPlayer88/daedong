## 계란님과 Claude가 확인할 흐름

1. `npm ci` 후 `npm run dev:workhub`를 실행한다. 고정 포트 5176이 사용 중이면 서버는 다른 포트로 넘어가지 않고 중단한다.
2. 화면에 표시된 **가상 자료·기준일·새로고침 초기화** 안내를 확인한다. 실제 학생·교사 자료를 입력하는 용도로 사용하지 않는다.
3. 일정을 등록한다. 열람 범위와 관련 대상의 차이, 포함되는 이름과 이유가 이해되는지 확인한다.
4. 홈 카드에서 원본을 연다. 목록과 홈이 같은 ID·버전의 자료를 표시하는지 확인한다.
5. 다른 교사·학교로 전환한다. 학교 전체 열람과 홈 추천 대상이 서로 다르며, 작성자 전용 일정은 타인에게 나타나지 않아야 한다.
6. 수정 중 다른 변경을 발생시킨다. 자동 덮어쓰기 대신 충돌을 알리고 사용자의 초안을 남기는지 확인한다.
7. 조회 실패·저장 실패·빈 목록·소속 종료 사례를 확인한다. 실패를 빈 결과나 성공으로 표시하지 않아야 한다.

구체적인 조작과 실행 명령은 [앱 README](../../apps/workhub/README.md), 입력과 반환값은 [타입 계약](../../apps/workhub/src/contracts.ts)을 기준으로 본다.

## 다음 실제 구현으로 넘길 사항

1. **T02 계약 검토:** Claude가 이 합성 사례와 최종 기획의 C01~C04를 대조한다. 현재 간소화된 소속 상태, 담당 유효기간, 오류 코드·반환 구조는 서버 계약 확정 전에 맞춘다. 미리보기의 성공을 V01~V48 전체 통과로 올리지 않는다.
2. **T03 배포 실증 준비:** 기존 Vercel Root와 함수 포함 경로를 확인하고, 새 Root에서 보호 엔진과 자산을 포함하는 구체적인 배포안을 제시한다. 로컬 Python 생성 성공만으로 Vercel 성공을 선언하지 않는다.
3. **T04/AP02 승인 자료:** 계정·학교·소속·가입 신청·기간·학교 전환의 허용/거부표, 기존 `public.users`와 옛 API 접근의 대응표, 데이터 이관·복구 순서를 먼저 작성한다. SQL 확정본은 Claude Web, 실행은 계란님이 담당한다.
4. **AP07 검증 환경:** 별도 검증용 데이터·Storage·OAuth 원본·환경변수·백업·복구의 설정 전후표를 준비한다. 서비스 설정을 실제로 바꾸기 전에 검토받는다.
5. **첫 서버 연결:** 위 계약과 승인을 반영한 뒤 메모리 어댑터 자리에 서버 어댑터를 붙인다. 등록→재조회→홈 반영→동시 수정→소속 종료를 실제 세션 두 개와 DB로 다시 시험한다.

`CLAUDE.md` 2절의 “DB 마이그레이션·스키마·RLS 변경”, “인증·보안 로직 변경”, “외부 서비스 설정 변경”은 실제 적용 전 승인 대상이다. 지금의 로컬 화면·문서·합성 시험 작업은 그 적용을 포함하지 않는다.
