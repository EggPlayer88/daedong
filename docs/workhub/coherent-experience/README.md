# 홈·메시지·수합·AI 화면 통일

2026-11-25 · 기준 main `be379a8a` · `feat/workhub-coherent-experience`

업무를 찾고, 내용을 작성하고, 처리 결과를 확인하는 화면의 간격과 표시 순서를 맞췄다. 홈의 2×2 구성과 AI 대화로 업무를 이어 가는 방향을 유지한다. 스쿨톡에서는 목록과 상세 구분, 선택 대상 요약, 주요 동작의 일관된 배치를 참고했다. 외부 서비스의 코드·이미지·브랜드는 사용하지 않았다.

## 변경 내용

| 영역 | 변경 | 유지한 동작 |
|---|---|---|
| 홈 | 확인할 일·내 수업·오늘 일정·내 업무를 공통 2×2 카드로 정리, 급식은 보조 영역으로 분리 | 긴급 업무, 실제 건수, 조회 실패·미연결 안내, 원본 이동 |
| AI | 오늘 업무 요약을 홈과 같은 순서로 배치, 예시 도움말은 입력창 밖의 보조 도구로 이동 | 일반·전문 대화, 자료 범위 선택, 기본·정밀 모델 승인, 근거·결과·복구 |
| 메시지 | 선택한 수신자 이름·인원·전송방식을 요약, 상세 명부는 변경할 때 펼침, 목록·원문·작성·접수 표시 통일 | 동명이인 구별, 개인별·단체 전송 차이, 최종 확인 사본, 원래 요청 번호 복구 |
| 수합 | 제출 대상 요약, 검토자·추가 답변 설정 접기, AI에서 작성 화면으로 바로 이어가기 | 입력 보존, HWPX 검사, 초안·공개·최종 제출 구분, 공동 작성·마감·보완·판 충돌 검사 |
| 공통 메뉴 | 상단 메시지에 이름 표시, AI 진입 강조, 여백·테두리·간격 통일 | 메뉴 공개 범위, 이동 잠금, 키보드 초점, 큰 글자·테마·모바일 설정 |

전체 회귀 중 기존 PC용 시간표 계산 시험에서 Windows 파일 교체 오류도 재현했다. 계산기 시작 전 `manifest.json`을 원자 교체하는 과정의 `PermissionError(errno=13, winerror=5)`였다. 화면이나 계산기 없이 독점 생성 직후 교체하는 최소 재현에서도 발생했다. 진단용 재시도는 해결 효과가 입증되지 않아 제품 코드에 넣지 않았다. 계산기·실행 한도·접수증·원본 시험은 그대로이며, 최초 실패와 환경을 분리한 재검사 결과를 따로 기록한다. 파일 접근을 막는 외부 프로세스는 특정하지 못했다.

## 줄인 단계와 남긴 확인

- AI 수합: 사용자가 대화에서 작성 화면으로 이어 간 경우, 현재 소속과 편집 가능 상태를 검사한 뒤 기존 초안 편집기를 연다. 일반 수합 화면의 직접 선택은 그대로다.
- AI에서 제출 초안 저장: 접수된 판을 다시 조회해 일치하면 검토 카드만 연다. **최종 제출 명령은 사용자가 확인 버튼을 눌러야 실행된다.**
- 저장 이후 입력·파일·판·대상·마감이 바뀌면 기존 검토를 사용할 수 없다. 응답을 잃으면 새 번호로 다시 저장하지 않고 원래 요청을 확인한다.
- 받는 사람을 접어도 단체 대화의 필수 제목은 보인다. 누락 시 브라우저 검증과 입력란 초점이 유지된다.
- 공개·전송·제출 확인, AI 유료 실행 동의, 파일 검사, 오류·미확정 요청 복구 안내는 줄이지 않았다.

## 판단해서 정한 것

- 홈과 AI의 업무 요약을 같은 네 영역으로 맞췄다. 화면을 옮겨도 같은 위치에서 업무를 찾도록 하기 위해서다. 배치와 공통 스타일은 `DailyOverviewLayout`과 `daily-overview-layout.css`에서 조정할 수 있다.
- 선택한 사람과 제출 단위를 먼저 보여 주고 전체 명부는 변경할 때 펼친다. 선택 결과를 확인하기 위해 긴 명부를 다시 읽지 않도록 했다. 메시지는 `MessageRecipientPicker`, 수합은 `CollectionEditorView`의 대상 선택 영역에서 조정할 수 있다.
- AI에서 명시적으로 이어 온 수합 초안의 중간 진입 버튼과, 저장 확인 뒤의 검토 카드 열기만 줄였다. 저장·전송·공개·최종 제출 명령은 자동 실행하지 않는다. 두 화면 전환은 `CollectionEditorView`의 효과와 `useCollectionEditor`의 `savedAnswerReview` 신호로 분리했다.
- 신규 기능은 넣지 않았다. 현재 기능을 더 쉽게 찾고 끝내는 데 변경 범위를 집중했다.
- Windows 파일 오류를 우회하려고 파일 삭제·복사 대체·계산 제한 완화는 하지 않았다. 진단 코드는 저장소의 제품 코드와 분리한 로컬 검증 산출물로만 보관한다.

## 검증 범위

운영 데이터와 유료 API 없이 합성 응답으로 실제 React 화면·훅·어댑터를 시험한다.

- `npm test`: 기존 전체 단위·계약 시험과 수신자 요약 렌더 시험.
- `npm run check:workhub`, `npm run build`, `npm run build:workhub`, `npm run check:workhub:design`.
- `npm run test:workhub:browser`: 기존 전체 브라우저 회귀와 아래 신규 파일.
- `workhub-collection-coherent`: AI 초안 진입, 미저장 입력 보존, 최신 판 재조회, 공동 작성자·마감·판 변경 차단, 원키 복구, 320px 큰 글자.
- `workhub-messaging-coherent`: 수신자 변경·본문 보존, 조회 오류, 필수 단체 제목, 최종 확인, 원키 복구, 320px 다크·큰 글자.
- 기존 홈·AI 시험에 공통 카드 순서, 중첩 여백 제거, 모바일 흐름과 조회 실패 보존 검증 추가.

### 최종 로컬 결과

| 검사 | 결과 |
|---|---|
| 전체 단위·계약 시험 | 267개 파일 · **5,881건 통과** |
| 전체 브라우저 실행 | 206개 파일 실행, 최신 재검사 포함 **205개 통과 · 1개 실패** |
| 이번 신규 수합·메시지·초안 복구 재검사 | 12 + 6 + 7건 통과, 자동 외부 호출 없음 |
| 타입 검사 / main 빌드 / workhub 빌드 | 통과 |
| 설계·배포 문서 계약 검사 | 통과 |
| 실제 자료 변경 / 유료 AI 호출 | 0 / 0 |

최초 브라우저 실패 중 `workhub-tab-checkpoint`는 복구된 선택기가 접힌 상태를 반영해 시험의 탐색 순서만 고쳤고 7건을 다시 통과했다. 대상·본문·요청 번호 보존 기대값은 낮추지 않았다.

남은 `workhub-timetable-local-engine`은 기존 Windows 파일 교체 오류다. 원본 단독 재검사에서도 실패했다. GitHub의 별도 환경 검사와 검토를 확인하기 전에는 병합을 권하지 않는다. 진단 환경에서 우연히 통과한 결과를 최종 통과 수에 넣지 않았다. 첫 실행·재검사 결과는 `validation.json`에 구분했다.

단위 시험의 마지막 실행은 저장소 밖 전용 임시 폴더에서 했다. 중간에 임시 폴더를 저장소 안에 지정한 실행에서는 시험 계정 보관 정책이 의도대로 거부됐으며, 이 설정을 바로잡은 뒤 전체 5,881건을 통과했다. 제품의 비밀 보관 정책이나 시험 조건은 변경하지 않았다.

## 보존 범위와 후속

DB·SQL·인증·RLS·모듈 공개 범위·AI 모델과 예산·파일 생성 및 검사 계약은 바꾸지 않았다. 실제 교사 계정과 시험 데이터도 수정하지 않았다. 별도 SQL 적용은 없다.

신규 기능 채택은 전부 보류한다. 예약·주소록 그룹·새 읽음 추적·전자결재·설문·학부모 앱뿐 아니라 메시지를 할 일로 바꾸는 기능도 이번 변경에 추가하지 않는다.

미병합 #134의 CL1·TR2 검토 및 적용은 별도 작업이다. 이 PR은 main에서 시작하며 해당 SQL과 미병합 기능을 포함하지 않는다. 병합은 사용자 확인 후 진행하고, 배포 뒤 기존 시험 자료로 네 화면의 표시와 작성 진입만 확인하면 된다.
