## 2. Node 게이트웨이에서 확인한 것

- AES-256-GCM 왕복, 매번 다른 IV, 학교·키 판·태그·IV·마스터 키 ID 훼손 거부.
- 사용자 검증과 기존 회원 승인 이후에만 학교 공통 게이트웨이를 호출하고, 클라이언트의 위조 actor/school을 사용하지 않음.
- Haiku·Sonnet별 예약액, 80,000 입력 사전 계수, 100,000 입력/8,000 출력 범위의 자동 정산.
- `예약 → 토큰 계수 → 1회 시작권 → 생성 → 정산` 순서와 같은 키 재전송·내용 충돌·완료 복구.
- 계수 실패·입력 초과·예약 부족·시작권 거부에서 답변 생성 0회.
- 공급자 응답 유실·정산 응답 유실·공급자 ID 누락·모델 불일치에서 예약 보존 및 자동 재생성 없음.
- 예약 범위를 넘는 실제 사용량은 `observedUsage`로 남기며 성공 정산이나 예약 해제를 하지 않음.
- 요청 시작부터 50초 기한, 시작 전 시간 부족 해제, 시작 후 부족 시 결과미상 기록. 생성 호출은 정산용 8초를 남김.
- 토큰 계수와 생성의 `thinking`·`output_config` 일치, 캐시·강제 도구 호출 차단, 추론 원문 미저장.
- Sonnet 5.5에서 거부되는 `thinking.type=disabled`를 사용하지 않음. 두 모델 모두 `adaptive`로 실제 핸들러 본문을 검사.
- 미접수 닫기 장벽 뒤 늦은 요청 차단, 시작 뒤 닫기는 결과미상 유지, 완료 뒤 닫기는 원래 답변 반환.

단위 시험의 공급자·원장 응답은 합성이므로 실제 공급자의 정산, SQL 경합, Vercel 시간 제한을 독립적으로 증명하지 않는다. SQL 원자성과 실제 응답 모양은 별도 PG 시험·캡처로 확인한다.

## 3. 평가계획서 화면에서 확인한 것

실제 `DocAiPage`, 사용자 계정 문맥, `postJson`, CSS를 브라우저에 올리고 요청 응답만 합성했다.

1. 첫 진입·새 대화에서 자동 유료 호출이 없으며 명시 시작 버튼만 실행한다.
2. 기본/정밀 선택이 요청에 고정되고, 정상 완료 후 다음 질문은 새 번호를 사용한다.
3. 결과미상 동안 새 질문·모델 변경·대화 변경을 막고 같은 번호로 결과만 확인한다.
4. 같은 탭에서 화면을 다시 열어도 원요청이 남고 자동 재호출하지 않는다.
5. 서버 미접수 확인 뒤에는 새 번호 대신 같은 번호·같은 내용을 명시 재접수한다.
6. 깨진 PLAN_READY는 자동 유료 재작성 없이 별도 확인 버튼을 제공한다.
7. 닫기 응답 유실 후 화면을 다시 열어도 닫기만 재확인하고, 서버 종료 접수증 이후 잠금을 푼다.
8. 이미 시작한 요청을 닫아도 성공으로 표시하거나 새 요청을 허용하지 않는다.
9. 계정 변경 후 이전 입력·원요청·늦은 응답을 표시하지 않는다.
10. 입력 길이 초과는 원입력을 보존하고 HTTP/생성을 실행하지 않는다.
11. 320px에서 가로 넘침 없이 모델 선택·키보드 전송·원요청 복구가 가능하다.

처음 실행에서 모바일 키보드 복구 시험이 아직 비활성인 버튼에 Enter를 보내 실패했다. 최종 시험은 버튼이 활성화된 것을 확인한 뒤 키보드 동작을 검증한다. 제품의 잠금 조건이나 기대 결과를 완화하지 않았다.

## 4. 실제 PG 응답 대조의 범위

재실행 도구: `tests/verify_school_ai_gateway_capture.mjs <captures.json>`.

최종 캡처는 통합 실행기가 최종 작업트리에서 PG 72개 회귀를 실행하며 생성했다. 평가계획 gateway 봉투 45건 중:

| 구분 | 수 | 방법 |
|---|---:|---|
| 완료·복구·미접수·닫힘·미상·오류 | 28 | 실제 SQL JSON을 Node 게이트웨이의 봉투·최종 응답 검증에 그대로 입력 |
| claimed 정책·학교·키 판·예약액 | 10 | SQL 시험의 가짜 암호문만 같은 학교·판의 유효한 합성 암호문으로 교체, 실제 policy→count→시작권 거부 경로 확인 |
| 시작권 응답 | 7 | 실제 SQL의 `{started:boolean}` 필드 대조 |

외부 네트워크·실제 키·유료 생성은 0회다. claimed의 암호문 대체는 실제 DB에 저장된 비밀키 복호화 검증을 뜻하지 않는다. 브라우저와 실제 Supabase·PostgREST·Anthropic을 이어 실행한 시험도 아니다.

## 5. 재실행

저장소 루트에서 실행한다. Python 환경과 SQL 테스트용 PostgreSQL 준비는 해당 패키지 안내를 따른다.

```text
node tests/test_school_ai_gateway.mjs
node tests/test_doc_ai_request.mjs
node tests/test_gate.mjs
node tests/test_smoke_subjects.mjs
node tests/browser/doc-ai-school-policy.mjs
node tests/verify_school_ai_gateway_capture.mjs <PG에서 생성한 captures.json>
npm run test:workhub:ai-sql
```

전체 검증은 `npm test`, 브라우저 묶음은 기존 `npm run test:workhub:browser` 러너를 사용한다. SQL 통합 실행기는 `P10_AI_PG_BIN`에 PG17 bin 경로를 지정하고 psycopg2-binary·앱 Python 의존성을 설치한 환경에서 실행한다. `PYTHON`으로 인터프리터를 지정할 수 있다. `WORKHUB_AI_SQL_REPORT`에 로그·합성 캡처·summary.json을 보관하며 CI도 같은 명령을 실행한다. 실제 공급자 호출을 자동 검증에 섞지 않는다.

최종 점검에서 학교 키 `recover_key` 요청의 `expectedCredentialVersion` 누락을 발견했다. 원래 키 판을 복구 요청에 함께 보내도록 보강하고, 평문 키를 복구 요청에 넣지 않는 조건과 실제 Python 요청 계약을 다시 확인했다. 이 보강은 기존 복구 접수증 판정 조건을 낮추지 않는다.

## 6. 아직 확인하지 않은 실제 환경

- 운영 SQL 설치와 기존 데이터·권한 지문 보존.
- Production 마스터 키·학교 API 키 등록, 실제 암호문 저장·복구·키 교체.
- 운영의 승인된 기존 평가계획 회원과 학교 연결 명단.
- 실제 PostgREST의 학교 원장·동시 요청·비활성/활성 전환.
- 실제 두 모델의 응답·지연·사용량·공급자 요금 대조.
- 실제 서비스에서 요청 종료·답변 유실·원장 정산 복구.
- 이전 전역 키 경로를 쓰는 배포·열린 탭·진행 중 호출의 전환 완료.

이 항목들이 남아 있으므로 현재 판정은 **구현 및 합성·격리 DB 검증 단계**다. 운영 활성화나 일반 교사 공개 완료로 판정하지 않는다.
