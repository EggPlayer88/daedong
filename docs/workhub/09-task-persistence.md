# 4차 개발 — 내 업무 서버 저장 연결

## 이번에 연결한 흐름

기존 앱의 `/workhub`에서 학교를 고르면 홈 요약과 **내 업무**가 같은 서버의 본인 할 일을 조회한다. 제목·메모·선택 기한을 등록하고, 진행 전/진행/대기/완료/취소 상태를 바꾸며, 완료한 일을 다시 열 수 있다. 목록 조회 실패는 빈 목록과 구별한다. 기존 가상 업무·수합·학생 미리보기는 독립적으로 유지한다.

현재 결과는 **화면·어댑터·SQL 제안·자동 검증까지**다. 실제 Supabase에 SQL을 적용하거나 실제 회원 자료를 옮기지 않았다. 실제 Google 로그인부터 저장·재조회까지의 운영 연결 시험은 남아 있다. 이미 제공한 연결 진단의 성공도 새 할 일 RPC 준비를 보장하지 않는다.

## 권한과 자료 소유

- 기존 공용 Supabase 인증 인스턴스와 가입 승인 검사를 사용한다. 신규 계정·프로필·인증 공급자를 만들지 않는다.
- 시험 메뉴와 서버 rollout은 기존과 같이 슈퍼관리자 대상이다. 이번 작업으로 일반 교사 공개 범위를 넓히지 않는다.
- 할 일은 **학교 + 소유 소속 ID**에 묶인다. 같은 학교의 다른 교사·관리자에게도 개인 할 일을 공개하지 않는다.
- 겸임 학교의 자료를 섞지 않는다. 소속 종료·권한 회수 시 이전 자료를 조회하거나 요청 영수증으로 다시 가져올 수 없다.
- 같은 사람이 재발령되어 새 소속 ID를 받더라도 이전 할 일을 자동 이전하지 않는다. 전출·재입교 시 이관 정책은 별도 설계 대상이다.
- 이번 단계는 현재 학교의 개인 업무 공간이다. 학교와 관계없이 지속되는 계정 단위 개인 공간은 아직 구현하지 않았다.

## 서버 계약

| RPC | 입력 | 결과 |
|---|---|---|
| `workhub_task_list` | `p_member_id` | 본인의 현재 학교 할 일 배열 |
| `workhub_task_get` | `p_member_id`, `p_task_id` | 열람 가능한 원본 한 건 |
| `workhub_task_mutate` | `p_member_id`, `p_command`, `p_request_key` | 원자적으로 저장한 원본 또는 같은 요청의 이전 결과 |

변경 명령은 `create + input`, `update + taskId + input + expectedVersion`, `status + taskId + status + expectedVersion` 중 하나다. 화면에서 임의의 학교·작성자·버전·식별자를 주입하지 못하도록 서버가 소속과 소유자를 결정한다. 실제 연결 어댑터는 응답의 식별자·학교·소유자·버전·필드 형식을 다시 검사한다.

`TaskInput`은 제목 `title`, 메모 `notes`, 기한 `dueDate` 세 필드다. 제목은 필수이며 최대 120자, 메모는 최대 2,000자다. 길이는 유니코드 코드포인트로 센다. 원문 길이를 먼저 검사하고 ECMAScript trim과 같은 공백 집합으로 양끝 공백을 정리한다. 기한 없음은 빈 문자열, 기한 있음은 실제 존재하는 `YYYY-MM-DD` 날짜다. 상태는 `todo`, `doing`, `waiting`, `done`, `cancelled` 다섯 개다.

## 재시도와 동시 수정

등록·수정·상태 변경은 서버에서 권한 재검사, 버전 확인, 원본 변경, 요청 영수증, 감사를 한 트랜잭션으로 처리한다. 같은 요청 번호와 동일 입력의 재시도는 처음 결과를 반환한다. 같은 번호에 다른 입력을 넣으면 거부한다. 새 명령에는 새 요청 번호를 사용한다.

저장 응답만 유실된 경우 화면은 성공을 추정하지 않고 입력과 원래 요청을 유지한다. 재시도는 같은 번호·입력으로 보낸다. 다른 창에서 먼저 수정한 경우 원본 버전을 비교하고 최신 내용과 내 입력을 확인한 뒤 명시적으로 다시 적용한다. 이전 버전에 조용히 덮어쓰지 않는다.

같은 계정의 창 복귀·토큰 갱신은 작성 중인 입력을 유지한다. 다른 계정으로 바뀌거나 소속을 바꾼 경우 이전 화면을 폐기하며, 뒤늦게 도착한 응답을 새 학교에 표시하지 않는다. 실제 업무 자료를 합성 localStorage로 우회 저장하지 않는다.

업무 편집·저장·미확정 결과·충돌 비교 중에는 신축 업무 공간의 메뉴와 학교 이동을 잠근다. 새로고침·창 닫기에는 브라우저의 이탈 경고를 연결했다. 입력과 미확정 요청은 메모리에 보관하므로 강제 종료나 기존 앱의 외부 메뉴로 인한 컴포넌트 해제 후까지 복구하지는 못한다. 전국 공개 전 앱 전체의 이동 보호와 미확정 요청 복구를 보완해야 한다.

## SQL 확정·적용 인계

`database/workhub/004-personal-tasks.proposed.sql`은 기존 `001-calendar-foundation.proposed.sql` 위에 적용하는 **추가형 검토안**이다. 기존 `migrations/*.sql` 확정본을 수정하지 않는다. SQL 확정은 Claude Web, 실제 적용은 계란님 담당이라는 저장소 규칙을 따른다.

1. 기존 회원·인증 트리거 보존을 사전 점검하고 복구 기준을 확보한다.
2. 격리된 검증 환경에서 기반 001과 개인 업무 004를 검토·적용한다. 002는 읽기 전용 사전 확인, 003은 승인된 기존 회원을 학교와 연결하는 검토안이다.
3. PostgREST가 새 함수 계약을 인식하는지 확인한다.
4. 승인된 기존 계정으로 로그인해 홈·내 업무의 등록/수정/완료/재개/재조회와 학교 분리를 확인한다.
5. 두 개의 실제 계정과 두 브라우저를 이용해 타인 거부·동시 수정·응답 유실·승인 회수·소속 종료를 확인한다.

이번 PR은 적용·배포·공개 확대를 수행하지 않는다. 테스트 DB는 실제 회원과 관계없는 합성 자료만 쓰며 CI가 끝나면 폐기한다.

## 검증 범위

어댑터 검증은 잘못된 입력·다른 학교/소유자 응답·잘못된 충돌 자료를 차단하는지 확인한다. PGlite 검증은 실제 PostgreSQL 엔진에서 RLS, RPC 권한, 직접 쓰기 차단, 멱등·버전·감사와 회원 보존을 검사한다. GitHub Actions는 별도 PostgreSQL 16 연결 사이의 실제 잠금 경합을 추가로 검사한다.

Playwright는 실제 TaskPanel과 실제 ConnectedWorkspace에 합성 전송 계층을 주입해 입력·재시도·충돌·학교 전환·늦은 응답·모바일을 확인한다. 이 시험들은 실제 Supabase/PostgREST·Google OAuth 종단 시험을 대신하지 않는다. 최신 건수와 PR 증거는 [누적 진행 현황](PROGRESS.md)에 기록한다.
