# 11차 — 시범 운영을 위한 DB 연결·적용 인계

2026-10-13 · 상태: **DB 구축 보류**, 운영 DB 미접속·미변경

> 통합 작업 반영: 현재 목표 설계의 단일 기준은 [통합 DB 설계 v1.1](database-integrated/README.md)이다. 해당 설계에는 배치·시간표 참조·outbox 선후관계와 상속 제약의 보강, 메신저·양식 수합·시간표 계약이 포함된다. 문서·카탈로그 검증과 실제 SQL 구현 검증은 별개다. 아래 절차는 DB 구축 재개 후의 참고용이며, 이번 코드 통합으로 DB 보류가 해제되거나 SQL이 확정·실행되지 않는다.

사용자 목표는 **문서작성 AI와 시간표를 제외한 기능을 완성한 뒤 시범 운영**하는 것이다. DB 구축과 시간표는 사용자 요청으로 보류한다. 향후 재개 시 SQL 확정은 Claude Web, 검증 환경·운영 환경 실행과 main 병합은 계란님이라는 [협업 규칙](../../CLAUDE.md)을 유지한다. 이 문서 자체가 SQL 실행본이나 공개 범위 변경은 아니다.

## 1. 지금 실행할 수 있는 것과 아직 확정할 것

**현재 SQL 제안은 기존 계정으로 일정·개인 업무를 연결하는 최소 단계까지다. 전체 통합 DB를 구축하는 최종 SQL은 아니다.** 기존 제안과 통합 설계는 스키마·계정·기간·RPC 표현이 다르므로 파일 이름 순으로 모두 실행하지 않는다.

통합 브랜치에는 [PR #12](https://github.com/EggPlayer88/daedong/pull/12)의 설계와 [PR #22](https://github.com/EggPlayer88/daedong/pull/22)의 v1.1 보강이 `docs/workhub/database-integrated/`에 함께 있다. 바탕화면 `GPT작업/DB통합설계_v1/`은 전달본이며 저장소의 현재 설계와 대조한다. [이전 Codex DB 설계](database/README.md)와 원본 Claude DDL은 변경 근거·과거 호환 계약으로 보존한다. 충돌 시 현재 통합 설계를 참조하되, 실제 적용은 별도로 검토·승인한 SQL만 사용한다.

002는 `public.users`, `doc_ai_conversations`, `doc_submissions`, `storage.objects`, `handle_new_user()`의 존재를 전제한다. 모든 환경에서 실행되는 범용 조사기가 아니며 **개수 일치만으로 회원·파일 보존을 증명하지 못한다.** 001·004의 `CREATE TABLE`을 부분 적용 DB에 그대로 재실행하는 것도 복구 절차가 아니다.

## 2. 통합 설계로 넘어갈 때 반드시 맞출 차이

| 항목 | 현재 구현/001~004 | 통합 목표 계약 | SQL 확정본에 필요한 처리 |
|---|---|---|---|
| 물리 위치 | `public.workhub_*`, 공용 클라이언트의 기본 `rpc()` | `workhub`, 비노출 `workhub_private` | schema 노출·함수 권한·호환 RPC 또는 새 어댑터 전환을 하나의 변경 대조표로 확정 |
| 계정 | `public.users.id` TEXT가 기존 Auth UID 문자열과 연결 | `accounts.id` 내부키 + `auth_user_id` UUID + 명시적 legacy 연결 | 기존 UID·프로필·승인·참조 보존, 새 내부키와 UID 구분. 재가입·이메일 매칭 금지 |
| 소속 | `teacher/calendar_manager`, active, 종료일 포함 | 계정/소속/역할·담당 분리, 상태·권한판, 종료일 제외 | 역할·상태 대응표와 중첩/회수 시험. 미승인과 퇴직을 기존 false 하나로 추정하지 않음 |
| 기간 | `valid_from ≤ 오늘 ≤ valid_through`, 서울 기준일 | 학교 시간대, `[from,to)` | 기존 date 마지막 유효일은 다음 날 exclusive로 명시 변환. UI DTO 의미를 조용히 변경하지 않음 |
| 개인 업무 | 학교와 소유 소속에 묶임 | 학교 업무와 계정 전용 개인 공간을 명시 구분 | 기존 학교 업무를 계정 개인 공간으로 자동 복사하지 않음. 전출/재임용 접근은 별도 승인 계약 |
| 일정·대상 | 일정 JSON draft와 관계 ID 배열, 전체 허용 목록 반환 | 정형 대상/승인된 담당, 원본판, 범위·커서 조회 | 기존 입력·추천/열람·버전·재시도 동등성 및 새 조회 계약 시험 |
| 원자적 변경 | 도메인별 receipt/audit | 공통 접수·감사·outbox, 현재 권한·정책·근거판 | 현재 멱등키·결과 연결을 잃지 않음. 재시도가 권한 회수나 과거판을 우회하지 않음 |
| 공개/옛 경로 | 신축 UI와 서버 기본 gate가 superadmin | 학교별 파일럿·서비스 정책, legacy 실제 경로 회수 | DB만 열고 UI만 숨기는 운영 금지. 승인된 공개 대상과 구 REST/API/Storage 범위를 함께 검증 |

통합 계약에서 추가한 R01~R12 반례·감사 주체·이관 재실행·파일/학생 연결 규칙은 원본 Claude DDL과 동일하다고 간주하지 않는다. SQL 확정자는 통합 설계의 `01~07` 공통 계약, `12~15` 보강 계약과 `schema-contract.json`의 `mandatory_*`, `acceptance-tests.json`을 기준으로 카탈로그 차이를 제출해야 한다. 목표 29개 API 기능군과 21개 구현 티켓은 설계 상태이며, 현재 7개 RPC가 존재한다는 이유로 완료 처리하지 않는다.

### 현재 앱이 실제로 호출하는 7개 RPC

| RPC | 입력 |
|---|---|
| `workhub_context()` | 없음 |
| `workhub_calendar_list(p_member_id text)` | 본인 소속 |
| `workhub_calendar_get(p_member_id text, p_event_id text)` | 본인 소속·일정 원본 |
| `workhub_calendar_save(p_member_id text, p_command jsonb)` | 본인 소속·기존 저장 명령(요청키 포함) |
| `workhub_task_list(p_member_id text)` | 본인 소속 |
| `workhub_task_get(p_member_id text, p_task_id text)` | 본인 소속·업무 원본 |
| `workhub_task_mutate(p_member_id text, p_command jsonb, p_request_key text)` | 본인 소속·명령·별도 요청키 |

연결 근거는 `apps/workhub/src/connection/legacy-client.ts`, `supabase-connection.ts`, `supabase-calendar.ts`와 `tasks/supabase-task-adapter.ts`다. `context`는 학교·소속·`basisDate`·`schoolLabels`를 반환한다. 달력과 업무의 요청키 위치는 같지 않다. 실제 기존 응답/오류·버전·충돌 원본 계약까지 보존하거나, 새 계약에 맞춘 어댑터 변경과 함께 배포해야 한다. 여기서 임의의 새 RPC 이름을 확정하지 않는다.

## 3. 첫 연결의 실행 순서

R0는 **기존 계정 로그인 → 유효한 학교 선택 → 일정·본인 업무 등록/수정/재조회·재시도**를 실제로 확인하는 내부 구축 단계다. 사용자가 목표로 한 전체 기능 시범 공개를 R0 공개로 축소하지 않는다.

| 순서 | 담당 | 구체적인 결과물과 다음 단계 조건 |
|---|---|---|
| 1. B00 실측 | Claude Web 조사본 확정 → 사용자 실행 | 검증/운영 환경 식별, 실제 객체·정책·함수·적용 기록, 기존 계정/파일 보존 기준. 개인정보 대신 안전한 차이 건수·지문 보고 |
| 2. 적용 경로 확정 | Claude Web, Codex 대조 | 아래 세 분기 중 해당 경로 선택. B01/B02 SQL·RPC/DTO 변환표·역할/기간 매핑·실패복구·검증 SQL을 묶어서 검토 |
| 3. 복구 리허설 | 사용자 환경 준비·실행, 결과 검토 | 격리 환경에서 DB와 파일 원본 복원, 지문·참조 확인. 기존 UID/login 복구 경로 검증. 외부 발송·AI 실행은 격리 |
| 4. 격리 DB 적용 | 사용자 | 승인된 확정 SQL만 선행 조건대로 실행. 적용 파일 SHA·환경·순서·전후 차이·오류를 기록. 실패하면 후속 파일 실행 중단 |
| 5. 최초 학교 연결 | 사용자 | 확인한 기존 계정과 학교·역할·기간만 연결. 신규 가입/기존 승인 일괄 변경 없음 |
| 6. 코드 계약 검증 | Codex | 확정 SQL의 반환형/오류/권한과 기존 화면 왕복 검증. 새 계약이면 연결 코드를 별도 PR로 수정하고 재검사 |
| 7. 실제 세션 R0 | 사용자·Codex | 같은 origin의 기존 로그인 → `/workhub` 연결 진단 → 일정/업무 저장·새로고침·재조회 → 두 계정/두 창의 분리·충돌·회수 확인 |
| 8. 다음 DB 배치 | Claude Web/사용자/Codex | R0 증거 통과 뒤 파일·수합·학생·지식 등으로 확대. 전체 시범 운영 게이트는 별도로 통과 |

적용 상태별 분기는 다음과 같다.

- **신축 표가 없음:** 통합 B01/B02 목표를 기준으로 신규 확정 SQL을 작성한다. 현재 001/004 계약을 호환 경로로 유지할지 새 DTO로 전환할지 먼저 확정한다. 잠시 쓸 구 구조를 무조건 만들었다가 다시 옮기지 않는다.
- **001/004 계열이 이미 있음:** 기존 표·데이터·접수키를 실측하고 신규 번호의 전환 SQL과 대조/재시작 절차를 작성한다. 이관 후 원본·접수·감사 연결을 검증하며 운영 표 삭제를 전제로 하지 않는다.
- **부분 적용 또는 문서와 구조가 다름:** 성공/실패 파일·객체 차이를 먼저 고정한다. `IF NOT EXISTS`로 통과시키거나 전체 초기화하지 않는다. 그 상태만 다루는 전방 수정/롤백 계획을 확정한다.

확정 SQL 없이 지금 001→002→003→004를 운영 SQL Editor에 붙여 넣는 단계는 없다. 원본 `migrations/000_reset_v1_project.sql`과 기존 001~007은 과거 이력이며 운영 재실행 대상이 아니다.

| 정책 | 해당 기능에 필요한 보존·파일·공개·Claude 비용 정책의 승인 여부 | 법적 보존연수·모델/한도·대상 교사 공개를 새 기본값으로 확정하지 않음 |

현재 003 제안의 수동 값은 `v_user_id`, `v_school_id`, `v_school_name`, `v_valid_from`, `v_valid_through` 다섯 개다. 이것은 **구 구조용 참고 변수 목록**이며 통합 스키마의 최초 연결 함수 인자라고 가정하지 않는다. 실제값은 확정 SQL의 매핑표에만 입력한다.

보존 대조는 Auth UID·프로필 ID/역할/승인/부서/추가 권한·기존 소유 참조·가입 트리거 정의/권한을 같은 기준점으로 확인한다. 기존 회원의 정상 가입/수정은 오류 차이와 구분한다. 회원 개수는 같아도 사람이 바뀌면 실패다. 통합 이관의 `initial_link` 이후 재실행은 회수한 역할·종료 소속을 복구하지 않아야 한다. 기존 문서작성 AI는 이번 신축 범위에서 제외해도 **현재 실사용 문서·대화·제출 파일의 보존 대상**이다.

## 5. 검증 명령과 실제 계정 인수 조건

다음 명령은 저장소 루트에서 실행한다. 앞의 PGlite 두 시험은 기존 `public.workhub_*` SQL 제안을 합성 임시 DB에서 검증하며, `--check-guard`는 DB에 접속하지 않는다. 이 결과가 통합 설계 v1.1의 구현·학교 간 격리·운영 연결을 증명하지는 않는다.

```sh
node tests/test_workhub_database.mjs
node tests/test_workhub_tasks_database.mjs
node tests/integration/workhub-postgres.mjs --check-guard
npm test
npm run check:workhub
npm run build
npm run build:workhub
node tests/browser/workhub-readiness.mjs
node tests/browser/workhub-connection.mjs
node tests/browser/workhub-tasks.mjs
```

Python 회귀는 `lxml`, 브라우저 시험은 Playwright·Chrome이 필요하다. 환경 지정은 [tests/README.md](../../tests/README.md)를 따른다. 별도 `npm run test:workhub:postgres`는 [07-postgres-verification.md](07-postgres-verification.md)의 폐기 가능한 **빈 로컬 전용 DB**와 테스트 환경변수 조건에서만 실행한다. 운영 Supabase 주소를 그 명령에 넣지 않는다. 확정 SQL로 바뀌면 그 적용본 지문을 고정한 별도 계약/경합 시험으로 갱신해야 하며, 기존 제안 시험 통과를 새 SQL 검증으로 기록하지 않는다.

| 실제 R0 시험 | 합격 증거 |
|---|---|
| 기존 로그인/회원 | 같은 Auth UID·profile·승인/역할, 가입 트리거 불변, 재가입 없이 로그인 |
| 학교 연결 | 본인 유효 소속만 학교 선택 가능, 진단 성공 후 별도로 실제 목록 조회 성공 |
| 일정/업무 | 등록·수정·완료/재개·새로고침 재조회와 홈 반영이 같은 원본/버전을 가리킴 |
| 학교/개인 분리 | 타학교·타인 업무·private 일정 거부, 입력 ID 변조 거부. 일반 교사 공개를 위해 최고관리자로 일괄 승격하지 않음 |
| 동시에 수정 | 두 창이 같은 버전 수정 시 하나만 저장, 나머지는 현재 권한을 통과한 충돌 응답 |
| 응답 유실 | 같은 요청키 재확인으로 결과 한 건, 업무/접수/감사가 일치 |
| 회수/종료 | 기존 승인 회수·소속 종료 후 새 요청과 과거 접수증 조회 모두 차단, 다른 유효 학교는 정상 |
| 보존/복구 | 기존 회원 행과 참조·파일 지문 대조, 파일 포함 격리 복원 결과 |

각 기록에 코드 commit, SQL SHA, DB/환경 버전, 시험 ID, 결과·시각·차이 건수만 남긴다. 실제 학생/회원 원문·세션/키를 결과 파일에 넣지 않는다. 합성 시험·HTTP 200·진단 `ready`만으로 실제 저장/전체 보존/다학교 공개를 통과시키지 않는다.

## 6. 전체 시범 운영까지의 후속 DB 배치

| 배치 | 이번 사용자 목표에 포함할 범위 | 통과 후 가능한 사용자 업무 |
|---|---|---|
| B03 | 공통 파일·실물/지문·접수·작업/outbox·삭제/복원 원장 | 파일 업로드/다운로드의 현재 권한과 실패 후 복구 |
| B04~06 | 조직/학기/수업 공통 기반·일정/업무·일반 자료함·수합·알림·인계 | 공동 작성→책임자 제출→검토/보완→집계, 정확한 목록의 후임 수락 |
| B07~08 | 명부/학적/수강/담당·관찰·정정·수업 앱 연결/채택 | 디지털윤리 활동을 정확한 학생·원자료판에 연결하고 교사가 기록으로 채택 |
| B09~10 중 포함 | 학교 규정/지식·효력판·검색, Claude 상담·개인 비서의 확인/실행·사용량 계약 | 근거가 있는 안내와 확인한 업무 실행. 정책·비용 승인 후 실제 호출 |
| 보류 | 문서작성 AI 전용 생성/문서팩 확장, 시간표 편성/배포/교체 | 재개 요청 전 구현·공개하지 않음 |
| B11 | 실제 계정 통합, legacy 경로 격리/전환, 시트 권위 전환, 파일 포함 복구·서버 부하·현장 확인 | 문서작성 AI·시간표를 제외한 시범 운영 후보 |

`spaces`, `course_groups`, `course_group_classes`, `course_group_teachers`는 학생 수강/담당과 일반 업무의 공유 기반이다. 시간표 보류 때문에 이 기반을 통째로 생략하지 않는다. 반대로 시간표 전용 FK나 solver를 미리 켜지 않는다. 일반 자료함·첨부 수합은 문서작성 AI 제외 범위에 들어가지 않는다. 생기부 **근거 기록·검토**는 학생 영역으로 유지하고 AI 문장 생성은 이번 보류 범위와 맞춰 별도 확정한다.

10차의 20개씩 표시는 DOM 최적화다. 서버의 학교·권한 제한/커서/집계 계약과 실제 자료량의 부하 검증은 이 단계에서 추가한다. Google 시트 병행 중에는 자료종류별 쓰기 기준을 하나로 정하고, 전환 대조 후 사이트로 바꾼다. 양쪽을 자동 덮어쓰는 동기화는 전환 완료 조건이 아니다.

## 7. 실패 시 되돌림과 다음 인계

| 실패 시점 | 실행자가 따라야 할 경계 |
|---|---|
| 적용 트랜잭션 안 | 확정본의 rollback/중단 절차 사용. 실패한 객체와 선행 적용본 확인 후 다음 파일 실행 중단 |
| commit 후 신규 사용자 쓰기 전 | 별도 승인된 역변경 또는 전방 수정으로 복구하고 보존 대조 재실행. 무조건 DROP은 아님 |
| 신규 쓰기 후 UI 장애 | 기능/학교 단위 쓰기·공개 제한, 원본·접수·감사·파일 보존, 호환 코드 복구. 코드만 되돌려 새 자료를 숨기지 않음 |
| 무결성/접근 경계 의심 | 해당 학교/도메인 격리 후 원본판·접수·파일 대조. 결과 불명확 요청은 확인 없이 새 키로 반복하지 않음 |
| legacy 복귀 필요 | 신규 발생분 보존/역이관·현재 권한 재적용을 검증한 뒤 권위 전환. 한 학교 사고로 전체 DB 과거 덮어쓰기 금지 |

DB 구축 재개 후 Claude Web에 넘길 구체적 작업은 다음과 같다. 현재는 인계 문안이며 작업 배정·SQL 실행 지시가 아니다.

> 저장소의 통합 DB 설계 v1.1(`docs/workhub/database-integrated/`)을 기준으로 B00~B02/R0 확정 SQL을 작성해 주세요. 현재 `database/workhub/001~004`와 실제 연결 어댑터를 대조하고, 운영 상태를 없음/기존 적용/부분 적용으로 분기해 주세요. 기존 Auth UID·프로필·가입 승인·실사용 문서/파일은 보존해 주세요. 목표 `workhub/workhub_private`와 기존 7개 RPC/DTO의 호환 방식, 기간/역할 매핑, 운영 감사 주체, 이관 재실행·권한 부활 방지, 검증/실패복구를 함께 제출해 주세요. 실제 값과 불확실한 정책은 추측하지 말고 필요한 입력표로 남겨 주세요. 문서작성 AI 전용 생성과 시간표는 보류입니다.

DB 구축 재개와 그 산출물 검토가 끝나면 계란님께 맡길 첫 실행은 **대상이 명확한 검증 환경에서 B00 읽기 조사본 실행 → 기존 회원/파일 보존·복구 증거 확인 → 확정된 B01/B02 적용 → 기존 계정의 R0 화면 확인**이다. 아직 없는 확정 SQL 파일명이나 명령을 만들어 안내하지 않는다. 운영 적용과 교사 공개는 검증 결과·대상·되돌림이 구체화된 뒤 진행한다.

### 판단해서 정한 것

- 현재 SQL 제안과 통합 목표를 별개로 표시했다. 목적은 이미 검증한 화면을 살리면서 두 원본 저장 구조가 동시에 진실이 되는 전환을 막는 것이다. 변경 시 이 문서 2~3절과 실제 어댑터/확정 SQL 차이표를 함께 갱신한다.
- R0는 내부 연결 검증이며 시범 공개 범위를 축소하지 않는다. 문서작성 AI·시간표를 제외한 목표의 완료 조건은 6절과 기능별 출시 목록에서 추적한다.
- SQL·인증·권한·운영 설정을 변경하거나 원격 DB에 접속하지 않았다. 이번 산출물은 실제 저장 연결을 진행할 수 있게 하는 선후 관계와 인계 기준이다.
