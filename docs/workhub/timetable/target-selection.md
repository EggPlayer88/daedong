# 준비 대상 학기 선택 — 앱 구현과 검증 경계

2026-10-19 · PR #70 추가 구현. SQL 적용·모듈 활성화·일반 교사 공개는 하지 않았다.

계약 기준은 [PR #71](https://github.com/EggPlayer88/daedong/pull/71)의 **`339f063275688a55f5f2334b221948cf1f6f5159`**이다. 원문은 해당 커밋의 [T1-07 대상학기 설계와 앱 연결](https://github.com/EggPlayer88/daedong/blob/339f063275688a55f5f2334b221948cf1f6f5159/database/workhub-timetable/t1/T1-07_%EB%8C%80%EC%83%81%ED%95%99%EA%B8%B0_%EC%84%A4%EA%B3%84%EC%99%80_%EC%95%B1%EC%97%B0%EA%B2%B0.md) 4·5절과 `T1-07_대상학기_선택.sql`이다. 이 앱 변경은 SQL 원문이나 기존 인증·비용 구조·메뉴 공개 범위를 바꾸지 않는다.

최신 기준은 이전 `68a5dcc`에서 SQL을 바꾸지 않고 앱 연결 안내와 학기 삭제의 판 유지 범위를 정정한 문서 커밋이다. 선택 학기가 삭제되면 FK가 선택만 비우고 판은 유지할 수 있다. 따라서 이전 선택이 있었던 화면에서 `termId: null`을 저장할 때 같은 판의 정상 no-op 접수증을 허용한다. 다른 학기 선택의 판 검증은 그대로이며, 접수증의 자동 대상이 이전 조회와 달라도 성공 뒤 현재 대상을 반드시 재조회한다.

## 담당자가 보는 동작

시간표 편성 화면의 진입부에 **준비할 학기**를 표시한다. 기준판이 아직 없는 학교도 이 선택기에 접근할 수 있다. 학년도·학기명·공식 기간·식별자, 지금 학기 표시, 기준판 및 준비 초안 유무를 함께 보여 준다.

이 선택은 개인별 환경설정이 아니라 **학교의 모든 시간표 담당자가 함께 쓰는 준비 대상**이다. 다음 학기를 고르는 행위가 학년도를 새로 만들거나 현재 공개 시간표를 바꾸지는 않는다. 학교 관리에 학년도와 공식 학기를 먼저 등록해야 한다.

1. 현재 준비 대상과 목록을 조회한다.
2. 준비할 학기 또는 `원래대로 · 지금 학기`를 선택한다.
3. 변경 전후를 확인하고 학교 공통 선택임을 명시 확인한다.
4. 조회한 판으로 저장한다. 성공 접수증만으로 현재 학기를 결정하지 않는다.
5. 대상을 다시 조회하고, 현재 준비 학기에 맞는 readiness·준비 원본·공간/수업 연결·기준판을 다시 읽는다.

목록에 선택 가능한 학기가 없으면 학교 관리에서 학년도·학기 날짜를 등록하도록 안내한다. 선택했던 학기가 닫히거나 끝나 자동 대상과 달라진 경우에는 자동 복귀를 설명한다. SQL은 학기 목록을 최대 20개만 반환하므로, 선택값이 목록 밖에 있다는 이유만으로 그 학기가 삭제됐다고 단정하지 않는다.

공개 함수와 데이터 모양은 아래와 같다. 남는 키와 잘못된 필드 타입은 거부한다.

```ts
// get(p_member_id)
workhub_timetable_target_get
{
  termId: string | null,
  automaticTermId: string | null,
  selectedTermId: string | null,
  version: number,
  terms: [{
    id, schoolYear, label, firstDay, lastDay,
    state: 'planning' | 'current', hasBasis, hasPreparationDraft
  }]
}

// set(p_member_id, p_input, p_request_key, p_recover_only)
workhub_timetable_target_set
p_input = { termId: string | null, expectedVersion: number }
receipt = { requestKey, termId, version, effectiveTermId }
```

봉투의 `contract`, `schoolId`, `memberId`는 현재 연결과 일치해야 한다. 날짜는 실제 존재하는 날짜와 범위를 검사한다. 목록 ID 중복·시작일 역순·알 수 없는 상태·잘못된 판·선택값과 실효 대상의 모순은 성공으로 읽지 않는다. 같은 `selectedTermId` 재선택은 판이 그대로인 접수증을 허용하며, 실제 변경은 다음 판이어야 한다. 복구에서는 당시 조회 원본을 요구하지 않고 원래 명령과 접수증을 대조한다.

새 명령은 성공한 조회 원본의 판과 선택 가능한 학기를 기준으로 한다. 같은 요청 번호에 다른 입력을 붙여 보내지 않는다. 새 소속이나 다른 권한 범위의 조회 캐시를 재사용하지 않는다. 최종 권한 판단은 기존 연결 및 서버가 담당한다.

## 입력 보존과 전환 잠금

다음 상태에서는 대상 학기를 변경하지 않는다.

- 공간·수업 연결 편집, 시수·일과 초안, 아직 추가하지 않은 시간대 또는 조건 입력
- 엑셀 변경 비교·선택, 일괄 저장의 미완료 항목
- 편성 계산, 저장 요청, 결과를 알 수 없는 원래 요청
- Claude에 아직 보내지 않은 질문, 처리 중 요청 또는 적용을 검토 중인 내용

대상 학기 선택 자체의 미확정 변경도 다른 준비 쓰기를 잠근다. 선택을 취소하면 서버에 쓰지 않고 잠금을 해제한다. 학기 전환 때문에 작성 중인 문구·배치·엑셀 선택·원래 요청을 자동으로 지우지 않는다.

직접 전환이 성공했고 다른 미저장 작업이 없으면 이전의 깨끗한 편성 세션을 정리하고 새 대상을 읽는다. 다른 담당자가 학기를 바꾼 경우에는 현재 탭의 미저장 자료를 보존하되 새 대상에 그대로 저장하거나 AI 제안을 적용하지 않는다. 창에 다시 초점을 맞추거나 보이는 상태로 돌아올 때 대상을 재확인한다.

`targetScopeKey`는 실효 학기·선택 학기·선택 판을 함께 비교한다. 같은 학기로 돌아왔더라도 판이 달라졌다면 공간/수업 입력 원본을 다시 읽어야 한다. 학기 삭제로 선택값이 해제되는 등 판이 그대로인 변화도 실효/선택 학기가 달라지면 감지한다. 학기 삭제의 서버 판 정책을 앱이 임의로 고치지는 않는다.

보존 위치는 기존 `useEditDraft`와 `usePendingRequest`의 **현재 탭 메모리**다. 컴포넌트 재진입에서는 보존하지만 브라우저 종료·새로고침 이후 영속 복구는 약속하지 않는다.

## 충돌과 결과 미상 처리

| 상황 | 처리 |
|---|---|
| 다른 담당자가 먼저 선택을 바꿈 | `CONFLICT` 후 최신 목록을 읽고 내 선택을 보존한다. 최신 판과 다시 비교·확인하기 전에는 재전송하지 않는다. |
| 저장 응답 유실·시간초과·깨진 저장 응답 | 원래 입력·요청 번호를 유지한다. 새 변경을 막고 `p_recover_only=true`로 접수 원장만 확인한다. |
| 복구 결과 `NOT_FOUND` | 그 조회 시점에 원장이 없다는 뜻이며, 늦은 최초 요청을 취소하는 증거는 아니다. 원래 요청을 보관한다. 명시 확인을 받은 뒤 같은 번호·같은 입력으로만 다시 보낼 수 있다. |
| 성공 접수증 뒤 현재 대상 조회 실패 | 접수증을 별도 메모리에 보관하고 잠금을 유지한다. 다시 확인은 조회만 수행하며 저장을 재전송하지 않는다. |
| 복구 접수증보다 현재 대상이 더 바뀜 | 접수증은 원래 저장의 증거로만 쓴다. 재조회한 현재 대상과 판을 화면에 전달하고 후속 변경이 있었음을 알린다. |
| 학교·소속·승인 범위 변경 후 늦은 응답 | 이전 응답을 현재 범위의 성공으로 채택하지 않는다. |

`TargetServer.resend`는 해당 학교·소속 범위에서 원래 입력을 등록하고 `recover`가 `NOT_FOUND`를 반환한 요청만 받는다. 현재 학기 목록이나 판으로 명령을 다시 만들지 않는다. 동일한 `p_request_key`·`p_input`을 `p_recover_only=false`로 보내며 기존 `createScopedRpc`의 쓰기·신원·봉투 검사를 유지한다. 최초 요청이 그 사이 저장됐다면 서버는 그 접수증을 돌려주고, 실제로 미접수였다면 원래 명령을 현재 서버 조건으로 판단한다. 원장 조회 없이 재전송 버튼을 열거나 새 키로 바꾸지 않는다. 재전송도 결과를 확인하지 못하면 다시 원키 조회로 돌아간다.

대상 학기가 바뀌거나 조회가 실패해도 기존 편성·준비·공간 저장의 **원래 요청 복구**는 현재 학기 검사 때문에 차단하지 않는다. 그 요청의 명령과 키를 그대로 서버 원장 조회에 전달한다. 이를 새 학기의 신규 저장으로 바꾸지 않는다.

## 초기 오류와 구 T1 호환의 한계

기존 T1은 대상 학기 RPC가 없어도 현재 학기의 준비 기능을 제공한다. 따라서 선택기 실패만으로 기존 T1 전체를 사용할 수 없게 만들지 않는다.

- 선택기를 최초 조회하는 동안에는 새 준비 쓰기를 잠시 막는다.
- `NOT_READY` 또는 어댑터까지 전달된 명확한 `PGRST202`는 선택기 준비 중으로 표시한다.
- 실제 공통 연결의 `rpcFailure()`는 일부 원본 오류 코드를 `QUERY_FAILED`로 바꾼다. 이 경우 앱은 **함수 미설치와 일반 네트워크 실패를 확실히 구별할 수 없다.** 공통 인증/전송 코드를 바꾸거나 실패를 SQL 미설치로 단정하지 않았다.
- 성공한 대상 조회가 아직 한 번도 없으면, 초기 조회 오류는 선택기에 표시하고 기존 T1 기능은 원래 서버 계약에 따라 계속 사용하게 한다. 이는 기존 T1 호환을 위한 정책이며 대상 선택 기능의 설치 여부를 증명하지 않는다.
- 한 번이라도 대상을 성공적으로 확인한 뒤에는 그 정보를 잊지 않는다. 이후 오류·중지·재조회 중에는 새 준비 쓰기를 막고 정상 재조회 뒤 해제한다. 기존 요청의 결과 확인은 계속 가능하다.

실제 배포 확인에서는 T1-07 미설치, 설치했지만 비활성, 정상 활성, 일시적인 네트워크 실패를 각각 확인해야 한다. 합성 시험의 `PGRST202` 분기를 실제 연결 오류 분류 전체의 증명으로 사용하지 않는다.

## T2 공개 시간표와의 분리

이 선택기는 **T1 준비 대상**을 변경한다. 공개된 수업을 조회하는 운영 화면에 준비 대상 ID를 자동으로 주입하거나, 다음 학기를 현재 공개 시간표로 바꾸지 않는다. 앱 연결 시험은 다음 학기 준비를 선택한 뒤에도 운영 조회에 원래 날짜 범위가 전달되는지 확인한다.

실제 T2 SQL은 PR #71 계약에 따라 현재 공개 시간표 판정에 `t1_term_auto`를 사용해야 한다. 앱의 날짜 범위 유지 시험만으로 미완성/미적용 T2 SQL이 이 원칙을 충족했다고 주장하지 않는다. 교환·동의·승인·날짜별 운영 연결은 T2 적용 후 별도로 확인한다.

시험은 실제 React·타입 어댑터·parser를 사용하지만 DB/RPC 응답은 합성이다. 이 문서의 숫자는 독립 시험 단위이며 전체 회귀 총계는 릴리스 검증 기록에서 관리한다.

이번 작업에서 실제 Supabase/PostgREST 왕복, 운영 DB 적용, SQL 권한·트랜잭션 잠금, 실제 여러 담당자 브라우저 동시성은 검증하지 않았다. 새 쓰기 직전의 `target_get`과 실제 저장 호출은 **서로 다른 요청**이다. 사이에 다른 담당자가 다시 바꿀 가능성을 앱의 사전 조회만으로 원자적으로 제거할 수 없다. 최종 학교 범위·학기·판·요청 번호·권한·동시성 판단은 해당 SQL 트랜잭션과 기존 제약이 담당하며, 실제 SQL 대조 및 운영 연결 검증이 남아 있다.

## Claude의 실제 SQL 응답과 앱 parser 대조

PR #71의 `test/run_t1_07.py`는 `T1_07_CAPTURE`를 지정하면 격리 PostgreSQL 시험에서 나온 이름별 응답을 JSON으로 저장한다. SQL 시험 실행은 Claude의 실행 안내와 시험 환경에서 수행한다. 운영 DB에서 시험용 설치 스크립트를 실행하지 않는다.

그 JSON을 받은 뒤 저장소 루트에서 다음과 같이 앱의 실제 parser와 대조할 수 있다.

```powershell
$env:TIMETABLE_TARGET_CAPTURE = 'C:\검증결과\T1_07_CAPTURE.json'
node tests/test_workhub_timetable_target.mjs
Remove-Item Env:TIMETABLE_TARGET_CAPTURE
```

```sh
TIMETABLE_TARGET_CAPTURE=/tmp/T1_07_CAPTURE.json node tests/test_workhub_timetable_target.mjs
```

대조기는 `timetable.target.v1` 성공 응답만 골라 조회 원본은 `targetSnapshot`, 쓰기 접수증은 실제 `input`과 요청 번호를 사용해 `targetReceipt`로 검증한다. 조회와 접수증이 각각 한 건 이상 있어야 통과한다. 출력에 실제 대조한 원본/접수증 수가 따로 표시된다. 이 추가 경로는 준비했지만 **이번 앱 작업에서 Claude의 SQL capture를 받아 실행한 결과는 아니다.**

다음 검토에서는 특히 현재/미래 학기, 같은 선택 no-op, 자동 복귀, 닫힘·삭제, 원장 복구와 판 변경의 실제 SQL 응답을 대조한다. 이후 T1 설치·T1-07 적용·관리자 활성화·실제 DB 왕복 확인은 각각 별도 단계로 진행한다.
