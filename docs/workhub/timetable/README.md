## 1. 교사가 쓰는 순서

**일반 교사는 내 시간표와 변경 요청만**, **시간표 담당자는 편성과 공개 관리까지** 본다.
관리자의 학교 설정을 담당자가 다시 입력하는 방식은 피한다. 학교 관리의 학급·교사·교과·학기, 수업 관리의 수업 집단을 버전이 고정된 편성 기초 자료로 가져온다. 원자료가 달라지면 바뀐 부분을 확인한 후 새 판으로 편성한다.

```mermaid
flowchart LR
 A[관리자: 학교·교사·시수·배정 승인] --> B[담당자: 기초 자료 확인]
 B --> C[필수·선호 조건 정리]
 AI[Claude: 질문·조건 제안·설명] -.사람 확인.-> C
 C --> D[별도 작업에서 후보 계산]
 D --> V[독립 검증: 시수·충돌·조건]
 V --> E[후보 비교·수업 이동·다시 검증]
 E --> F[새 초안 저장]
 F --> G[적용 기간·영향 확인]
 G --> H[담당자 공개 확정]
 H --> I[교사: 날짜별 내 시간표]
 I --> J[교환 제안→당사자 동의→담당자 승인]
 J --> K[같은 트랜잭션에서 수업·자원·이력·알림 기록]
 K --> I
```

AI는 수업의 가능 여부를 보증하는 주체가 아니다. 조건과 배치를 계산하는 코드, 그 결과를 다시 검사하는 코드, 서버에서 권한·최신 판·충돌을 확인하고 확정하는 절차를 분리한다.

## 2. 이번에 작동하게 만드는 범위와 이후 연결

| 구분 | 이번 앱·도메인 구현 | 실제 학교 활성화에 필요한 것 |
|---|---|---|
| 내 시간표·공유 | 현재 교사의 날짜별 수업, 허용 범위의 확정판·교사/일자 필터 조회 화면 | 확정 시간표·날짜별 수업 조회 SQL |
| 기초 자료 | 학교·학기·판·지문, 시수·자원·배정·슬롯 참조 검사 | 학교 관리와 수업 관리에서 승인 기초판 작성 |
| 조건 입력 | 고정 배치·자원 불가시간·선호 벌점, 기초 필수조건 삭제 방지 | 학교가 정한 조건 관리 권한 |
| 후보 계산 | 브라우저 Worker의 제한 시간 탐색, 취소, 유효 후보 독립 재검사 | 실제 학교 규모 성능 측정, 필요하면 서버 최적화 엔진 연결 |
| 수동 조정 | 수업과 목적 시간 선택, 충돌 차단, 후보 유지 | 없음: 읽어온 기초판 또는 명시한 예시로 로컬 계산 가능 |
| 초안 저장 | 새 후보 저장 어댑터, 같은 요청 재확인, 입력 보존 | `workhub_timetable_save_draft` 등 3개 RPC |
| AI 도움 | 기초판·작업 중 조건·배치 지문에 묶인 제안 자료형과 확인 후 적용 검사 | 기존 Claude 실행권·비용 예약·출력 검증을 시간표용으로 확장 |
| 공개 | 기간 선택·제외일·전후 수업 미리보기·명시 확인·확정 어댑터 | 실제 영향 계산, 판 고정·잠금·원자 공개 SQL |
| 날짜별 교환 | 이동/두 수업 교환의 작성·미리보기·동의·반려·철회·승인 화면과 어댑터, 순수 사전 검증 | 현재 자료·동의·자원 잠금과 원자 처리 SQL, 알림 연결 |
| 대강·취소·보강 | 구분과 시수 원장·보상 정정 설계 | 실제 처리 도메인·SQL·화면, 현재는 미지원 거부 |

**완성 서비스나 전국 학교 성능을 검증한 상태라고 표현하지 않는다.** 계산·검증·편성 및 운영 화면을 연결한 앱 후보이며 실제 DB·Claude 연결은 별도 검증이 필요하다. 미설치 RPC를 성공으로 바꾸지 않으며, 예시 연습은 사용자가 따로 선택하고 실제 저장 버튼을 제공하지 않는다. 공개·변경 화면은 준비 상태와 권한을 확인한 뒤에만 원래 명령을 전송하며, 성공 접수증을 받기 전 완료로 표시하지 않는다.

## 3. 편성 기초 자료의 의미

- `basis.id/revision/sourceFingerprint`: 학교·학기 및 관리자 승인 배정·시수·교시 기준판. 서버가 원자료와 판을 고정해 만든다. 클라이언트 지문을 신뢰해 권한을 부여하지 않는다.
- `lessons`: 주간 수업 발생 단위. 한 교과 주당 4시간이면 1시간 4개 또는 승인된 연속 블록으로 분해한다. 영구적인 날짜별 `lesson_instance.id`와 다른 ID다.
- `courseLoads`: 수업 집단별 승인된 주당 교시 수. 누락·초과는 편성 시작 전에 막는다. 교시 수와 분 수를 같은 단위로 합산하지 않는다.
- `resources`: 교사·학급·수강생 충돌 집단·교실·장비. 교사와 학생 집단의 용량은 1. 공동 수업은 관련 자원을 모두 점유한다. 교사 두 명은 둘 다 참여하는 뜻이며 둘 중 한 명을 고르는 뜻이 아니다.
- `slots`: 요일·시작/끝 분·표시 이름·교시 수가 고정된 배치 가능 시간 구간. 같은 '1교시'라도 실제 시간이 겹치면 충돌이다. 연속 블록은 하나의 구간으로 취급하며 쉬는 시간을 포함해 자원을 점유한다. 블록 후보는 서버가 학교의 연결 가능한 교시 규칙으로 만든다.
- `allowedSlotIds`: 각 수업이 들어갈 수 있는 승인 후보. 학년별 종례·교실 이동 시간·요일별 운영을 이미 반영한다. 모델에 넣지 않은 조건을 엔진이 알아서 지킨다고 주장하지 않는다.
- `fixed/unavailable`: 반드시 지킬 조건. 학교 기초판의 항목은 초안에서 지울 수 없다. 임시 담당자 조건은 직접 수정하고 다시 계산한다.
- `preferences`: 수업·시간별 비음수 벌점. 작은 값이 선호된다. 이번 엔진은 첫 유효 후보를 찾으므로 점수가 전교 최적이라는 뜻이 아니다. 연강 제한·공강·오전 편중 등 복합 선호는 별도 유형·점수 설명·회귀를 갖춘 다음 추가한다.

학급별 수업시간 차이는 각 활동의 후보 시간으로, 선택 수업의 학생 중첩은 `student_group` 자원으로 표현한다. 이를 만들 실제 수강 자료가 없으면 `unsupportedFeatures`를 기록해 생성을 막는다. 교육과정별 완전 지원 여부는 학교급 이름이 아니라 **필요한 조건이 모두 모델에 반영되고 검증됐는지**로 판단한다.

## 4. 화면 원칙

1. 기본은 ‘내 시간표’. 교시뿐 아니라 실제 시각을 보이고, 변경된 수업과 취소를 구분한다. 결근·상담의 민감한 사유는 시간표 응답에 담지 않는다.
2. 담당자는 기초 자료 → 조건 → 후보 편성 → 공개 검토 순서로 이동한다. 원자료 수정은 학교 관리로 연결하며 시간표 화면에서 교사 배정을 몰래 바꾸지 않는다.
3. 필수조건과 선호조건을 나눠 표시한다. AI가 ‘되도록’을 ‘반드시’로 바꾸거나, 불가능을 해소하려 필수를 선호로 낮추지 못한다.
4. 수동 변경은 드래그가 없어도 가능하다. 수업 버튼을 선택하고 목적 시간을 선택한 뒤 결과를 검사한다. 충돌 시 기존 후보를 보존하고 사유를 읽을 수 있게 표시한다.
5. 계산은 Worker에서 수행한다. 취소·페이지 이동·학교 변경 시 작업을 종료하고 늦은 결과는 반영하지 않는다. 버튼 중복 클릭으로 계산을 여러 개 겹치지 않는다.
6. 결과 미상 저장은 원래 요청 번호와 내용을 유지한다. 다른 조건으로 재전송하지 않는다. 초안 보존은 현재 탭 메모리이며 브라우저 종료 후 복원을 약속하지 않는다.
7. 학교·권한 재조회 실패 때는 이전 학교 자료를 계속 보여 주지 않는다. 입력은 같은 범위 재검증 후 복구하고, 다른 학교로 넘어가면 이전 자료를 노출하지 않는다.

## 5. 결과 상태를 정확하게 설명한다

| 상태 | 화면 의미 | 하지 않을 일 |
|---|---|---|
| `invalid` | 입력·시수·참조·조건 형식 확인 필요 | 잘못된 입력을 적당히 고쳐 진행 |
| `unsupported` | 학교에 필요한 미지원 조건 있음 | 미지원 조건을 무시한 후보 제공 |
| `feasible` | 포함된 필수조건을 통과한 후보 | 최적·전국형·오류 0이라고 보증 |
| `unknown` | 계산 한도 내 후보를 찾지 못함 | 편성 불가능이라고 단정 |
| `infeasible` | 이 입력의 탐색을 끝냈지만 유효 배치 없음 | 시간이 부족한 경우와 혼동 |

기존 PR #5 `6595dbac`의 교사 변경 재현에서는 이전 배정이 새 정의로 해석되어 변경량·최소 증명이 잘못 보고됐고, 새 정의 기준 이전 배치 충돌이 편성 재시작까지 막았다. 이 코드를 통째로 병합하지 않았다. 향후 CP-SAT 최적화 엔진도 같은 입력/후보 계약과 독립 검증기를 거치며, 과거 후보의 기초판을 덮어쓰지 않는다.

탐색 상태 구분은 [OR-Tools의 해 상태 설명](https://developers.google.com/optimization/cp/cp_solver), 취소 방식은 [Worker 종료 API](https://developer.mozilla.org/en-US/docs/Web/API/Worker/terminate)의 의미를 참고했다. 새 브라우저 엔진은 OR-Tools를 사용하지 않는다.

## 6. Claude 연결 흐름

- 준비: ‘수요일 오후는 회의라 수업이 없어야 해요’ → 대상 교사·시각·기간을 질문 → 현재 ID로 고정/불가시간/선호 제안 → 사람이 확인 → 검증·재계산.
- 조정: 현재 유효 후보, 조건, 기초판, 질문을 함께 묶는다. 이전 제안 후 조건 하나라도 바뀌면 다시 검토한다. 이번 자동 제안은 필수조건 추가와 선호 설정까지만 지원하며 삭제/완화/교사배정 변경/공개/전송은 허용된 도구가 없다.
- 운영: 확정 수업의 영구 ID·날짜·판을 바탕으로 교환안을 제안한다. 상대 동의와 관리자 확정은 AI 발언으로 대신하지 않는다. 날짜별 운영 AI는 별도 승인 계약 구현 후 연결한다.
- 문서나 채팅에 있는 지시문은 자료로 취급한다. 서버는 승인된 학교 자료만 제공하고, 기존 Claude 단일 실행권·비용 예약/정산·결과 미상 재호출 금지를 재사용한다. 모델·토큰·API 키·요금 설정은 이번에 바꾸지 않는다.

상세 함수는 `apps/workhub/src/timetable/assistant.ts`. 현재 provider 호출이나 새로운 API 경로는 설치하지 않았다. 전달 형식만 마련해 놓고 실제 AI가 이미 운영 중이라고 안내하지 않는다.

## 7. 공개와 날짜별 변경의 완료 기준

[운영 설계](operations.md) 및 [SQL 전달 요청](sql-handoff.md)을 따른다.
기본 시간표는 유효기간을 갖는 판이며, 날짜별 수업은 안정된 ID로 유지한다. 공개 미리보기 이후 기초 자료·부재·자원·대상 수업이 바뀌면 확정을 거절한다. 수업 기록이 있거나 이미 실시한 날짜를 재편성으로 덮어쓰지 않는다.

교환 전 모든 영향 수업·교사·학급·교실과 시수 영향을 보여준다. 다자 교환도 한 묶음이다. 참여자의 동의는 제안 지문과 각 수업 판에 묶고, 내용이 바뀌면 동의를 다시 받는다. 요청자가 최종 승인까지 스스로 하지 못한다. 최종 저장 직전에 다시 충돌을 검사하고 이력·알림 원장과 함께 한 번에 기록한다.

## 8. 다음 구축 묶음과 검수 순서

1. **기초판 서버**: 학교 관리·수업 관리 기준을 편성용으로 변환. 주당시수·교시표·공간·학생 중첩 입력 UI, 관리자 승인과 미지원 판단. 이번 3개 RPC 및 실제 응답 대조.
2. **편성 품질**: 실제 학교를 비식별한 데이터로 시간/탐색량/유효율 측정. 교사 공강·연강·요일 균형 등 유형별 선호, 후보 비교, 잠금 유지. 기존 PR5를 재활용하려면 위 결함을 먼저 고치고 같은 회귀·validator로 평가.
3. **확정·공유 서버 연결**: 구현한 기간·영향 미리보기·교사 조회 화면을 실제 SQL에 연결. 확정판 atomic publish와 기존 수업 기록 보존·경합을 검증.
4. **교환 운영 연결·추가 유형**: 구현한 이동/두 수업 교환 화면의 동의·승인·반려·철회를 실제 서버에 연결하고 경합·알림/수업시수 원장을 시험. 대강·보강·다자 교환 작성 화면은 후속.
5. **Claude 실제 연결**: 현재 코드의 typed 계약을 기준으로 초기 세팅/조정/교환 에이전트 작업. 권한·근거·사용량·결과 미상 회귀 후 켠다.
6. **일괄 실사용 확인**: 사용자의 기존 요청대로 나중에 모아서 한다. 그전 자동검증은 가상자료·합성서버라는 경계를 유지한다. 모든 교사 공개와 main 병합은 사용자가 결정한다.

별도 서버의 배포나 SQL 실행 없이 이 단계들을 이미 끝냈다고 보고하지 않는다. 보류 중인 독립 파일 검사기·자동정리·예약 운영 작업은 시간표 보류 해제로 함께 재개되지 않는다.
