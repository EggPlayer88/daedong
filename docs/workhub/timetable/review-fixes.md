# 시간표 정책 확정과 PR #65·#66 보완 인계

사용자가 다섯 정책의 보완안을 승인했다. 이 문서는 앱 수정·SQL 작성 기준이다. SQL 적용·운영 활성화 완료를 뜻하지 않는다.

## 확정한 다섯 정책

| 항목 | 확정 내용 | Claude SQL 작성 시 지킬 점 |
|---|---|---|
| 주당 시수 | 시간표 담당자가 실제 시수를 확인해 준비 초안에 입력하고 편성 기준판에 고정한다. | 현재 DB에 없는 값을 이름·과거 시수로 추정하지 않는다. 공식 값이 생긴 경우 출처를 구분한다. 확정 뒤 변경은 새 기준판이다. |
| 공간 수용량 | `capacity`는 학생 정원이 아닌 **동시에 사용할 수 있는 수업 수**다. 공간별로 담당자가 확인한다. | 미입력을 1로 채워 계산하지 않는다. 학생 좌석 수 검사는 별도 계약 없이는 지원으로 표시하지 않는다. |
| 수업·학급 연결 | 담당자가 공식 수업과 공식 학급·집단 ID의 관계를 직접 확인한다. | 학생 수강 기록의 학급 문자열이나 비슷한 이름으로 연결하지 않는다. 유효기간과 같은 학교·학기 관계를 검사한다. 미완성 관계는 확정을 막는다. |
| 담당·승인 권한 | 초기에는 기존 `year.manage` 권한 보유자가 담당한다. | 자동 권한 부여나 일반 교사 공개를 하지 않는다. 영향을 받는 당사자의 동의, 요청자 본인 승인 금지, 반영 직전 판·권한 재검사는 유지한다. |
| 기존 제약 확장 | 기존 확정 SQL 파일을 수정하지 않고 **새 증분 SQL**로 필요한 제약을 확장한다. | R0 학기 기준판 자리와 P3→P8 알림 출처 제약을 별도 명시 단계로 변경한다. 적용은 사용자·Claude가 진행한다. |

다섯째의 정확한 대상은 R0 `terms_timetable_basis_pending`와 P3의 `notifications_source_check`(P8에서 cooperation 추가)다. 둘 다 R0에서 생긴 제약으로 설명하지 않는다. 학기 기준판은 같은 학교·학기의 실제 기준판만 연결할 수 있게 대체한다. 알림 출처는 기존 허용값과 cooperation을 보존하고 timetable을 추가한다. 기존 자료 보존 지문, 사전·사후 점검, 실패 시 변경 없는 중단, 되돌림 범위를 문서화한다.

## 수정 범위

- B-1: Python 계산 요청 검증·용량·인수의 실패를 해당 작업으로 격리한다. 식별자가 유효한 취소 표식은 손상된 요청 원문보다 먼저 처리한다.
- B-2: 브라우저 접수 전에 보관 100개·대기/실행 16개·용량을 검사한다. 서로 다른 요청도 큐 단위 접수 잠금을 사용한다. 이미 접수한 같은 번호 복구는 새 접수 한도로 막지 않는다. Python 조회·수동 정리는 초과 개수 때문에 막지 않는다.
- 추가 재현: 브라우저가 ready/cancel 파일을 만든 뒤 닫기 전의 빈 파일을 작업자가 읽어 전체 중단되던 경합을 수정했다. 미완성·식별 불일치 표식은 해당 요청만 보류하며 가짜 접수증·취소 완료를 만들지 않는다. 실행했을 가능성이 있는 손상 manifest는 계속 복구 대기 상태로 막는다.
- 문자 판정: Python/TypeScript가 U+0085·짝 없는 서로게이트·공백을 같은 기준으로 검사한다.
- 운영 화면: 미전송 입력 오류와 서버 응답 이상을 구분한다. 미리보기 만료 시 반영을 잠그고 입력을 보존한다. 재조회 후에도 거절 안내를 유지한다.
- 출력: 현재 수업 판과 일치하는 교환을 표시하고, 변경됐으나 상세 이력이 없으면 그 사실만 표시한다. 명세·조회 시간대가 다르면 확정하지 않는다.
- AI 조건: 기존보다 약한 선호 제안은 강도를 낮추지 않는다. 기존값·반영값, 동명 ID, 고정/불가의 사전 충돌을 보여 준다.
- 부분 배치: 유효한 이전 완성판이 있으면 비교에 사용한다. 없으면 변경 최소화 비교가 없다는 명시 확인 전에는 계산하지 않는다.
- 통합 CI 후속: 부분 배치의 확인을 당시 입력 지문에 묶어 조건이 바뀐 첫 렌더부터 무효화한다. 효과 처리만으로 뒤늦게 확인을 해제하던 경합을 보강했다. 화면 시험은 렌더 완료를 기다려 미확인 상태와 새 요청 차단을 함께 확인하며, 설정을 되돌려도 이전 확인은 재사용하지 않는다.
- 로컬 계산기: 알려진 Finder 표식·자체 임시 파일, PID 재사용을 다룬다. 기록한 프로세스 생성 토큰 불일치와 담당자의 종료 확인이 모두 있어야 재사용 PID에서 복구하며 임의 프로세스를 종료하지 않는다.

브라우저와 CLI를 같은 큐의 동시 접수자로 섞는 것은 지원하지 않는다. 브라우저 탭끼리와 CLI끼리의 접수는 각각 직렬화하며 실제 실행 전 Python 한도 검사를 유지한다. 과거 PID 생성 토큰이 없고 해당 PID가 살아 있으면 추측으로 해제하지 않는다.

| K-5 | 1회 전체 확정 한도는 **100,000행·500쪽·쪽당 최대 200행**, 미리보기 최대 15분이다. 기존 신원 재확인을 유지한다. 한도 초과는 날짜 범위를 나눠 새 미리보기를 요청하며 일부 목록을 완료로 반환하지 않는다. |

## K-5 측정

`scripts/benchmark-workhub-timetable-publication.mjs`는 실제 앱 연결 어댑터·프로필 재확인·해시 parser·전체 페이지 검증을 사용한다. 프로필 조회 3회와 페이지 RPC 1회 각각에 합성 지연을 넣는다. 실제 Supabase 왕복이나 학교 규모별 서비스 응답시간 측정은 아니다.

Windows, Node 24.15.0, 쪽당 200개 합성 수업, 실제 시계로 측정했다. 개발·시험 프로세스가 함께 실행되는 환경이었다. 기존 한도 검증 경로를 메모리에 불러온 뒤 아래 세 측정을 실행했으며, 서버 호출은 전부 합성이다.

| 변경 수·쪽 수 | 각 프로필/RPC 지연 | 경과 | 결과 |
|---|---:|---:|---|
| 250,000개·1,250쪽 | 50ms | 452.840초 (7분 32.8초) | 완료. 프로필 3,750회 / 페이지 1,250회 |
| 250,000개·1,250쪽 | 200ms | 900.915초 | 901번째 페이지 조회 후 만료되어 CONFLICT. 전체 완료 아님 |
| 100,000개·500쪽 | 200ms | 493.271초 (8분 13.3초) | 완료. 프로필 1,500회 / 페이지 500회. 기한 약 406.7초 남음 |

이 결과로 **신원 확인 횟수는 줄이지 않고** 최종 한도를 100,000개·500쪽으로 낮췄다. 이 경로는 1,250쪽에서 페이지당 4번의 200ms 지연만으로도 1,000초가 필요하므로 최대 15분 수명에 맞지 않는다. 모든 회선에서 15분 내 완료한다는 보장은 하지 않는다. 최종 코드에는 만료 응답을 진행률에도 포함하지 않는 검사를 추가했고, 실제 지연을 넣은 짧은 회귀 두 건으로 전체 npm 검사에 포함했다. 전체 한도를 넘기는 명세와 501쪽 명세의 거부도 검사한다.

현재 한도를 재현하는 명령: `node scripts/benchmark-workhub-timetable-publication.mjs --pages 500 --delay-ms 200`. 과거 1,250쪽 결과는 한도 축소 전 기록이며 현재 앱은 그 크기를 입력 단계에서 거부한다. 실제 Supabase 지역·혼잡·교사 PC에서의 처리 시간은 별도 운영 확인이다.

## 자동 검증 기록 (#65 수정)

- 최종 전체 `npm test`: **3,662건 통과 / 실패 0 / Python 생략 없음**. 실제 Python 큐 42건, TS 접수 24건을 포함한다.
- 시간표 브라우저 22파일을 실행했다. 처음 전체 실행은 20통과·2실패였다. 기존 공개 화면의 중복 오류 배너는 부모 안내를 학사 변경에 한정해 수정한 뒤 공개 16·전체 확정 14·학사 변경 11건을 재통과했다. 실제 Worker 시간초과는 계산 제한을 바꾸지 않고 단독 경로 2건을 재통과했다. 따라서 22파일의 경로가 모두 재확인됐으나, 한 번의 전체 실행이 모두 초록이었다고 기록하지 않는다.
- 타입 검사·메인/업무실 빌드·시간표 보호 범위·패치 공백 검사 통과.
- 중간 전체 npm에서는 새 경합 보류 동작에 맞추기 전의 위조 취소 시험 기대값이 실패했다. 최종에는 직접 CLI 거절과 worker 보류를 각각 단언하고 전체 3,662건을 다시 통과했다.
- K-5는 위의 세 장시간 측정 외에 실제 앱 어댑터의 짧은 지연·만료 회귀를 전체 npm에 포함했다. #66 병합 후 전체 결과와 CI는 해당 PR 설명과 완료 보고에 별도로 기록한다.

## Claude 재검토와 남은 연결

**정책 확정과 입력 화면 구현을 구분한다.** 현재 준비 화면은 시수·시간대·수업 블록을 편집하지만 공간 목록·동시 수업 수, 수업→공식 학급 ID를 편집하는 화면/쓰기 RPC는 아직 없다.

- `PreparationDraft`는 title/slots/plans만 허용하며 resources·course.resourceIds는 원본 조회 자료다. 공간 capacity의 null은 현재 source parser에서 허용하지 않는다.
- 공식 학급 ID 등록은 있어도 수업과 그 학급을 연결하는 명령이 없다. 학생의 `classLabel` 문자열로 자동 연결하지 않는다. Excel의 대상 목록도 참고용이며 변경 업로드는 거부한다.
- T1이 완성된 source를 반환하면 편성할 수 있지만, 이를 곧 담당자가 필요한 모든 정보를 사이트에서 입력할 수 있다는 뜻으로 보고하지 않는다. T1 저장 모델과 함께 공간/동시수업수·수업/학급 연결의 **미완성 조회·담당자 입력·검산·판 고정 계약 및 화면**을 후속으로 연결해야 한다. SQL이 임의의 capacity=1이나 이름 추정 매핑으로 빈칸을 숨기면 안 된다.

1. #65 최신 수정과 이를 merge한 #66의 최종 커밋을 검토한다. 앱 브랜치는 Codex가 유지한다.
2. 다섯 정책과 K-1~5를 기준으로 T1·T2 SQL을 작성하고 실제 응답을 최신 앱 parser와 대조한다.
3. R1S/P1~P8의 설치·활성화 상태를 구분한다. #64 기반 설치를 마친 뒤 시간표 증분 SQL을 적용한다.
4. 코드 병합은 사용자, SQL 작성·적용 안내는 Claude, SQL 실제 적용은 사용자에게 있다.
5. 이후 관리자 한정으로 준비→계산→확정→공유/일정→교환 신청→당사자 동의→담당 승인→날짜별 반영을 실제 Supabase에서 확인한다.

실제 Claude 에이전트 호출·비용 설정, 운영 Supabase/Storage 왕복, 교사 PC Excel/인쇄, 일반 교사 공개는 이 수정의 자동 검사로 완료했다고 판단하지 않는다. 별도 검사기 서버와 보류한 운영 자동화도 다시 켜지 않는다.
