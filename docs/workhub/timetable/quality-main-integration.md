# #135 최신 main 통합 검증

2026-11-25 · `feat/timetable-quality-portfolio` · 통합 전 `68faff46`

`origin/main`의 `de5a0de186018a6c027f0b22cb61725f89062b71`(#136 병합)을 merge했다. rebase와 force push는 사용하지 않았으며 기존 미추적 자료는 삭제하거나 이동하지 않았다.

## 보존한 변경

- #135의 품질 우선 탐색, 후보별 독립 평가·다양성 검사, 기존 변경 최소 모드와 저장 요청 복원, 명시적인 후보 채택을 유지했다.
- #136의 Windows 독점 파일 게시(`rename`), POSIX의 `link`, 일반 `replace`, 기존 대상 덮어쓰기 거부와 링크 경로 차단을 유지했다.
- `Popen` 시작 실패의 `ENGINE_START_FAILED`, 파일 작업 실패의 `FILE_ACCESS_FAILED`, 자식 종료·상태 기록 미확인 시 복구 대기와 다음 계산 차단을 유지했다.
- 자동 병합된 로컬 계산 화면에는 품질 모드의 조회 간격과 파일 오류 안내가 함께 남았다. 브라우저 시험의 작업 접수증 진단도 유지했다.

## 실행 결과

| 검사 | 결과 |
|---|---|
| 실제 Windows 로컬 계산 브라우저 | 21건 통과 |
| 품질 후보 파일 왕복·비교 브라우저 | 16건 통과 |
| 최초 전체 `npm test` | 270파일 실행: 269파일 통과, 작업자 시험 1파일 실패 |
| 원자 저장 / 품질 탐색 / 기존 CP-SAT | 최초 전체 실행에서 10 / 19+35 / 29건 통과 |
| 짧은 QA 임시 경로의 작업자 재검사 | 59건 모두 통과 |
| Workhub 타입 검사 | 통과 |
| main / Workhub 빌드 | 모두 통과 |

최초 실패는 실제 비동기 작업자가 계산하기 전 `request.snapshot.json`을 준비하는 단계였다. 오류 분류는 `FILE_ACCESS_FAILED`, 접수증은 `sequence:1`, `startedAt:null`이었다. 독립 진단에서 원자 저장용 임시 파일의 경로 길이가 265자였고 `FileNotFoundError(errno=2)`가 발생했다. 이번에 길게 지정한 QA 폴더명을 기존 `qa-temp`로 줄여 같은 제품 코드로 작업자 전체 59건을 통과했다. #136의 `WinError5`와 동일한 오류로 취급하지 않는다.

시험의 성공 기대값과 5초 계산 조건은 유지했다. 작업자 실패 단언에는 접수증과 작업자 진단만 추가했다. 제품 런타임, Windows 권한·보안 설정, 원본 보존·종료 확인 정책은 변경하지 않았다. 최초 전체 실패와 작업자 재검사는 별도 결과이며, 이를 새 전체 실행 한 번의 통과로 합쳐 표현하지 않는다. 최종 통합 전체 시험과 원격 CI 결과는 후속 통합 검증에서 확인한다.

운영 데이터·운영 DB·유료 AI를 사용하지 않았고 SQL·모델 비용 구조·공개 범위를 변경하지 않았다. 로컬 계산기는 긴 임시 경로가 겹치지 않도록 짧은 전용 작업 폴더를 사용해 검증했다.

## 판단해서 정한 것

최신 main의 저장소 보완과 #135의 탐색을 각각 유지하는 일반 merge를 사용했다. 자동 병합에 별도 제품 수정을 추가할 필요는 없었다. 실패 원인 판별에 필요한 최소 진단은 `tests/test_timetable_jobs.mjs`의 첫 비동기 작업자 단언에 두었다.
