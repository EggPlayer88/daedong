## 1. 담당자가 사용하는 순서

학교 준비 입력 → 시수·교시 구성 → 기준판 확정 → 조건 수집·검토 → 생성 → 후보 보관·비교 → 조정·독립 검사 → 서버 초안 저장 → 적용 기간·전체 영향 검토 → 명시 확정 → 공유·교환·학사 변경.

이번 묶음은 이미 있는 계약과 기능 사이의 연결을 완성한다. 화면 이동·후보 보관·AI 도움 열기만으로 저장·유료 호출·학교 공개를 실행하지 않는다. 계산 성공과 최적해 보장, 서버 저장과 학기 확정을 각각 구분한다.

## 3. 앱 구조와 확장 방식

- `flow.ts`는 다음 행동과 저장 접수증 연결을 계산하는 순수 함수다. UI는 `TimetableFlowGuide`에서 표시하고 실제 명령은 기존 Workspace·서버 어댑터가 수행한다.
- 후보 보관·검증은 `candidate-library.ts`, UI는 `TimetableCandidateLibrary`, 한도는 `_assets/candidate-library-policy.json`으로 나눈다. 서버 후보 저장 API를 추가할 때 이 경계를 재사용할 수 있다.
- `condition-review.ts`는 원본 조건의 인덱스를 유지한다. 검색·쪽 이동 결과의 인덱스로 다른 조건을 삭제하지 않는다.
- `operation-review.ts`는 변경의 검색·요약만 담당한다. 원래 서버 미리보기와 승인 명령은 바꾸지 않는다.
- 지연 로딩을 유지한다. 편성 화면에서 공개되지 않은 운영 자료를 추측해 만들지 않는다.
- 학교/소속/권한 범위가 바뀌면 기존 공통 초안 저장소·복구 범위에 따라 입력을 분리한다. 후보는 추가로 학교·학기 범위에 묶는다.

## 4. 데이터 보존과 한계

1. 후보와 입력은 **현재 탭 메모리**다. 브라우저 종료 후 복원이나 서버 동기화를 약속하지 않는다. 필요한 편성은 서버 초안 저장 또는 기존 XLSX 내려받기를 사용한다.
2. 부분 배치는 조정 화면에서 이어서 작업할 수 있으나 완료 후보 보관·서버 저장·확정에는 전체 검사를 요구한다.
3. 동일 조건의 후보끼리만 점수를 비교한다. 조건을 바꾼 이전 후보는 참고용 차이만 표시하고 그대로 채택하지 않는다.
4. 최적화 엔진의 결과를 채택할 때에도 현재 조건과 작업 고정을 독립 검사한다. 거부하면 기존 계산 응답을 지우지 않는다.
5. 확정 화면 연결은 현재 저장 초안 번호·판을 전달할 뿐이다. 기간·영향·권한·서버 준비·승인은 기존 절차에서 다시 검사한다.
6. 전체 학기 명세는 기존 페이지 조회/전체 검증을 유지한다. 화면의 현재 페이지 검색 결과를 전체 변경 수로 표시하지 않는다.
7. 이미 main에 들어간 T1 파일은 그대로다. 보호 검사의 기준만 #69 main으로 옮기고 #68/#69 포함 이력을 검사한다. `database/`를 예외로 풀지 않는다.

## 5. 검증

최종 수치와 실행 환경은 [검증 기록](flow-verification.md)에 기록한다. 브라우저는 실제 React·RPC 어댑터·파서와 합성 서버 응답을 사용한다. 계산은 실제 JS 알고리즘과 별도의 기존 Python/OR-Tools 회귀로 검사한다. 새 통합 동선 시험의 Worker 전달은 합성이다. 실제 Web Worker 회귀도 별도로 유지한다.
