# 3차 통합 후보 — P8 및 SQL 실행 경계 검토

2026-10-16 · Codex 읽기 전용 검토. SQL 기준은 Claude PR #61 `edd743f`, 앱 기준은 PR #63 `ed9ea32`이며 두 이력을 합친 후보 `1c46d02`에서 확인했다. SQL 원문·기존 회원·운영 설정은 변경하지 않았다. **1~8단계 전체 SQL의 완전한 감사나 운영 DB 적용 승인은 아니다.**

## 판단

- 검토한 P8 정책 SQL의 주요 변경 경로에서 새로 확정한 데이터 손상·권한 우회·C8 재발 결함은 없다. 아래 실행 안내 정정 2건은 실제 적용 안내를 전달하기 전에 반영해야 한다.
- 코드 통합 검토와 운영 SQL 설치·활성화는 별개다. 운영 기준선 `INT-03`·`R1-04` 결과를 아직 받지 않았으므로 **운영 설치 검증 완료로 표시하지 않는다**.
- Claude의 `2,309 / 0`, 옛 SQL `1,993 / 0`, P8 `322 / 0`은 `database/workhub/integration/재검토_PR63.md`에 기록된 결과다. 이 독립 검토에서는 SQL 시험을 중복 실행하지 않았으며, 통합 후보의 자동 실행 결과는 별도 검증 기록을 따른다.

## Claude에게 정정 요청할 내용

### S1. ‘비활성 설치는 기존 동작에 영향이 없다’는 포괄 문구 정정

근거:

- `database/workhub/integration/통합_실행안내.md:9`는 모든 새 함수가 `NOT_READY`이고 설치만으로 화면이 바뀌지 않는다고 적는다. 같은 문서 `:77`도 이미 설치한 단계는 화면에 영향이 없다고 적는다.
- 실제 `database/workhub/p8/P8-01_학년도_시작연도.sql:98`와 `:248`은 새 학년도 생성 두 경로에 즉시 시작 연도 검사를 추가한다.
- `database/workhub/p8/P8-03_업무인계_관리자확인.sql:204`, `:232`, `:322`, `:436`은 설치 직후 공식 담당 자원을 숨기고 새 신청·미리보기·수락을 관리자 확인 모듈 활성화까지 막는다.
- 관계 조회·변경은 `database/workhub/p8/P8-04_수업_담당수강_변경.sql:641`, `:721`처럼 `UNAVAILABLE`을 돌려주므로 ‘모든 새 함수가 NOT_READY’도 정확하지 않다.

영향: 사용자가 ‘설치만 하는 날에는 기존 업무 동작이 전혀 달라지지 않는다’고 판단할 수 있다. 현재 운영에 P7이 아직 없어 즉시 발생할 인계 자료는 없지만, 재사용할 실행 안내에는 이 전제를 분명히 해야 한다.

요청: 서두와 중단 안내에 **설치는 새 모듈을 자동 활성화하지 않지만 Q4와 공식 담당 인계 보호는 즉시 적용된다**고 적는다. 이미 준비된 기능의 조회·원장 재생까지 일괄 `NOT_READY`로 묶지 않는다. SQL 로직은 이번 지적으로 수정할 필요가 없다.

### S2. 적용 파일과 배포 확인 기준을 최신 통합 후보로 고정

근거:

- `database/workhub/integration/통합_실행안내.md:19`는 `INT-03`을 PR #58 head에서 받으라고 안내한다. 현재 P8 포함 기준선은 PR #61/이번 통합 후보의 파일이다. #58 판을 받은 뒤 같은 파일로 P8 설치 후 점검까지 계속하면 새 객체가 예상 목록에 없어 잘못된 실패 판정을 받게 된다.
- 같은 문서 `:97` 및 `database/workhub/p8/P8_실행안내.md:38`은 C8 수정 전 상태를 현재 실행 조건처럼 유지한다.
- `database/workhub/p8/P8-06_정책모듈활성화_양식.sql:4`, `:10`, `:27`, `:39`는 ‘PR #60 이상’을 배포 확인 기준으로 적지만, #60·#62만 배포한 것은 C8 수정이 아니다. 최신 판단은 `database/workhub/integration/재검토_PR63.md` 5절에 있다.

영향: 승인한 SQL과 다른 판의 점검 파일을 사용할 수 있고, 업무 전환 활성화에 필요한 C8 수정 배포를 빠뜨릴 수 있다.

요청: 실행 패키지의 **PR·커밋·파일 해시**를 하나로 고정한다. 업무 전환의 앱 배포 근거는 ‘#63 `ed9ea32`의 C8 수정이 포함된 통합 후보’로 적고, ‘C8 미해결’은 이전 검토 이력으로 분리한다. `app_deploy_ref`는 실행자가 확인한 배포 근거를 남기는 칸이며, 문자열을 입력했다고 서버가 GitHub/Vercel 배포 내용을 자동 증명하는 것은 아니다. 원본 SQL의 주석·입력 안내 변경은 Claude가 담당한다.

## 남아 있는 구현 경계

1. 담당 교체의 겹침 판정은 SQL이 **원래 기간**, 앱이 유효 기간을 사용한다. 과거 종료했던 교사를 원래 기간 안에 다시 배정하려 하면 SQL이 더 엄격하게 거절할 수 있다. `P8_설계_계약.md`에 이미 적힌 제한이며 이번 검토의 새 결함으로 세지 않았다. 이를 풀려면 기존 겹침 제약과 이력 보존 정책을 함께 설계해야 한다.
2. 운영 DB 기준선, 실제 PostgREST 오류 변환, 실제 Storage 전송, 실제 Supabase 동시 요청은 이 읽기 전용 검토 범위 밖이다. 로컬 SQL 성공이나 합성 브라우저 성공으로 대체하지 않는다.
3. C7·D1~D10 비용 결정 전 비서 활성화, 일반 교사 공개, 운영 예약·자동 정리, 시간표 DB 설치는 이번 SQL 검토 승인 범위가 아니다.

## 다음 검토·적용 순서

1. Claude가 이번 통합 후보의 앱 변경을 확인하고 S1·S2 실행 문구를 정정한다. SQL 변경이 생기면 변경 범위와 회귀 결과를 따로 확인한다.
2. 사용자가 최신 패키지의 `INT-03`·현재 R1용 `R1-04`를 읽기 전용 실행하고 결과를 저장한다. 실패하면 앞 단계 재실행이나 되돌림 대신 차이를 조사한다.
3. 사용자가 승인한 순서로 R1S→P1~P7→별도 P7-05→P8을 설치하고 단계별 지문·사후 점검을 보존한다. 이는 자동 활성화나 일반 교사 공개가 아니다.
4. 검토된 통합 앱 배포를 확인하고 비용 보류 비서를 제외한 모듈을 각 조건에 따라 승인한다. 이어 실제 연결·화면·파일·복구를 묶어서 확인한다.
