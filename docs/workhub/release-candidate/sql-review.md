## 운영 안내에서 Claude가 정리할 문구

SQL 로직의 추가 결함은 아니며, 다음 실제 실행 안내에서 아래 두 점을 명확하게 한다.

1. `운영_마무리_안내.md` 단계 3의 공통 순서는 P8에 그대로 적용하지 않는다. **P8은 00→01→02→03→04→05→00**이다. 04는 관계 설치, 05는 사후 점검이다. `통합_실행안내.md` 2절의 P8 줄과 `P8_실행안내.md`가 정확한 기준이다.
2. HWPX는 **운영 API 배포·서버 설정 → 활성화 전 NOT_READY 등 보호 응답 확인 → 승인받은 관리자 범위 활성화 → 실제 업로드·검사·제출/전송·다운로드 왕복 확인**으로 구분한다. 활성화 전에 성공 왕복까지 요구해 진행이 서로 막히지 않도록 통합 안내 문구를 맞춘다.

수합·메시지 최소 검사 API는 이미 있다. 남은 일은 운영 Vercel 배포와 `SUPABASE_SERVICE_ROLE_KEY`의 Production 서버 변수 설정, 위 실제 왕복 확인이다. 별도 검사기 서버 `R1-05`는 계속 보류한다. 이 두 문서 정정은 Claude 브랜치에서 맡으며, 이번 Codex 작업에서는 운영 설정·SQL 실행·기능 활성화를 하지 않는다.

## 남아 있는 구현 경계

1. 담당 교체의 겹침 판정은 SQL이 **원래 기간**, 앱이 유효 기간을 사용한다. 과거 종료했던 교사를 원래 기간 안에 다시 배정하려 하면 SQL이 더 엄격하게 거절할 수 있다. `P8_설계_계약.md`에 이미 적힌 제한이며 이번 검토의 새 결함으로 세지 않았다. 이를 풀려면 기존 겹침 제약과 이력 보존 정책을 함께 설계해야 한다.
2. 운영 DB 기준선, 실제 PostgREST 오류 변환, 실제 Storage 전송, 실제 Supabase 동시 요청은 이 읽기 전용 검토 범위 밖이다. 로컬 SQL 성공이나 합성 브라우저 성공으로 대체하지 않는다.
3. C7·D1~D10 비용 결정 전 비서 활성화, 일반 교사 공개, 운영 예약·자동 정리, 시간표 DB 설치는 이번 SQL 검토 승인 범위가 아니다.
