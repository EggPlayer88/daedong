## 실제 브라우저에서 확인한 흐름

1. 학교 전체 열람과 홈 추천 분리, 다른 교사의 개인·지정 대상 일정 비노출.
2. 일정 등록 → 대상 미리보기 → 작성자 홈 반영.
3. 원본 ID 확인 → 수정 충돌 → 입력 보존 → 변경 확인 후 새 버전 반영.
4. 조회 실패 안내 → 다시 불러오기 성공.
5. 빈 목록 안내 → 자료 표시 복구.
6. 저장 실패 → 입력 보존 → 같은 입력 재시도 성공.
7. 다른 관련 교사의 홈 반영 및 학교 전환 시 타학교 자료 비노출.
8. 소속 종료 후 조회 거부와 등록 버튼 차단.
9. 새로고침 시 실제 합성 자료 초기화.
10. 모바일 편집 창의 폭, Escape 닫기와 호출 버튼 초점 복구.
11. 페이지 오류·외부 서비스 요청이 없는지 확인.

단일 HTML은 개발 화면을 검토하기 위한 별도 산출물이다. **새 앱의 일반 운영 빌드와 다르다.** HTML은 합성 자료와 개발 조작을 포함하고, 일반 빌드는 업무 동작을 포함하지 않는다. 미리보기 파일을 운영 배포 파일로 사용하지 않는다.

## 통과 범위의 한계

- HWPX 생성은 로컬 Python 실행 증거다. 한글 프로그램의 육안 검수, 새 Vercel Root의 함수 패키징, 새 인증 아래 생성 요청은 별도 검증 대상이다.
- 메모리 어댑터의 학교·소속·권한 사례는 계약 시뮬레이션이다. 서버 인증, RLS, 실제 다중 세션·트랜잭션, 권한 회수 후 캐시·파일 URL 차단을 증명하지 않는다.
- 현재 기존 앱 메뉴·배포 설정·DB·키·모델·보호 엔진의 코드는 바꾸지 않는다. 신규 기능의 운영 공개는 이번 검증에 포함되지 않는다.
- 기존 의존성 진단 `BASE-DEP-001`은 [기준선 문서](00-baseline.md)에 기록한다. 기능 시험 통과와 의존성 진단 해소는 별개다.
