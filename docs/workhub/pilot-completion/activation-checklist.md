# 실제 활성화와 나중에 모아서 할 사용 확인

2026-10-16. 앱 코드의 자동 시험과 실제 서비스 확인을 구분한다. 사용자의 요청대로 지금 실사용 시험을 재촉하지 않는다.

## A. 코드 검토·배포 준비

1. Claude가 통합 앱 PR과 각 RPC 계약을 검토한다. 수정사항 반영 후 같은 최신 커밋의 CI·Vercel 빌드를 확인한다.
2. 사용자가 merge commit으로 병합한다. 원본 #43·45·46 이력 포함을 확인한 후 중복 앱 PR을 정리한다. #47 SQL은 별도 검토/적용 이력이다.
3. 기존 Google 로그인·회원 승인·평가계획 제출의 경로/자료를 보존한다. 신규 업무실의 superadmin 제한은 유지한다.
4. Vercel 함수 includeFiles에 collection helper·새 메시지/문서/AI 파일이 포함되는지 실제 배포에서 확인한다. 새 서버는 만들지 않는다.

## B. SQL·외부 설정 담당자가 수행할 단계

- [SQL 인계](sql-handoff.md) 순서로 Claude가 작성·시험하고 계란님이 직접 적용한다. R0/R1 기존 설치를 재실행하지 않는다.
- 브라우저용 기존 Supabase URL/anon 설정과 서버용 프로젝트가 일치하는지 확인한다. 서버 전용 `SUPABASE_SERVICE_ROLE_KEY`는 브라우저 번들/공개 VITE 변수에 넣지 않는다.
- 서버에서 읽는 `SUPABASE_URL`(또는 기존 `VITE_SUPABASE_URL`)은 의도한 프로젝트와 대조한다. 운영 키 본문을 문서·채팅·로그에 복사하지 않는다.
- `ANTHROPIC_API_KEY`·모델/가격/일월예산은 사용자가 승인한 설정만 적용한다. 기존 평가계획 AI의 모델·키·한도를 임의 교체하지 않는다.
- 파일별 크기/개수·보존·정정 기간, 지식 게시권, 학생 상담권, 일반 교사 소속/메뉴 공개를 확정한다. 미정 정책은 NOT_READY 상태로 남긴다.
- R1S 기본 확인 경로를 열기 위해 보류한 R1 작업자 연결이나 `allowUnscanned=true`를 대신 사용하지 않는다.

## C. 실사용 확인 묶음

| 묶음 | 확인할 실제 동선 | 통과 증거 |
|---|---|---|
| 기존 기능 보존 | Google 로그인·기존 회원/승인·평가계획서/기존 제출/파일 | 전후 지문과 기존 파일 실제 열기 |
| 학교·권한 | 관리자·교사·승인대기·다른 학교·소속종료 | 의도한 자료만 조회, 허가 없는 쓰기·URL 차단 |
| 일정·업무·협업 | 생성/수정/수락/완료, 시트 중복과 충돌 | 재로그인 후 실제 DB 자료, 같은 요청은 1회 |
| HWPX 수합 | 원본 배부→답변/파일→기본 확인→최종 제출→보완/정정→ZIP | 실제 Storage SDK, 원본 해시·대상·판, 마감 뒤 새 제출 차단 |

| 모바일·장애 | 390/320 화면·키보드·재조회실패·전송후 응답단절 | 입력/원키 유지, 다른 메뉴 회복, 가로넘침 없음 |

## D. 공개 판단

자동 시험 전부 통과, 실제 주요 동선 통과, 미해결 중대 결함 없음, DB/정책/키/회원 연결 확인 후 일반 교사 공개를 별도 승인한다. 그때의 완료율은 코드·연결·실사용 결과를 함께 평가한다. 지금의 시험 건수를 최종 목표의 90%로 환산하지 않는다.

문제가 생기면 해당 모듈 새 쓰기만 비파괴 중지하고 기존 결과 조회·자료 보존을 우선한다. destructive rollback을 앱 롤백의 자동 절차로 사용하지 않는다.
