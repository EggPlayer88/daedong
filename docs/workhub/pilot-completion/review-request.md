이번에는 작은 앱 PR을 추가로 나누기보다, [14개 작업 묶음 상태표](README.md)를 기준으로 기능 간 연결과 오류 처리를 함께 검토해 주세요.

## 우선 검토할 부분

1. **공통 입력/복구**: 계정·학교·소속·역할 변경, 배경 재조회 실패, 시간초과 후 늦은 응답, 원래 request key와 명령의 보존, 모듈 오류 격리. 입력 보존은 현재 탭 메모리이며 브라우저 종료 이후 복원을 약속하지 않습니다.
2. **학교/교사 관계**: 학급·부서·담당의 유효기간, 자기 입력과 공식 배정 구분, 전체 충돌 필드 비교, 승인 정보 변경 후 이전 자료 비노출.
3. **수합과 문서**: 마감/재개 상태, HWPX 검사 실패와 서버/다운로드 실패 구분, 원본 ID·hash·판·임대 고정, 질문형 생성물의 명시 첨부 및 최종 제출, 기존 파일 다운로드 보존.
4. **메신저/협업**: 수신 대상 최종 확인, 변경된 대상 재확인, 결과 미상 시 중복 전송 방지, 읽음/완료요청/완료확정 구분, 첨부 private 접근.
5. **학생·평가·CSV**: 상담 분리, 실제 수업관계, 평가 당시 기준판, 원문 정정과 sourceReviewRequired, 학생 초안의 revision/hash/epoch/구간, 잘못된 학교/학생 근거 차단.
6. **학교 자료/Claude**: 원본 추출과 정리본의 구분, 초안/게시/유효기간, 실제 근거 인용, 단일 start권·비용 예약/정산, provider unknown 후 자동 재호출 금지, AI 제안만으로 실제 전송/제출이 되지 않는지.
7. **인계·학년도**: 선택한 범위만 미리보기→확인→수락, 오래된 fingerprint/판 거절, 개인 상담/메시지/사적 학생 기록 미이관.
8. **확장성·운영**: UI/계약/어댑터/API 분리, 지연 로딩, 없는 RPC가 기존 일정/업무를 막지 않는지, 비활성화해도 기존 결과를 조회하는 계약.

[검증 결과](verification.md)에 통과 건수와 합성 서버/실제 서비스 경계를 적었습니다. 브라우저 시험은 실제 React와 전송 어댑터를 사용하지만 DB/Storage/provider 응답은 합성입니다. 실제 운영 연결 성공으로 평가하지 말아 주세요.

## SQL 작성 요청도 함께 드립니다

[통합 SQL 요청서](sql-handoff.md)의 의존 순서와 모듈별 exact 계약을 기준으로 증분 SQL을 작성해 주세요. 초안 응답 JSON을 먼저 현재 앱 parser와 대조하면 SQL 완성 뒤의 계약 불일치를 줄일 수 있습니다. 기존 R0/R1은 재실행하거나 고치지 않습니다.

R1S #47 `884056f`를 현재 앱과 격리 PostgreSQL 17.6에서 대조한 결과는 **410/411**입니다. 남은 L44는 짧은 다운로드를 현재 앱이 `RESULT_UNKNOWN`/finish 없음으로 보존하는 반면 시험이 영구 rejected를 기대하는 차이입니다. 기존 정상파일을 네트워크 단절 때문에 영구 거절하지 않으려는 변경입니다. 기대값/운송완료 판정 기준을 검토하고 새 회귀로 고정해 주세요. `.sh` CRLF 때문에 시험 사본의 셸만 LF로 보정한 점도 원본에서 정리해 주세요. SQL 원문을 수정하거나 운영 DB에 적용하지 않았습니다.

## 답변 형식

- 실제 사용을 막는 문제: 재현 조건·파일/함수·데이터 영향·권장 수정.
- SQL 계약이 빠졌거나 충돌하는 곳: 앱 parser와 다른 필드/판/권한·원자성.
- 단순 사용성 제안: 시범 사용 전 필수인지 이후 개선인지 구분.
- 코드 병합 판단과 실제 DB 활성화 판단을 별도로 기록.

보류한 시간표·독립 검사기·자동 정리·운영 예약 작업을 이번 검토 완료 조건에 다시 넣지 않습니다. 자동 병합·SQL 실행·일반 교사 공개도 하지 않습니다.
