# C8 기존 인계 처리와 원요청 복구 수정

2026-10-16. 기준은 앱 PR #62 `8f6847ccfc24dbbf3b37595e576ac0bcf0cc4c34`, 작업 브랜치는 `fix/workhub-transition-recovery`다. Claude PR #61의 C8 지적에 따라 앱을 수정했다. SQL 파일·운영 DB·인증·메뉴 공개 범위·비서 비용은 변경하지 않았다.

## 이번 수정

이전 앱은 관리자 확인 기능이 없는 구 목록이나 `dutyApproval:null` 상태에서 협업·수합 인계의 인수·반려까지 막았다. 이미 보낸 요청을 같은 번호로 복구할 때도 현재 목록을 먼저 조회해 막혔다. 기존 서버가 처리할 수 있는 요청이 앱에서 `NOT_READY`로 끝나는 결함이다.

| 경우 | 수정 후 동작 |
|---|---|
| 구 목록의 협업·수합 인수·반려 | 서버의 `canAccept`와 현재 판으로 버튼·최종 확인을 판단하고 원래 RPC로 처리 |
| 새 목록이지만 관리자 확인 모듈 중지 | 일반 인계 인수·반려와 요청자 취소 유지 |
| 공식 담당의 새 신청·인수 | 관리자 확인 준비 조건 유지. 확인되지 않은 공식 인계는 인수 불가 |
| 새 관리자 확인·반려 | 모듈 준비·관리 권한·요청자 자기 확인 차단 유지 |
| 공식 담당 요청의 수신자 반려·요청자 취소 | 서버가 허용하는 기존 요청 정리 경로 유지 |
| 결과를 모르는 요청의 복구 | 현재 목록 조회 없이 원래 명령·번호를 재전송하고 접수증 검증 |
| 다른 페이지의 기록 | 새 인수·관리자 명령 전에 다음 페이지까지 조회. 첫 페이지에 없다는 이유로 차단하지 않음 |

`transitions.ts`에 처리 판단을 모았고 화면 버튼과 최종 확인이 같은 함수를 사용한다. 목록 탐색은 반복 커서와 자산에 둔 50페이지 한도에서 중단한다. 목록 끝까지 기록이 없으면 쓰기 서버가 존재·현재 권한·판을 최종 판단한다.

입력과 미확정 요청은 기존처럼 현재 탭 메모리에 보관한다. 학교·계정 범위 변경은 격리하며, 같은 번호에 다른 명령을 넣거나 다른 기록·판·상태의 접수증을 성공으로 받아들이지 않는다. 브라우저 종료 뒤의 영속 복구는 이번 범위가 아니다.

**복구는 읽기 전용이 아니다.** 원장에 접수증이 있으면 그 결과를 되받는다. 접수증이 없으면 사용자가 이미 확인한 원명령을 서버가 현재 권한·상태·모듈 조건으로 다시 검사한 뒤 최초 실행할 수 있다. 따라서 새 번호로 다시 보내거나 기존 명령을 조용히 바꾸지 않는다.

이번 실행 범위는 관련 브라우저 **3개 파일, 67개 시나리오**다. 전체 브라우저 56개 파일을 이번에 모두 다시 실행했다는 의미는 아니다.

수정 전 단위 시험에서 구 인수 권한 차단을, 실제 React 브라우저에서 인수 버튼이 사라지는 현상을 각각 재현했다. 추가 시험은 다음을 포함한다.

- 구/신 목록 × 협업/수합 × 인수/반려 8종.
- 저장 후 응답 유실 → 목록 실패 또는 모듈 중지 → 원키·원문 복구 4종. 합성 원장의 실제 반영 횟수는 1회.
- 목록 밖·다음 페이지 기록, 반복 커서, 서로 다른 커서의 기술 한도와 마지막 허용 페이지.
- 접수 전 준비 오류에서도 입력·기존 요청 번호 보존.
- 원키에 다른 내용, 위조 접수증의 기록 ID·키·판·상태, 학교·권한 변경 거부.
- 공식 담당의 신규 인수·관리자 확인 보호와 수신자 반려의 구분.

브라우저는 실제 React·호출 어댑터를 사용하고 RPC 응답과 요청 원장은 합성이다. **실제 Supabase/PostgREST 호출 성공이나 DB의 중복 방지·동시성 검증 결과로 계산하지 않는다.** SQL 적용·실사용 시험은 수행하지 않았다.

## Claude 재검토 요청

1. C8 후속 앱을 기준으로 구 SQL·P8 SQL 대조를 다시 실행한다. 구 목록 수락 4건, 모듈 중지 후 수신자 반려, 같은 번호 재전송이 더는 앱에서 잘못 차단되지 않는지 확인한다.
2. **새 명령은 `service.mutate`, 기존 요청 재전송은 `service.recover`로 시험한다.** `database/workhub/p8/test/app_contract_p8.ts`는 캡처한 mutate RPC를 앱의 새 명령으로 일괄 재생하므로, 모듈 중지 후 기존 관리자 명령을 재전송하는 사례를 복구로 구분해야 한다. 그 사례를 통과시키려고 새 관리자 명령의 준비 조건을 제거하면 안 된다.
3. P8의 원장 조회가 현재 모듈·판 검사보다 먼저 수행되는지, 기존 접수증이 없는 복구에는 현재 서버 조건이 적용되는지 재확인한다.
4. 새 공식 담당 신청·인수, 관리자 확인/반려, 자기 확인 차단과 현재 판·권한 검증이 유지되는지 확인한다.
5. #60의 잘못된 구 목록 호환 설명은 이번 인계 계약과 수정 보고로 대체한다. #60·#62만 병합한 상태를 C8 수정 완료로 기록하지 않는다.
6. 앱 자동 검증과 SQL 통합 검증, 실제 배포 확인 결과를 구분해 보고한다. 이번에는 Claude 통합 SQL 회귀를 다시 실행하지 않았으므로 이전 C8 실패 수치를 임의로 0으로 바꾸지 않는다.

## 누적 상태와 남은 작업

- #62의 학생 기록 출력·스킨·관계 목록·홈 메시지 구축을 유지하면서 C8 앱 결함을 보완했다.
- 기존 협업·수합 인계와 원요청 복구는 앱·합성 호출 경로의 자동 검증을 마쳤다. 공식 담당 관리자 확인 정책도 유지된다.
- Claude의 #60·#61·#62 및 이번 수정 검토, 최신 앱과 SQL 통합 회귀가 남았다.
- 사용자가 Claude와 운영 DB 읽기 전용 기준선을 확인한 뒤 SQL 적용·기능 활성화 시점을 결정한다. 이 앱 수정 자체가 DB 적용을 수행하지 않는다.
- 비서 비용 C7·D1~D10은 별도 결정 사항이다.
- 실제 PostgREST·Storage·브라우저 연결·동시 처리·실사용 확인은 요청대로 나중에 모아서 한다. 일반 교사 공개와 PR 병합은 사용자 판단을 따른다.

## 판단해서 정한 것

- 관리자 확인 모듈 전체를 모든 인계의 조건으로 쓰지 않고, 인계 종류와 서버가 제공한 처리 권한으로 나눴다.
- 새 명령과 원요청 복구를 분리했다. 복구로 현재 서버 권한을 우회하지 않으며, 현재 목록 조회 실패가 과거 접수증 확인을 막지 않게 했다.
- 새 명령의 기록 조회는 페이지 전체를 확인하되 무한 조회를 막는 기술 한도를 자산으로 관리한다.
- 이 수정은 #62 이후 독립 후속 PR로 둔다. 기존 검토 대상의 커밋을 바꾸거나 Claude SQL 브랜치를 수정하지 않는다.
