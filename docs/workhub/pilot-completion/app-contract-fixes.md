## 데이터와 복구 기준

- 과거 협업 actor/comment를 현재 담당자로 고쳐 쓰지 않는다. 현재 당사자·학교·개인 업무 소유자 검증은 유지한다. 인계 명령은 학년도·인계 서비스에서만 처리한다.
- P7 v1에는 첫 인계 전 담당자 ID가 별도로 없다. 수신자 행동이 없는 최초 구간은 앱이 추정하지 않는다. 서버의 원 담당자 검증이 필요하며, 더 자세한 from/to·당시 이름은 후속 계약 확장 항목이다.
- 새 할 일은 원문 코드포인트 길이를 검사한 뒤 공백을 정리한다. 비서는 정리한 내용을 확인 화면에 보여 준 후 전송한다. 과거 읽기 응답은 정규화하거나 자르지 않는다.
- 전송 전 오류는 입력 오류, 잘못된 서버 읽기는 응답 오류, 쓰기 이후 응답 유실·훼손은 결과 미상으로 구분한다.
- 미확정 요청의 원 명령·원 번호를 유지한다. 과거 긴 요청 또는 공백 정규화가 필요한 요청이 새 규칙과 다르면 자동 수정·삭제·재전송을 하지 않고 관리자 확인을 안내한다. 현 API에는 원 수신증만 조회하는 별도 경로가 없어 이 경우 자동 복구를 약속하지 않는다.
- 입력 보호는 기존대로 현재 탭 메모리다. 브라우저 종료 후 복원 기능을 추가하지 않았다.

## Claude 재검토 요청

1. 이 앱 PR을 #48 위에 놓고 확인한다. SQL 브랜치의 현재 최종 응답과 현재 parser를 대조하되 앱 변경을 SQL 적용 승인으로 간주하지 않는다.
2. 실제 P7 인수→P2 get 출력으로 새 담당자·발신자·재인계·완료 확인 대기를 검증한다. handover actor는 새 인수자라는 현재 의미를 유지했는지 확인한다. 다른 계약으로 바꿨다면 앱을 조용히 우회하지 말고 차이를 알려 달라.
3. P6 새 finish/confirm은 120/2,000 및 코드포인트·공백 정리 기준을 맞추되 과거 200/4,000 대화 읽기를 보존한다. 이미 처리된/미확정 요청은 원 본문과 원 키를 변경하지 않는다.
4. 잘못된 로컬 입력은 RPC 전 차단, 실제 서버 읽기 오류는 INVALID_RESPONSE, 전송 후 알 수 없는 결과는 원 키 보존으로 분리되는지 확인한다.
5. 코드 병합 판단·SQL 적용 판단·실제 모듈 활성화 판단을 각각 보고한다. 실제 SQL/브라우저 서비스를 실행하지 않은 검증은 그렇게 표시한다.
