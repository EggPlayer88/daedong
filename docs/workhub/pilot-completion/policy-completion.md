# 시범 사용 정책 보완 — 앱 구현과 SQL 인계

2026-10-16. 사용자 확정 정책을 하나의 앱 작업으로 구현한다. 기준 앱 #59 `f668b2527af1375787b423d6a6f4a10493427fab`, 참조 SQL #58 `aa6f04d`. 작업 브랜치는 `feat/workhub-pilot-policy-completion`이며 #59를 기준으로 한 후속 PR이다. Claude SQL 브랜치를 수정하거나 DB에 적용하지 않는다.

C8 후속 정정: 구 인계의 인수·반려와 원키 복구를 관리자 확인 모듈로 막던 제한을 제거했다. 아래 호환 설명은 이 수정에 맞췄으며, 최초 #60 검증 수치는 당시 결과다. 후속 수정과 검증은 [C8 인계 복구](transition-c8-fix.md)를 기준으로 한다.

## 확정 범위

사용자가 2026-10-16에 아래 권장안을 확정하고 앱 구축을 요청했다. SQL 적용은 사용자와 Claude가 진행한다.

## 사용 흐름

1. 협업 알림에서 원본 열기 → 해당 요청의 현재 담당·상태·이력 검증 → 명시적인 수락·완료 요청·완료 확인. 알림 읽음은 협업 처리와 구분한다.
2. 공식 담당이 포함된 인계 → 관리자 확인 대기 → 관리자 확인 또는 반려 → 확인된 요청을 받는 교사가 수락 또는 반려. 본인 신청을 본인이 관리자 확인할 수 없다.
3. 새 학년도는 실제 확인한 기간을 입력하고 연도 불일치를 먼저 수정한다. 기존 학년도 자료를 소급 변경하지 않는다.
4. 수업 관계에서 바꿀 교사·학생과 마지막 유효일을 선택 → 함께 바뀌는 관계를 미리보기 → 기록 보존 안내 확인 → 확정. 서버 결과가 불명확하면 원문·요청 번호로만 다시 확인한다.

## 계약 파일

- 협업 알림: `messaging-contract.md`의 C6 절. 원본 이동은 `resource-navigation`과 실제 협업 화면에 연결한다.
- 공식 담당 인계: `school-transitions-contract.md`. 새 상태·관리자 검토 정보·구 SQL 호환 경계를 확인한다.
- 학년도: `school-admin-contract.md`의 2026-10-16 Q4 절 및 전환 계약.
- 수업 관계: `teaching-contract.md` 및 `teaching-relations-contract.md`. 기존 P5 명령을 덮어쓰지 않고 새 계약을 사용한다.

## 이번 구현 결과

| 묶음 | 앱에서 구현한 결과 | SQL이 준비되기 전 동작 |
|---|---|---|
| 협업 알림 | 알림·홈 카드에서 정확한 요청 ID를 열고 현재 담당·상태·이력 재조회. 읽음과 협업 처리를 구분 | 기존 알림 유지. SQL이 협업 알림을 생성해야 새 알림이 도착 |
| 공식 담당 인계 | 관리자 확인/반려와 수신자 수락/반려 화면 분리. 본인 신청의 관리자 확인 차단, 승인 이력·상태·판 검사 | 구 협업·수합 인수·반려와 원요청 복구 유지. 공식 담당의 새 신청·수락 및 관리자 확인은 준비 상태 검사 |
| 학년도 검사 | 학교관리 생성과 학년도 전환의 시작 연도 검사 공유. 입력 유지, 다음 해 종료 허용 | 기존 읽기/수정과 원래 요청 복구 유지. 두 SQL 새 쓰기 경로에도 검사 필요 |
| 수업 관계 | 담당 교체·종료, 수강 종료·전출 4종. 전체 영향 미리보기, 확인 후 확정, 원요청 복구 | 확장 RPC 3개가 없으면 관계 패널만 준비 중. 기존 수업·학생 기록은 계속 사용 |

모든 보관은 현재 탭 메모리다. 배경 조회 실패에도 입력·원래 명령·요청 번호를 보존하며 계정·학교·권한 범위가 바뀌면 이전 자료를 표시하지 않는다. 브라우저 종료 이후 복원을 약속하지 않는다.

## SQL 후속 작업과 연결 순서

1. Claude가 이번 앱 계약을 읽고 Q2/Q4/C6 및 수업 관계 확장의 SQL 응답 초안을 현재 parser와 먼저 대조한다. 기존 SQL PR을 앱에서 임의 수정하지 않는다.
2. Q2는 앱이 새 필드/상태를 읽을 수 있도록 배포를 먼저 준비한다. SQL 목록은 `dutyApproval`와 모든 record 확장 필드를 일관되게 반환한다. 관리자 확인 전 공식 담당을 이전하지 않는다.
3. C6는 현재 사용자가 볼 수 있는 협업 원본 ID를 반환한다. 원본 변경과 알림 기록은 원자적이며 같은 요청 재실행으로 중복 알림이 생기지 않게 한다. 알림 읽음은 원본 변경이 아니다.
4. Q4는 P1·P7 새 명령에서 검사하고 기존 접수증을 먼저 확인한다. 과거에 저장한 자료나 이미 완료한 원요청에 새 의미검사를 소급하지 않는다.
5. 수업 관계는 기존 P5 불변 행을 보존하는 증분 확장이다. 종료 사건을 현재 접근/신규 작성/근거 재검증 경로에 연결하는 함수 보강도 함께 검토한다. 미리보기·확정만 추가하고 기존 기간 검사를 방치하면 완성이 아니다.
6. SQL 통합 회귀, 앱 parser/어댑터 대조, 기존 자료·권한 지문 확인 후 사용자가 Claude와 적용한다. 설치·기능 활성화·전체 교사 공개 판단을 구분한다.
7. 실제 Supabase/PostgREST 연결·알림·권한·동시 수정·과거 기록 보존은 이후 모아서 확인한다. 자동 합성 시험을 운영 연결 성공으로 대신하지 않는다.

## 판단해서 정한 것

- **인계 종류와 처리 권한에 맞게 제한**한다. 모든 구 기록을 막던 초기 판단은 C8의 원인이므로 철회했다. 구 기록은 서버의 처리 권한을 사용하고, 공식 담당으로 확인된 기록의 새 인수에 관리자 확인 조건을 적용한다. 원요청 복구는 원장 우선 확인 경로로 분리한다. 구현은 `administration/transitions.ts`와 전환 계약에 모았다.
- **수업 관계는 별도 계약으로 확장**한다. 학생 원본 판을 관계 판으로 사용하거나 불변 명부를 수정하지 않는다. 세 RPC와 DTO는 `teaching/relations-*` 및 전용 계약 문서에 모았다.
- **이번 관계 종료는 오늘 이후 날짜**만 허용한다. 담당 교체는 마지막 유효일 다음날 시작하므로 가장 빠른 새 담당은 내일이다. 당일 시작·소급 정정·종료 취소는 별도 영향 검토가 필요한 후속 범위다. 날짜 검사는 `relations-validation.ts`, 설명은 `RelationsPanel.tsx`에 있다.
- **미리보기 만료와 원요청 복구를 분리**한다. 만료 뒤 새 확정은 막지만 이미 보낸 원요청은 같은 번호로 확인한다. 손상된 거절 응답은 결과 미상으로 남기며 입력을 버리지 않는다.
- **사유 한도는 기존 정책 자산에 모았다.** `teaching/policy.json`의 `relationReasonCharacters`를 화면과 검증이 함께 읽는다.

## 자동 검증

전체 회귀 **2,935건**, 브라우저 **52개 파일**, 타입 검사·두 앱 빌드·보존 검사를 통과했다. 세부 결과는 [검증 보고](policy-completion-verification.md)에 기록했다. 자동 브라우저 시험은 실제 React·어댑터와 합성 전송이며 실제 Supabase/Storage/Claude 연결 결과로 계산하지 않는다. 이번에는 DB SQL을 실행하거나 실제 사용자 자료를 넣는 시험을 하지 않았다.
