# 개인 업무·글/숫자 수합 — 로컬 계약 구현

이 문서는 `apps/workhub/src/workflows/`의 실제 구현 범위를 설명한다. 기존 로그인·회원·Supabase·운영 모듈을 변경하지 않는다. 합성 자료를 사용하는 브라우저 로컬 업무이며 실제 인증·서버 권한·공식 접수·외부 결재를 구현했다는 의미가 아니다.

## 1. 구현 범위

| 업무 | 동작 |
|---|---|
| 개인 할 일 | 생성·편집·완료·재개·취소, 진행/대기 상태, 마감순 정렬, 본인 메모 |
| 홈 | 빠른 할 일 추가·체크, 책임자인 제출 단위의 현재/완료 상태, 남은 보완 의무·기한, 원본 이동 |
| 수합 개설 | 글·숫자 문항, 필수 응답, 검토 없음/있음, 개인/공동 제출 단위 |
| 게시 | 초안 비공개, 게시 시 책임자·공동 구성원의 ID/표시 이름 snapshot 생성 |
| 공동 초안 | 지정 구성원만 읽기·편집, 버전 충돌, 미제출 초안은 관리자/검토자에게 비공개 |
| 제출 | 책임자만 최종 제출, 필수 입력 검사, 불변 답변판, 로컬 접수증, 재시도 중복 방지 |
| 검토 | 지정 검토자의 보완 요청·특정 판 확정, 제출 책임자 자기 검토 금지 |
| 정정 | 새 판과 사유, 기존 완료본 보존, 마감 후 단위별 허용 기간 |
| 철회 | 사유·행동자·대상판 이력, 모드별 현재/완료본 재계산, 검토 완료본 직접 철회 거부 |
| 집계 | 열람 가능한 제출 단위, 유효 제출, 완료본 수, 완료본의 숫자만 합산 |

파일 업로드·문서 생성·공식 처리·면제·명시 대리·인계·알림 발송·게시 후 대상/문항 변경은 이 묶음에 포함하지 않는다. 해당 상태를 완료한 것처럼 표시하지 않는다. 수합은 실제 학교 데이터로 게시되지 않는다.

개인 할 일은 **현재 학교 안에서 본인만 사용하는 업무**다. 순수 계정 개인 공간의 학교 간 공유 기능과 구분한다. 독립적인 기본 주 메뉴 추가를 요구하지 않으며 홈에서 추가·체크하고 상세 관리 화면으로 이어지는 컴포넌트를 제공한다.

## 2. 소유 파일

- `apps/workhub/src/workflows/types.ts`: 업무·수합·접수·검토·철회·저장 snapshot 타입.
- `apps/workhub/src/workflows/store.ts`: 입력 검사, 상태 전이, 개발용 범위/행동 계약, 저장 경계.
- `apps/workhub/src/workflows/WorkflowPanel.tsx`: 홈 요약, 개인 업무 상세, 수합 개설·응답·검토 화면.
- `apps/workhub/src/workflows/workflows.css`: `wf-` 이름을 사용하는 독립 스타일.
- `tests/test_workhub_workflows.mjs`: 실제 도메인 및 JSX 렌더 회귀.

공통 셸·인증·저장 구현은 별도 담당이다. 이 모듈은 직접 localStorage 또는 네트워크에 접근하지 않는다.

## 3. 셸·저장 어댑터 연결

```ts
import { createWorkflowStore } from './workflows/store'
import { WorkflowPanel, HomeWorkSummary } from './workflows/WorkflowPanel'

const store = createWorkflowStore({
  members,
  date: '2026-10-19',
  snapshot: savedWorkflowNamespace, // 최초에는 undefined
  onChange(nextSnapshot) {
    // 공통 어댑터가 동기적으로 저장한다. 실패하면 예외를 던진다.
    persistWorkflowNamespace(nextSnapshot)
  },
})

store.setContext({ members, date })
const snapshot = store.exportState()
```

모든 변경 메서드는 동기 함수다. 실행 순서는 다음과 같다.

1. 현재 소속과 요청 키·본문·원본 버전 검사.
2. 현재 상태를 복제해 변경·접수 결과·필요 이력을 함께 작성.
3. `onChange(nextSnapshot)` 호출.
4. callback 성공 시에만 메모리 원본 교체와 구독자 갱신.

callback이 실패하면 메모리 원본과 성공 접수 결과를 유지하지 않는다. callback은 Promise를 반환하는 비동기 저장으로 사용하지 않는다. 영속 저장이 이미 성공한 뒤 알림 실패를 같은 예외로 던지면 저장 결과가 불명확해지므로, 공통 어댑터는 저장 이후 부수 알림 실패를 분리해야 한다. 다른 탭과의 optimistic envelope 비교는 공통 저장 어댑터가 담당한다.

`exportState()`는 분리된 복사본을 반환한다. `reset()`도 빈 snapshot의 저장이 성공한 뒤에만 초기화한다. 손상된 snapshot은 자동 초기화하지 않고 `INVALID_INPUT`을 반환한다. `setContext`는 최신 소속/기준일만 교체하며 저장 내용을 변경하지 않는다.

화면 계약:

```tsx
<WorkflowPanel
  member={currentMember}
  members={members}
  date={date}
  store={store}
  page="collections" // 또는 "tasks"
  initialRequestId={selectedRequestId}
/>

<HomeWorkSummary
  member={currentMember}
  members={members}
  date={date}
  store={store}
  onOpenCollections={requestId => openCollection(requestId)}
  onOpenTasks={() => openTaskDetail()}
/>
```

학교·사용자 전환 시 셸이 컴포넌트의 `key`를 바꾸어 이전 사용자의 입력을 닫아야 한다. `subscribe`/`getRevision`은 `useSyncExternalStore` 연결용이다. 구독 갱신이 있어도 편집 중인 입력을 자동으로 최신 원본으로 덮지 않는다. 충돌 화면에서 원본을 확인하고 기준 버전을 새로 선택한다.

| `homeSummary` | 개인 업무와 책임 제출 단위의 원본 기반 상태, 미충족 보완을 포함한 `pendingObligations` |
| `collectionSummary` | 현재 열람 가능한 단위와 완료본 숫자 집계 |

변경 시 원본의 `expectedVersion`과 요청 키가 필요하다. 초안 최초 저장은 버전 `0`, 이후는 확인한 초안 버전을 사용한다. 최종 제출은 초안 버전과 제출 단위 버전을 모두 검사한다. 동일 요청 키/동일 본문은 기존 접수 결과를 재사용하며 재조회 때도 현재 열람 계약을 검사한다. 다른 본문은 `IDEMPOTENCY_CONFLICT`다. 화면은 실패 후 같은 입력·버전으로 다시 누를 때 같은 키를 재사용한다.

역할은 실제 인증이 아닌 개발용 계약이다. 같은 학교 관리자라는 이유만으로 개인 할 일이나 미제출 초안을 열람하지 않는다. 수합 요청 관리자·검토자·공동 작성자·책임자는 각 수합/제출 단위의 명시적인 배정으로 구분한다.

## 5. 제출·완료본 규칙

- **검토 없음:** 제출 v1에서 `current=v1`, `effective=v1`. 정상 정정 v2는 둘 다 v2. 사람이 검토했다고 표시하지 않는다. 현재 완료본 철회 시 둘 다 비우며 옛 v1을 자동 복구하지 않는다.
- **검토 있음:** v1 제출은 `current=v1`, `effective=null`. 승인 후 둘 다 v1. 새 v2 제출은 `current=v2`, `effective=v1`. v2 승인 후 둘 다 v2. 대기 v2 철회 시 둘 다 v1이다.
- 검토 결과는 특정 제출판에 붙는 별도 이력이다. 불변 답변과 과거 접수증을 덮어쓰지 않는다.
- 필수 숫자의 `null`은 미입력이고 `0`은 유효하다. 설정되지 않은 문항의 응답, NaN/Infinity, 잘못된 형식은 거부한다.
- 공동 구성원 수는 제출 부수가 아니다. 게시된 단위 하나는 의무 하나이며 책임자만 최종 제출한다.
- 완료본 숫자 집계는 검토 대기 중인 정정판을 합산하지 않는다. 합이 유한 수 범위를 벗어나면 계산 불가로 표시한다.
- 완료본 유무는 원본 포인터로 계산하고, 해야 할 수합은 미충족 보완 의무까지 함께 계산한다. 개인 할 일 체크로 수합 의무를 완료할 수 없다.

## 6. 시간·보완·철회

날짜 단위 마감이며 종료일까지 포함한다. 가상 `date`보다 마감일이 이르면 연체다. 로컬 접수증의 시각은 **가상 기준일 09:00, +09:00**으로 기록하여 재현 가능한 시험을 만든다. 실제 서버 시계나 운영 접수시간이 아니다.

최초 제출 지연, 현재 미제출 연체, 보완 기한 초과는 따로 계산한다. 재제출은 최초 제출 지연을 바꾸지 않는다. 유효 보완 제출은 `fulfilledSubmissionId/fulfilledAt`을 기록해 현재 보완 초과를 해제하고, 해당 보완 제출을 철회하면 유효 보완을 다시 계산한다. 각 제출판에는 당시 마감과 접수 날짜가 남는다.

이전 완료본이 있는 상태에서 **보완 요청판을 철회하거나, 보완 재제출 대기판을 철회해 이전 완료본으로 돌아가도 미충족 보완 의무는 유지한다.** `pendingSupplements`는 남은 보완 요청을 기한순으로 반환한다. 홈은 완료본 v1 등의 정보와 별도로 `보완 제출 필요`, 남은 보완 건수, 가장 이른 기한과 기한 초과 여부를 표시하고 해당 제출 단위를 해야 할 수합 건수에 한 번 포함한다. 보완 요청의 개수가 수합 부수를 늘리지는 않는다. 새 보완 제출은 보완 요청을 충족하고, 검토 대기인 새 판은 검토가 끝날 때까지 홈 수합 건수에 남는다. 완료본 숫자 집계는 계속 기존 완료본을 사용한다.

첫 제출은 마감 후에도 가능하며 지연으로 표시한다. 기존 제출이 있는 마감 후 정정/철회는 해당 단위의 명시적 허용 기간이 있어야 한다. 검토자의 보완 요청에는 보완 기한이 있으며 그 기간 동안 해당 단위가 보완 제출할 수 있다. 요청 관리자가 별도로 정정 기간과 사유를 지정할 수도 있다. 이 동작은 로컬 정책 계약이며 학교 운영 정책 승인·외부 공식 처리까지 완료했다는 뜻이 아니다.

## 7. 검증과 실행 예

```sh
npm test -- workhub_workflows
npm run check:workhub
```

현재 34개 회귀는 개인 자료 경계, 마감순 정렬, 버전 충돌, 멱등 재시도, 저장 실패 원자성, 깨진 입력, 게시 snapshot, 공동 단위, 초안 비공개, 책임자 제출, 숫자 0, 모드별 완료본, 보완·정정·철회, 세 연체 축, 완료본 집계, snapshot 복원, JSX와 원본 직접 이동·명시적 입력 이름을 검사한다. 보완 요청판 및 보완 재제출 대기판의 철회 후 홈 의무·기한 표시, 저장 복원, 최종 검토 후 의무 해제도 포함한다.

대표 브라우저 흐름:

1. 한소연 계정의 홈에서 개인 할 일 추가→완료→상세에서 재개/취소. 새로고침 보존은 공통 영속 저장 연결과 함께 확인한다.
2. 이민준 계정에서 수합 생성. 책임자 한소연, 공동 작성자 김서진, 필요하면 검토자 이민준 지정.
3. 초안 저장→대상 확인→게시. 한소연의 홈에서 같은 수합 원본을 연다.
4. 김서진은 공동 초안을 작성할 수 있으나 최종 제출은 할 수 없다. 이민준은 미제출 초안을 읽을 수 없다.
5. 한소연이 초안 저장→최종 제출. 검토 없음은 즉시 완료, 검토 있음은 이민준의 특정 판 검토를 거친다.
6. 보완 요청→책임자 새 판 제출→검토 완료. 완료본 v1 뒤 새 v2의 대기/철회를 확인한다. 보완 요청판 또는 보완 재제출 대기판 철회 후에는 완료본 v1을 유지하면서 홈에 보완 필요와 기한이 남는지 확인한다.

브라우저 영속 저장·교차 탭·화면 접근성·기존 로그인 회귀는 공통 셸의 통합 검증과 함께 기록한다. 이 파일의 도메인 통과를 서버 보안·전국 운영 준비도 전체 통과로 계산하지 않는다.
