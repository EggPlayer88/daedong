# 10차 개발 — 목록 성능과 전체 자료 일관성

작성일: 2026-10-13 · 기준 PR #16 · 브랜치: `feat/workhub-scaled-lists` · [검토용 PR #17](https://github.com/EggPlayer88/daedong/pull/17)

## 목적과 적용 범위

한 학기 동안 업무·수합·학생 기록이 쌓여도 첫 화면에 모든 카드와 접힌 이력 본문을 생성하지 않도록 했다. 개인 업무, 수합 요청, 제출 단위 원본, 관찰 기록, 수업 활동을 **20개씩** 표시한다. 접힌 관찰 개정 이력과 제출 이력은 펼칠 때 생성하고 닫으면 화면 요소를 회수한다. 원본과 이력 데이터는 삭제하지 않는다.

개인 업무는 기존 연결 화면에서도 같은 구성요소를 사용한다. 수합·학생은 합성 자료 미리보기 단계다. 이번 작업은 화면 표시량의 개선이며 서버 조회 페이지 처리, 실제 Supabase 연결, 전국 규모 부하 시험의 완료를 뜻하지 않는다. DB 구축과 시간표는 계속 보류하며 로그인·회원·인증·권한·SQL·보호 자산·Claude 공급자와 비용·메뉴 공개 범위는 변경하지 않았다.

## 교사에게 달라지는 동작

| 화면 | 표시 방식 | 유지한 동작 |
|---|---|---|
| 내 업무 | 20개씩, 전체 분류 건수·현재 범위·전체 쪽수 | 검색·상태·기한, 최신 원본 재조회, 홈 4건 요약과 전체 기한 집계 |
| 수합 요청 | 받은 수합/내가 만든 수합 각각 20개씩 | 전체 검색 결과 수, 선택 원본 유지, 작성·저장 후 정확한 요청 위치 |
| 수합 원본 | 제출 단위 20개씩, 이력 펼침 생성 | 전체 완료본 합계, 진행 표 필터, 표에서 정확한 단위 열기 |
| 관찰 기록 | 조회 조건에 맞는 기록 20개씩, 개정 이력 펼침 생성 | 전체 상태 집계, 본인 전체 유효 근거 검증·출력, 정정·철회 |
| 수업 활동 | 받은 활동 20개씩 | 학생 연결 확인, 미확정 입력 보호, 원문 최신판 확인과 채택 |

모든 페이지 메뉴는 ‘처음·이전·다음·마지막’ 버튼, 전체 수·표시 범위·현재 쪽 안내를 제공한다. 키보드 이동 후 해당 목록 제목으로 초점을 옮긴다. 검색이나 업무 찾기에서 특정 원본을 열면 그 원본이 속한 쪽을 계산하고 정확한 카드로 이동한다. 20개 미만인 목록에는 불필요한 페이지 메뉴를 만들지 않는다.

## 자료 일관성과 실패 복구

- **전체 집계 뒤 표시 분할:** 목록의 일부를 전체 자료처럼 계산하지 않는다. 완료본 합계·학생 상태 집계·근거 출력은 기존 전체 원본을 사용한다.
- **입력 보호:** 개인 업무 편집·저장·미확정 결과 동안 쪽 이동을 잠근다. 수합 응답·검토 의견·학생 관찰·활동 연결은 기존 편집 보호를 통과해야 쪽을 바꿀 수 있다.
- **정확한 원본:** 마지막 쪽의 업무·요청·제출 단위·정정 기록도 정확한 위치로 연결한다. 찾을 수 없는 원본을 다른 항목으로 대신 열지 않는다.
- **목록 축소:** 마지막 쪽이 사라지면 마지막 유효 쪽으로 보정하고 그 상태를 기억한다. 자료가 다시 늘어도 과거 쪽으로 튀지 않는다.
- **필터와 학교 변경:** 필터·학생·수업·학교 맥락이 바뀌면 유효한 첫 쪽으로 돌아간다. 편집 보호와 학교 변경 시 이전 자료 제거 원칙을 유지한다.
- **화면 밖 자료:** 1,000번째 원자료가 변경되어도 재검토 집계와 근거 내보내기 차단에 반영한다. 쪽 이동을 이유로 권한 검사나 원자료 최신성 검사를 캐시하지 않는다.
- **일시 조회 실패:** 학생 활동 입력 중 읽기에 실패하면 입력과 기존 쪽을 보존한다. 오류를 빈 목록으로 간주해 첫 쪽으로 바꾸지 않으며, 복구 후 원래 쪽에서 작성·취소를 이어 간다.

## 같은 자료로 측정한 변경 전후

`tests/browser/workhub-scale-baseline.mjs`가 기준 커밋 `137a871`과 현재 실제 React 구성요소에 동일한 합성 자료를 넣어 Chrome에서 비교한다. root 아래 DOM 요소 수이며 각 기능별 별도 검증 화면의 수치와 섞지 않는다. 관찰 기록과 제출 이력은 항목마다 3개 판을 사용했다.

| 합성 자료 | 이전 DOM 요소 | 현재 DOM 요소 | 감소 | 카드 수 |
|---|---:|---:|---:|---|
| 개인 업무 1,000건 | 17,031 | 379 | 97.8% | 1,000 → 20 |
| 관찰 기록 1,000건 | 26,101 | 369 | 98.6% | 1,000 → 20 |
| 수업 활동 1,000건 | 40,023 | 831 | 97.9% | 1,000 → 20 |
| 수합 요청 1,000건 | 4,028 | 117 | 97.1% | 1,000 → 20 |
| 제출 단위 100개 | 5,045 | 954 | 81.1% | 100 → 20 |

접힌 관찰 이력 3,000개·제출 이력 300개의 본문 DOM은 처음에 0개다. 펼친 항목의 내용과 개정 사유는 보존된다. 이 비율은 **DOM 감소율**이며 실제 응답 속도 개선율이나 서버 p95 보장이 아니다.

남은 비용도 측정했다. 활동 카드의 명부/수업 읽기는 1,001회에서 21회로 줄지만, 수합 요청 1,000건의 `listUnits`는 여전히 1,000회다. 전체 학생 기록 검증·정렬·집계와 합성 저장소의 복제 비용도 남는다. 서버 전환 시 학교·사용자·권한 범위의 커서 조회, 서버 집계, 항목별 이력 조회를 구현하고 현실적인 학기 자료량으로 측정해야 한다.

## 판단해서 정한 것

1. **기본 표시 20개:** 이미 사용하던 수합 진행 표와 맞춰 명시적 쪽 이동을 선택했다. 키보드 순서와 원본 위치를 예측할 수 있다. 변경은 `app/list-window.ts`의 `LIST_PAGE_SIZE`와 각 화면 연결부에서 되돌릴 수 있다.
2. **접힌 이력 지연 생성:** 원본 이력은 보존하고 DOM만 줄인다. 변경은 `StudentsPanel.tsx`의 `RecordCard`, `WorkflowPanel.tsx`의 `UnitPanel`이다.
3. **표·집계와 상세 페이지 분리:** 상세 일부를 보여도 표의 검색 범위와 완료본 합계를 유지한다. 변경은 `WorkflowPanel.tsx`의 `RequestDetail`이다.
4. **권한 캐시를 추가하지 않음:** 화면 최적화 중 이전 권한·원문을 오래 보유하는 새 경로를 만들지 않는다. 조회 최적화는 DB 재개 때 서버 계약과 함께 다룬다.
5. **보존된 입력으로 복귀:** 오류 중 빈 표시를 목록 삭제로 해석하지 않는다. 학생 목록의 상태 보정은 조회가 성공한 경우에만 수행한다.
