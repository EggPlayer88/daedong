# 05. DB 구축·SQL 확정 인계서

> 2026-10-11 · 설계 인계. **이 문서에는 실행할 운영 SQL이 없다.** 기존 SQL 제안 파일을 그대로 운영에 실행하라는 지시가 아니다. 사용자 요청은 전체 DB 설계이며, 실제 적용은 아래 검증과 협업 역할을 따른다.

## 1. 역할과 전달물

- Codex: 현재 구현·기획·기존 SQL 계약을 대조한 통합 설계, 연결 명세, 수용시험, 변경 영향.
- Claude Web: 실제 스키마 실측 결과와 본 설계에 맞춘 확정 SQL, RLS/GRANT/함수/트리거/인덱스/검증 SQL. 존재하는 적용본을 사후 편집하지 않고 신규 번호 사용.
- 사용자: 검증 환경·운영 환경 식별, 적용본 확인, SQL Editor 실행, 결과 확인, 운영 main 병합.
- 구현 담당: 확정 RPC와 화면의 양방향 계약 시험, 실패/복구/동시성 검증. SQL 완료만으로 UI 완료 판정 금지.

[CLAUDE.md](../../../CLAUDE.md)의 “SQL 확정본은 Claude Web이 작성하고, 실행은 계란님이 한다”는 역할을 유지한다. 이번 설계 문서로 적용 승인이 자동 완료되지는 않는다. 현재 규칙·보호된 migrations/확정 문서 자산·OAuth·운영 설정을 변경하지 않았다.

## 2. 먼저 수집할 실측 자료

민감 데이터 본문·실제 학생 명단·API 키 없이 구조와 합계부터 수집한다.

| 자료 | 확인 내용 | 실패 시 |
|---|---|---|
| 환경표 | 프로젝트 식별자, 운영/검증 표시, PG/확장 버전, Data API 노출 schema, DB/Storage 백업 가능성 | 환경이 불명확하면 적용 중단 |
| 회원 보존 기준 | auth/public 사용자 ID 대응, 총수·활성/대기 수, 고아 profile, auth trigger 정의·권한 helper | 새 계정 생성으로 대체하지 않음 |
| 기존 DB | tables/columns/PK/FK/unique/check/index/trigger/policy/function owner/EXECUTE·GRANT/default privilege | 문서와 차이는 drift로 기록 |
| 신축 적용 여부 | workhub_* 존재·열·함수 signature·적용 이력 | 없는 표와 이미 있는 표에 다른 migration 계획 |
| 파일 | 버킷 공개 여부·경로·정책·파일 수·총용량·지문 확보 범위 | DB 백업만으로 복구 가능 판정 금지 |
| 기존 경로 | main API·공용 client·문서 대화·제출·직접 Storage에서 승인/학교 검사가 어디에 있는지 | 다학교 공개 전 제한/전환 계획 필수 |
| 실제 정책 | 첫 학교 코드·관리자, 학년도/학기, 명부·배정, 보존/파기·전출 정정 | 임의 실자료/법적 보존연수 채우기 금지 |

현재 `database/workhub/002-account-preservation-dry-run.sql`은 조사 참고자료다. read-only 내용과 현재 schema 일치 여부를 Claude가 먼저 확인한 뒤 별도 세션에서 실행한다. `migrations/000_reset_v1_project.sql`은 과거 실행 기록이며 이번 구축에 재사용하지 않는다.

## 3. 첫 구축 범위: R0를 독립적으로 완결한다

R0의 완료 결과는 **기존 회원 그대로 로그인 → 학교 선택 → 본인 할 일/학교 일정 조회·등록·수정·재시도**다. 수합·학생·AI의 모든 미래 표를 선행 생성하지 않는다.

현재 코드가 요구하는 기존 이름:

| 표/함수 | 유지할 계약 |
|---|---|
| workhub_settings, workhub_schools, workhub_memberships | 현재 연결·rollout·학교·소속 DTO와 기간 해석 |
| workhub_calendar_events, workhub_calendar_receipts, workhub_calendar_audit | draft 구조·원본 version·같은 명령 재시도 |
| workhub_personal_tasks, workhub_task_receipts, workhub_task_audit | 본인 소속의 개인 업무·원자적 상태 변경·본인 전용 접수증 |
| workhub_context | 현재 계정의 학교·소속·관계 labels·basisDate |
| workhub_calendar_list/get/save | 기존 매개변수와 오류 JSON·response 형식 |
| workhub_task_list/get/mutate | 기존 command 종류, request_key·expectedVersion·입력 정규화 |
| workhub_today/gate/member 등 helper | 변경 필요 시 호출자·권한·직접 EXECUTE 범위 전수 확인 |

**R0 보강 대상으로 검토할 것:** 학교복합 FK가 빠진 기존 일정 자식 관계, 소속 상태와 전역 가입 승인 구분, 승인된 관계 ID, 학교 역할·권한 범위, public/Storage 옛 경로, 함수 owner와 grants, 권한 회수와 오래된 접수증, 날짜 경계, 페이지 조회 확장.

이미 표가 존재하면 ALTER/새 함수/호환 전환을 신규 migration으로 작성한다. 존재하지 않으면 검토를 반영한 신규 확정본을 작성하되 원래 제안 파일과의 차이를 첨부한다. `CREATE TABLE IF NOT EXISTS`로 서로 다른 schema가 같은 것으로 통과하게 만들지 않는다.

양방향 참조는 먼저 헤더→자식 관계를 만들고 자식 생성 뒤 current/effective 포인터 FK를 추가한다. submit 본문+receipt의 순환은 한 트랜잭션 안의 사전 할당 ID와 검증된 지연 FK 또는 단방향 receipt→결과 참조로 풀며, NULL인 채 committed 결과가 남지 않게 검사한다.

다른 배치에 아직 없는 표를 가리키는 “예비 FK”를 생성하지 않는다. typed evidence 링크는 해당 도메인이 생기는 배치에서 CHECK+FK를 함께 확장한다. 초기에는 미지원 종류를 반환하지 않는다.

## 5. SQL 확정본 한 묶음의 필수 구성

1. 사전조건: 적용 대상 DB·필수 객체·직전 migration·기존 row/constraint 범위. 예상과 다르면 명시적 중단.
2. 변경 DDL: 표/열/기본값/NOT NULL/CHECK/unique/FK와 삭제 동작.
3. index: 핵심 목록·참조·RLS 경로. 큰 운영표 인덱스는 lock 시간을 고려해 별도 배치/CONCURRENTLY 가능 여부 판단.
4. 권한: RLS, 각 작업의 USING/WITH CHECK, 테이블·sequence·function GRANT/REVOKE. public 기본권한 상속 포함.
5. 함수/trigger: 완전한 schema 경로, 안전한 search_path, actor/학교/소유자/버전/입력 검증, lock 순서, 실제 영향 행 수 확인.
6. backfill: 의미가 확정된 매핑만. 소속·학생을 이름·이메일 도메인만으로 자동 추정하지 않음. unresolved는 보고하고 중단/보류.
7. 검증: 양성·음성·변조·동시성·응답유실·운영 보존·실제 API 응답.
8. 실패 처리: 아직 쓰기 전 DDL 취소와 쓰기 시작 후 데이터 포함 전환 복구를 구분.
9. 적용 기록: 파일 SHA, 적용 시각, 실행자, 환경, 전후 합계, 실패/재개, 성공한 검증 ID.

함수에 단순히 SECURITY DEFINER만 붙여 RLS 거부를 없애지 않는다. 필요한 최소 권한과 함수 내부 학교·소유 검사가 반드시 짝이다.

## 6. RPC 구현 계약표

| 명령 종류 | 서버가 신뢰하는 값 | 한 트랜잭션의 결과 |
|---|---|---|
| 소속 승인/역할 변경 | 로그인 승인자·현재 학교 권한 | 소속/역할 변경+permission_version+감사+무효화 사건 |
| 일정·할 일 변경 | 기존 DTO의 현재 member·command·request key | 원본+버전+기존 receipt/audit |
| 수합 게시/제출/검토 | 요청판·단위판·책임자·서버 시간·파일 상태 | 고정 대상/불변 제출판·검토·현재/완료 포인터·receipt+outbox |
| 학생 관찰/정정 | 현재 교사·학생 담당·사건일·기대판 | 새 불변 근거판+영향 표지+outbox |
| 활동 수신/연결/채택 | 연결 주체·event/revision·교사 확인 | 원본판/매핑판/채택 기록, 중복/역순 격리 |
| 문서 출력 | 학교·팩판·정형입력·근거판·최종파일 지문 | 검사 결과+문서판/출력 참조, 공식 처리 완료와 구분 |
| AI 확인/실행 | 현재 actor·registry·확인판·만료·원본판 | 1회 claim+domain command+실행결과 |
| 인계 | 후임 수락·적용일·현재 양측 소속·대상판 | 기존 업무 ID의 책임 변경+같은 의무 수+감사 |
| 작업 완료 | job ID+현재 lease token·현재 원본권한 | 결과판+job 완료·사건, 옛 worker는 거부 |
| 파기 | 승인 정책·고정 영향목록·hold 여부 | 항목별 실제 처리결과+복구 재적용 원장 |

신규 명령의 공통 잠금 순서는 users → school gate/공통 platform grant → memberships → 권한/정책 → 멱등 advisory key → 필요 시 근거 owner gate → 원본(종류/ID 정렬) → 파일 → receipt/audit/outbox 기록이다. 게이트 읽기와 권한 회수의 잠금 모드가 실제 충돌하는지 검증한다. 기존 001·004의 구현 기록과 후속 제안을 혼동하지 않는다.

모든 RPC는 무효 입력·권한 거부·변경 충돌·같은 키 다른 payload·존재하지 않음·일시 실패를 구분한다. 민감 원본이 현재 사용자에게 보이지 않으면 conflict 응답에 원본문을 포함하지 않는다. 클라이언트는 update 0행을 성공으로 처리하지 않는다.

## 8. 성능·확장 시험의 시작 기준

아래 값은 **시험 계획 제안**이며 서비스 지원 한도·측정 결과가 아니다.

| 표본 | 구성 | 평가 |
|---|---|---|
| 단일학교 | 교사 100·학생 1,000·일정 5,000·업무 20,000·관찰 100,000 | 대표 목록의 인덱스/정책 비용, 홈 결과 정확성 |
| 다학교 | 위 표본의 10학교, 겸임·개인자료 포함 | 학교 증가에 따른 타학교 scan과 누출 여부 |
| 확대 | 관찰/활동/감사 100만 이상 합성 | 쿼리 계획·쓰기 경합·백업시간·필요파티션 판단 |
| 동시성 | 같은 단위 제출·수정·인계에 20개 동시 요청, 서로 다른학교에도동시부하 | 정확성 먼저, 잠금대기/실패재시도/연결수 측정 |

초기 목표 후보: 대표 API의 p95 1초 이내, 홈 조합 2초 이내. 환경/네트워크/데이터/동시수/쿼리 계획을 함께 기록하고 달성 전 보장하지 않는다. 전국 동시 접속은 별도 용량 산정과 부하 시험으로 결정한다.

RPO/RTO·백업 보존일·학생자료 보존연수는 임의 확정하지 않는다. 복구 시험의 실제 시간·누락 범위를 측정한 뒤 학교 운영과 요금제에 맞춰 승인한다.

## 9. 실패와 되돌림

- 아직 사용자 쓰기가 없으면 실패 migration의 트랜잭션 롤백/확정된 복구 절차로 되돌린다.
- 쓰기가 시작됐으면 코드만 이전판으로 돌려 새 자료를 고아로 만들지 않는다. 구판이 새 필드를 읽고 무시해도 안전한지, 새 원본을 기존화면에서 확인할 수 있는지 먼저 대조한다.
- 표/열 삭제 대신 기능별 쓰기 차단·미리보기/운영 rollout 축소·호환 API 유지로 영향을 제한한다.
- backfill은 청크·체크포인트·manifest·재시도키를 두고 미확정 명단 자동 병합을 하지 않는다.
- DB 전체 초기화, 회원 삭제, 기존 confirmed migrations 편집, force push는 이번 경로에 없다.
