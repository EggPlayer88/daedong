# 2차 개발 인계 — 2026-10-11

## 결과와 운영 상태

신축 앱에 일정·개인 업무·자료 수합·학생 기록의 실행 가능한 흐름을 만들었다. 기존 로그인은 기존 공유 클라이언트로 연결하고 회원·가입 승인·가입 트리거를 보존한다. 기존 운영 앱과 보호 문서 엔진을 삭제하지 않았으며 실제 Supabase·인증 공급자·Vercel 설정은 변경하지 않았다.

이번 작업은 **검토 가능한 코드와 로컬 기능 검증 완료**다. 실제 교사들이 새 기능을 사용하도록 배포한 상태가 아니다. 일반 교사에게 신규 메뉴를 공개하지 않으며 `main` 병합은 계란님이 한다. 세부 SQL은 `.proposed.sql`이고, 확정·실행 담당은 기존 작업 규칙을 따른다.

## 재사용과 신축의 경계

- 재사용: 기존 공유 인증 인스턴스와 회원 프로필, React/Vite와 workspace, 검증된 기존 문서 엔진·템플릿·회귀시험.
- 신축: `apps/workhub`의 화면·도메인·저장 경계·학교 일정 RPC와 별도 테이블 제안. 기존 전체 앱을 수정해 기능을 덧붙이는 방식으로 되돌리지 않는다.
- 기존 앱 수정: superadmin용 `/workhub` 진입만 추가하고 신축 화면을 지연 로드한다. Shadow DOM으로 스타일을 격리한다.
- 기존 회원을 복제·재가입·자동 승인시키지 않는다. 원래 ID·역할·추가 권한·승인 상태를 그대로 보존한다.
- 기존 전체 시스템의 `users` RLS는 아직 전국 서비스의 학교 격리 기준을 충족하지 않는다. 신규 일정의 격리만으로 기존 API까지 안전해졌다고 판단하지 않는다.
- Claude의 시간표 브랜치와 미커밋 작업에는 커밋하지 않았다. 향후 합칠 때 공통 학교·소속·수업 식별자부터 대조한다.

838건은 코드 회귀시험 수다. 전국 서비스 출시 준비율 또는 실사용 검증 건수를 뜻하지 않는다. PGlite는 실제 PostgreSQL 엔진을 사용하지만 실제 Supabase 구성·Google OAuth·서로 독립된 DB 연결의 동시 요청은 별도 검증해야 한다.

독립 HTML 시험은 할 일 등록/완료/재개/새로고침, 저장 실패와 재시도, 두 번째 창 차단, 공동 초안 비공개와 숫자 0 제출, 보완/재제출/확정/홈 원본, 관찰 정정/출력/타인 격리, 활동 원문 정정 전파, 학교 전환, 반응형, 일괄 초기화 실패/성공을 포함한다. 화면도 직접 확인하고 왼쪽 메뉴 겹침을 수정했다.

독립 검토에서 발견한 다음 결함도 수정했다.

1. 보완 요청판 또는 보완 재제출 대기판을 철회했을 때, 기존 완료본이 있어도 미충족 보완을 홈에서 계속 표시한다.
2. 일정·업무·학생 자료를 한 저장 단위로 확정해 전체 초기화가 일부만 성공하지 않게 했다. 실패하면 세 영역을 모두 유지하고 대기 중인 예전 일정 요청은 성공한 초기화 후 취소한다.

## 실행과 산출물 재생성

```sh
npm ci
npm run dev:workhub
node scripts/export-workhub-preview.mjs [저장할 절대 경로]
```

- 개발 서버: `http://127.0.0.1:5176`. 포트가 사용 중이면 실패한다.
- 일반 workhub 빌드는 합성 기능을 배포하지 않는다. 실제 진입은 기존 앱의 `/workhub`이며 SQL·학교 연결이 없으면 준비/실패 상태를 보여 준다.
- 독립 HTML은 외부 네트워크 요청 없이 실행한다. 가상 학교·계정·학생 자료만 포함한다.
- 저장 키는 `workhub:synthetic:v2:workspace` 하나다. 기존 인증 저장 키와 별개이며 전체 초기화도 합성 키만 대상으로 한다.
- 파일 URL의 저장·잠금 기능은 브라우저별로 다를 수 있다. 사용 불가 시 임시 메모리 안내가 나온다. 실제 업무 자료를 입력하지 않는다.
- 개발 기준일은 2026-10-19다. 일정·공통 소속의 마지막 날은 포함하며 학생 학적/수강/배정의 종료는 제외한다. 실제 서버 연결 전 공통 날짜 계약을 함께 검토한다.

브라우저 회귀는 Playwright와 Chrome이 필요하다. `PLAYWRIGHT_MODULE`로 Playwright 설치 경로를 지정할 수 있다. `WORKHUB_QA_URL`은 가상 업무 시험의 대상 URL이고 `WORKHUB_QA_OUTPUT`은 화면/결과 저장 위치다.

## PR 순서와 다음 구현

의존 순서는 **#2 → #4 → #6 → 업무·수합·학생 PR**이다. 앞 PR이 `main`에 병합되면 다음 PR의 기준을 `main`으로 변경하고, 필요한 경우 `main`을 merge해서 다시 검증한다. 의존 브랜치에 뒤 PR을 합치거나 rebase/force push하지 않는다.

[#6 일정 연결 기반](https://github.com/EggPlayer88/daedong/pull/6)은 `feat/workhub-foundation`, 후속 묶음은 `feat/workhub-school-workflows`다. 둘 다 검토용이며 실제 DB 적용을 포함하지 않는다.

다음은 기획 확장이 아니라 현재 구현을 운영으로 옮기는 순서다.

1. **계정·학교 연결 실증:** 보존 점검 → 추가형 SQL 최종 검토 → 검증 DB 적용 → 기존 Google 계정 로그인 → 학교 소속 연결 → 실제 세션 두 개의 허용/거부·복구 검증.
2. **일정 첫 실사용:** 등록→재조회→홈 추천→충돌→소속 종료까지 확인하고 superadmin 시험 후 제한된 교사 파일럿의 공개 범위를 검토한다.
3. **업무·수합 서버 전환:** 현재 명령/조회 계약을 비동기 서버 어댑터로 옮기고 초안 비공개·완료본·보완·접수 원자성을 DB에서 강제한다. 이후 파일과 기존 문서 초안 엔진을 연결한다.
4. **학생 기록 서버 전환:** 실제 명부 확인·승인 담당·작성자 RLS·정정 이력·출력 제한·보존/삭제부터 구현한 뒤 디지털윤리 활동 연계를 붙인다. 브라우저 합성 저장소를 실제 학생 데이터 저장소로 재사용하지 않는다.
5. **시간표·문서·AI 통합:** Claude 시간표 결과를 공통 식별자에 맞춰 검토하고, 기존 문서 엔진의 배포 실행을 실증한 뒤 근거 기반 상담·개인 비서 기능을 붙인다. 이번 묶음은 AI 호출·비용 설정을 변경하지 않았다.
