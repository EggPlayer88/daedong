## 이번 변경

첫 진입에서 문서 작성 AI·평가계획 제출·학사일정·사용자 관리 코드를 모두 받던 것을 해당 화면을 열 때 받도록 나눴다. 대시보드와 로그인, 업무실의 기존 경로는 그대로다. 사용 가능한 메뉴를 고르는 기존 판정과 라우트 등록도 바꾸지 않았다.

다운로드 중에도 메뉴를 유지하고, 실패는 해당 화면 안에서 안내한다. 재시도는 사용자가 누를 때만 한다. 브라우저가 실패한 import를 보관할 수 있으므로 반복 실패 시 입력과 처리 중 요청을 정리한 뒤 수동 새로고침하도록 안내하며 자동 새로고침하지 않는다.

느리게 열린 화면의 제목으로 키보드 초점을 이어 주되, 그 사이 사용자가 다른 메뉴로 초점을 옮겼으면 빼앗지 않는다. 화면을 떠난 뒤 도착한 응답으로 돌아오지도 않는다.

DB·서버 API·권한·메뉴 공개 범위·AI 모델/비용·HWPX 생성/검사 코드의 변경은 없다. 운영 설정과 데이터 변경 SQL은 필요 없다.

## 실측

원자료: [loading-measurements.json](loading-measurements.json). 바이트는 10진수 KB로 표기했다.

| 항목 | 변경 전 | 변경 후 | 차이 |
|---|---:|---:|---:|
| 초기 JavaScript 원문 | 509.35KB | 425.89KB | −16.4% |
| 초기 JavaScript gzip 전송량 | 152.09KB | 125.05KB | −17.8% |
| DOMContentLoaded 중앙값 | 1,084ms | 922ms | −14.9% |
| 첫 내용 표시(FCP) 중앙값 | 1,208ms | 1,076ms | −10.9% |

동일 PC의 로컬 프로덕션 빌드, Chrome, 1280×900, CPU 4배 감속, 지연 60ms, 다운로드 200,000B/s, 캐시 없는 새 컨텍스트를 각 5회 측정했다. 로그인하지 않은 진입 화면이며 운영 Supabase·AI API 요청은 차단했다. 글꼴은 기존 파일 그대로다. 운영 서버 응답 속도·실제 교사 PC·통계적 성능 보장을 뜻하지 않는다.

측정은 `node scripts/measure-site-loading.mjs <변경전 빌드 폴더> <변경후 빌드 폴더>`로 반복한다. 두 빌드 모두 `vite build --manifest`가 필요하며 같은 합성 환경값(`VITE_SUPABASE_URL=https://example.invalid`, `VITE_SUPABASE_ANON_KEY=synthetic-loading-measurement`)을 사용한다. 실제 로그인 정보나 키를 넣지 않는다. `SITE_LOADING_REPORT` 환경변수로 결과 JSON 저장 경로를 지정할 수 있다.

## 운영 화면에서 직접 확인한 범위

기존 관리자와 일반 교사 시험 계정으로 확인했다. 실제 교사 연결, 새로운 수업/교환 확정, 유료 AI 요청은 하지 않았다.

| 계정 | 확인 내용 | 결과 |
|---|---|---|
| 관리자 | 홈의 수업·일정·미제출 요약, 메시지 바로 열기 | 정상 |
| 관리자 | 메시지 미전송 입력 접기 → 시간표 → 작성 계속하기 | 입력 그대로 복구, 시험 입력만 비움 |
| 관리자 | 공유 시간표 → 교환·변경 요청 | 날짜·현재 수업 선택과 요청 화면 정상 |
| 관리자 | 게시된 질문형 양식 → 연결된 수합 → 원래 양식 복귀 | 저장 답변, 양식 v4·응답 v1 및 기존 제출 v1 유지 |
| 일반 교사 | 허용된 메시지·시간표·업무·일정 메뉴, 기존 대화·읽음 | 정상, 관리자 권한 추가 없음 |
| 일반 교사 | 자신의 확정 수업 → 상세 → 이 수업 변경 요청 | 선택한 수업을 그대로 전달, 새 요청 전송 안 함 |
| 일반 교사 | HWPX 첨부 다운로드 | 80,270바이트 및 SHA-256 원본 일치 |

첨부 SHA-256: `acfc1f18e24bd74f4056907e1b57bf5a1514805ce63098258affaa075803c7e1`.
다운로드 도중 브라우저 연결이 멈춘 첫 시도는 성공으로 세지 않았다. 다시 실행한 파일과 화면의 다운로드 요청 완료 안내를 확인했다. 기존 게시·제출 기록을 다시 쓰지 않고 조회했으므로 모든 업무의 신규 저장/승인을 운영에서 재시험했다는 뜻은 아니다.

브라우저 총 75건이다. 실제 React·라우터·화면을 사용하되 자동 시험의 DB/Storage/provider 응답은 합성이다. 자동 시험에는 신규 생성/전송/제출, 응답 유실의 같은 번호 복구, 계정/학교 변경 후 늦은 응답 차단도 포함된다. 운영 계정의 새 권한을 부여하지 않는다.

처음 샌드박스 실행에서 임시 폴더 접근 권한과 Chrome 다운로드 취소가 발생했다. 전체 시험은 작업 폴더 내부 임시 디렉터리로, 다운로드 시험은 같은 내용의 로컬 Chrome 환경으로 다시 실행해 통과했다. 기대값을 낮추거나 실패 시험을 제외하지 않았다.

## 판단해서 정한 것과 남은 일

- 첫 진입에 필요 없는 네 화면만 분리했다. 데이터 조회·AI·파일 코드는 건드리지 않고 초기 전송량을 줄이기 위해서다. 되돌리려면 App의 네 import를 복구하고 DeferredPage 및 Layout의 지연 초점 연결을 제거한다.
- 로딩 오류를 전체 새로고침으로 복구하지 않는다. 다른 화면의 탭 메모리 입력·미확정 요청을 보존하기 위해서다.
- 기존 시험 자료를 조회하고 미전송 입력으로 이동을 검증했다. 운영에서 신규 결재·최종 제출까지 반복하는 일은 별도 전체 시나리오 점검으로 남긴다.
- 병합 전 최신 CI와 미리보기에서 대시보드→문서 작성 AI→평가계획 제출 이동, 느린 로딩, 실패 재시도 안내를 확인한다. 병합은 사용자, 이후 Vercel Production Ready 및 커밋 일치를 확인한다.
- 실제 학교 PC/모바일의 네트워크 측정과 필요 시 한글 글꼴 전송량 최적화는 다음 우선순위다. 이번 수치로 DB 조회 성능이나 모든 화면의 완성을 주장하지 않는다.
