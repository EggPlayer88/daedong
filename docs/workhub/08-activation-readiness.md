# 3차 개발 — 기존 계정·학교 연결 진단

## 이번 작업

기존 연결 화면에서는 세션·프로필·학교 조회 중 무엇이 실패했는지 알아보기 어려웠다. 화면 아래 명시적 **연결 상태 확인** 버튼을 추가해 원인을 구분하고, 지원용 JSON을 내려받을 수 있게 했다. 진단은 기존 공유 인증 인스턴스의 읽기 함수만 사용한다.

| 결과 | 확인된 사실 | 다음 조치 |
|---|---|---|
| 로그인 없음 | 현재 세션이 null | 기존 사이트의 로그인 상태 확인 |
| 프로필 연결 누락 | 세션은 있으나 같은 ID의 회원 프로필이 null | 기존 계정을 보존하며 프로필 연결 확인 |
| 승인 미확인 | 회원의 기존 승인 값이 true가 아님 | 승인/비활성 상태 확인. 퇴직과 가입 대기를 자동 구분하지 않음 |
| 권한 확인 필요 | 최고관리자가 아니거나 서버가 접근 거부 | 현재 계정의 시험 화면 이용 범위 확인 |
| 설정 확인 필요 | 연결 설정·서비스 또는 실행 옵션을 확인할 수 없음 | 사이트 관리자에게 설정 점검 요청 |
| 학교 조회 기능 준비 문제 | `workhub_context`가 PGRST202로 응답 | 함수 등록·서명·스키마 캐시 확인. SQL 미실행으로 단정하지 않음 |
| 학교 소속 없음 | 조회 결과에서 본인의 활성 학교 소속이 없거나 소속 거부 | 학교 소속·이용 기간 확인 |
| 학교 소속 조회 성공 | 같은 세션의 승인된 최고관리자이며 본인의 유효 학교 소속 조회 가능 | 별도 일정 목록·저장 시험으로 진행 |
| 확인 실패·지연·계정 변경 | 안전한 판정을 마치지 못함 | 이전 성공 결과를 재사용하지 않고 재시도 |

`ready`는 학교 소속 조회까지의 성공이다. 일정 목록·저장, Google OAuth 전체, 운영 회원/파일 전체 보존을 검증했다는 의미가 아니다. 진단 결과를 실제 접근 권한이나 캐시된 승인으로 재사용하지 않는다.

## 구현과 정보 보호

- `connection/readiness.ts`: 세션→본인 프로필→세션 재확인→학교 조회→세션 재확인. 승인된 최고관리자가 아니면 학교 조회를 호출하지 않는다.
- 총 제한 시간은 기본 10초다. 취소·제한 시간 후 늦은 응답은 후속 조회로 이어지지 않는다. 이미 전송된 읽기 요청의 실제 네트워크 중단은 공용 서비스가 제공하지 않아 보장하지 않는다.
- `ConnectionReadinessPanel`: 자동 실행하지 않는다. 실행 중 중복 클릭을 막고 이전 결과를 비운다. 계정 변경·화면 종료 후 늦은 결과와 다운로드 완료 메시지를 표시하지 않는다.
- JSON은 `stage`, `code`, `checkedAt`, `readySchoolCount`만 허용한다. 이름·이메일·회원/학교 ID·세션 토큰·일정·서버 오류 원문을 넣지 않는다. 임의 필드와 잘못된 보고서도 안전한 고정 결과로 정규화한다.
- 오프라인은 요청 전에 구분한다. 서버가 권한을 거부했으면 이전 프로필 승인 확인만으로 현재 권한을 확인했다고 표시하지 않는다.
- 실제 화면은 기존 `/workhub`의 superadmin 범위에 통합했다. 새 로그인 클라이언트·가입·승인·회원 수정 호출은 없다.
- `AuthContext.jsx`는 계정 삭제를 권하는 과거 오류 문구만 수정했다. 세션 처리와 승인 판정 로직은 바꾸지 않았다.

## 확인한 결과

- 전체 회귀 **868건 통과**. 이전 838건에 진단 도메인 23건·화면 7건 추가.
- 기존 앱 `build`, 신규 앱 `build:workhub` 타입/빌드 통과.
- Chrome 진단 브라우저 시험 **9묶음 통과**. 실제 연결 JSX의 PGRST202→복구, JSON 실제 다운로드, 소속 없음, 통신 실패와 별도 패널의 계정 상태·오프라인·중복 클릭·늦은 응답·화면 종료를 확인했다.
- 기존 연결 브라우저 **6묶음 재통과**. 정상 토큰 갱신/포커스의 초안 유지와 권한 거부/계정 변경의 화면 폐기를 확인했다.
- 바탕화면 독립 HTML의 합성 상태 8종과 390px 화면을 확인했다. 진단 브라우저 시험은 360px에서도 확인했다.
- 실제 PostgreSQL 16 경합 **6개 통과**. 실행 링크와 경계는 [07 검증 기록](07-postgres-verification.md)에 있다.

브라우저 시험은 합성 전송 계층을 사용했다. 현재 작업 폴더와 프로세스에는 실제 Supabase 접속 설정이 없었고, 실제 계정 로그인·원격 SQL 실행·Vercel 설정 변경을 하지 않았다.

## 실행과 확인 자료

```sh
npm test
npm run build
npm run build:workhub
node tests/browser/workhub-readiness.mjs
node tests/browser/workhub-connection.mjs
node scripts/export-workhub-readiness-preview.mjs [저장할 절대 경로]
```

브라우저 시험에는 Playwright와 Chrome이 필요하다. `PLAYWRIGHT_MODULE`로 설치 경로를 지정하고, 진단 시험의 `WORKHUB_QA_OUTPUT`으로 화면 저장 폴더를 지정할 수 있다. 독립 HTML은 외부 접속 없이 진단 화면을 시연하며, 화면 상단에 합성 결과임을 표시한다. 여기서 받는 JSON도 실제 계정의 증빙이 아니다.

## 실제 환경으로 넘어가는 순서

1. 현재 PR과 추가형 SQL을 검토한다. 순서는 **#2 → #4 → #6 → #7 → #8**이며 앞 PR 병합 후 다음 PR의 기준을 main으로 바꾸고 재검증한다. 병합은 계란님이 한다.
2. 계정 보존 사전 점검과 백업/복원 확인 후 SQL 확정본을 검증 환경에 적용한다. SQL 확정·실행 역할은 기존 규칙을 따른다. 이번 PR 자체는 신규 SQL 변경·실행을 요구하지 않는다.
3. 기존 계정의 승인·ID를 유지한 채 학교와 소속을 연결하고, 같은 origin의 `/workhub`에서 진단을 실행한다. 로그인 설정·키를 채팅이나 보고서에 붙이지 않는다.
4. 학교 소속 조회 성공 후 일정 등록→재조회→홈 반영을 실제 세션으로 확인한다. 이어서 서로 다른 계정의 학교/개인 열람·동시 수정·소속 종료를 확인한다.
5. 이 과정을 통과한 뒤 제한된 교사 파일럿의 공개 범위를 검토한다. 구형 API/Storage의 학교별 격리와 업무·수합·학생 서버 전환은 별도 남은 작업이다.

## 판단해서 정한 것

진단 결과는 읽기 범위에 한정하고, 실패를 계정 삭제나 설정 자동 변경으로 해결하지 않는다. 실제 동시성은 여러 PostgreSQL backend로 확인하되 운영과 분리된 일회용 DB에서만 실행한다. 변경하려면 `readiness.ts`, 진단 패널, 전용 브라우저 시험과 PostgreSQL 실행 조건을 함께 검토한다.
