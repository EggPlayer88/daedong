## 판단해서 정한 것

1. 조회 범위를 바꾸어도 보내지 않은 입력은 버리지 않는다. 전송 가능 여부는 기존 `inputFor`와 서버 검증에 맡기고, 화면에서 입력 정리를 할 수 있도록 한다.
2. 조회 실패·새 요청 권한 없음에는 보관 입력을 계속 숨긴다. 화면이 다시 열릴 때까지 임의의 이전 자료로 전송하지 않는다.
3. 확정 탭을 숨기더라도 기존 관리자 입력·결과 미상 요청을 복구할 경로는 남긴다. 권한 자체는 변경하지 않는다.
4. 운영 시험 자료를 임의로 미래로 옮기지 않는다. 새 승인 왕복을 다시 확인하려면 별도로 미래 시험 수업을 준비한다.

앱 변경을 되돌릴 대상은 `TimetableExchangePanel.tsx`, `TimetableOperationsWorkspace.tsx`이다. DB 되돌리기나 환경변수 변경은 없다.

### 시험 준비 단계의 경쟁 조건

기존 사례는 관리자 응답으로 시작한 뒤 `canPublish=false`와 React 재조회를 요청했다. 다음 줄의 사유 입력칸 대기는 **새 조회 전에도 존재하는 입력칸**을 바로 받아들일 수 있었다. 이 경우 일반 교사 화면으로 바뀌기 전에 이전 관리자 확정 탭을 세었다.

로컬 원문 12회는 모두 통과했지만, 새 렌더 시작을 250ms 늦춘 임시 사본에서는 첫 탭 검사에서 `1 !== 0`이 재현됐다. 앱은 그대로 두고 시험을 다음과 같이 보완했다.

1. 일반 교사 사례는 화면을 처음 구성하기 전에 `canPublish=false`를 고정한다. 초기 조회가 끝난 뒤 시작하므로 이전 관리자 화면이 섞이지 않는다.
2. 일반 재조회와 지연된 재조회 두 사례를 실행한다. 서버 응답은 보류하고, **로딩 안내가 보이는 동안 즉시 탭이 0개인지 검사**한다. 탭이 없어질 때까지 기다리는 방식으로 기대를 완화하지 않았다.
3. 실패 시 assertion 값과 위치가 남도록 전체 오류 스택을 출력한다.

원래의 `!view` 조건을 로컬에서 잠시 복원한 음성 대조에서는 2건 모두 실패했다. 따라서 실제 로딩 탭 노출은 계속 탐지한다. 대조 직후 앱 파일을 원래 바이트로 복원했고 최종 앱 차이는 없다.
