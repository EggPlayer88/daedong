# 28차 — 학교 연결 읽기 조사와 Claude Web 인계

2026-10-14 · 상태: **B00 조사 명세 작성 · 운영 DB 카탈로그 미조회 · 확정 SQL 미작성·미실행**

## 1. 목적과 현재 적용 범위

현재 학교 연결의 `CONTEXT_FUNCTION_MISSING` 원인을 좁히고, 기존 회원·문서·파일을 보존하면서 통합 DB의 B01/B02로 진행할 근거를 모은다. 이 문서는 Claude Web이 **읽기 전용 조사 SQL부터 작성할 수 있도록 하는 요청서**다. SQL 실행본, 운영 설정 변경, 학교 생성·회원 연결 완료 보고서가 아니다.

사용자는 DB 준비를 재개했고 확정 SQL을 검토한 뒤 직접 적용하기로 했다. [협업 규칙](../../CLAUDE.md)에 따라 SQL 확정본은 Claude Web이 작성하고 실행은 사용자가 한다. Codex는 현재 앱과의 계약 대조·검증·연결 코드를 담당한다. 이 문서 작성으로 다른 AI에게 메시지를 전송하거나 SQL 실행을 요청한 것은 아니다.

기존 Google 로그인·Auth UID·회원 프로필·가입 승인·기존 자료를 유지한다. 현재 신축 화면은 승인된 슈퍼관리자 범위로 유지하며, 문서작성 AI 전용 개발과 시간표 실행은 계속 보류한다. 학교 지식 상담과 개인 비서를 문서작성 AI 보류에 묶어 제외하지 않는다.

## 2. 확보한 증거와 아직 모르는 것

### 2.1 사용자가 전달한 로그인 상태의 진단

- 확인 시각: `2026-10-13T15:56:16.639Z` / 한국시간 `2026-10-14 00:56:16.639`.
- 결과: `foundation_missing / CONTEXT_FUNCTION_MISSING`.
- 당시 같은 계정의 세션 재확인, 기존 가입 승인, 슈퍼관리자 화면 이용 조건을 통과했다.
- 현재 코드상 이 결과는 `workhub_context()` 응답의 정확한 오류 코드 `PGRST202`에 대응한다.

이는 새 학교 API의 모든 권한·조회·저장 성공을 뜻하지 않는다. 학교 소속을 성공적으로 조회하지 못했으므로 **소속 없음, DB 전체 없음, SQL 전부 미실행으로 판정하지 않는다.** 실제 Google 로그인 절차를 새로 실행한 시험이나 전체 회원 보존 검증도 아니다.

### 2.2 공개 배포물과 비로그인 API 읽기 조사

다음은 별도 관측이며 사용자의 인증된 세션 진단과 합쳐 하나의 시험으로 표시하지 않는다.

| 관측 항목 | 2026-10-14 06:37:49 KST 결과 |
|---|---|
| 공개 사이트 | `https://daedong-school.vercel.app/` |
| HTML이 가리킨 모듈 | `index-BOiC1M5I.js` |
| 모듈 SHA-256 | `658d18b0c6aaf81cd750083ba2589cc57f6a9c7bc339c201f6c651dc8d831054` |
| 공개 번들에서 확인한 Supabase host | 1개. host 지문의 SHA-256 앞 16자리: `69322d886758e9e8` |
| 공개 anon 키의 project ref 대조 | 번들의 연결 host와 일치. 키 원문은 기록하지 않음 |
| OpenAPI GET | HTTP 401. 공개 API 목록·schema 노출 여부는 **미확인** |
| `public.workhub_context` GET | HTTP 404 / `PGRST202` |
| 사용자가 의도한 Supabase 프로젝트와 일치 | **사용자 확인 대기**. 배포 번들 내부 일치만으로 올바른 운영 프로젝트라고 확정하지 않음 |

HTTP 404 하나만으로 함수가 물리적으로 없다고 판단하지 않는다. 이번 응답의 `PGRST202`는 요청한 함수를 현재 API가 찾지 못했다는 조사 근거이며 프로젝트·schema·호출 서명·캐시를 더 확인해야 한다. 공개 anon 요청은 로그인한 교사의 역할·학교 격리·저장 동작을 검증하지 않는다.

후속 공개 배포 점검 도구는 `scripts/check-workhub-deployment.mjs`다. 그 도구의 결과 역시 공개 번들·API 응답의 제한된 관측이며, SQL 카탈로그·실제 회원·Storage 실물 조사 결과로 대체할 수 없다.


### 2.3 반복 실행할 수 있는 조사 도구

저장소 루트에서 Node.js 22로 실행한다. API 키·사용자 세션을 입력하지 않는다.

```powershell
node scripts/check-workhub-deployment.mjs --site https://daedong-school.vercel.app/
node scripts/check-workhub-deployment.mjs --site https://daedong-school.vercel.app/ --expected-project '<사용자가 확인한 프로젝트 ID>' --output './workhub-deployment-audit.json'
```

두 번째 명령의 프로젝트 ID는 Supabase 대시보드 주소에서 사용자가 확인한 값으로 바꾼다. 입력하지 않으면 `project.expectedMatch: "unknown"`이다. 다른 대상이면 `EXPECTED_PROJECT_MISMATCH`로 **Supabase API 요청 전에** 멈춘다. 사이트가 공개 번들에 선언한 host의 SHA-256 지문으로 비교하며, 출력에는 원문 프로젝트 ID·URL·키를 담지 않는다.

- GET만 사용한다. HTML·같은 origin의 명시된 module/modulepreload JS와 고정 API 두 경로를 읽는다. JS를 실행하거나 내부 import·sourcemap을 따라가지 않는다.
- 모든 리디렉션을 거부하고, HTML의 base href·inline/외부 module 등 지원하지 않는 구성은 추정 해석하지 않는다.
- 표준 HTTPS `*.supabase.co`와 기존 HS256 anon JWT 형식만 지원한다. role/ref/issuer 대조는 공개 키의 분류이며 **JWT 서명의 진위 검증이 아니다**. 새 publishable 키·사용자 토큰·service role 키는 사용하지 않는다.
- 요청마다 8초, HTML 512 KiB, JS 3 MiB/개·총 8 MiB·최대 8개, API 2 MiB/응답으로 제한한다.
- 보고서에는 요청 범위·상태·고정 코드·HTTP 상태·관측 시각·자산 지문만 남긴다. 원시 오류·응답 본문·함수 목록·학교/회원 데이터는 출력하지 않는다.
- `--output`은 새 파일만 쓴다. 이미 있는 파일은 덮어쓰지 않고 `REPORT_WRITE_FAILED`로 종료한다.
- 기본 회귀와 CI는 합성 HTTP만 쓰며 운영 사이트에 접속하지 않는다.

| 종료 코드 | 의미 |
|---|---|
| 0 | 두 익명 API 응답을 관측했다. 로그인·저장·SQL 적용 완료가 아님 |
| 1 | 일부 관측이 미완료. 401·404·연결 오류 등을 안전한 JSON으로 남김 |
| 2 | 입력/대상/지원 범위로 차단됐거나 결과 파일을 쓰지 못함 |

`openApi.contextListed=false`는 **그 익명 역할의 응답 목록에 없음**만 뜻한다. 목록 조회 자체가 실패하면 `null`이다. `context.code=RPC_NOT_RESOLVED`는 정확한 원격 코드 `PGRST202`를 관측한 경우이고, 비슷한 오류 문구나 다른 오류를 이 코드로 바꾸지 않는다.

구현한 CLI의 재확인 결과(2026-10-14 **06:46:30 KST**): 같은 번들 SHA, OpenAPI 401/`SCHEMA_VISIBILITY_UNKNOWN`, context 404/`RPC_NOT_RESOLVED`, 예상 프로젝트 `unknown`, 종료 코드 1. 이 1은 도구가 현재 미확인 연결 상태를 그대로 보고한 결과이며, 자동 회귀 실패와 구분한다. 전송 내용·키·개인정보는 결과에 없다.

해석 근거: [PostgREST PGRST202 오류](https://docs.postgrest.org/en/v16/references/errors.html#group-2-schema-cache), [역할별 OpenAPI](https://docs.postgrest.org/en/stable/references/api/openapi.html), [GET/HEAD 읽기 전용 트랜잭션](https://docs.postgrest.org/en/stable/references/transactions.html). HTTP 읽기 전용 제약은 서버 자료 전체 보존이나 외부 시스템 상태까지 검증했다는 뜻이 아니다.

## 3. Claude Web에 요청할 조사본

> 기존 운영 자료를 변경하지 않는 B00 읽기 조사 SQL, 입력 설명, 결과 해석표를 작성해 주세요. 우선 현재 앱이 요청하는 `public.workhub_context()`를 찾지 못한 원인을 좁히고, 기존 회원·문서·파일 보존 기준을 확보합니다. 기존 `database/workhub/001~004`나 원본 160표 DDL을 일괄 적용하지 마세요.
>
> 객체·열·함수 존재와 조사 권한을 먼저 확인하고, 확인된 대상만 상세 조사하도록 나눠 주세요. 없는 객체, 권한 때문에 확인하지 못한 객체, 0행인 객체를 구별해 주세요. 현재 앱의 7개 RPC는 호출 시험이 아니라 함수 카탈로그·서명·권한·정의 지문을 조사합니다.
>
> B00 결과를 받은 뒤 신축 없음·구 신축 적용·부분 적용/불일치로 나누고, 통합 B01/B02의 선행 의존과 기존 RPC 호환 방식을 정리해 주세요. 실제 변경 SQL은 F5/F6/F8의 해당 적용분을 검토한 뒤 별도로 작성합니다.

조사본에 필요한 안전·실행 조건은 다음과 같다.

- 읽기 전용 트랜잭션과 제한시간, 종료·실패 시 정리 방법을 명시한다. 가능한 집계·대응 조회는 같은 snapshot 기준으로 비교한다.
- 첫 조사에서 없는 표를 발견해도 “0건”으로 위장하거나 나머지 결과를 전부 성공으로 만들지 않는다. 후속 조사에 필요한 존재·열·권한 조건을 명시한다.
- 학교·일정·업무 명령이나 기존 업무 helper를 호출하여 정상 여부를 시험하지 않는다. 읽기처럼 보이는 함수도 감사·접수 등에 쓰기를 할 수 있으므로 이 단계는 카탈로그 조회로 제한한다.
- DDL/DML, 회원 생성·승격·승인 변경, 임시/영구 객체 생성, 확장 설치, 역할·JWT 위장, 권한/RLS 변경, 캐시 reload·외부 설정 변경을 넣지 않는다.
- 토큰·비밀번호·키·Auth provider 원문·전체 환경설정을 덤프하지 않는다. 필요한 설정은 항목을 한정하고 조회 불가 시 미확인으로 기록한다.
- SQL Editor의 실행 역할과 일반 교사의 API 역할은 다르다. SQL Editor의 조회 성공을 교사 권한 시험 통과로 기록하지 않는다.
- 실행 전 사용자가 대상 프로젝트와 환경을 확인하고, 조사본의 민감 출력·저장 위치를 검토할 수 있게 한다. 대상 확인을 기다리는 동안 문서·조사본 준비는 계속할 수 있다.

## 4. 입력과 반환 결과 집합

### 4.1 조사 입력

| 입력 | 입력하는 사람·근거 | 미확인일 때 |
|---|---|---|
| 의도한 프로젝트와 환경(운영/검증) | 사용자 대시보드 확인. 비공개 실행 기록에서 식별하고 공유본에는 환경 표식·대조 결과만 기록 | 대상 확정 전 해당 환경 조사 실행을 완료 처리하지 않음 |
| 앱 origin·관측 시각·번들 SHA 또는 commit | 공개 배포 조사와 배포 기록 | 모르는 commit을 번들명으로 추정하지 않음 |
| 조사본 ID·버전·SHA | Claude Web이 확정한 조사본 | 이전 초안과 섞어 실행하지 않음 |
| 사용자 진단 상태·시각 | 개인정보 없는 진단 JSON | 다른 시각/계정의 관측과 구분 |
| 기존 자료 보존 기준점 | 사용자의 비공개 보존 기록·백업 계획 | 개수만으로 보존 완료 판정 금지 |
| 최초 R0 후보 계정 | 사용자가 비공개로 특정한 기존 계정. 가입 승인·역할은 실제 조회로 확인 | 이메일·이름으로 임의 연결하거나 새 계정 생성 금지 |

학교명·기간 등의 실제 초기 설정값은 학교 생성 단계의 입력이다. 원인을 찾는 B00에 미리 넣어 학교나 소속을 생성하지 않는다.

### 4.2 공통 결과 계약

결과는 이름 있는 표 또는 JSON 결과 집합이면 충분하다. 별도의 범용 JSON Schema 검증기를 요구하지 않는다. 모든 항목은 관측 범위와 미확인 이유를 보존한다.

| 결과 집합 | 필수 필드 |
|---|---|
| `run` | 조사 ID, 시작/종료 UTC, 조사본 SHA, 앱 증거 참조, 대상 환경 표식, DB 버전, 실행 DB role, 읽기 전용 여부, snapshot 기준점, 제한시간·실패 여부 |
| `checks` | check ID, 대상, 상태, 관측값, 증거 위치, 제한사항 |
| `objects` | schema·객체명·종류·존재, 열/타입/NULL/기본값, PK/FK/CHECK/인덱스, RLS, 정책·ACL·트리거의 상태/정의 지문 |
| `routines` | schema·함수명·모든 오버로드, 인자명/타입/mode/기본값 수/필수 인자 수, 반환형, 언어, SECURITY DEFINER, owner, search_path 설정, ACL·유효 EXECUTE, 정의 지문 |
| `preservation` | 대상 범위, 기준점, 전체 대조/일부/개수만 여부, 개수·누락·변경·고아 참조 수, 미확인·예외 수 |
| `assessment` | 원인별 판정, 근거 check ID, 다음 조사, B01/B02 차단 항목 |

`checks.status`는 `observed / absent / not_checked / permission_denied / error`로 구분한다. `observed`는 관측 성공이지 업무 합격이 아니다. `assessment`는 `confirmed / suspected / not_checked`를 구분한다. 권한 제한으로 일부 행만 보인 결과를 전체 건수로 표시하지 않는다.

사용자 보관용 비공개 대응표와 공유 인계표를 분리한다. UID·파일 경로·행별 대응이 필요한 자료는 사용자 보관 영역에 남기고, Git·채팅·공유본에는 식별자·이메일·이름·학생 자료·대화 본문·키·서명 URL을 넣지 않는다. 지문은 비교 대상을 정규화하는 방식·버전·기준시각과 함께 기록한다. 함수 본문이나 정책 원문에 민감 상수가 포함될 수 있으므로 공유본에는 우선 지문·차이 요약을 사용한다.

## 5. 프로젝트·schema·서명·캐시의 판정 순서

| 단계 | 필요한 증거 | 판정과 다음 동작 |
|---|---|---|
| A. 프로젝트 | 배포 앱의 Supabase 연결 대상과 사용자가 의도한 프로젝트, 조사 실행 대상의 대응 | 불일치면 원인 후보를 대상 불일치로 확정하고 설정 수정은 별도 검토. DB 이름만 같거나 URL/키가 서로 일치하는 것만으로 완료하지 않음 |
| B. 요청 schema | 공용 클라이언트의 기본 `rpc()` 경로, 함수 실제 schema, API 노출 schema의 실제 설정 | 다른 schema에만 존재하면 현재 호출과 차이를 기록. `workhub` 함수가 있다는 이유로 기본 `public` RPC가 연결됐다고 보지 않음 |
| C. 함수·서명 | `workhub_context` 이름의 모든 함수, 무인자 호출 가능 여부, 기본값·오버로드, 반환형 | 이름만 있고 필수 인자가 있으면 현재 요청과 불일치. 선언 인자 수뿐 아니라 필수 인자 수도 대조 |
| D. 접근 조건 | 요청 역할의 schema USAGE·함수 EXECUTE, 보안 속성, 실제 노출 근거 | 메타데이터의 필요조건만 판정. 함수 본문 권한과 JWT 실제 실행 성공은 후속 검증 |
| E. 캐시·런타임 | A~D와 같은 시점의 API 응답·설정/배포 증거 | 카탈로그상 호출 후보가 맞아도 API가 찾지 못하면 캐시·런타임 차이 의심. SQL만으로 캐시 원인 확정 금지, B00에서 갱신하지 않음 |

OpenAPI 401은 API 목록 조사 실패다. 이를 “아무 RPC도 없음”, “public schema 미노출” 또는 “잘못된 프로젝트” 중 하나로 단정하지 않는다.

`NO_ACTIVE_MEMBERSHIP`은 별도 분기다. 현재 코드는 정상 컨텍스트에서 본인의 유효 소속이 없거나 서버가 명시적으로 `INACTIVE_MEMBERSHIP`을 반환한 경우에만 그렇게 분류한다. 함수 조회 실패를 소속 미등록으로 고치려고 회원을 재가입시키거나 소속을 임의 생성하지 않는다.

### 6.1 현재 7개 RPC

일정 저장의 요청키는 `p_command` 안에 있고 업무는 별도 인자다. 현재 context는 학교·소속·`basisDate`·`schoolLabels`를 반환하며, 기존 Auth UID 기반 `userId`, `teacher/calendar_manager`, 종료일 포함 기간을 기대한다. 통합 목표는 내부 accounts 키·분리된 역할·종료일 제외 기간을 사용하므로 임의로 같은 DTO라고 간주하지 않는다.

- 기존 운영: `public.users`, `departments`, `schedules`, `tasks`, `doc_ai_conversations`, `doc_submissions`, `academic_terms`, `calendar_events`와 실제 추가 참조.

- 통합 목표: `workhub`, `workhub_private`의 실제 객체·함수·정책 존재와 정의. 목표 190표가 현재 존재한다고 전제하지 않는다.

## 7. 회원·문서·파일 보존 조사

### 7.1 회원과 기존 권한

1. `auth.users.id`와 `public.users.id`를 같은 인물별로 대조한다. 양방향 누락·형식 이상·충돌을 기록한다. 이름/이메일 유사성으로 연결하지 않는다.
2. 기존 프로필의 role, is_active, extra_permissions, department_id와 회원 참조를 행별로 보존할 기준을 만든다. `is_active=false`를 조사만으로 미승인·퇴직 중 하나로 단정하지 않는다.
3. 문서 대화·제출·일정·업무·부서장 등의 소유/작성/담당 참조를 조사한다. 알려진 표 외의 FK도 실제 카탈로그에서 찾아 보존 범위에 포함한다.
4. `auth.users`의 가입 트리거와 `handle_new_user`, `users_protect_privileged`, 승인/역할 helper, 관련 정책·ACL의 활성 상태·정의 지문을 확인한다. 개인정보를 확인하려고 Auth 세션·자격증명·provider 원문을 출력하지 않는다.
5. 통합 accounts/memberships가 이미 있다면 기존 UID → 프로필 → 새 내부 계정 → 소속 대응과 중복·충돌·종료 상태를 조사한다. 없으면 아직 이관하지 않았다는 분기로 남긴다.
6. R0 후보는 기존 UID·프로필 일치, 현재 승인, 현재 superadmin 조건 충족 여부만 보고한다. 조사 단계에서 승인·승격·소속 생성은 하지 않는다.

회원 수가 같아도 사람이 바뀌거나 역할·승인이 달라지면 보존이 증명되지 않는다. 적용 전후에 정상 가입·수정이 발생할 수 있으므로 기준시각과 행 대응 차이를 기록하고 승인된 정상 변화와 오류를 구분한다. 이관 재실행으로 회수한 권한·종료 소속이 부활하지 않는지는 이후 R0 검증 항목이다.

### 7.2 제출 행과 Storage

비공개 대응표에서 제출 ID·소유자·상태·file_path와 Storage의 버킷/객체를 연결하고, 공유본에는 다음 결과만 남긴다.

- 제출 상태별 건수와 소유자 참조 누락.
- 참조 객체 없음, 여러 제출의 같은 경로 참조, 참조 없는 객체, 미확인 건수.
- 버킷 공개 여부, 관련 정책/ACL 지문, 크기 등 조회 가능한 객체 메타데이터.
- 대조 기준시각과 조사 범위, 권한/페이지 제한 등 전수 확인을 막은 조건.

기존 [제출물 삭제 계약](../../migrations/007_submission_delete.sql)은 제출 행을 `status='deleted'`로 남기고 파일 실물을 삭제한다. 따라서 모든 제출 행의 객체 부재를 손실로 세지 않는다. `submitted/replaced/deleted`를 구분하고 삭제된 제출에 실물이 남은 경우도 별도 분류한다. 조사 과정에서 고아 파일·행을 정리하지 않는다.

`storage.objects`는 파일 실물이 아니다. **객체 수·경로·메타데이터만으로 원본 바이트 보존·다운로드·복구 성공을 판정하지 않는다.** 실제 바이트의 지문·크기·열기, 백업 포함 여부, 격리 복원 후 검증은 별도 증거다. Auth의 제공자 관리자료가 다른 프로젝트에 그대로 복제된다고 가정하지 않으며 기존 UID·로그인 복구 방법도 따로 확인한다.

기존 문서작성 AI의 신규 개발을 보류해도 현재 대화·작성 자료·제출 파일은 보존 조사 대상이다. 공개 보고서에 대화나 문서 본문을 복사하지 않는다.

| 인수 항목 | 통과 기준 |

조사 결과가 “대상 불일치” 또는 “함수 없음”이어도 근거가 충분하면 **조사 산출물**은 완료할 수 있다. 이것은 **학교 연결 준비 완료**가 아니다. 원인 일부가 미확인이라면 그 항목의 조사 완료도 표시하지 않는다. 로컬 문서·정적 시험 통과를 실제 PostgreSQL·PostgREST·Storage 시험으로 기록하지 않는다.

R0는 **기존 승인 계정으로 학교 연결 → 일정·업무 등록/수정 → 재조회·재로그인 후 보존 확인**을 하는 최소 실제 왕복이다. 문서작성 AI·시간표를 제외한 전체 시범 운영의 완료와 구분한다.

1. Claude Web의 읽기 조사본을 검토하고 사용자가 대상 환경을 확인한다.
2. 사용자 실행 결과로 원인·적용 상태·회원/파일 보존 기준을 정리한다. 필요한 복구 수단과 격리 검증 환경을 확인한다.
