# HWPX 전용 수합 간소화 검증·인계

2026-10-16 · 기준: PR #43 (`66be765`) · 작업 브랜치: `feat/workhub-hwpx-simple`

## 교사가 보는 변화

- 새 수합과 새 첨부는 HWPX만 받는다. 선택 단계에서 확장자·빈 파일·크기·개수 제한을 안내한다.
- 담당자 검토 설정은 선택 항목으로 접어 기본 작성 화면을 줄였다.
- 양식 배포 → 작성본 첨부 → 제출 → 담당자 확인·수정/보완 → 전체 ZIP 흐름은 유지한다.
- 기존 PDF 등 역사 자료는 조회·다운로드한다. 기존 수합 정책이나 제출판을 자동으로 바꾸지 않는다.
- 준비 상태·전송 실패·확인 대기·확정 파일 거절을 구분한다. 응답이 끊기면 원래 파일과 완료 요청 번호로 재확인한다.

## 실행 구조와 범위

브라우저 → 기존 Supabase 비공개 Storage 직접 업로드 → 기존 complete → Vercel 최소 확인 API → 새 DB claim/finish.

API는 사용자 JWT를 실제 Auth 조회로 확인한다. 이후 서버 전용 RPC가 발급한 원본만 읽어 크기·SHA-256·HWPX 필수 ZIP 항목과 mimetype를 확인한다. 원문 파일을 Vercel 요청 본문에 싣지 않는다. 원본 경로·서버 키·임대 토큰은 브라우저 응답에 담지 않는다.

기술 상한은 30 MiB이며 더 낮은 학교/수합 정책을 유지한다. 전체 XML·문서 내용·악성코드를 검사하지 않는다. 검사하지 않은 것을 clean으로 기록하지 않는다. 미첨부 파일의 자동 삭제도 이번에 켜지 않는다.

API 네트워크 예산은 45초, 브라우저와 어댑터의 기본 확인 대기는 55초다. 기존 일반 조회·저장의 제한 시간은 유지한다. 일시적인 API 실패는 같은 요청 번호로 재확인하고, 파일의 확정 거절은 정상 봉투의 rejected로 처리한다.

## 자동 검증

아래는 로컬 자동 검증 결과다. 실제 Supabase·Storage를 호출한 결과와 구분한다.

- 전체 `npm test`: **2,375건 전부 통과**, Python 건너뛰기 없음.
- 신규 서버 API: 58건. 실제 보호 양식 6종을 읽어 최소 확인을 통과했고 원본은 수정하지 않았다.
- 신규 API 클라이언트: 16건. 로그인 변경, 응답 중단/크기 상한, 초기·본문 대기 제한, 같은 요청 번호 복구.
- 수합 어댑터: 57건. 이 중 11건은 기본 프로필·서버 확인·과거 PDF 보존에 관한 신규 시험이다.
- 브라우저: 37개 파일 실행 후 바뀐 안내/RPC와 HWPX 신규 입력 fixture를 보완했다. 수정 대상 시험을 재실행해 모두 통과했다. 서버 수합 전체 흐름 38건, HWPX 전환 8건, 실제 미리보기 파일 보존 5건을 포함한다.
- 타입 검사와 운영 앱·업무실 빌드 통과.
- `git diff --check` 통과. 별도 `git diff` 대조에서 기존 SQL·확정 양식·인증 모듈·메뉴 공개 범위 변경이 없었다.

첫 전체 실행에서 기존 R1 전송 시험의 80ms 제한이 병렬 브라우저 부하 중 실패했다. 해당 시험은 변경하지 않았으며 단독 21건을 통과했다. 이후 전체 시험을 순서대로 다시 실행했다. 브라우저 최초 실패는 새 안내/RPC·HWPX 정책과 기존 시험 기대값의 불일치였고, 동작을 되돌리는 대신 시험 입력을 새 요구사항에 맞췄다.

`check:workhub:integration:r2`는 #43 통합 후보의 원래 API 범위를 고정하는 검사이므로, 이번에 추가한 collections API 3파일을 변경으로 감지해 실패한다. 후속 기능 PR에 이 범위 고정 검사를 적용하거나 우회하도록 수정하지 않았다. CI도 이 명령은 #43 브랜치에만 실행하도록 기존부터 한정돼 있다. 관련 회귀 시험 22건은 전체 시험에서 통과했다.

대역 RPC·Storage, 로컬 HTTP 서버, 합성 브라우저 자료로 검증했다. 실제 로그인·PostgREST·Storage·Vercel 운영 API 왕복은 수행하지 않았다. 새로운 R1S SQL은 아직 작성/적용되지 않았다.

## Claude 검토 및 DB 작성

상세 요청은 [HWPX 전용 수합 R1S 요청서](42-hwpx-basic-collection-request.md)를 따른다.

1. 새 업로드 제한과 기존 자료 읽기의 분리, UI 입력·같은 요청 번호 복구를 검토한다.
2. API 인증·서버 전용 claim/finish·권한/임대/원본 불변 계약을 검토한다.
3. 기존 R0/R1 실행 파일을 보존하고 새 R1S 증분 SQL을 작성·시험한다. readiness만 추가하지 말고 기존 쓰기 게이트·not_scanned·ready 제약·cleanup 경합도 프로필별로 맞춘다.
4. 비활성 SQL 적용 → 앱/API 배포·서버 환경값 준비 → 승인 정책/배포 확인 후 학교별 활성화 순서를 제공한다. R1-05/06의 기존 양식을 그대로 실행하지 않는다.
5. 실제 확인은 이후 묶어서 한다. 새 DB/API 응답 계약이 달라져야 한다면 적용 전에 Codex와 맞춘다.

## 판단해서 정한 것과 보류

- **별도 검사 서버 PR #44 보류:** 이 후보는 #43에서 분기했다. #44의 Docker/운영 배포 구성을 포함하지 않는다.
- **기존 검사 코드 보존:** 새 제출 경로에서 사용하지 않으며 과거 코드와 시험은 지우지 않았다. SQL/운영 상태를 되돌리는 것으로 착각하지 않도록 한다.
- **실제 활성화 보류:** 키 생성·환경값 변경·SQL 적용·사용자 병합은 수행하지 않았다. 앱 구현만으로 수합 실사용 완료라고 보고하지 않는다.
- **후속 범위:** R1S 연결과 실제 수합 왕복, 일반 교사 소속, 학생·수업 실제 저장, 메신저·학교 지식·Claude 에이전트, 알림/운영 기능. 문서작성 AI·시간표·보류 운영 자동화는 그대로 보류한다.
