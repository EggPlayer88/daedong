# 학교 업무실 UI 개편 — 2026-10-20

## 후속 보완: 홈 우선순위와 준비 입력

- 홈 읽기 순서를 **확인할 학교 업무 → 내 수업 → 오늘 일정 → 개인 업무 → 다가오는 일정**으로 정리했다. 실제로 읽은 기존 조회 결과를 재배치하며 새 RPC·DB 집계는 추가하지 않는다. 합성 미리보기에서는 연결된 수합 요약이 첫 영역에 나온다.
- 학교 업무는 서버가 준 순서를 유지하여 먼저 4건과 모든 긴급 항목을 표시한다. 나머지는 ‘모두 보기’로 펼치며 원본 이동과 마감·긴급 표시를 유지한다.
- 정상 빈 상태만 짧게 표시한다. 조회 중·조회 실패·일부 미확인·저장 결과 미상은 빈 상태로 바꾸지 않는다. 조회 오류의 재시도는 펼침 없이 보인다.
- 시간표 준비는 일과, 시수·수업, 기준판 검토의 단계 이동을 제공한다. 공간·수업 연결과 엑셀 가져오기는 기존 기능으로 유지한다. 단계는 내용을 접을 뿐 입력 컴포넌트를 제거하지 않는다.
- 초안 저장·원래 요청 복구·원본 변경·충돌 안내는 단계 밖에 유지한다. 수업 점검에서 해당 수업으로 이동하면 닫힌 영역도 열고 초점을 잇는다. 최종 확인은 기존 체크와 검증 조건을 그대로 사용한다.
- 홈 수업 요약의 이중 테두리를 없애고 준비 중·정상 빈 상태의 여백을 줄였다.
- 수합이 있는 홈도 큰 중첩 카드 대신 간결한 행으로 표시한다. 넓은 화면은 두 열을 쓰고, 보완 기한·완료본·남은 보완·검토 대기와 원본 이동을 유지한다.

판단해서 정한 것: 빈 상태를 숨겨 버리는 대신 작은 안내와 원래 이동 동작을 남겼다. 긴급 업무는 기본 표시 건수를 넘어도 접지 않는다. 단계 이동은 저장이나 확정 명령을 만들지 않는다. 되돌릴 때는 해당 UI 커밋을 되돌리는 PR만 필요하며 SQL 작업은 없다.

이번 범위에 포함하지 않은 것: AI 옆 패널, 계정 간 스킨 동기화, 메뉴 개인화, 기존 평가계획 화면 전체 재구성, DB 미활성 모듈 켜기.

## 목표와 범위

첫 화면에서 오늘의 일정·내 업무·확인할 일이 먼저 읽히고, 자세한 설명과 덜 쓰는 메뉴는 필요할 때 펼치는 화면으로 개편한다. 사용자 요청의 화이트·차콜·차분한 블루를 기본으로 기존 스킨 설정을 함께 정리했다.

처음 기준은 main aa7f195이며, 작업 중 사용자가 병합한 #70을 포함한 main 1b0938f를 merge commit으로 반영했다. 미병합 시간표 #72와는 별도 브랜치다. SQL·DB·RPC 계약·인증·회원·공개 범위·AI 모델/비용·외부 설정은 변경하지 않는다. 코드 병합과 운영 기능 활성화는 별개다.

## 판단해서 정한 것

1. 모든 메뉴를 항상 펼치지 않는다. 첫 화면 선택지를 줄이고 기존 기능은 더보기에서 접근한다.
2. 모바일에는 자주 쓰는 세 메뉴와 AI·더보기를 둔다. 업무실 핵심 동선을 손가락이 닿는 하단에 유지한다.
3. 반복 설명·서버 표시 기준만 접는다. 실패·저장 대기·결과 미상 안내와 명시적 확인은 줄이지 않는다.
4. 기존 화면을 전부 새로 만들기보다 공통 스킨과 탐색 구조를 먼저 통일한다. 이후 각 업무의 세부 개선이 동일한 버튼·색상·여백 체계를 사용하게 한다.
5. 인스타그램 등의 콘텐츠 구조를 복제하지 않고, 간결한 탐색·일관된 위계·명료한 주요 동작을 학교 업무에 적용한다.

## Claude 검토 중점

1. 기본 메뉴→더보기→기존 메뉴의 이동과 입력 보호가 유지되는가.
2. AI 비서 버튼이 실제 비서 화면과 정확한 준비 안내로 연결되는가.
3. 초점·Escape·320px·큰 글씨·3가지 스킨에서 조작이 가능한가.
4. 홈의 시각·긴급·마감·조회 실패 정보가 줄이거나 옮긴 설명 때문에 사라지지 않는가.
5. 기존 모듈 공개 범위, SQL·인증·비용·전송/제출 명령이 바뀌지 않았는가.
6. 시간표 단계 이동·접기·다시 펼치기에서 시수·활동·시간대 입력이 유지되고, 복구·충돌 안내는 접힘 밖에 남는가.
7. 정상 빈 상태의 축약이 조회 실패·일부 미확인·저장 결과 미상에 적용되지 않고, 긴급 학교 업무는 기본 4건 밖이어도 표시되는가.

## CI 대상 학기 잠금 시험 보완

`e8e214c`의 GitHub 검사에서는 브라우저 94개 파일 중 `workhub-timetable-target-connected` 한 곳이 실패했다. 공간 편집 입력 직후 자식→준비 패널→Workspace의 잠금 렌더가 끝나기 전에 `isDisabled()`를 한 번 읽은 것이 원인이다. 해당 실행의 실패 직후 HTML에는 대상 학기 선택기가 이미 `disabled`이고 작성 중 입력 정리 안내도 나타나 있었다.

제품 화면·SQL·공개 범위를 고치지 않고 시험이 실제 잠금 상태를 기다리도록 정리했다. 고정 시간 대기나 실패 재시도로 넘기지 않으며, 잠금이 누락되면 제한 시간 내 실패한다. 입력 원문과 초안, 원래 학기, 실제 저장 0건을 함께 대조하고 명시적으로 입력을 버린 뒤 잠금이 해제되는지도 추가했다. 수정한 11개 시나리오는 CI와 같은 Chromium에서 부하 중 5회 연속 통과했다. 전체 회귀와 최신 CI 결과는 PR에 별도 기록한다.
