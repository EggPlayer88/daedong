## Phase 1 — 데이터 모델 + 시간표 보기 기반

### 데이터 모델
- 4개 핵심 테이블: `timetables`, `timetable_changes`, `school_calendar`, `notifications`
- `timetables.data` 형식: `{ classId: { 'day-period': {sid, tid}, ... } }`
- 시간표 한 번에 하나만 active (UNIQUE INDEX on `is_active`)
- 변동 요청은 별도 테이블 (`timetable_changes`) 로 시간표 본체와 분리

### 시간표 보기 정책
- 학급 뷰 / 교사 뷰 토글
- 주차 단위 네비게이션 (한 번에 한 주)
- 캘린더 오버레이 (휴일/시험/행사 라벨)
- 본인 수업 셀만 클릭 가능 (관리자 모드는 예외)

### 시뮬레이션 페르소나
- Phase 4 (인증) 전까지 임시
- 시드 시간표에 등장하는 6명 + admin
- 기본값 't2' (국어T2)

## Phase 2A — 변동 요청 + 2단 승인 + 알림

### 결정 1 — 변동 유형 (4가지)
- `swap` (교환수업) — 다른 시간 수업과 맞바꿈, 1:1/1:1:1/1:1:1:1 가능
- `substitute` (보강) — 다른 교사가 대신 들어감
- `self_study` (결강/자습) — 자습 처리, 감독 교사 지정 가능 (없으면 결강)
- `period_move` (시수변경) — 같은 교사가 시간만 옮김

### 결정 2 — Swap 정책
- **같은 학급 안 swap 이 원칙**
- **다른 학급 swap 도 가능하지만 경고 표시** (노란색 ⚠️)
- 학교 운영 관점에서 같은 학급 안 교환이 학생/학부모 혼란 적음

### 결정 3 — 승인 흐름
- **2단계**: 영향받는 파트너 교사 승인 → 시간표관리자 승인
- partner 가 한 명이라도 거절하면 전체 반려
- 시간표관리자가 거절하면 반려
- 모두 승인 시 즉시 시간표에 반영

### 결정 4 — 알림 표시 위치
- 사이드바 메뉴 옆 빨간 점 (숫자 배지)
- 시간표 페이지 안 알림 탭
- 대시보드 알림은 Phase 6 으로 미룸

### 결정 5 — 알림 갱신 방식
- 페이지 로드 시 + 30초 폴링
- Supabase Realtime 은 Phase 5~6 에서 업그레이드 검토

### 결정 6 — 페이지 구조
- TimetableViewer 안에 탭 4개 (시간표 / 알림 / 내 요청 / 관리자만 승인 대기)

## Phase 2B — AI 추천 + 시간표 전용 AI 비서

### 결정 1 — API 엔드포인트 구조
- 별도 엔드포인트들로 분리 (단일 chat.js 에 통합 안 함)
- `/api/recommend-substitute`, `/api/recommend-move`, `/api/timetable-chat`

### 결정 2 — AI 추천 진입점
- 폼 안에 "✨ AI 추천받기" 별도 버튼
- 첫 진입 시 자동 호출 안 함 (사용자가 직접 선택 가능, 토큰 절약)

### 결정 3 — 채팅 위치
- 우측 사이드 패널 (토글 가능)
- 모바일은 우측에서 슬라이드 인/아웃 (768px 미만)

### 결정 4 — 일반 교사 AI 권한 범위

**할 수 있는 일**:
- 시간표 조회 (본인 + 다른 교사)
- 변동 요청 흐름 안내
- 보강/이동 추천 (변동 폼에서)
- 변동 통계 (조회만)
- 본인 변동 안내문 초안

**할 수 없는 일** (시스템 프롬프트로 거절):
- 시간표 직접 수정
- 다른 교사 변동 대신 만들기
- 시수 검증, 학교 전체 분석
- 시험기간 시간표 생성

## Phase 3A — 일반/관리자 모드 분리

### 결정 1 — 직권 변경 진입 방식
- **명시적 모드 토글** 로 일반/관리자 모드 전환
- 페르소나가 시간표관리자일 때만 토글 노출
- 일반 교사 페르소나는 항상 교사 모드

### 결정 2 — 학사일정 vs 일정관리
- **학사일정** (`school_calendar`): 학교 운영 차원 (휴일/시험/행사)
- **일정관리** (`schedules`): 개인/부서 업무 (이전 채팅 작업, 별도)
- 학사일정은 별도 메뉴 "📆 학사일정", 관리자만 접근

### 결정 3 — AI 비서 권한 분기
- 같은 사이드 챗봇, 시스템 프롬프트와 tool 만 페르소나에 따라 다름
- 시각적 구분: 관리자 모드일 때 보라색 헤더 + "관리자 AI" 라벨

### 결정 4 — 직권 변경 사후 통보 범위
- **영향받는 교사들에게만** (담임/부서장 등은 포함 안 함)
- 알림 kind: `admin_notice` (응답 버튼 없음, 단순 통보)

### 결정 5 — 학사일정 4가지 유형
- `holiday` (휴일)
- `no_school` (재량휴업일)
- `exam` (시험)
- `event` (행사) — 일부 학급만 영향 가능 (affected_classes)

## Phase 4C — 셀 단위 편집 (예정)

### 결정 4 — 편집 대상
- B. **드래프트만 편집 가능**
- 활성 시간표는 직접 편집 불가 (임시 변경 시스템으로 처리)

### 결정 5 — 편집 작업 단위
- C. **단일 셀 편집 + swap 둘 다**
- 단일: 교사/과목 변경 (예: 김국어T1 → 김국어T2)
- swap: 두 셀 내용 교환

### 결정 6 — 충돌 검증 강도
- **확실한 충돌만 강제 차단**: 한 교사 동시간 두 학급, 한 학급 한 시간대 두 과목
- **시수 불일치는 경고만**: 편집 중간 단계에서 일시적 부족/초과 허용
- 합반 케이스 없음 (이 학교) 확인됨

### 결정 7 — 변경 추적
- A. **edit_log 누적 기록**
- 어떤 셀이 어떻게 바뀌었는지 모두 기록
- Phase 7 (영구 변경 시스템) 의 기반

## 학교 운영 정책 (절대 변경 금지)

이 학교의 운영 정책으로 결정된 사항들. 코드 작업 시 반드시 반영:

1. **합반 없음** — 한 교사가 동시간 두 학급에 들어갈 수 없음
2. **같은 학급 swap 우선** — 다른 학급 swap 도 가능하나 경고 필요
3. **직권 변경 즉시 적용** — 관리자 직권 변경은 승인 단계 없음
4. **사후 통보는 영향받는 교사만** — 담임/부서장 포함 안 함
5. **시간표 한 번에 하나만 active** — UNIQUE INDEX 보장
6. **드래프트 → 명시적 활성화** — 자동 활성화 안 함
7. **변동은 새 timetable row 생성** — 활성 시간표 직접 수정 안 함
8. **모든 변경 추적** — edit_log 누적 기록
